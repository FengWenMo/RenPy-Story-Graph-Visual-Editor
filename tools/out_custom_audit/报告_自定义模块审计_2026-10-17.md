### 2.3 卡片编辑器“服装格”到底什么时候消失

当前 `attr_slot_rows`（`beats.py:1663`）的结构来源有**三档**：

1. 引擎事实 `facts` → `grouped_choices`；
2. 没有事实/事实没这个 tag → 项目 `layeredimage`；
3. 前两档都没有、但有 `groups` → 项目声明的 `attr_groups`（`beats.py:1756-1774`）。

`probe_disappear_matrix.py` 实测（`groups=服装/动作`）：

| 场景 | 行数 | 标签 |
|---|---:|---|
| spec 只有 tag、也没有分组来源 | 0 | — |
| spec 只有 tag + 引擎事实 2 组 | 2 | 服装=—、动作=— |
| spec 只有 tag + layeredimage 2 组 | 2 | 服装=—、动作=— |
| 引擎事实 2 组（正常） | 2 | 服装=swim_suit、动作=stand |
| 引擎事实只有 1 组 | 1 | 服装=swim_suit |
| 没事实，layeredimage 2 组 | 2 | 服装=swim_suit、动作=stand |
| 没事实，layeredimage 1 组 | 1 | 服装=swim_suit |
| 没事实，也没有 layeredimage | 0 | — |
| symbols=None（拿不到资源表） | 0 | — |
| 引擎事实里 outfit 的候选 ∩ 组成员 = 空 | 1 | 动作=stand |

**结论：服装格会消失的条件**

1. **没有分组来源**：没有 `engine_facts`、没有可读的 `layeredimage`、也没有 `attr_groups` → 0 行；卡片回到单个“属性/表情”chip。
2. **拿不到 `symbols`**（资源表没读出来）→ 0 行。
3. **tag 写错**：`show lan …` 而 `layeredimage`/facts 里是 `lan_tag` → 这个 tag 没有任何组 → 0 行（截图 `05_wrong_tag_lan_window.png`）。
4. **只有 rules.json、没有引擎/`layeredimage`**：第三档能建格，但**没归到任何声明组的词会被过滤掉**（`beats.py:1774` `if e.get('group')`），只剩已声明的组；`happy` 这类词从卡片上消失（P0-3，截图 `15_declared_only_hides_ungrouped.png`）。
5. **新增立绘卡**：`SpriteGridWidget._on_add` 没有把 `choice_groups_for` 传给新卡（`sprite_grid.py:906-918`）→ 新卡永远 0 行，直到重新载入（P1-3，截图 `03_new_card_no_provider.png`）。
6. **所有组的候选都被过滤空**（engine facts 的 `candidates` 和组成员没有交集）→ 该组不出现；全部组都空 → 0 行。
7. **只有一组**：当前已修，会显示 1 个 chip（`07_single_group_window.png` 显示 `服装：uniform`）；**旧版会消失，现已不是问题**。
8. **只写 tag、没写属性**：当前已修，只要组来源存在就建格（`beats.py:1711-1715`）。

### 2.4 服装与动作混为一谈

**实测（截图 `06_mixed_group_window.png` / `02_no_facts_mixed_group_window.png`）**

合成项目 `mix` 的 `layeredimage`：

```renpy
group outfit: swim_suit, uniform, stand, wave
group expressions: happy, sad
```

rules.json 里声明了 `pose/动作`（`stand/wave`）。卡片实际得到：

```text
chips = ['服装：swim_suit', '神态：—']
rows  = [
 {'group':'outfit','label':'服装','value':'swim_suit',
  'options':['swim_suit','uniform','stand','wave']},
 {'group':'expressions','label':'神态','value':'','options':['happy','sad']}
]
```

- `stand/wave` 被画进「服装」下拉；`pose/动作` 声明**完全不参与**。
- `apply_attr_slot('mix swim_suit stand', 'pose', 'wave', …)` 返回原串（没有 pose 行）——动作声明是死配置。
- 卡片底部甚至已经提示“`stand` 没生效（outfit 组里引擎用的是 `swim_suit`）”，但仍把这一组叫「服装」，没有解释“你声明的动作组被引擎的 outfit 组吃掉了”。

**根因**

- `attr_slot_rows` 只在 `not group_rows` 时才用 `groups`（`beats.py:1756`）；一旦 facts/layeredimage 有组，声明只通过 `rename_overlay` 做改名（`beats.py:1721`、`engine_facts.py:526-545`）。
- `rename_overlay` 明确忽略 `options`（`engine_facts.py:532-533`），所以 `pose` 的成员关系永远不会生效。
- `layered_model._pose_from_groups`（`161-165`）把“出现在 `when` 条件里的属性”统称“姿势/服装”，也是同一类概念合并。
- 资源表 `Attributes` 列表头被硬编码成「表情」（`asset_registry_constants.py:40`），进一步把所有属性都当表情。

**这不是 `outfit` 特化**：代码里没有 `if group == 'outfit'`。真正的问题是“引擎组名即 UI 标题 + 声明只改名不建结构”。要通用，修法应该是对**任意组名**成立，而不是再加一个 `pose` 特例。

**最小修复（二选一，建议 B）**

- A（保守）：保持引擎结构为唯一真源，但当声明组的 `options` 与某个引擎组重叠、且组名不在引擎组里时，在卡片/第④页给出明确警告：“`pose` 的 stand/wave 在引擎里属于 `outfit` 组，无法分成「动作」；要分开请改 `layeredimage` 的 group”。这样至少不再让用户以为声明生效了。
- B（满足用户预期）：给 `attr_groups` 增加显式的 `split: true`（或“用这组声明来分格”开关）；当它为真时，按声明 `options` 生成**展示用维度**（只影响卡片/下拉，不改引擎语义），并保证所有属性仍有一个归属（未归组的进「其他」）。默认仍保持“只改名”，避免旧项目行为变化。

**该补的测试**

- `test_declared_group_can_split_one_engine_group`（`outfit` 同时含 stand/wave，声明 pose；期望卡片出现「动作」或明确警告）。
- `test_apply_attr_slot_pose_group_is_not_silently_ignored`。
- `test_engine_group_not_in_declared_groups_warns`。

### 2.5 通用性检查：有没有对 outfit 做特化？

**生产代码里没有 `if group == 'outfit'` / `if label == '服装'` 这类分支。** 搜索到的 `outfit`/`服装` 字面量集中在：

- `authoring/spec_groups.py` 的 docstring 示例（`outfit`/`服装`）；
- `app/beats.py` 的注释/示例；
- `core/engine_facts.py` 的 `rename_overlay` 示例；
- `authoring/pattern.py` 的 docstring 示例；
- `assets/asset_registry_constants.py:40` **`'Attributes': '表情'`**（这是真正的硬编码，见 P2-3）。

所以“对 outfit 做了特化”这个怀疑，**代码层面不成立**。但用户看到的现象成立，原因是：

1. 引擎组名 `outfit` 被直接当 UI 标题（无声明时）；
2. `attr_groups` 的 `name` 必须等于引擎组名才生效，而 UI 不给引擎组名列表，用户只能盲填；
3. 硬编码的「表情」列名把所有立绘属性都归到表情语义；
4. 单组时不再消失，但组内混着的动作值仍然叫「服装」。

这四个都是通用性/文案问题，不需要（也不应该）加 `outfit` 特判。

- **根因**：`statement_registry.py:1602-1620` replace 分支直接 `data[ATTR_GROUPS_KEY] = clean`；`dialog_learn._save_columns_now`（`684-704`）构造的 `clean` 只有 `name/label/options`，不保留同名的未知键。
- **影响**：用户手写在 attr_groups 里的条件/备注在“保存分栏”时被删；备份可救但用户未必知道。
- **最小修复**：replace 前按 `name` 把旧条目里的**未知键**合并进新条目；或在检测到未知键时弹窗确认“会丢这些字段”。
- **该补测试**：`test_replace_preserves_unknown_group_fields`。

### P2-1 第①页在只有分栏时仍说“项目没有声明任何自定义语句”

- **类型**：文案（误导）
- **现象**：截图 `08_dialog_page1_declared.png` 第一行是“项目**没有声明**任何自定义语句……”，下面紧接着“候选分栏（attr_groups）：服装/动作/神态”。

- **影响**：用户扫一眼首句就以为定义丢了；原始抱怨 #1 的“看不到”仍有心理残留。
- **最小修复**：有 groups 时首句改成“没有语句声明；候选分栏有 N 栏（见下）”，或统一叫“项目清单”并分节。更好：把 groups 直接并进 `format_registry_report`，让体检/构建报告也能看到（目前 `asset_report.py:48`、`build.py:253` 仍只显示语句）。

### P2-2 工具栏叫「🧩 自定义动作」，tooltip 只提语句声明

## 7. 结论（给修复者的一句话）

**不要继续给 `outfit` 加特判。** 当前剩余问题集中在五处：
1. **角色名到 `show` tag（ImageTag）的映射没有暴露**（P0-1）；
2. **chip 回调在换图后仍用旧组名**（P0-2，最危险）；
3. **声明分栏的兜底会丢未归组词**（P0-3）和**非法标识静默丢弃**（P0-4）；
4. **主 OK 的空/非法分栏会静默清空已有 attr_groups**（P0-5，数据丢失）；
5. **引擎单组无法拆分服装/动作**（P1-1）——这需要产品决策（显式 split 或明确警告），不是文案补丁。

其余是路径一致性、数据展示键、文案与测试假绿。按 P0→P1 做，先把 P0-2、P0-1、P0-5 修掉，用户的“切不上/点错/配置被清空”就会消失大半。
