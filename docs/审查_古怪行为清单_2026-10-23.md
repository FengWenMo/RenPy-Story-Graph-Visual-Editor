## 一、P0：门禁拦下坏产物，却把它放进游戏会读的地方

**在哪**：`storygraph/story/generation_guard.py:1233`、`:1253`、`:1334`

```python
review = out_path.with_suffix('.blocked.rpy')
write_text_atomic(review, text)        # text = 被判定"会让游戏跑不起来"的那份产物
```

**发生了什么**

门禁发现产物有 block 级问题（中文 image tag、Python 块语法错、label 重名），
按设计**不写目标文件**，改写一份副本"供人对照"。

问题在落点。实测：

```
game/ch01.rpy        -> game\ch01.blocked.rpy
game/ch01.script.rpy -> game\ch01.script.blocked.rpy
```

`.blocked.rpy` 的后缀**还是 `.rpy`**。Ren'Py 的规则是"扫 `game/` 下所有 `.rpy`，
当成同一个脚本"。所以：

1. 门禁的理由是"这份产物写进 game/ 会让游戏起不来"；
2. 它拦住之后，把同一份产物写成了 `game/ch01.blocked.rpy`；
3. Ren'Py 下次启动就会读它，游戏照样起不来，报错还指向一个用户从没创建过的文件名。

而 `grep` 全仓**没有任何地方删除** `.blocked.rpy`。它会一直躺在那儿。

**第二重后果更致命：门禁把自己锁死了**

`generation_guard.py:486` 的 `occupied_labels()` 扫项目里所有 `.rpy` 找已占用的 label，
用来判 `LABEL_COLLISION`。它的扫描器是 `parsing/discover.py:47`，排除规则只有：

```python
if fp.name.endswith(GENERATED_SUFFIX):   # 只排除 *.generated.rpy
    continue
```

**没有排除 `*.blocked.rpy`**。而拦下的副本里恰好带着 `label ch01:`。实测：

```
occupied_labels(root)     = ['ch01']        # 来自 ch01.blocked.rpy，不是用户的文件
labels_in_danger(ch01.rpy)= ['ch01']        # → 下次导出必被判 LABEL_COLLISION
```

于是完整的死循环是：

1. 第一次导出被拦 → 写 `game/ch01.blocked.rpy`（含 `label ch01:`）
2. 用户照着提示修好了问题，第二次导出
3. `occupied_labels` 扫到那份副本 → **又报 label 重名** → 再次拦下
4. 再拦一次又覆盖一份副本 → 回到第 2 步

用户唯一的出路是**手动删掉一个他从没创建过、也从没被告知存在的文件**。
而报错文案指向的名字（`ch01.blocked.rpy`）他没见过，只会以为工具坏了。

**为什么说这是"组合扭曲"而不是笔误**

`with_suffix('.blocked.rpy')` 单独看完全合理（同目录、好找、不覆盖原文件）。
错的是它默认了"同目录 = 无害"，而 Ren'Py 的粒度是"整个 game/ 目录"。
两个模块各自正确的直觉，合起来正好抵消了护栏本身。
注释里写着"绝不能写进目标路径（那正是事故的形态）"，但 `.blocked.rpy` 对引擎来说**就是**目标路径那一类。

**建议**

- **立刻**：把副本落在 `game/` **之外**（项目根的 `build/review/` 或系统临时目录），
  路径走 `inside_game_dir()` 判一次：落在 game 里就换地方。
- **同时**：`discover_scripts` 的排除名单加上 `*.blocked.rpy`、`*.bak.rpy` 这类派生文件。
  这一条**独立于上一条**都该做——就算副本挪走了，历史项目里已经躺着的副本也要能免疫。
- **判据**：写副本前断言 `not inside_game_dir(review, root)`；这条断言本身应该进
  `test_single_write_entry.py` 那一类守卫。
- **加两条测试**：
  ① 构造必然 block 的产物、`out_path` 在 `game/` 下，断言"事后 `game/` 里 `.rpy` 文件数不变"；
  ② 放一份 `ch01.blocked.rpy` 在 `game/` 里，断言 `occupied_labels()` **不**把它算进去。
  两条现在都没有。第二条尤其重要——它钉的是"门禁不会自己把门焊死"。

## 二、P0：多 label 文件里插一拍，身份挂到第一章

**在哪**：`storygraph/app/editor.py:272-274`

```python
for i, b in enumerate(self.beats, 1):
    b.seq = i                                    # seq = 全文连续序号
    if not str(getattr(b, 'label', '') or '').strip():
        b.label = label                          # label = 循环外取的"第一个非空 label"
```

`label` 是在循环**外面**取的：`for b in self.beats: if b.label: label = b.label; break`。
所以它是"文件里第一个 label"，不是"这一拍当前所属的 label"。

**实测**

```python
beats = [ch01, (空), ch02, (空)]
s._renumber()
1. seq=1 label='ch01' line_id='ch01.0001'
2. seq=2 label='ch01' line_id='ch01.0002'
3. seq=3 label='ch02' line_id='ch02.0001'
4. seq=4 label='ch01' line_id='ch01.0003'   ← 明明在 ch02 后面
```

第 4 拍在 `ch02` 之后，却被登记成 `ch01`。

**为什么诡异**

`EditorSession.load()` 的文档明确说"一个 `.rpy` 可以有多段 label，载入的是整个文件"。
既然支持多 label，那"空 label 填第一个"就是把**位置信息**当成了**章节信息**。
用户只是在第二章里插了一张卡，这一拍的身份就跨章了。

后果不是显示错，是**归属错**：编译按 `label` 分块、翻译单元按 `line_id` 前缀归属、
协作锁按 `line_id` 上锁、TTS 按 `line_id` 命名语音文件。四样一起错，而且静默。

**建议**

- 把"第一个非空 label"换成"**这一拍往前最近的**非空 label"：

  ```python
  current = ''
  for i, b in enumerate(self.beats, 1):
      b.seq = i
      if str(b.label or '').strip():
          current = str(b.label)
      else:
          b.label = current          # 继承上文，而不是继承文件头
  ```

- 更稳的做法是**不填**：空 label 说明"这一拍没有归属"，交给编译期报出来，
  而不是替它猜一个。猜错的代价（跨章、错序）远大于"留空然后报错"。
- 测试：`[ch01, 空, ch02, 空]` → `_renumber()` → 断言第 4 拍 `label == 'ch02'`。
  这条现在也没有。

## 三、P1：协作合并的 ID 不在语法内，撞一次车就丢章名

**在哪**：`storygraph/collab/collab_store.py:1605`

```python
def _unique_line_id(conn, lid):
    """给"两句都留"的新行找个没人用的 LineId（`ch01.0002~2`、`~3`…）。"""
    cand = f'{lid}~{i}'
```

而全项目认 ID 的正则是 `storygraph/story/line_identity.py:37`：

```python
LINE_ID_RE = re.compile(r'^(?P<label>.+)\.(?P<num>\d{4,})$')
```

`ch01.0002~2` 结尾是 `~2`，不是数字。**实测**：

```
parse("ch01.0002~2") -> None
parse("ch01.0002~3") -> None
allocate(used={ch01.0002, ch01.0002~2}) -> ch01.0003      # ~2 在它眼里不存在
```

**最狠的一档**：两条 `~2` 撞在一起（协作合并做两次就会）

```
前: ['ch01.0002~2', 'ch01.0002~2']
后: ['ch01.0002~2', 'start.0001']     label 字段仍是: ['ch01', 'ch01']
```

`unique_ids()` 里 `parse(lid)` 返回 `None` → label 退化成 `'start'` →
这一拍的身份写着 `start.0001`，而它的 `label` 字段写着 `ch01`。
`start` 是 `allocate()` 的兜底常量，不是这个项目里的任何一章。

**为什么诡异**

`line_identity.py` 的模块文档专门写了历史教训："从前分配规则散在四处，各写各的，
结果同一个'稳定身份'在四条路上语义不同"。这段文档写在 2026-10-23。
而 `_unique_line_id` 就在当天还活着一套**第五种**规则，并且产出物不在语法内。

契约说"发号的唯一实现是 `line_identity`"，实际是"除了协作库之外都走它"。

**建议**

- `_unique_line_id` 删掉后缀方案，改用 `allocate()`：它本来就保证不撞车，
  只是"两句都留"需要保证**新行拿到比原行大的号**，这一步用 `used = 全库 ID` 传进去即可。
- 如果一定要保留"这行是从哪行分出来的"这层信息，把它放进**载荷**（`payload['forked_from']`），
  不要放进 ID。ID 是主键，不是注释。
- 兼容：已经落库的 `~N` ID 需要一次迁移（`parse` 失败的行按 `seq` 重新发号），
  否则翻译和语音 key 会带着这个非法字符一直走下去。
- 守卫：加一条断言"任何写进 `line_id` 的值都能被 `parse()` 认出来"，
  放在 `Beat.line_id` 的 setter 上最省事（`beat_model.py:903` 已经有 setter）。

## 四、P1：同一行有两个身份（编译报表 vs 表格）

**在哪**：`storygraph/pipeline/compile.py:411`

```python
line_id = unit[0].line_id or f"{unit[0].label}.{unit[0].seq:04d}"
```

而表格那边是 `beat_model.assign_identity` → `line_identity.allocate`（`max + 1`）。

**两个数字来源不同**

`_renumber` 里 `b.seq = i` 是**全文连续**序号，`line_id` 的号是**label 内连续**。
所以只要文件里有两个 label，这两个数必然不同（上面实测：第 3 拍 `seq=3` 但 `line_id=ch02.0001`）。

于是同一拍：

| 谁在算 | 结果 |
|---|---|
| `allocate()`（表格/导出/协作） | `ch02.0001` |
| `compile.py` 兜底（编译结果表） | `ch02.0003` |

**为什么诡异**

- 兜底**不回写**：`compile` 算完就丢了，`beat.line_id` 还是空的。所以这不是"补号"，
  是"临时捏一个号给报表看"。
- 用户在"编译结果表"里看到 `ch02.0003`，拿它去做翻译或语音命名；
  下次导出到 Excel 后同一行变成 `ch02.0001`。**同一条台词，两个 key。**
- 更隐蔽的是 `seq=0` 的情况：兜底会产出 `ch01.0000`，而 `parse('ch01.0000')` 是
  **合法**的（`('ch01', 0)`）—— 一个"第 0 句"会顺着正常管道流出去。

**建议**

- 兜底改成调 `allocate()`，并且**先补号再算**（`assign_identity(beats)` 已经在
  `excel_export` / `excel_import` 里这么做，`compile` 抄一次就行）。
- 或者干脆**不许兜底**：没有 `line_id` 的拍在报表里显式标成"未编号"，
  而不是给它编一个。契约 R5 说的是"发号"，不是"显示时编个号"。
- 加一致性测试：对同一批拍，`compile` 报表里的 `line_id` 集合 == `to_row()` 出来的 `LineId` 集合。

## 五、P1：舞台位置有两套算法，能看见的那套是死的

**两份定义**

| 文件 | 表 | `left` | `right` | `close` | `far` |
|---|---|---|---|---|---|
| `stage.py:49` `_POSITION_X` | 预览用 | **0.2** | **0.8** | 0.5 | 0.5 |
| `atl.py:58` `_WORD_X` | ATL 用 | **0.0** | **1.0** | 0.5 | （没有） |

`atl.py:57` 的注释写着"与 `app.stage._POSITION_X` **同源**；这里只做兜底"——
不同源，差 0.2 个屏宽。

**谁真的在用**

`stage.py` 的 `build_frames()` 里是这样的（`stage.py:258`）：

```python
place = placement_of(at, transform_index, registry, size)   # 无条件调用，永不返回 None
x = place.x
```

`placement_of` 的兜底分支返回 `Placement(x=x, source=source)`（`atl.py` 第 4/5 步），
**永远不是 None**。所以：

- `SpriteLayout.place` 的字段注释"`None` = 没算出来"是假的；
- `build_frames` 的注释"不传就退回老的启发式"也是假的（没有这个分支）；
- `transform_x()` 这个函数**只被测试调用**（`tests/test_stage_preview.py`），
  产品代码一次都没用过。

**第二层扭曲**：`transform_x` 把 `xpos` 和 `xalign` 塞进同一个 `float()` 再 clamp

```python
for token in ('xpos', 'xalign'):        # stage.py:87
    ...
    return max(0.0, min(1.0, float(tail[0])))    # stage.py:93
```

`xalign` 是 0~1 分数，`xpos` 是**像素**。`xpos 200`（1920 宽下约 10%）会被
clamp 成 `1.0` → 贴到屏幕最右。而 `atl.py` 专门为此分了 `xpos_frac` 字段
（`Placement.xpos_frac`），注释还写了"否则 `xpos 0.5` 会被当成半像素"。
同一个语义，一个模块分得清，另一个模块没分。

**为什么诡异**

测试 `test_stage_preview.py:28` 断言 `transform_x('left') < CENTER_X` 通过
（0.2 < 0.5）。这条测试给人一种"位置算法有覆盖"的安全感，而它测的是**死代码**。
真正跑在用户眼前的 `placement_of` + `_BUILTIN_PROPS` 走的是另一套值，
测它的是另一个文件。

这是"双实现 + 死代码 + 测试给假信心"三件套。漂移不是会不会，是什么时候被发现。

**建议**

- 短期：删掉 `transform_x` 和 `_POSITION_X`，或者让它直接委托
  `placement_of(name, ...).x`。**不要留两份表**。
- 判据：`transform_x('left')` 必须等于 `placement_of('left').x`。
  加一条测试钉住这个等式，两边以后谁改都会被拦。
- `SpriteLayout.place` 的注释要改（它永远不为 None）；`build_frames` 的
  "退回启发式"那句话也要删，否则下一个人会照注释去写一个不存在的分支。
- `_LETTER_X` 也是两份（`stage.py:59` / `atl.py:103`），目前值相同。
  同一条规则要写两遍，早晚不同。合并成一个常量。

## 六、P1：引擎事实"没取到"和"真的没有"在文件里长一样

**在哪**：`storygraph/pipeline/engine_collect.py:613`

```python

```

`probe_ok` 的判据是"**探针文件有没有产出**"（`engine_collect.py:78` 的注释原话：
"`probe_complete` 只看文件有没有产出"）。探针内部每一项是独立 `try/except`——
这是对的（API 改名时不崩）。但"取到的是 None"和"这项真的没有"在产物里没区别。

**实测**：模拟"探针跑完了，但 images 这一段没取到"

```python

                     'transforms': [('json_dump', ['left'])],
                     'tags': [('probe', {})]},
                    collection={'parse_clean': True, 'probe_complete': True, ...})

facts 段里的键: ['transforms']        ← images 和 tags 整个消失了
validate_facts: []                    ← 校验通过
```

`value_of(facts, 'images', {})` → `None`，调用方一句 `or {}` 就变成"这个项目没有图片"。

**为什么诡异**

`engine_facts.py:23` 说"`parse_clean` 或 `probe_complete` 为假时整份事实不可用"，
意思是要一个"可用/不可用"的闸门。但闸门只判"进程有没有产出文件"，
不判"每类资源有没有取到"。于是引擎升级把 `renpy.list_images` 改名之后：

- 探针不崩（`try/except` 兜住了，符合设计）；
- `probe_complete = True`（文件产出了）；
- 事实里没有 `images` 这个键；
- 校验通过；
- 下游认为这个项目**一张图都没有**。

它和"项目真的没有图片"在事实文件里**完全无法区分**。而工具最怕的就是

**建议**

- `build_facts` 里对"值为 None / 缺失"的键，**留一条显式的缺口记录**：
  `facts['gaps'] = [{'key': 'images', 'reason': 'probe returned None'}]`。
  键可以没有值，但"为什么没有"必须在文件里。
- `validate_facts` 加一条：`gaps` 非空时 `usable` 必须降级为"部分可用"，
  并在界面上说出来（"这次没读到图片清单，可能引擎版本变了"）。
- 判据升级：`probe_complete` 从"文件产出了"改成"**每个声明的 key 都给了值或给了缺口理由**"。
  这才对得上它的名字。

## 七、P2：`assign_identity` 名字是"发号"，顺手干了两件别的事

**在哪**：`storygraph/story/beat_model.py:3389`

```python
def assign_identity(beats):
    unique_ids(beats)               # ① 可能改掉已有 ID（重号时）
    ...
    b.beat_fingerprint = _beat_content_hash(b)    # ② 无条件重算全部指纹
```

**为什么诡异**

1. **可能改掉已有的身份**（重号时重发号），这不是"分配"是"改判"；
2. **一定重算全部内容指纹**，这是另一个语义（`beat_fingerprint` 是"这行现在长什么样"）。

反过来也危险：任何只读场景（比如导出报表）为了拿到新指纹，被迫调用一个

**建议**

- 拆成两个名字：`ensure_ids(beats)`（只补空，绝不改已有）和 `refresh_fingerprints(beats)`

- 如果不想拆，至少把它改名 `renumber_and_fingerprint`，让"它会改东西"写在名字上。
- `unique_ids()` 里 `parse(lid)[0] if parse(lid) else 'start'` 这一行，
  遇到不认识的 ID 就丢章名（见第 3 条）。应改成"认不出就原样保留 + 报出来"。

## 九、P0：`return` 的"保真"是两个错误互相抵消出来的

**在哪**：`storygraph/story/beat_build.py:1165` 和 `storygraph/story/beat_render.py:2817`

```python
# beat_build.py —— 收到 return 语句，什么都不产出
def _emit_return(self, stmt, payload, _ln):
    self.flush_stage_only()
    self.last_speaker = ''
    return False, False        # 参数 stmt / payload / _ln 一个都没用

# beat_render.py —— 每个 label 块结尾，无条件补一行 return
out.append(indent + 'return')
```

**发生了什么**

第一步：`return` 语句进了解析器，走到 `_emit_return`，它**不生成任何拍**，三个参数一个都没读。
第二步：渲染时，每个 label 块结尾**无条件**补一行 `return`。

一个丢、一个补，正好抵消。所以绝大多数脚本看起来"逐字节保真"——
`label ch01: "台词" return` 往返之后还是它。**这个保真是假的，是巧合。**

只要写法偏离"章尾一个裸 return"，抵消关系就破。实测四档：

| 源 | 产物 | 结果 |
|---|---|---|
| `"台词"` + `return` | `"台词"` + `return` | 看起来对（抵消成功） |
| `"台词"` + `return 42` | `"台词"` + `return 42` + **`return`** | 多一行 |
| `"第一句"` + `return` + `"第二句"` | `"第一句"` + **`"第二句"`** + `return` | **控制流被改** |
| `"一"` + `return` + `label ch02` + `"二"` + `return 7` | 末尾多一行 `return` | 多一行 |

第三档最严重。原文件里 `"第二句"` 在 `return` 之后，是**死代码，永远不会执行**。
产物把 `return` 挪到了章尾，`"第二句"` 变成**会执行**。
如果那句不是台词，而是 `$ gold += 100` 或 `play music "x"`，产物就会多做一件事。

第四档还有第二层：`label ch02` 结尾多了裸 `return`，把 `return 7` 的返回值盖掉了。
`call ch02` 拿到的会是 `None` 而不是 7。

**为什么诡异**

这是**"两个错误互相掩护"**的教科书案例：

- `_emit_return` 丢掉语句 → 本该被保真测试抓住
- 但 `beat_render` 无条件补 return → 恰好补回来了
- 于是金标测试（`audit_byte_exact` 52/52）**全绿**

也就是说，**测试全绿恰恰是因为没人敢修其中任何一个**。
谁要是"顺手把 `_emit_return` 补好"（让它吸收 return 行），立刻变成两个 return；
谁要是"顺手去掉无条件补 return"，所有正常章节的 return 全丢。

这是本清单里最难自查的一类：修任何一边都炸，不修就永远带着这个雷。

**建议**

- 判据要改成"**return 是被保真回来的，还是被补出来的**"。做法：让 `_emit_return`
  正常吸收（`return True, False`），把它落成一个 `KIND_FLOW` 拍（和 `jump`/`call` 同一档，
  `raw` 存原文）；渲染时**只在 label 块里确实没有任何 return 拍**时才补。
  这样裸 return 走"保真"，`return 42` 走"保真"，两者都不靠补。
- 补 return 之前加一条硬判断：**已经渲染出 return 拍就不再补**。
- 加四条测试，就是上面那张表。它们现在一条都没有——
  现有的保真金标用的是"标准写法"，正好全在抵消成立的区间里。
- 顺带：``"第二句"` 被救活"这一档，`structure_loss` 也抓不到（它比的是菜单签名）。
  它不是排版问题，是**可达性变化**，值得单独一条门禁。

## 十、P1：`indent` 参数是死的，而"已知排版漂移"的病根就是它

**在哪**：`storygraph/story/beat_render.py:494`

```python
def render_beat_to_rpy(beat: Beat, indent: str = '    ', ...) -> list:
    ...
    def emit(line, source='', intent='', status='ok'):
        lines.append(line)          # ← indent 从头到尾没出现过
```

**实测**：四种 indent 值，输出**完全相同**

```
indent=''         -> ['"一句台词"']
indent='    '     -> ['"一句台词"']
indent='        ' -> ['"一句台词"']
indent='\t'       -> ['"一句台词"']
四种 indent 的输出是否完全相同： True
```

**为什么诡异（这一段是本清单里最"绕"的）**

`beat_render.py:1890` 有这么一段：

```python
raw = render_beat_to_rpy(beat, indent='', audit=audit, trace=trace)
base = None
for ln in raw:
    if ln.strip():
        base = len(ln) - len(ln.lstrip())     # 自己重新量一遍基准缩进
        break
```

它传 `indent=''`，意思是"给我**不带**缩进的原文，我自己按 base 平移"。
但 indent 是死的，拿到的原文缩进由**内部函数各自决定**，跟传什么无关。
于是 `base` 量到的可能是 4，而它以为是 0，平移时就多叠一档。

而它的 docstring 正写着：

> ⚠ **已知的排版漂移（未修）**：`python:` 块里续行的缩进每往返一轮会大一档……
> 试过三种改法（基准改成从非续行取、只给续行减一档、`_indent_block_body` 不叠基准），
> **每一种都让全项目丢失数变多或让解析异常从 0 涨到 5**，所以保持现状。

**三种改法都失败，是因为改的都是下游。** 上游那个本该控制缩进的参数，从第一天起就是空的。
"试过三种改法都不行"这个结论是对的，但它指向的原因错了——
不是"这个问题无解"，而是"你在调一个不接线的旋钮"。

**建议**

- 要么让 `indent` 真的生效（`emit` 里 `lines.append(indent + line)` 可能不是想要的语义，
  要先定义清楚"indent 是前缀还是基准"），要么**删掉这个参数**，
  让调用方不再以为自己能控制它。
- 删掉之后，`beat_render.py:1890` 那段的 `base` 逻辑才有意义（它自己量、自己平移）。
- 判据：加一条测试 `render_beat_to_rpy(beat, indent='')` 与 `indent='    '`
  **必须不同**，或者参数不存在。现在的状态是"参数存在但两者相同"，这是最坏的一种。

## 十一、P1：预览里的 BGM 只播一遍，游戏里是循环的

## 十二、P1：写回哪个文件，取决于"画布上选中了哪个节点"

**在哪**：`storygraph/ui_qt/window_export.py:298` 和 `:357`

```python
res = tables.export_table(
    table_path, ...,
    source_rpy=self._source_rpy_for_table(table_path))    # 298

def _source_rpy_for_table(self, table_path):              # 357
    """增量补丁的底稿 .rpy。
    优先用**画布上当前章节**的源文件……其次让 app.tables 退回"表旁边同名 .rpy"。

    nid = self._canvas.selected_node_id()
```

**发生了什么**

2. 同时，函数去问画布"你现在选中了哪个节点" → 那个节点的 `.rpy` 当作落点

**两个 UI 状态之间没有任何一致性检查。** 用户挑了 `ch01.xlsx`，而画布上正好选中了
`ch02` 的节点，落点就是 `ch02.rpy`。

`_source_rpy_for_table(table_path)` 的 `table_path` 参数**就是用来做这个检查的**，
但它一次都没被读。

**实测：护栏救了一半**

我造了 `ch01.xlsx` + `ch02.rpy`（工具生成过的，带标记），模拟"选中 ch02、导 ch01 的表"：

```

ok      : False
blocking: [block] LABEL_COLLISION（整体）：`label ch01` 在项目其他 .rpy 里已经定义过
```

**没有发生覆盖**——这是 `LABEL_COLLISION` 挡的，不是"选错章"这件事被发现了。

## 十四、P2：同一个 `_indent_of`，四份实现、三种返回类型、两种 tab 口径

| 文件 | 返回 | `'    x'` | `'\tx'` |
|---|---|---|---|
| `assets/atl_block.py:38` | int（tab 按 **4** 算） | 4 | **4** |
| `parsing/renpy_parser.py:805` | int（字符数） | 4 | **1** |
| `story/patcher.py:159` | **str（缩进前缀）** | `'    '` | `'\t'` |
| `story/python_lift.py:62` | int（字符数） | 4 | **1** |

实测输出：

```
样例                        atl_block   renpy_parser      patcher   python_lift
'    show ling'                   4              4       '    '             4
'\tshow ling'                     4              1         '\t'             1
atl_block 与 renpy_parser 对 tab 行结论相同吗： False
patcher 的返回类型： str （另三个是 int ）
```

**为什么诡异**

四个私有函数同名不同义，其中 `patcher._indent_of` **返回的是字符串**，另外三个返回数字。
这个差别不是学术问题：`patcher` 那边的用法是 `indent + line`（拼前缀），
如果有人从 `renpy_parser` 复制一行 `n = _indent_of(line)` 到需要前缀的地方，
得到的是 `4 + "show ling"` —— `TypeError`，或者更糟，`str` 拼接成功但结果荒谬。

tab 口径不一致更隐蔽：`atl_block.py:39` 的注释说"tab 按 4 算 —— 与 Ren'Py 默认口径一致"，
说明作者知道 Ren'Py 是 4。而 `renpy_parser` 按字符数算（tab=1）。
两者判"这一行比块头深几层"时，对 tab 缩进的文件会给出不同结论。

（这一条我标"潜在"：目前两个模块吃的是不同内容，不一定同时看同一行。
但同一个项目里一旦有人用 tab 缩进，`atl_block` 认得出层级而 `renpy_parser` 认不出，或反之。）

**建议**

- 在 `core` 里放两个函数，名字区分语义：
  `indent_width(line)`（视觉宽度，tab=4，给 ATL 用）和 `indent_prefix(line)`（字符串，给拼接用）。
  四个地方全部改成调用它们。
- 加一条测试：`indent_width('\tx') == 4`、`indent_prefix('\tx') == '\t'`、
  `len(indent_prefix(s)) == len(s) - len(s.lstrip())`。
- 这类"同名不同义"值得一次性清一遍。全仓 79 处未使用参数里也埋着同类问题（见下）。

## 十九、P2：协作租约用**无时区的本地时间**，跨时区会让锁提前/延后失效

**在哪**：`storygraph/collab/collab_store.py:180`（写）与 `:496`（读）

```python
def _now() -> str:
    return datetime.now().isoformat(timespec='seconds')   # '2026-10-23T20:34:09'，无 tz

def lock_state(row, now=None) -> dict:
    now = now or datetime.now()                            # 同样是本机本地时间
    ...
    until = _parse_ts(row['locked_until'])                 # fromisoformat，不会带 tz
```

**发生了什么**

租约到期时间由**加锁那台机器**用本地时间写进库，由**读锁那台机器**用本地时间比较。
两台机器时区不同时，差值直接变成"时间差"：

| 场景 | 结果 |
|---|---|
| 北京（UTC+8）加锁，写 `20:49 到期`；东京（UTC+9）同事此刻 `21:34` 读 | 判为**已过期**，直接抢锁（实际才过 0 分钟） |
| 反过来：伦敦（UTC+1）同事此刻 `13:34` 读 | 判为**还有 7 小时**（实际 15 分钟） |

团队都在一个时区时看不出来。有远程/外包/出差，就变成"我的锁莫名其妙被抢了"或
"这个人下班了锁还在，谁都改不了"——后者正是当初加租约要解决的那个问题。

**还有一档更硬的**：`_parse_ts` 用 `datetime.fromisoformat`。
如果库里出现**带时区**的时间串（`+08:00`），它返回 aware datetime，
与 `datetime.now()`（naive）相减 → **`TypeError: can't subtract offset-naive and offset-aware datetimes`**。
也就是说"混进一条带时区的记录"不是算错，是直接抛异常。

**建议**

- 写库一律存 UTC + 明确后缀：`datetime.now(timezone.utc).isoformat()`；
  比较也统一在 aware 域（`datetime.now(timezone.utc)`）。
- `_parse_ts` 对**不带 tz 的老数据**要显式当本地时间处理（`dt.replace(tzinfo=...)`），
  而不是让它和 aware 值混在一起——否则老库一升级就炸。
- 加一条测试：同一行用 UTC+8 写入、用 `now=` 拼出的 UTC+9 时间读，断言 `expired` 判定不变。
  这正是"跨时区"能做到的最小复现。

## 二十一、共性问题：不是十九种病，是三种

两轮查下来，十四条里有十三条能归到三个模式。它们不是"代码质量差"，
是三种**结构性的自欺**——每一种都有一个共同点：**测试是绿的**。

### 模式一：双实现（第一条到第八条，占多数）

> **一个概念有两份实现，其中一份是"更懂的人后来写的补丁"，但没有把老的那份删掉。**

| 概念 | 老的一份 | 新的一份 | 现在谁在用 |
|---|---|---|---|
| 行身份 | `collab._unique_line_id` / `compile` 兜底 | `line_identity` | 都在用，规则不同 |
| 舞台位置 | `stage.transform_x` | `atl.placement_of` | 只有新的在用户眼前 |
| 内容指纹 | `beat_fingerprint`（持久化） | `BeatSnapshot.fingerprint`（会话内） | 两个都在判"改没改" |
| 引擎事实完整性 | `probe_complete`（文件产出了） | 无（缺） | 只有一个不够用的判据 |
| 缩进测量 | 四份 `_indent_of`（三种返回类型） | 无 | 各用各的 |
| 列清单 | 手抄的「列说明」25 行 | `COLUMN_SPECS` 35 列 | 用户看手抄的，代码用真源 |
| `show` 的生成 | `compose_show_cell` | `compose_stage_extra` | 靠注释维持"严格互补" |
| 资产分组树 | `asset_extensions.get_tree` | `asset_panel` 里又写一遍 | 面板/导出两套分组，`type` 只在一边有 |
| "这一拍属于哪一章" | `editor._renumber` 取文件第一个 label | `unique_ids` 取 ID 前缀 | **两处都在猜，都不看 `beat.label`** |

共同点不是"写了两遍"，是"**第二遍写完了、第一遍还活着，而且还有测试在测第一遍**"。

### 模式二：假旋钮（第十、十一、十二、十五条）

> **参数在签名里、在文档里承诺有效，函数体一次都不读。**

- `indent`（§十）→ 有人真的在传，还因此写下了"试过三种改法都不行"；
- `loop`（§十一）→ 有人真的传了 `True`，于是预览里音乐不循环；
- `table_path`（§十二）→ 本该用来判"表和画布是不是同一章"，没用，于是报错文不对题；
- `native_ok`（§十五）→ 全仓零调用，纯装饰。

代价不是"不好看"，是**下一个改代码的人会对着一个不接线的旋钮调半天**，
最后得出"这个问题无解"的结论（§十 就是这么发生的）。

### 模式三：错误互相抵消（第九条，最危险）

> **两个 bug 正好互相盖住，于是测试全绿；修任何一边都会炸。**

`return` 那一档是标本：`beat_build` 丢掉 return（bug A），`beat_render` 无条件补 return（bug B），
A + B = "看起来保真"。全项目 52 条逐字节金标全过，**恰恰因为没人敢修其中任何一个**。

这类问题的识别信号是：**某处的"正确"需要用两行注释来解释为什么错着也能跑**
（`beat_render.py:1880` 那段"已知漂移、未修"就是这种气味）。
它不是"已知限制"，是"两个错误结成了稳定结构"。

### 给后续改动的四条指导意见

1. **新增"更懂"的实现时，同一份提交里删掉老的。** 并且删掉**测老那份的测试**——
   否则测试数会骗人（§五 就是一条测试在守护死代码）。
2. **判据不许只判"过程完成"。** P0-1（`.blocked.rpy`）和 §六（`probe_complete`）
   是同一类：把"动作执行了"当成"结果对了"。判据要判**结果**
   （文件不在 game 里了 / 每个 key 有值了），不判**过程**（我写了 / 我跑了）。
3. **ID 是主键，不是注释。** 凡是往 ID 里塞额外信息（`~2` 表示分叉、`0000` 表示没有号），
   都会在下游某处炸，而且炸的时候是静默的。额外信息放载荷。
4. **签名里的每个开关，必须有分支读它。** 这条可以在 `health_check.py` 里做成静态检查
   （AST 能算，见附录脚本），成本极低，能一次性拦住模式二的复发。
