## 〇、先把话说明白：什么叫"工具认识一句写法"

我们以前把这件事当成一件，其实它是**三件完全不同的事**。混在一起谈，就会永远谈不清。

想象工具是一个刚来的**前台**，你在脚本里写的话是"客户提要办的事"。

| 三件事                 | 前台的表现                               | 现在做到没有  | 做不到会怎样                       |
| ------------------- | ----------------------------------- | ------- | ---------------------------- |
| **① 保管**（不弄坏）       | "这话我听不懂，但我原样抄下来，一个字不改"              | ✅ 已做到   | 工具一导出就把你的东西改没了 → **你会立刻卸载它** |
| **② 认人**（知道它是个什么东西） | "这行是个'动作'，它叫 `swim_suit`，后面还跟着两个东西" | ⚠️ 一半   | 它在表格里只是一坨看不懂的字，你没法编辑         |
| **③ 懂业务**（知道它什么意思）  | "这一步就是让凌跃捷换上泳装"                     | ❌ 永远不该猜 | 猜错 = 改剧情。**只能由人告诉它**         |

**这张表就是整篇设计的地基。** 它带来三条铁律：

1. **保管是底线，不是能力。** 哪怕工具一辈子不懂 `swim_suit`，也绝不能把它弄丢、改错、或者吃掉旁边的行。—— 这是"保真"。
2. **"认人"可以慢慢长。** 今天认识 3 个写法，明天认识 30 个，靠的是**项目自己声明**，不是工具硬编码。—— 这是"通用"。
3. **"懂业务"永远靠人点。** 工具负责把选项摆出来、把后果说清楚；点不点由人决定。—— 这是"易用"。

**为什么这个顺序不能反**：因为最贵的事故是静默的 —— 工具"以为懂了"，把 `mycue "闪电" intensity=3:` 里那个 `mycue` 当成说话人，产出一句**由 mycue 说的台词**，冒号和参数全没了。**假懂比不懂危险一百倍。** 所以本工具一切设计都遵循一句话：

> **宁可说"我不认识"，也绝不装作认识。**

（本仓库真出现过这个事故：`minigame` 的主循环 `while ...:` 被整块吃掉，小游戏一轮都跑不起来。这不是假想。）

## 一、为什么现在这版你不能用（把你的原话逐条对上）

| 你的原话                                 | 病根                         | 为什么它这么难用                                                                                                |
| ------------------------------------ | -------------------------- | ------------------------------------------------------------------------------------------------------- |
| "作为一个程序我都看不明白它写的东西"                  | **它满嘴是给机器看的词**             | 界面上写着"语句名 / 参数（会成为表格列）/ `attr_groups` / `T1 通用行` / 候选值 / `Describe`"。这些词**连程序员都要想一下**，编剧看了只会退出。         |
| "参数表非常丑，一行只能显示一个"                    | **排版是"电子表格表头思维"**          | 它长得像一张三列表：参数名 / 中文名 / 候选值。**加一个参数就要拖横向滚动条**，字段还被裁成半截。工具作者自己看着方便，用的人看得痛苦。                                |
| "`with`、`window`、`pause` 不都是默认关键字吗？" | **它把工具本来就认识的，当成"工具还不认识"**  | 这是最严重的一条：**它在教错人**。真项目里已经因此被误导着写出一份 `pause` 的声明 —— 而 `pause` 是 Ren'Py 自带语句，**根本不需要声明**。工具输出的是**错误的知识**。 |
| "候选值非常繁琐，有多少动作我也不知道，却要我一个个手填"        | **它让"本来能自动算出来的东西"变成人的体力活** | 你已经在剧本里写过 `swim_suit lyj "泳装"` 十几次了 —— **它要填的东西，工具扫一遍脚本就能反推出来**，却让你从零手打。而且"项目里一共有哪些动作"这个问题，界面根本**不回答**。 |
| "卡片编辑器里有没有自定义模块的显示？没有的话我怎么编服装？"      | **学习和使用是两条断开的链**           | 你可以在弹窗里"声明"一个写法，但**声明完，卡片上并没有一个地方让你真的用它**。等于教会了工具一个新词，却没给它一张能写这个词的纸。                                    |

**一句话总结病根**：这版工具是**照着"程序员的思维"长的** —— 参数、键值、注册表、等级、候选值数组。它没有回答"**编剧坐在卡片前，想做一件事，第一眼看到什么、点几下能完成**"这个问题。

## 二、三条地基：保真、通用、易用

这三样有时候会打架，所以先说清**它们各自的定义、以及谁让谁**。

### 2.1 保真（不弄坏）

**定义**：打开工具再导出，你的 `.rpy` **一个字节都不该变**；工具不认识的行，原样躺在那里，不许多一个空格、不许少一行。

**为什么是第一优先**：用户的信任只有一次。只要发生过一次"我只点了个导出，文件就变了"，这个工具就再也回不来了。所以本工具把保真做成了**结构性保证**，而不是"我们小心一点"：

- 工具**从来不是**"重新生成整个文件"，而是**逐行配对，只替换它真改过的那几行**；
- 任何一步对不上，就**整份放弃**（"要么全对、要么完全不动"），绝不产出"半对"的文件；
- 每次落盘前对一遍指纹，文件被别的程序改过就拒绝写。
- **【给程序看】** `.rpy` 唯一真源；改已有文件走 `story.patcher` 的增量补丁；落盘唯一入口 `generation_guard.write_generation`；盘点守卫 `tools/audit_idempotence.py`（53/53 逐字节）、`tests/test_roundtrip_idempotent.py`。

### 2.2 通用（不写死任何项目的词）

**定义**：工具**不认识**"服装""表情""泳装""下雨"这些具体词。它只认&#x8BC6;**"项目声明过哪些词、这些词长什么形状"**，然后照着摆出来。

**为什么必须这样**：因为下一个项目可能没有"服装"这个概念，而有个"天气"；再下一个用的是完全不同的自定义语句。**但凡工具写死了"服装"，它对别的项目就是废的。**

**怎么落地**：把"是什么"从**代码**里搬进**一份项目自己的文件**（`storygraph.rules.json`）。这份文件是数据、不是代码，因此：

- **能进 git**：谁改的、改了什么、能不能回滚，一目了然；
- **能被 diff**：程序改了代码，工具的认知跟没跟上，能自动查出来；
- **能被要求"签字"**：工具绝不偷偷往这里写东西。
- **【给程序看】** 优先级真源 `story/stament_registry.py`：项目声明 > 宿主注册表 > 形状识别；词表真源 `core/vocabulary.py`；一个组名都不认识的底线判据 `tests/test_spec_groups.py`。

> ⚠️ 这里有一个**反直觉但关键**的取舍：**"没有声明" = "完全平铺"，不是"给个默认分组"。**  
> 因为一般人根本没有"服装"这个概念，他就不该看到任何分栏。**少了是保守，多了是骗人。**

### 2.3 易用（编剧听不懂代码）

**定义**：编剧要知道的只有三件事 —— **我能做哪些动作**（清单）、**这个动作要填什么**（有例子、有下拉）、**填完长什么样**（当场预览）。

**为什么它排第三但仍然必须做**：因为没有它，前两条再正确也没人用。你的原话是最好的注脚：**"我不会用！你更别提编剧了。"**

**怎么落地**：

- 界面上**只出现编剧能听懂的词**：动作、名字、例子、只能填这些、教会它；
- **"要填什么"由工具从真实脚本里猜出来**，编剧只是"改改它猜的"，不是从零填；
- **"有多少动作"这个问题必须有答案**：一个可浏览的**动作清单页**，还能导出成 Markdown 给编剧看（不用装工具）。

## 三、工具怎么"学会"一个写法？—— 四条途径，有先后

这是全文最核心的一节。**"让工具认识自定义写法"不是一种方法，是四种，而且有优先级。**

```
  ① 宿主自带说明书   （最可靠：不是猜的，是项目自己公布的）
        ↓ 没有？
  ② 项目自己的声明   （主路径：可评审、可 diff、可回滚）
        ↓ 没有？
  ③ 从真实脚本反推   （只用来"发现"和"猜形状"，绝不用来定意思）
        ↓ 都用不上？
  ④ 人当场教一句     （弹窗问一句，教完自动落成 ②，下次不用再教）
```

### 3.1 途径① 读"说明书"：Ren'Py 其实自己公布了答案

**Ren'Py 官方有一个机制叫"用户自定义语句"（CDS）**：程序在 `python early:` 里写一句  
`renpy.register_statement(name="mycue", block=True, ...)`，就相当于**在项目里立了一块牌子**：  
"我这个 `mycue` 是一个语句，它带块、它有哪些参数。"

**为什么这是最高优先级**：它不是我们猜的，是**程序亲手写的**。而且它**永远不会漂移** ——  
程序改了代码，牌子跟着变，工具重新扫一遍就看到新形状。

**现在的问题**：Ren'Py 把答案公布在项目里，**而我们的工具选择了不看**  
（我们明明认识 `python early:` 这个块头，却把它的内容整块跳过了）。

**【给程序看】** 现状：`parsing/renpy_parser.py` 认识 `python early:`；`story/project_conventions.py` 的 `_CONTAINER_HEADS` 把它整块跳过。落地：`story/cds_registry.py` 已有雏形（括号配平扫描 `renpy.register_statement(...)`），**只认字面量名字，认不出就跳过**（猜名字比说不知道坏得多）。真机 `sr_general` 里**没有 CDS**，所以这条路的价值在通用性、不在这一个项目。

> **行业佐证**：**Yarn Spinner**（另一个对话工具，Unity/Godot/Unreal 通用）就是这条路 ——  
> 它的 VS Code 插件会**自动从你的 C# 源码里找出自定义命令**，然后给编剧**自动补全**。  
> 见 §九。

### 3.2 途径② 项目自己的声明（主路径）

项目在 `storygraph.rules.json` 里写一段，告诉工具："有这么个写法、它中文叫什么、它要填哪些东西"。

**为什么这是主路径**：

- **它不依赖任何一种引擎**（不像途径① 只对 Ren'Py 有效）—— 这是"能迁 Unity"的伏笔；
- **它是一份文件**，能进版本库、能被评审、能被回滚；
- **人不用写代码**，填的是数据。

**规矩（重要）**：

- 声明里**只填数据，绝不填代码**。参数取值来源用**名字锚点**（"从角色表取"`characters`、"从变换表取"`transform`、"从图片表取"`images`、"从音乐表取"`music`），工具自己去解析，项目侧一行 Python 都不用写。
- **声明没写参数形状** = 工具仍然保真地认识它（能定位、能原样保存），只是不给你摆参数格子。
- **声明可以只写"有这个词"，不写参数。**

**【给程序看】** 真源：`storygraph.rules.json` 的 `statements[]` / `attr_groups[]`；写入口 `story/statement_registry.py` 的 `declare_statement` / `declare_attr_groups`（同名=更新、坏清单拒写、其它键保留）；表单→声明的纯函数 `authoring/learn_statement.build_declaration`。

### 3.3 途径③ 从真实脚本里"反推"（只用来看，不用来定）

编剧不需要填参数名 —— 因为**他已经在剧本里写过好几遍了**。工具扫一遍他在哪儿用过这个词、怎么用的，把形状**反推**出来：

```
剧本里出现过（5 次）：
    outfit lyj "泳装" mood=happy
    outfit lyj "校服" mood=calm
    ...
        ↓ 反推
  · 第 1 个位置  例：lyj        （是角色表里的角色 → 候选 = 角色表）
  · 第 2 个位置  例：泳装/校服   （是引号里的词，出现过 2 个不同的 → 这两个是候选）
  · mood 这一项  例：happy/calm  （作者自己写了名字 = 直接用这个名字）
```

**为什么允许它存在**：这是"编剧也能懂"的**技术支撑** —— **不让任何人手填参数名**。  
这也是直接回答你那句"有多少动作我也不知道，却要我一个个填"。

**它的铁律（三条，都有判据）**：

1. **只报"出现过 ≥2 次的值"当候选** —— 只出现一次的，可能是笔误，不能当候选摊给编剧选；
2. **猜不出名字就不猜** —— 裸数字那一项默认叫「第 1 项」「内容」，**绝不生成 `intensity` 这种看着像真、其实是我编的英文名**；
3. **反推只影响"界面上摆什么"，绝不影响"产物写什么"** —— 教之前导出的文件，和教之后导出的文件，**逐字节相同**（唯一差别是少一条告警）。

**【给程序看】** `authoring/learn_statement.suggest_shape(statements, head)`（M-V2-2，核心已在真项目跑通：`outfit` 反推出 3 项）；候选来源优先级：同动作真实出现过的值 → 角色表 → 资源表某列 → 手输。**"精化不改字节"是不变量（M2）**。

### 3.4 途径④ 人当场教一句

前面三条都没有时，工具**问一句**："这个 `swim_suit` 我还不认识，它中文叫什么？要填什么？"  
人答完，**自动落成途径② 的那份文件**。

**为什么一定要落成文件、不能只记在内存里**：因为"只存在内存里的知道不算知道" —— 程序员明天改了代码、工具明天换了台机器，两边就对不上了。落成文件，才能被评审、被 diff、被回滚。

**"问一句"本身就是安全边界**：字符串长得像不能证明是同一个东西（`MOM` 和 `妈妈` 没有任何字符关系），所以**判定权交给人**，工具只负责"给候选 + 说清凭什么"。

**【给程序看】** `authoring/char_decisions.py`（28 条判据）+ `ui_qt/dialog_chars.py`（11 条）；`LJK` 与变量名只差大小写时必须**拒绝自动加别名**（加了会变歧义）。

## 四、教会之后，它在四个地方同时生效

这是整篇设计里**最省事的一条**：声明一次，表格 / 卡片 / 校验 / 图 **四处自动同时变**，不需要各自再配一遍。

```
                 你写一条声明（"swim_suit 要填 角色+服装"）
                                │
        ┌───────────────┬───────┴───────┬───────────────┐
        ▼               ▼               ▼               ▼
   Excel 表格       卡片编辑器       校验器          构建报告
   多出参数列       多出一组控件     按声明检查      "本项目声明了 N 个写法"
   每列挂下拉       下拉=候选值     缺必填要报      覆盖率仪表盘
```

**为什么这么设计**：如果不这么做，每加一种语句就要在"解析 / 表格 / 卡片 / 渲染 / 校验"**五个地方各登记一遍** —— 漏一处就是**静默丢内容**（本仓库已经因为漏登记吃过亏）。收成"一处声明、四处投影"，改一处就全都对了。

**【给程序看】** 这是"投影"思想（MPS 的做法，见 §九）：真源只有一个，其它都是它的**记法**。现状依据：`story/spec_args.py`（每参数一列的唯一真源）、`app/beats.py` 的 `spec_arg_fields_for` / `spec_arg_choices_for`（卡片与 Excel **同源**，避免"表里是 A、卡片是 B"）、`pipeline/validate.py` 的 `W120/W121`。

## 五、卡片编辑器：自定义动作到底在哪儿"露脸"

这是你最后那个问题的正面回答：**"卡片编辑器里有没有自定义模块的显示？没有的话我怎么编服装？"**

**现状**：卡片的**代码层**其实已经有一组"参数控件"（`set_spec_args`），后端全通。问题是 —— **普通人根本走不到那里**：它藏在参数区、显示的是英文参数名、而且没有"我想加个动作"的入口。**等于有管道，但没有水龙头。**

**新设计：两个入口，一个清单。**

### 5.1 主入口：卡片上的「＋ 加一个动作」

编剧坐在某一拍前，脑子里想的是"让凌跃捷换泳装"。所以他需要的是：

```
在这一拍的动作：  [ 泳装切换 ▾ ]  [ ＋ 加一个动作 ▾ ]
                     ↑ 用中文名，下拉里是"能选的动作清单"
```

点「＋ 加一个动作」→ 出来一个**中文名的下拉**（泳装切换 / 下雨 / 淡入淡出 / 停一拍…）→ 选一个 → 需要填的格子**当场按声明长出来**（每格带例子和下拉）→ 填完 → "加进这一拍"。

**为什么不让他去弹窗里"声明"**：声明是**第一次**才做的副产品。日常 99% 的操作是"用"，不是"定义"。所以**主路径是"从剧情出发"，不是"从配置出发"**。

### 5.2 第二个入口：动作清单页（回答"我一共有多少动作"）

你问"有多少动作我也不知道" —— 所以必须有一页**专门回答这个问题**：

```
┌─ 动作清单（本项目） ──────────────────────────────────────────┐
│ 编剧看到的名字      动作名        要填什么            谁在管       │
│ 泳装切换           swim_suit    角色 服装 表情       本项目声明    │
│ 下雨               rainy        强度                本项目声明    │
│ 淡入淡出           with         效果                工具自带      │
│ 停一拍             pause        时长                工具自带      │
│ 显示/隐藏对白框     window       show/hide           工具自带      │
└───────────────────────────────────────────────────────────────┘
                        [ 导出这张表给编剧（Markdown/CSV） ]
```

**两个关键点，各自都有理由**：

- **工具自带的动作也列出来，并标"工具自带"** —— 这样编剧才知道"原来 `with`/`pause` 这些**本来就能用，不用声明**"。**这就是修"工具在教错人"**。
- **一栏"谁在管"** 把"本项目声明"和"工具自带"分开 —— 直接回答你那句"**你确定通用性够强吗**"：能一眼看出哪些是工具给的、哪些是你们自己加的。
- **能导出给编剧**：编剧不用装工具、不用会电脑，拿到一张 Markdown 就能用。

### 5.3 界面改成"三段式"，参数竖排

v1 的"左发现 / 右填表"双栏，编剧不知道该看哪边。改成**单栏三段**（一屏看得完）：

```
① 要认识哪个动作？         只列真正不认识的（内置的已经会了，不在这里）
   ● swim_suit   "泳装切换"   用了 12 次   例：swim_suit 林月见 "泳装"
   ○ rainy       "下雨"       用了 3 次    例：rainy 0.5

② 给它起个编剧看得懂的名字   在编辑器里显示为：[ 泳装切换 ]  ← 编剧就点这个

③ 这个动作要填什么？（工具已经从你写过的 12 次里猜出来了，改改就行）
   第 1 项  名字[ 角色 ]  例[ 林月见 ▾ ]   ☑ 只能填这些：林月见 沈青
   第 2 项  名字[ 服装 ]  例[ 泳装   ▾ ]   ☑ 只能填这些：泳装 校服
   [＋ 再加一项] [－ 删这项]

④ 以后在编辑器里长这样（下面就是真实控件，你现在就能点着试）
   动作 [ 泳装切换 ▾ ]  角色 [ 林月见 ▾ ]  服装 [ 泳装 ▾ ]
                              [ 就这样，教会它 ]  [ 算了 ]
```

**逐条对病**：

- **参数**竖排，一项一行、整行宽、**能滚动的是这个区**（不是整页）→ 治"一行只能显示一个、还被裁切"；
- **所有词都换成大白话**（动作 / 名字 / 例子 / 只能填这些 / 教会它）→ 治"看不懂"；
- **④ 是真实控件**，按之前就能点点试试 → 编剧不用想象；
- **技术细节（`swim_suit` 本体、写到哪个文件）收进小字**，可展开、不默认展开。

## 六、`swim_suit` 到底怎么"理解"？—— 两条正路，别走错

你这个具体问题，答案不是一条路，是**两条**。选哪条，取决于"它到底在改什么"。

### 判断口诀（一句话）

> **它改的是"画面上的某个角色的样子"？→ 走 A。**  
> **它是一个"独立发生的事件 / 动作"？→ 走 B。**

### 路 A：服装就是"立绘的一个属性"（推荐）

**适用**：`swim_suit` 只是让凌跃捷**换一套衣服**，画面上还是那个人。

**做法**：把泳装那张图**登记进图片表**（`Tag=凌跃捷`、`Attributes=swim_suit`）。于是它和"表情"（`happy`/`shy`）**共用同一个下拉池** —— 编剧在卡片上点角色的 chip，就能在"泳装 / 校服 / 开心 / 生气"里挑。

**为什么推荐**：因为**这是它本来的样子** —— Ren'Py 里立绘的属性（表情、服装、姿势）本来就是一回事，用空格分开的一串词。工具不该为"衣服"发明一套新机制。

**想分开显示怎么办**（因为你说"要通用，一般人没有服装概念"）：不要新机制，用**词组分组** —— 项目声明"有这么几组词"（比如"服装"这一组含 `swim_suit`、`clothes2`、`swim_*`），工具按声明**把它分到"服装"栏**。项目没声明 → **完全平铺**，不显示任何分栏。

**【给程序看】** 登记进 `images.xlsx`（`Tag` / `Attributes`）；候选来自 `attrs_of_tag`；分组走 `rules.json` 的 `attr_groups` + `authoring/spec_groups.py`（规则：逐字 / 整段词序列 / 前缀通配 `swim_*` / 兜底组；**刻意不做子串包含**——`unhappy` 里含 `happy`，按子串会归错组）；判据 `tests/test_spec_groups.py` 20 条。


### 路 B：`swim_suit` 是一条"带参数的自定义指令"

**适用**：它其实是个**动作/事件**，比如 `swim_suit lyj "泳装" intensity=3`（不只是换图，可能带特效、带音效、带演出）。

**做法**：走 §三 的途径② —— 声明它有参数 → 卡片上长出**一组控件** → 表格里长出**动态列**（`swim_suit·pose`）。

**【给程序看】** 卡片：`spec_arg_fields_for` / `spec_arg_choices_for`；表格：动态列名 = `语句名·参数名`；⚠ `fold_spec_arg_columns` 的键是**整列名**，传裸参数名会静默无事发生。

### 两条路怎么选（给你一个能对号入座的表）

| 你想要的 | 走哪条 | 因为 |
|---|---|---|
| 只是换张立绘图 | **A** | 立绘属性本来就是为这个设计的 |
| 换衣服 + 播放换装动画/音效 | **B** | 它是一个"事件"，不只是画面状态 |
| 想让编剧在"表情"旁边看到"服装"下拉 | **A + 词组分组** | 同一个下拉池，分组只是显示 |
| 这个写法还带一句台词 / 一段块 | **B** | 它有参数、有结构 |
| 我不确定 | **先 A** | A 更简单，且不阻止以后升级成 B |

## 七、有人写了个新模块，工具怎么办？—— 完整闭环

这是"通用性"的实操检验。假设明天程序加了一个 `weather` 模块，编剧在剧本里写了 `weather 雨 0.5`。

**工具的完整流程（从左到右，全自动到"问一句"为止）**：

```
1. 程序改了代码（或编剧先写了脚本）—— 工具一个字都不动他的文件
        ↓
2. 打开项目时，工具扫一遍：发现"weather 这个词我没见过，出现 3 次"
        ↓
3. 工具栏「🧩 自定义模块」亮起一个小提示："我发现了 2 个还不认识的写法"
        ↓
4. 编剧/程序点开 → 一屏看到：写法 / 出现几次 / 来自哪个文件 / 原文样例
   （工具已经把"要填什么"从真实用法里反推好了，只等人改改）
        ↓
5. 点「就这样，教会它」→ 落成一份声明文件（可评审、可回滚）
        ↓
6. 立刻生效：表格多列、卡片多控件、下拉有候选 —— 下一次编剧直接点着用
```

**三条不能破的规矩（每条都有理由）**：

| 规矩 | 为什么 |
|---|---|
| **工具绝不偷偷往你项目里写任何东西** | 声明文件是"你的文件"，工具只在**你点了确认**之后才写；没确认 = 一个字节都不写。 |
| **工具绝不猜"这是什么意思"，只猜"它长什么形状"** | 猜形状错了顶多是"格子长得不对"；猜意思错了是**改剧情**。 |
| **发现要"先问角色表"再下结论** | 真项目里 `l oh "3"` 被 v1 判成"你写错了" —— 可 `l` 是角色表里"蓝"的 ID，那**是一句台词**。**骂错人比不提示更糟**。现在先问角色表，措辞也改成陈述事实。 |

**【给程序看】** 发现：`statement_registry.discover_undeclared(root)`（纯、只读）；V2-1 闸门 `_is_builtin_head()` / `_looks_like_dialogue()` / `declared_builtins()` / `remove_statement()`（先备份再移除），判据 `tests/test_discover_gates.py` 30 条，真项目"待认识"列表 **3 → 0**。

**关于"旧项目里已经被教错的怎么办"**：工具现在能**准确指认**"这条 `pause` 声明其实不用写"并提供**一键移除**（移除前先备份到 `storygraph.rules.backup/`）。**修错也是设计的一部分** —— 一个只会加法、不会纠错的学习机制，迟早把项目污染满。

## 八、通用性：凭什么说它能撑住 Unity 迁移？

这是你最尖锐的一问。**诚实的答案是：现在不能，但设计上留了唯一正确的口子 —— 而且这个口子必须现在留，事后补不回来。**

### 8.1 三层结构：把"你的剧本"和"某个引擎"隔开

```
  第一层：你的剧本（.rpy 原文）
        ↕ 双向、逐字节保真
  第二层：演出清单（跟引擎无关的一份"这一拍发生了什么"）
        ↕ 一个引擎一个导出器
  第三层：Ren'Py 产物   /   Unity 产物   /   Godot 产物
```

**为什么必须夹一层**：如果表格里的数据直接长成 Ren'Py 语法，那它一辈子只能是 Ren'Py。夹一层"中立清单"之后，**Ren'Py 只是第一个导出目标，不是唯一**。

**现状**：第二层（中立 IR）已经存在并接线了（加过 `targets`/`nest`），但**运行时组件、资源映射、运行期验证没做** —— 也就是说，"迁 Unity"目前只到"数据能表达"这一步，没到"Unity 里能跑"。

### 8.2 声明是"数据"不是"代码"，这是迁移的关键

因为声明（§三途径②）里**没有任何 Python**，全是数据 + 名字锚点（"从角色表取""从图片表取"）——
所以**同一份声明，Ren'Py 导出器能用，Unity 导出器也能用**。如果当初把"怎么解析"写成了 Python 代码，迁移时就得**重写一遍**。

### 8.3 行业佐证：这条路别人走通了

**Yarn Spinner** 就是活样板：编剧写的 `.yarn` 是引擎无关的；自定义命令通过**一份定义文件**（或**自动从游戏源码里发现**）声明；同一份剧本，**Unity、Godot、Unreal 都能跑**（见 §九）。

### 8.4 诚实的差距清单（不吹）

| 能迁的部分 | 现在还缺的 |
|---|---|
| 演出数据（谁说话、什么表情、什么位置、什么音乐） | Unity/Godot 的**导入器**（把中立清单读进引擎） |
| 自定义写法的"形状"（声明是引擎无关的） | 资源在别的引擎里怎么映射（图/音/变换 → 引擎 asset） |
| 多语言文本（已有 tl 链路） | 运行期验证（在 Unity 里真的跑一遍） |

**结论**：**"能迁"最值钱的部分是"数据与语法解耦"，这个已经做到了**；剩下的是工程量的活。**如果反过来（先写死 Ren'Py），就再也迁不动了。**

## 九、行业里别人是怎么做的（调研，附来源）

设计不是拍脑袋。这六条是本次调研的一手来源，每条都对应本文一个决定。

| 做法 | 谁 | 机制 | 我们抄了什么 |
|---|---|---|---|
| **宿主注册表（CDS）** | Ren'Py 官方 | 程序在 `python early:` 里 `renpy.register_statement(name, block, parse, lint, ...)` —— **项目自己公布语法形状** | §三 途径①："宿主已经公布了答案，工具不该选择不看" |
| **定义文件 + 自动发现** | Yarn Spinner（Unity/Godot/Unreal） | VS Code 插件从 `.ysls.json` **或直接从 C# 源码**找出自定义命令/函数 → 给编剧**自动补全 + 类型检查** | §三 途径①+③："一次定义，编剧全程下拉"；也是"一引擎编写、多引擎运行"的样板 |
| **模板系统** | articy:draft | 三层模板（属性定义 → 特征 → 模板）；对象挂一个模板；**改模板，所有对象自动更新** | §四 投影："一次声明、四处生效"；§五 动作清单页的"谁在管" |
| **投影式编辑** | JetBrains MPS | **同一份模型，可以用文本/表格/图/数学多种"记法"呈现**；不靠 parser，因此可以组合语言 | §四：表格与卡片都是"投影"；"同一个东西多处显示"是设计目标不是巧合 |
| **无损语法树 + trivia** | Roslyn / tree-sitter | 空白、注释都挂在 token 上，**能 100% 还原原文**；错误用节点**表达**而不是丢弃；**容错**：一行不认识不能搞坏整份 | §二 保真铁律；"降级分级且非阻断" |
| **渐进类型** | 类型系统（gradual typing） | `any` 不是失败，是**显式的逃逸**；标注的地方逐步收紧 | §〇 "不懂就是不懂，但逃生舱口永不丢内容"；覆盖率是**仪表盘**不是分数 |

**一句话提炼**：工业化工具的价值**不在于"认识所有语法"**，而在于
**不丢、不炸、能告状、能被教会**（lossless / non-blocking / self-reporting / teachable）。
**这正是本文四条地基的源头。**

## 十、保真这条底线，具体怎么保证？

前面说了它是第一优先，这里说它**怎么不是口号**。

| 保证 | 做法 | 为什么这么做 |
|---|---|---|
| **不重写整份文件** | 逐行配对，只替换真改过的行 | 重写整份 = 每次导出都可能改坏别处 |
| **要么全对、要么完全不动** | 任何一行配不上就整份放弃、报错 | "半对的产物"比"没产出"危险得多 |
| **改之前先算一遍给你看** | 涉及改你 `.rpy` 的操作（比如改名）**先出 diff 让你确认，没确认零写入**，还能一键回滚 | 最高危的写操作不该是"点一下就自动执行" |
| **认不出就原样抄** | 不认识的块进"原样保留"通道，**不补 `$`、不包 `python:`、不改缩进** | 凭推断补东西 = 改剧情（已经踩过） |
| **一次教，不变字** | 从"不认识"教成"认识"，**第一次导出的产物必须与教之前逐字节相同** | 若变了，说明"升级"顺手改了别人的脚本 |
| **有守卫** | 真机 53 个文件往返幂等审计（逐字节）、"唯一写盘入口"守卫、"不许静默丢行"判据 | 底线靠**自动化**守，不靠人的记性 |

**【给程序看】** `tools/audit_idempotence.py` 53/53；`tests/test_p0_no_silent_full_regen.py`；`tests/test_single_write_entry.py`；`assets/asset_extensions.py` 的两段式 `plan_rename_patch` → `apply_rename_patch(confirm=)` → `rollback_rename_patch`。

## 十二、明确不做的事（以及为什么）

| 不做 | 为什么 |
|---|---|
| **不给每个自定义语句写一个 Python 适配器** | 会变成插件地狱，且和程序代码必然漂移 —— 与"让工具自动得知"的目标相反。粒度应该是"一类结构"，不是"一个语句"。 |
| **不猜语义（它是"提示"还是"战斗"）** | 猜错是改剧情。工具只做展示与检索，标注交给人。 |
| **不给内置语句提供"声明"入口** | `with`/`pause` 本来就认识，让人为它们写声明就是**教错人**（真项目已经中过一次）。只提供"这其实不用写，要不要移除"。 |
| **不给"没声明"的项目配默认分组** | 一般人没有"服装"这个概念，就不该看到分栏。**少了是保守，多了是骗人。** |
| **不为了指标好看去吞掉已知的缩进问题** | 仓库历史记着"试过三种归一化写法都让全项目丢失数变多"。**宁可留一条看得见的已知问题，也不要引入一类新的静默错误。** |
| **不在没并发需求时做"三路合并"** | 没有场景时它是纯负债。 |

```
学完之后：一处声明、四处生效（表格 / 卡片 / 校验 / 报告）

服装（swim_suit）怎么理解：

```
