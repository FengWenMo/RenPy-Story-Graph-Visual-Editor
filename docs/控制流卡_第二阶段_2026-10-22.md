## 二、`kind='flow'`：三处配套，少一处就静默坏

改这一行本身很简单（`_emit_jump_call` 里 `KIND_NARRATION` → `KIND_FLOW`），
但它牵动三处：

| 位置 | 为什么必须一起改 |
|---|---|
| `flow.parse_flow` | 只认 `narration` 的话，**老表/旧内存对象里的 call 拍**升级后读不出来 → 控制流卡消失 |
| `Beat.from_row` 的类型白名单 | **这一条最容易漏**：表里写 `flow`、读回来被降级成 `say` → 拍还在、`raw` 还在，但 `parse_flow` 不认 `say`，卡片上是张空拍。导出、日志、校验**全都看不出异常** |
| `validate` 的空台词检查 | `empty_say = kind in ('say','narration') and not text` —— `flow` 天然不在里面，不用改（但要知道它不会误报） |

实测抓到过第二条：

```
解析         → kind='flow'            ✔
渲染         → call side             ✔
表里「类型」 → 'flow'                ✔
读表回来     → kind='say'            ✘  控制流卡会消失
```

修法就一行（白名单加 `KIND_FLOW`），判据是 `test_table_roundtrip_keeps_flow`。

## 三、参数 `(…)` / `from …` 变成卡片上的东西

### 后端

```python
update_beat_flow(beat, flow_type=None, target=None, args=None, from_clause=None)
```

- `None` = **保持原值**（只改目标时不用知道原来有没有参数）；
- `''` = 清空；
- 三条校验，任一不过就 `ok=False`，**Beat 一个字节都不动**：
  1. 参数必须以 `(` 开头且**括号配平**；
  2. `from` 必须是合法 label；
  3. 切到 `jump` 时参数与 `from` 明确丢掉（Ren'Py 的 jump 不接受）。

第 1 条不是洁癖：`call side(a` 这种写法会让**整份脚本解析不了**，
而工具这边看不出任何异常 —— "导出成功、游戏起不来"是最难查的一类。

### 前端

控制流卡加了「参数」「from」两行：

```
↳ 调用 side                    [↳ 调用（会返回） ▾]
调用后回到这里，继续第 3 拍
目标 [ side ▾ ]  可手写点号 label
参数 [ (1, flag)                    ]
from [ _call_side_1                 ]
```

切到「跳转」时两格直接**禁用并换提示**（"jump 不接受参数"）——
灰掉比"填了也不生效"诚实。

### 一处定义，两处引用

`FLOW_FIELD_KEYS = ('FlowType','FlowTarget','FlowArgs','FlowFrom')` 放在
`story/flow.py`。`fields_to_beat` 与 `EditorSession.apply` 从前各写一遍
`'FlowType' in fields or ...`，加字段时漏一处就是"**改了参数、保存后没反应**"。

## 四、图边有了来源（这是"删双真源"的前提）

```python
Edge(..., origin='source')   # 源文件里的 call/jump（解析出来的）
Edge(..., origin='manual')   # 用户在图上画的草图
```

**为什么必须先有这一位**：下一轮要做"按 `flow_edges(beats)` 重建 `source` 边"。
不分来源地重建，会把用户画的草图一起删掉 —— 那是"工具吃掉用户的动作"，
比双真源更糟。

| 入口 | origin |
|---|---|
| `Graph.add_edge(...)` | 默认 `source`（解析建边走这里） |
| `AddEdgeCommand(...)` | 默认 `manual`（它的常规用法是用户画线） |
| 控制流卡同步边（`_sync_flow_edge`） | 显式传 `source` |
| 布局存取（`save_layout` / `load_layout`） | 存；老布局没有这一位 → 默认 `source`（正确） |

### `flow_edges(beats)`：图边的唯一真源

```python
[{'from': 'main', 'to': 'side', 'type': 'call',
  'condition': '', 'from_clause': '_call_side_1', 'line_id': 'main.0007'}, ...]
```

**每条带 `line_id`** —— 所以"同一 label 里 call 同一目标两次"是两条边。
老做法按 `from + type + to` 找第一条，那种场景下会指错目标
（这正是待办 #4 要修的东西，基础设施在这一轮立好了）。

## 六、图边派生（待办 2、4 的落地）

`app/session_graph.rebuild_source_edges(graph, beats)`，接在
`import_chapters` 之后（导入 / 补全 / 重载都走这条路）。

| 动作 | 条件 |
|---|---|
| **补边** | 源里有 `call`/`jump`，图上没有对应 `source` 边 → 建一条（带 `line_id`） |
| **改指** | 同一个 `line_id`，目标 / 类型 / `from` 变了 → 就地改（`retargeted`） |
| **补身份** | 老边没有 `line_id` 但结构对得上 → **只补 line_id，不重建**（`identified`） |
| **跳过** | 目标不在图上 → 不造幽灵节点，记进 `skipped` |
| **不碰** | `manual` 边；`option_text` 一个字不动 |

返回值：`{added, retargeted, identified, skipped}`，也放进了 `import_chapters`
的返回里（`edge_rebuild`），界面能拿到"这次有几条边没画全"。

### 一个实测抓到的坑：菜单边被当成"新边"

`menu:` 每个选项块里的 `jump ch01_roof` **也是控制流拍**，`flow_edges` 会列它；
而图上那条边是解析器的**菜单逻辑**建的（带 `option_text`）。

第一版把"`option_text` 非空"的边排除在匹配池外 → 两条菜单边匹配不上 →
**又建了一模一样的**，demo 边数 **4 → 6**。

**是 `test_editor_session_snapshot` 的 golden 抓到的**（`edges: 4 → 6`）。
改法：按 `line_id` / `(from,to,type)` 配，**不看 `option_text`**。

### 判据

`tests/test_flow_edges_rebuild.py` **7 条**：两次 call = 两条边（line_id 不同）/
幂等 / 改目标变改指 / `manual` 不动 / 菜单边不被当新边 / 目标不在图上 skip /
真实入口 `import_chapters` 之后边已有 line_id。

golden 两处更新，各只多一个键：`edge_rebuild: {added: 0, identified: 4}`
（4 条边全部匹配、补了 line_id，**边数仍然是 4**）。
