## 二、10-02 ~ 10-05｜补"往返不变式"、立 P0 门禁、推三条边界

**10-02｜架构审查 + 发现测试有整类盲区**
- 结论：IR 是"语句流"不是"语句树"，表达不了嵌套；**测试只测了 A→B 半程，缺"往返不变式"整类** —— 1731 个用例全绿却没抓到 P0。
- 证据：真实项目往返真实丢失 76/3803 = **2.0%**（菜单 100%、选项 100%、`call` 87.5%）。

**10-03｜复验 + 挖出 P0"静默全量覆盖"**
- 确认三处缺陷已修；**纠正自己"`.rpy` 是投影"的错误说法**（`.rpy` 才是唯一真源）。
- 实测：写作环节一旦 patcher 失败就默默退回"全量覆盖"，能把已有 `.rpy` 覆盖成空壳。
- 结论：**病灶是"patcher 失败就退回全量"这个策略本身**，正解是拒绝写入 + 报给人。
- 证据：丢失率 2.0% → **0.03%**；产出 P0 报告 + 红测试当 bug 票。

**10-04｜通用检查 + 交付评审**

- 结论：`Notes` 列与 `Comment` 语义重叠 → 删除。

**10-05｜拓展"三条已知边界"（这天的日志最长）**
- ① `build` 在真实项目上"必然失败"其实是**门禁自己假阳性**（逐行编译 `python:` 块导致），改成整块编译后 `exit=0`。
- ② 命令行加 `--source` 也能增量了，并加 `OPAQUE_LOST` 门禁（顶层语句没进产物就拒写）。
- ③ 顶层内容（`screen`/`style`/`init python`…）原来整块静默消失，现在按原文收进隐藏表"文件级保真"随表走。

- 结论：**假阳性比漏报更贵** —— 它会让人照着假线索去改本来正确的代码。
- 证据：真实项目顶层语句丢失 4 文件/219 处 → **0**。

## 七、贯穿全程的 10 条结论

1. **`.rpy` 是唯一真源**；不归工具管的行/内容逐字节不动，工具从不重新生成整份文件。
2. **要么全对、要么完全不动** —— 任一行配不上就整份放弃 + 报错，绝不产出"半对"产物。
3. **认不出就原样抄；猜一个名字比说"不知道"坏得多**（只认字面量，不模糊匹配）。
4. **假阳性比漏报更贵** —— 错误的根因判断会让人照着假线索改本来正确的代码。
5. **"判据自己错了"比缺陷更常见** —— 先怀疑判据；判据要能被变异测试证明"改回去会变红"。
6. **引擎优先、契约驱动、扫描只做发现** —— 引擎能自己给的（图像/tag/属性/分组/候选/变换/label）就不让人填；扫描永不宣称"只有这些"，也永不当真源。
7. **几个不可信的信号**：`lint` 默认退 0（要加 `--error-code`）；`lint` 没报 ≠ 没问题（先确认没有 parse error）；`has_image()` 不是合法性判据；`[rpytest] Status: PASSED` 是假绿。
8. **报告要真的送到人眼前** —— 只写进 JSON 等于没有报告；拒绝 ≠ 缺陷，但必须给原因、指到具体文件:行号。
9. **一个落盘点一个登记**（`WRITERS` 守卫）；共享语义只许一处实现（引用判定、路径输出、列契约曾多次分叉而漂移）。
10. **并发写入是常态** —— 动手前查 `git status` + 时间戳；写完回读校验 → 单独提交 → 提交后回验；含中文/转义的复现一律写成 `.py`，中文源码禁止用 PowerShell 编码往返。

- 这一轮的 6 条红**全在"切分之后"**（切分本身前四轮 63 条已经压住了），

  1. **中文无空格行整行坏**（P0）：`show 小明泳装开心` 改任何一格 → 行尾追加。
     词法层明明切出了 4 个词、`token_spans` 的区间也全对，但 `slot_span`
     找区间用的是**按空白切**的 `positional_tokens`（只有 2 个词）→ 找不到
     "泳装" → 兜底追加。更贵的是**幂等**：把三格读出来的值原样写回一遍，
     整行被追加一遍（`show 小明泳装开心 小明 泳装 开心`）。

  3. **转义值每次往返多一层反斜杠**：`"a\"b"` 读出的值是 `a\"b`，写回时
     比较的是 `_unquote` 之后的 `a"b` —— 判定"值变了" → 重新转义 →
     `"a\\\"b"`，多导一次多一层。
  4. **可选段改值把固定字吃掉**：`show lan happy at left` 改位置 → `show lan happy right`

  5. **`required` 默认跟入口顺序有关**（P0）：`with_optional_defaults` 的判据是
     `'required' not in slot`，而 `parse_pattern` 会给每格补 `required: True` ——
     传原始 dict 补得上、传 parse 过的补不上。而读盘后的声明、表单、
     `match_line` 拿到的**都是** parse 过的 ⇒ **这条默认在真实入口上从没生效过**。

  · 写回区间一律从**词法层**来：新增 `spec_args._lex_slot_spans` ——
    `assign_tokens` 给**词下标**、`token_spans` 给**字符区间**，与试切/卡片读数
    **同一份分配**。`slot_span` 不再"按值在行里找"，`set_slot_value` 比较的是
    **原文那一段的值**（不是 `_unquote` 之后的），于是"值没变"真的逐字节原样；
  · 可选段的区间**含固定字**：改值留 `at`（`at right`）、删值才整段删；
    人把 `at` 一起写回来也不会变成 `at at right`；
  · 删一格改成 `_slot_junction`：**两侧只留一个分隔符**，都没分隔符才补一个空格
    —— 中文连写行删「服装」得到 `show 小明 开心`，不会粘成 `show 小明开心`；
  · `required` 的**来源**进 `parse_pattern` 的 `_required_set`（"这句话是谁说的"），
    `with_optional_defaults` 问它而不是"键在不在"；落盘时
    `declare_statement` 摘掉（清单里存具体值，读回来"键在 = 说过的"）。
- **自己再打出来的两个洞**（这轮修法把注意力吸到同一块，顺手扫出来的）：
  1. **`@N` 不是"第几格"**（P0，能把语句名换掉）：`columns[].positional`
     数的是"第几个**会吃词**的格子"（`_declared_positionals` 刻意为

**抓到的真 bug：假撤销。** 变量工作台/变量框是"一份改动、两个去处"

- 命令支持 `beat_states={session, before, after, refresh}`：`undo()` 退
  `before`、`execute()`（重做）进 `after`，两边都走 `session.restore()`。
  用**逐拍**快照而不是整份 `beats` 深拷贝：拍对象身份不变，章节树与
  卡片页"行 ↔ 拍"的映射才不会指到旧对象上；
- 撤销后 `refresh_edits_flag()` 重算 → "加了又撤"回到「✔ 已同步」，
  关窗也不再问。
- ⚠ `Beat` 是 dataclass（`__eq__` 比字段）：找拍下标必须用 `b is beat`，
  `list.index()` 会把内容相同的两拍认成同一拍。

## 十二、10-24 中午｜P0：接线默认写剧本，边记住"拍位置"

## 十四、10-24 下午｜P2：章末写编排层、草图改落点、跨章删源边

P1 留的三件"没做"这一轮都落地了。第一件不是体验优化，是**正确性**：
有 `_control` 包装还往章节源文件末尾插 `jump`，目标章会被跑两遍。

### 1. 章末写编排层（`story/control_route.py`）

P0/P1 的「章末」一直写章节源文件：

```
X_control: call X → X 里 jump Y → Y return → 回到 X_control
           → X_control 又 jump Y_control → Y 跑第二遍
```

现在 `plan_wire_landing(position='chapter_end')` 先看项目有没有独立控制流
文件（`X_control` label；`detect_placement` 认不出 `menu`/动态跳转时，
`find_control_file` 用 `*_control` label 兜底）：

- `jump` → `jump Y_control`；最后是 `return` 就**替换**它（不留死代码），
  最后是另一条 `jump` 就**改接**——后者必须进接线窗口，不能零弹窗替人拍板；
- `call` → `call Y`（章节本身），插在最后一条路由之前，返回后继续原路；
- 找不到 `X_control`/`Y_control`、最后是 `menu`/`if`/动态跳转 → 返回
  `control_blocked`，**不退回源文件**；
- 只改那一行，保留 BOM/CRLF/别的 label；写前核对锚点，文件被改过就拒写；
- 图上的边 `origin='control'`、`position='control_end'`，标签「章末（编排层）」，
  不是草图；删它只删 `X_control` 那一行，必要时补 `return`。

导出器同步补了一条：`origin='control'` 的 call 写 `call Y`（不是
`call Y_control`），没有后续路由时补 `return`，否则会掉进下一个 label。

### 2. 草图改落点（`SetEdgePositionCommand` + `EdgePositionDialog`）

右键草图 →「改落点…」：章末 / 第 N 拍；不能接的拍照旧置灰，当前拍不在了
会明说。只改图上的 `position/position_line_id`，剧本一个字节不动，进图级
撤销栈。

### 3. 跨章删源边（`app/source_line_delete.py`）

- **空项目根被当成当前目录**：`control_route.find_control_file(None)` 里

## 十五、10-24 傍晚｜P2.5：补**目标章**的 `_control` 包装

上一轮把"不自动补 `_control`"写进了边界。这一轮把能安全补的那一半做了，
另一半仍然不做 —— 不是因为麻烦，是因为**补了也不会执行**。

### 1. 为什么不能"见 label 就补"

`X_control` 不是装饰，它是**入口**。P2 的章末路由长这样：

```
X_control:
    call X
    jump Y_control
```

如果项目里原本没有编排层，X 是被 `jump X` 直接进入的，那么新建的
`X_control` **没有任何地方跳进来**；往里面写 `jump Y_control`，图上是
一条线，游戏里一次也不会走。这正是用户说的"连线给人一种已经理清楚了的
错觉"——只不过这次是工具自己造出来的错觉。

所以判据只有一条：**补出来的包装得有人进来**。

| 缺的是谁 | 现在谁进来 | 能不能补 |
|---|---|---|
| 目标章 `B_control` | 正要写的 `jump B_control` 就是第一个入口 | ✅ 补 |
| 源章 `X_control` | 多半是 `jump X` / `call X` 直接进 | ❌ 不补，说清要先接管入口 |
| 整个编排层 | 没有任何 `*_control` 可挂 | ❌ 不新建文件（同上） |

### 2. 补的形状是**语义等价**的

```renpy
label B_control:
    call B
    return
```

`jump B_control` → `call B`（B 结束 `return` 回到这里）→ `return`，和原来
`jump B` 执行到 B 的 `return` 落在同一个调用帧。之后
`plan_control_route` 把最后这条 `return` 换成 `jump C_control`，正好是
"跑完 B 再去 C"。

不是 `label B_control: jump B`：那样下一步接线会把 `jump B` 当成
"已有出口"**改接**掉，B 就再也不会跑了。

### 3. 接线窗口：先看见补什么，再动手

- `plan_control_route` 缺目标包装时不再只报"先导出控制流"，而是带上
  `ControlInitPlan`；
- 窗口层的 `plan_wire_landing` 返回新 kind `control_init`（不是静默可写）；
- 接线窗口的确定键变成「补包装并接线」，落点栏写明：补在哪个文件末尾、
  `label Y_control: call Y / return`、以及"还有 N 处 `jump Y` 不经过这个
  包装"的提醒；填了条件/菜单项仍只能草图；
- `ControlRouteCommand` 先补包装、**重算**路由行号、再写路由；旧全文存的是
  **补之前**的，所以一次 Ctrl+Z 把包装和路由一起撤回。补完路由失败会回滚
  包装，不会留下半个改动。

### 4. 顺手修的 BOM 问题

`find_control_file._labels_of` 原来直接 `read_text`，BOM 还在，第一行
`\ufefflabel X_control:` 匹配不上 —— 带 BOM 的 `chapter_controller.rpy`
会被当成"没有编排层"。现在走 `source_style.read_text`（剥 BOM、统一换行），
与写盘侧同一份判据。

### 5. 仍然不做（以及为什么）

- **源章缺包装**：要补就得**接管入口**——扫出所有 `jump X`，改成
  `jump X_control`，再补包装；`call X` 不能一起改（包装可能跳走，调用点
  永远回不来）。这是下一步 `ControlTakeoverCommand` 的活，需要多文件
  原子撤销与 diff 预览；
- **没有编排层时自动建文件**：同上，没有入口的文件只是死代码；先有
  "导出一次控制流 / 手写一个 `_control`"才有挂载点；
- **`menu` / `if` 结尾**：分支归控制流图/卡片，不往块体里插线；
- **跨章删 `menu`/`if` 块**：要按缩进找整块，当前只删单行 `jump`/`call`。

- `tests/test_control_init.py` **17 条**：目标补/已有/无编排层/缺章/带参数/
  源章直入/断掉的 `jump X_control`/直接入口提醒、BOM+CRLF、全文过期、

## 二十、10-24 夜｜条件 / 菜单分支真的写进编排层 + 接管进入点

用户这一轮点了两件事：**条件项 / 菜单项要能真实编辑**（不是草图），以及
把上轮列的"做到一半"补完。还加了一条硬约束：

> 对源剧本 rpy 文件本身要做到最小的插入原则（不要一大堆变量都堆在它
> 身上！尽量放控制流那里！）

### 1. 分支为什么不写源文件

条件 / 菜单回答的是"这一章**跑完之后**去哪"，可源文件里"跑完之后"经常
没有可插入的位置：

    label X:
        menu:
            "走": jump Y      ← 在选项体里
            "留": return      ← 这个 return 一执行 X 就结束了

往 `menu:` 后插会落进块体（缩进和分支语义一起坏），往 `return` 后插又
永远不执行。所以分支只写 `X_control`：

    label X_control:
        call X
        # storygraph-edge:12
        if score > 3:
            jump Y_control
        return

`call X` 在 X 的 `return` 之后回到这里 —— **menu / if 结尾的章因此也能
路由**（这一条就是上轮"menu / if 结尾没做"的正解，不是往块体里插一行）。

### 2. 标记段：改 / 删不认行号

`# storygraph-edge:<edge.id>` 是段首标记，改 / 删都按它找。行号会漂，
标记不会。编辑保留原缩进，段外字节不动；写前再读一遍文件，和计划时不同
就拒绝写（不覆盖别人的新改动）。`AddControlBranchCommand` /
`WriteControlBranchCommand` 一个动作同时管"写文件 + 改图上的边"，撤销
一次全回去。

菜单项这条路上还踩到一个语义坑：**两条菜单边各写一个 `menu:`** 时，第一个
选项永远先执行（无条件），第二个菜单永远轮不到 —— 图上有两条线，游戏里
只有一个选项。所以菜单项改成**一个组**：

    # storygraph-menu:ch01
    menu:
        # storygraph-edge:12
        "去屋顶":
            jump Y_control
        # storygraph-edge:13
        "留在教室" if has_key:
            jump Z_control

增 / 改 / 删只动一个选项；最后一个删掉时整个组一起走。`if` 分支不能静默
改成菜单（会多一次玩家选择）—— 拒绝，让人删了重接。

### 3. 接管进入点（补上轮"源章 X_control / 整个编排层"）

补一个没人跳进来的 `X_control` 只是死代码。`ControlTakeover` 两件事一起做：

  1. 补 `label X_control: call X; return`；
  2. 全项目 `jump X` → `jump X_control`。

`call X` 不改：包装可能 jump 走，调用点永远回不来 —— 只报告，由人决定。
多文件先全部核对再写，中途失败回滚；UI 先弹 diff 预览，确认后
`TakeoverCommand` 一次撤销全部文件。接管会直接改盘，所以当前打开的那一章
如果有未导出改动，**先拒绝**并让人导出（否则内存与磁盘马上分叉）。

### 4. 章末是 `jump` 时拒写分支

`call X` 永远不返回，分支写进去一次都不会执行。`plan_control_branch` 扫
源章最后一条顶层语句，是 `jump`（且不是 `jump X_control`）就拒绝并说清，
先让人改收尾 —— 不给"看起来接好了"的假线。

### 5. 源边改插入位置

`EditEdgeDialog` 的「插入位置」对源边也能选（本章顶层拍）。保存 = 把那一行
移到目标拍之后（`session.move_beat`，块结构由树维护），撤销走结构撤销栈
（`MoveSourceFlowCommand`）。跨 label / 跨章不做：那会改 `from`，是另一条边。

### 6. 跨章删 menu / if 整块

`plan_source_line_delete` 现在按缩进找块：

  · 块里只有这一行 → 删整块（`menu:` 只剩一个选项时连 menu 一起）；
  · 块里还有别的语句 → 只删这一行；
  · `if` 后面紧跟 `elif` / `else` → 不删整块（`elif` 不能没有 `if`），补 `pass`；
  · 整块删完 label 一拍不剩 → 不删整块，补 `pass`。

### 1. P0-9 · 菜单标题：审计的样本与真机不是同一种写法

真机 `script_pomo.rpy` 第 157/158 行是**块内标题**（Ren'Py 唯一合法的写法）：

```rpy
    menu:                        ← 拍的行区间只有这一行
        "是时候和青一起学习了."   ← 标题正文在这里，不属任何一拍
        "开始":
```

审计合成样本写的是 `menu "标题":` —— 那**不是 Ren'Py 语法**
（`engine_lint` 实测：`expected ':' not found`，`beat_render` 里那段注释
早就写明 `menu` 头只接受 `menu [名] [(参数)]:`）。但解析器认它，所以两件
都做了：

| 形态 | 从前 | 现在 |
|---|---|---|
| 块内标题（真机） | 改标题 → `ok=False`；**零改动往返也被拒** | 只动标题那一行 |
| 头行标题（审计样本） | 改标题 → `ok=False`；零改动往返也被拒 | 零改动**逐字节相同**、改标题只动那一行（写盘时由引擎闸门说真话） |

根因：**标题行不属任何一拍**。渲染这一拍写两行（`menu:` + 标题），而拍的
行区间只有 `menu:` 那一行 —— 生成的那一行"不属任何拍"，补丁贴不回去，
`_lost_content` 报"新增内容没能落进产物"。

- 真机形态：`MenuNode.caption_lines`（解析器记标题在块里的行号）→
  `Statement.caption_lines`（**运行期动态属性**，与 `nest_path` /
  `_menu_member` 同一类：不入表、不进内容指纹）→ `_emit_menu` 把
  `src_last` 推到标题末行。此后配对成立：`"标题"` 与 `"标题"` 都是
  `("say", "")` 键，改正文就是"换词"。
- 头行形态：`_menu_head_caption_merge` —— 源文件那一行是
  `menu "…": [注释]` 时，把渲染出来的两行**合并回头行**（`pre + 引号标题 +
  post`）。行尾注释**不许照抄**（渲染器会把这一拍的注释贴到标题行上，
  照抄写成两份注释 —— 第一次跑就踩到）。

顺带说明：审计说"改选项 / 改选项体里任何一拍都会整块对位失败"也对 ——
同一个根因（菜单拍那一段的配对整体错位）；修完两边都只动一行。

标题**多行**也顺手收了（Ren'Py 允许 `menu:` 块里写两行标题）：行数不变时
普通配对就够，行数变了（2→1、1→2）要多一条"按用户写的那几行整段换"
（`_replace_matched` 里那个只认"同一个不带标题的菜单头 + 其余全是裸字符串"
的窄分支）—— 否则多出来的旧标题行没有对手，会留在原地。

**没修的边界**（都不是合法 Ren'Py，零改动往返仍然逐字节保真，改了就由引擎
闸门说真话）：`menu:` 块里的 `$ x = 1`（`extras`）—— 引擎报
`expected menuitem`，原文本身就编译不过；`menu "标题":` 同理。

### 2. P0-10 · 删一拍把相邻 `elif` 展平：不在模型里改，在**对账**里改

现场（真机 `script_pomo.rpy` 删第 25 拍）：

```
-    elif breakline == 2:
-        q "您可能需要休息了."
+    if (breakline == 3) and not ((breakline == 1) or (breakline == 2)):
```

这是 `_chain_head_rewrites` 的"刻意设计"：拍上存的条件是**展平后的累积
形式**，删掉一支之后解析器从头累加，与拍上存的对不上 → 校验判"条件改动走
全量"。上一版图省事，把后面的 `elif` 头**改写成展平的 `if`** —— 语义等价，
但那是用户没碰过的结构行。

现在分成两半：

- **文件侧**：删 `[分支头 .. 拍末行]`，后面的兄弟分支**一个字节不动**。
  唯一还动结构行的是"被删的正好是链头 `if`"：紧跟的 `elif b:` 必须提升成
  `if b:`（Ren'Py 的链必须以 `if` 开头）—— **只换一个词**，条件正文不动。
- **模型侧**：`_chain_renumber` 按解析器口径算出"删掉这一支之后，后面每支的
  条件该长什么样"（纯文本：把被删那支的条件从 `not ((…) or (…))` 里摘掉），
  交给 `_verify_patch(renumber=…)` 当作**可接受的重编号** —— 只容忍这一处，
  且要求完全相等。`_condition_reasons` 里没有别的口子。

明确拒绝（不猜，退回"删这一拍不安全" + 点明原因）：

- 删掉链头后**只剩 `else:`**（要整块降一级缩进）；
- **后面那支的第一条不是拍**（是嵌套 `if` 头）—— 条件重编号算不出来。
  （上一版这里同样做不到：`_gen_for_src` 找不到那一拍。）

### 3. P0-11 · 移动越过 `return`：结构层守卫 + 拒绝后恢复原树

`move(0, 3)` 把第一句挪到 `return` 后面 → 台词静默变死代码；`move(2, 0)`
把 `return` 挪到最前 → 整章截断。两次都 `ok=True`。

`ChapterTree.move_beat` 现在先算落点（把 `insert_beat` 里的槽位解析抽成
`_slot_at` 共用），再问 `_guard_return`：

- 挪的是 `return` 那一拍 → 它必须是这一段的**最后**一条；
- 挪的是别的拍 → 不能落在某个 `return` 之后。

判据复用渲染层的 `_is_return_beat`（`raw` / `opaque` 里的 `return`），
不另写一份。拒绝时把树恢复原状（重新插回原位 + 还原 `nest_path` /
`condition` / `label`）—— **"不猜"不能留下半截结构**。

合法性照旧：`return` 在分支体里是**那一段**的最后一条；把拍移进别的块不受
影响（看的是新那一段的兄弟列表）。新插卡不在本轮范围（UI 那条路本来就有

### 4. 顺带修掉一处静默 no-op：`Position` / `Expression` 是死字段

审计自带的 `tools/p0_scan_struct.py` 里"改 show 的位置"那条用例报"零 diff"。
查下去发现**用例本身打偏了**（它改的是 `return` 那拍），但顺着查到了真问题：

- `beat_to_fields` 会算 `Position` / `Expression` 两格，**`session.apply` 根本不读
  它们**（这两格只活在旧的 `fields_to_beat`，也就是 tkinter 那条路）。
- 于是任何"拿 `fields()` → 改这两格 → `apply`"的调用方（脚本 / 表格导入 /
  AI agent）都是 **改了等于没改、还 `ok=True`** —— 与第二轮 P0-6 同一族。

修法（`session_table.apply`）：`cards is None` 时按字段写回，三条限制：

1. **只在新值非空、且与当前投影不同时**写 —— 空串在这两格的意思是
   "多张立绘位置不一致、没有统一值"，拿它去写会把位置全抹掉；
2. **只在没有立绘卡时**（`cards is None`）：卡片是真源，两处同时写会互相覆盖；
3. 位置有两种存法（拍级 `b.at` 渲染成 `show … at X` / 立绘项里的 `@X`），
   **这一拍用的哪种就改哪种**，不许叠出 `e happy@right at right`。

Qt 界面走的是立绘卡，不受影响；变的是 API 那面（现在与 `fields()` 说的一致）。

### 1. P0 · 含自定义语句的拍：**审计的现场没复现出来，但同一族里有两个真洞**

审计写的判据是「`mycue …` 与台词合成一拍 → 改 Text → `ok=True`、零 diff」。
在 HEAD 上逐一复现**十七种形状**（未声明 / 声明过 / 块形态 / 带引号 /
带行尾注释 / 在 `if` 里 / `with` 尾巴 / 两条语句 / 多行括号 / 带 `scene` /
`extend` …），补丁产物**全部正确**：只有台词那一行变，语句行原样。
`export()` 在"未声明"的那几种上返回 `ok=False`，原因是**引擎闸门**：
隔离工程里没有 `renpy.register_statement`，SDK lint 说 `expected statement`
—— 那是**有理由的拒绝**，不是静默（`_declared_stmt_heads` 对声明过的语句
已经豁免；在声明了 `mycue` 的项目里 `export` 直接 `ok=True`）。

顺着这条线查同一族，抓到两个**真洞**（都不是审计的合成样本，但都在
"工具不认识的语句"这一片上）：

| 现场 | 从前 | 现在 |
|---|---|---|
| `pause 0.1` 改成 `pause 0.2`（任何原生语句改正文） | **两行并存**（旧的留着、新的插进去），还报 `ok=True` | 只换那一行 |
| 声明过的语句，把参数写进「代码」格 | 产物变成 `$ mycue intensity=5`（python 通道补了 `$`）+ 旧行留着 | 写回**头行**，一行 |

第一条是这一族真正的静默改坏：`_line_key` 对原生语句返回
`('other', 整行原文)` —— 改一个数字就配不上对 → 生成行被当"新增内容"
插进去、旧行受"非结构行"保护没人删。现在：

- `patcher._statement_verb(line)`：这一行是**一条普通原生语句**时返回首词
  （排除台词 / 菜单头 / 选项 / `$` 代码 / 注释 / 块头 / 结构关键字 /
  舞台与音频 —— 它们各有各的身份键）；
- `_replace_matched` 的 ⑤：首词相同的两条普通语句配成一对；
- `_rewrite_line`：同一判据下允许换正文（`window hide` → `window show`、
  `with dissolve` → `with fade` …）。

第二条见 §6（P2-3）：`apply` 里 `_write_statement_head` —— 「代码」格写的
首词若是**这一拍自己那条语句的名字**，就写回 `spec_head` / `opaque` / `raw`，
不走 python 通道。"我就要写 python"照旧走代码通道。

审计的原始样本如果还能复现，请把那个 `storygraph.rules.json` 与文件一起
发我 —— 我这边十七种形状都对得上。

### 2. P1-1 · 无标题菜单加标题（从无到有）

上一轮把标题**行**归给了菜单拍，于是"改标题"只动一行；但"从没有标题到

`1 处新增内容没能落进产物`。现在那条窄分支允许**任意一边没有标题行**：

    menu:                  →  menu:
        "新标题"                "新标题"      ← 缩进借块体第一行（2 空格工程就 2 空格）
        "开始":                 "开始":

### 3. P1-3 · 改 `if` 条件：链头能增量，`elif` 那一支说清为什么不能

条件从来"改动走全量"：`if …:` 那一行不属任何一拍，逐拍对位看不见它 →
产物里条件一行没动 → 校验判"条件与要写的拍对不上" → 整份拒绝。

现在 `_plan_condition_rewrites`（与 label 改名同一类：块头单独改）：

- **只认最外层那一支**（`_has_outer_head`）：上面除了 `label` 没有别的块；
- 这一行必须是**这一拍自己的块头**（`_beat_owns_head`：中间只有空行/注释）；
- 新条件 ≠ 文件里那条 → 整行换成 `if <新>:`，**别的字节一个不动**。

后面几支的守卫在表里是**累积形式**（`(b) and not (a)`），链头一改，
否定项里那个 `(a)` 就过期了 —— 于是 `apply` 里同步重算兄弟分支
（`_rechain_siblings` → `patcher.rechain_condition`），保证**增量产物**与
**全量重写**是同一个语义（否则同一章导两次得到两种剧情）。

改不了的三类，理由各不相同（`_condition_hint`）：

| 情形 | 为什么 | 提示 |
|---|---|---|
| `elif` / `else` 那一支 | 表里存的是展平后的累积条件，一行 `elif` 写不下 | 改链头可以增量；这一支请全量 |
| `if` 里还有 `if` | 累积条件含外层，光改内层那行写不出你填的话 | 请全量 |
| 清空条件 | = 拆掉这一层 `if`（结构改动） | 请全量（`_plan_condition_rewrites` 直接点名第几拍） |

### 4. P1-2 · 移动拍：**普通拍能挪**，跨过块头的那一刀说明白

## 二十五、10-25 中午｜落盘安全复核：BOM 章节、选择点换行、GBK、表导出闸门

### 1. P0-2 · BOM 章节 100% 导不出去：门禁自己没剥 BOM

### 2. P0-1 · 选择点**追加**把整份文件换成 LF（还丢 BOM）

CRLF 是常态；`source_style` 的模块 docstring 记着同一类事故：tutorial
23/23 带 CRLF，逐字节相同率 0/23）。追加是那一轮**漏网的一处**。

现在与 `control_route` / `patcher` 同一套：`detect()` 记风格 →
写前 `style.apply()` 还原。⚠ 这里**不用** `source_style.read_text`
（它 `errors='replace'`）：追加是"读回来再写回去"，坏字节被换成 `\ufffd`
就是改坏用户文件 —— 所以严格 UTF-8 解码，解不开就报错（见 §3）。

## 二十六、10-25 下午｜《不安全因素》第二轮：改名 TOCTOU、改写范围、混合换行、表误删

3 条 P1 + 4 条 P2，全修。判据一律是**审计探针原样复跑**，不是"我觉得对了"。

审计自己先说了一句"真机不在触发面上"（54 个 `.rpy` 往返零改动；3123 行资产

### 1. P0-3 · 改名补丁是全仓唯一没有"写前复读"的原地改写点

`plan_rename_patch` 把每个文件的 `old_text` / `new_text` 算进计划，
`apply_rename_patch` 直接 `write_text_atomic(fp, f['new_text'])` —— **不重读、
不比对**。UI 是两段式（预览 → 人点应用），人看预览的几分钟里，程序员的 IDE /
另一个工具实例 / git 改过那个 `.rpy`，旧全文就把并发写进去的内容**静默盖回
去**，而 `apply` 返回 `ok=True`、零警告。`control_route` / `source_line_delete` /
`control_takeover` / 全部 undo/redo 都有这道守卫，只有这里漏了。

现在 `apply` 对每个文件：**复读 → 与 `old_text` 比对 → 对不上就拒写**，
其余文件照常写；结果里 `changed_since_plan` 列出被改过的文件、`ok=False`、
`reason` 说人话（"N 个文件在预览之后被改过，已拒写（原样未动，请重新预览）"）。
界面按部分成功渲染：已写的仍可回滚，被拒写的单列出来。

顺手补掉 P2-1：从前 `swallow` 之后循环继续、最后**无脑 `ok=True`**（界面显示
"改名成功"而文件没写）。现在 `failed` 收文件 + 原因，`ok = not failed and
not changed_since_plan`；**备份失败也不写**（`.bak` 是"可回滚"的另一半契约）。

### 2. P1-4 · "改哪里"从"整份词边界"收窄到"资产引用位"

### 3. P1-5 · 混合换行：`source_style.apply` 学会逐行还原

审计探针（前 4 行 CRLF、后 4 行 LF，只改第 6 行）实测：导后**全是 LF**。
根因不在 `patcher` 的 `splitlines()`，而在更后面那一层 —— `detect()` 按
`crlf > lf` 判主导，50/50 时判成 LF，`apply()` 就把整份翻成 LF。

现在 `SourceStyle.apply(text, source=路径)`：给了 `source` 就**逐行**还原 ——
`difflib` 把新文本对齐到原文，没动过的行用它自己那一行的 EOL，插入的新行
借前一行的，末尾换行沿用原文惯例；单一风格的文件走老路径（逐字节等价）。
所有 `.rpy` 原地写盘都传 `source=`（`write_generation` / `compile` /
`choice_point` / `control_route` / `control_branch` / `control_takeover`）。

探针复跑：4 行 CRLF 全保留、LF 那 4 行也保留、生成标记 2 行随前一行为 CRLF、

### 4. P1-6 · 资产表："文件在"和"文件不在"必须只有一个答案

`FileWalkIndex.match` 对绝对路径直接 `return None`（"索引不覆盖，不猜"），

`_missing_paths` 拿 `None` 当"缺失"就**删行**。审计的 7 行实验里 A/B/C 三行

同一个"文件在不在"不再有两个答案（那正是误删的来源）。

行绝不走这条"、`sync_asset_tables` 说"不做的事：删行"—— 实现早就按用户
2026-10-05 的"自动更新和增删"在删了，只有"工具扫不到的行"才不删）。

### 1. P1-A · 非 UTF-8 的 `.rpy` 加第二个 label → 坏字节被换成 U+FFFD

`_write_new_chapter` 读已有文件走 `source_style.read_text`（`errors='replace'`）。
那是"给解析器看"的口径，**不是**"读回来再写回去"的口径：用户盘上一个非法字节
0xE9 变成三个字节的 U+FFFD，`git diff` 显示这一行被改过 —— 而用户从没碰过它，
也没有 `.bak` 可回滚，状态栏一个字不说。同一个 hazard 在 `choice_point`
（§二十五 §3）早就按"严格解码、解不开就拒写"处理了，这里是漏网的第二处。

现在与 `choice_point` 完全同口径：追加前先 `p.read_bytes().decode('utf-8')`
探一次，解不开就**字节一个不动**地拒绝，并说清"第 N 字节起、先另存为 UTF-8"。
`detect()` 仍照旧管 BOM / 换行（BOM 在严格 UTF-8 里是合法字符，不会被误拒）。

### 2. P1-5b · 删源行（`source_line_delete`）漏传 `source=`，混合换行仍被统一

§二十六 的逐行还原只补了 `control_route` / `control_branch` / `control_takeover` /
`choice_point` / `window_nodes` / `session_export` / `compile` / `generation_guard`
八处调用点；`source_line_delete.apply_source_line_delete` 是**同级**的原地改写点，
漏了 —— 混合换行文件里删一拍，全文换行仍被统一（审计实测：期望
`[CRLF×4, LF×3]`，实际全 CRLF）。

一行修：`style.apply(plan.new_text, source=path)`。

`graph/commands` 的 undo/redo（10 处）**有意不传**：那条路的 `old_text` 在读取时
就被 `read_text` 统一成 LF，每行 EOL 信息在内存里本来就不存在 —— 要逐字节还原
undo，得在计划链里保存原始 EOL，那是设计题不是签名题。这条边界写进契约 §50.2。
