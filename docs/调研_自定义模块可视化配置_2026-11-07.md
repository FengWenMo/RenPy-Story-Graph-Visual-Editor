# 调研：自定义模块怎么"扩展"，以及能不能可视化配置

> 2026-11-07 · 只读调研 + 一次真跑探针（`storygraph.rules.json` 全在临时目录里，没碰任何真项目）
> 触发：用户「查一下如何扩展我们的自定义模块……能让它可视化配置……？上网搜索」

## 0. 先把问题拆成两个

| 问的是 | 其实是 | 现状 |
|---|---|---|
| **怎么扩展** | 加一个新声明键，要动几处、会不会漏一处 | 机制**已经存在**，缺的是"对账"；且已经漏了 1 个键 |
| **能不能可视化** | 表单覆盖了多少、剩下的是不是只能手写 JSON | 大头已经可视化（`dialog_learn.py`，2332 行，六版重构）；缺口只有 1 个真键 |

结论先行：**不需要换框架，也不需要通用表单生成器**。要做的是三件小事 + 一条判据
（§4）。先看证据。

## 1. 现状盘点：`storygraph.rules.json` 的每个键，谁在读、谁在用、界面有没有

数据来自 `story/statement_registry.py`（`_from_manifest` 第 107 行起、`declare_statement`
第 1527 行起）、`ui_qt/dialog_learn.py`、`pipeline/validate.py`：

| 键 | 后端读 | 后端**用** | 界面有 | 结论 |
|---|---|---|---|---|
| `name` / `aliases` | ✓ | ✓ | ✓（名字栏，空格分隔即别名） | 齐 |
| `block` | ✓ | ✓ | ✓（勾选框） | 齐 |
| `docs` / `label` | ✓ | ✓（显示名） | ✓ | 齐 |
| `columns` | ✓ | ✓（表格列） | ✓（格子卡） | ⚠ 清空清不掉（§2.2） |
| `pattern` | ✓ | ✓（第几格=第几个位置参数） | ✓（格子卡） | ⚠ 清空清不掉（§2.2） |
| `clauses` | ✓ | ✓（`spec_clauses`） | ✓（下拉，`CLAUSE_KIND_LABELS`） | 齐，**而且是唯一做对 tri-state 的** |
| `body.allows` | ✓ | ✓（`validate.py` 的 **W122**） | ✗ **没有** | ❌ 只能手写 JSON |
| `render` | ✓ | ✗ **没有任何分支用它** | ✗ | 占位键，**先别做界面** |
| `attr_groups` | ✓ | ✓（候选分栏） | ✓（分栏页） | 齐，`declare_attr_groups(clear=True)` 支持整段替换 |
| `calls` | ✓ | ✓ | ✓（`dialog_calls.py`） | 齐 |

`body.allows` 的分量不小：它是**结构级**约束（设计文档 §0 的 ②层），生效在
`pipeline/validate.py:666` 的 **W122**「块体里出现了声明之外的语句」——`name` 在
`_BODY_VERB_HEADS` 里、但不在 `allows` 里就报。也就是说：**这个键现在只有手写清单
才用得上，可视化用户拿到的是 W122 沉默**（`allowed` 为空 = 不校验）。

`render` 相反：`RegisteredStatement.render` 默认 `'verbatim'`，读进来、`to_dict()`
写回去，但全仓 `grep '\.render\b'` 只有 `to_dict` 自己那一处——**没有任何代码按它分支**。
给它做下拉，是把一个空转的键画在界面上，等于给"配置项"造假。

## 2. 真跑探针（推不出来，必须跑）

脚本：`.pip-tmp/probe_declare_coverage.py`（临时目录建清单，跑完就扔）。
种一条带 `body`/`render`/`pattern`/`columns` 的老声明，再模拟界面的保存：

```
=== 1) 更新时保住 body/render？ ===
  action = updated
  body   = {'allows': ['say', 'show']}
  render = verbatim
  => body/render 保住了

=== 2) 清空 pattern（界面删光所有格） ===
  pattern = [{'kind': 'word', 'text': 'mycue'}]
  => 清空 没生效（旧格子还在）

=== 3) 清空 columns（界面删光所有分栏） ===
  columns = [{'name': 'lan', 'key': 'lan', 'values': ['a']}]
  => 清空 没生效（旧分栏还在）

=== 4) 顶层别的段（choices）还在吗 ===
  choices = {'clothes': ['a', 'b']}
```

### 2.1 好消息：更新是**合并**语义，手写的键不会被界面吃掉

`declare_statement` 是 `merged = dict(it); merged.update(entry)`（1624 行）——
界面只提交它认识的键，`body`/`render` 这类它不认识的**原样留着**。
这条纪律救过一次命：`pattern` 当年就是"只在磁盘上、没进注册表对象"，于是界面一保存
就把位置语义丢了（见 `RegisteredStatement` 的 2026-10-12 补注）。现在不会了。

### 2.2 坏消息："删光"这个动作在写入口上**无法表达**

`declare_statement` 里：

```python
if cols:   entry['columns'] = cols     # 空列表 → 这个键根本不写 → merged 保留旧值
if slots:  entry['pattern'] = slots    # 同上
if clauses is not None:                # ← 只有这一段是对的
    entry['clauses'] = normalize_clauses(clauses)
```

于是界面里把格子全删了再保存 → 清单里旧 `pattern` 还在 → `_reload_registry()` 之后
那些格子**又回来了**。用户看到的是"我删了，它自己长回去了"。

这不是新问题，是**同一条纪律只落实了三分之一**：`clauses` 修的时候专门写了
`is not None` 的注释（"UI 能清空它（`[]`），而 CLI/MCP 不传时保留旧值"），
`attr_groups` 甚至单独有 `clear=True` 参数。只有 `pattern`/`columns` 漏了。

学名：这是 **JSON Merge Patch 的三态问题**（RFC 7386）——
*"Null values in the merge patch are given special meaning to indicate the removal
of existing values"*，缺省 = 保留，`null` = 删除。Python 里没有 `null` 可用，
就得用一个哨兵对象把"没传"和"传了空"分开。

### 2.3 修法（很小）

```python
_UNSET = object()

def declare_statement(..., pattern=_UNSET, columns=_UNSET):
    if columns is not _UNSET:
        entry['columns'] = cols          # [] → 写空（或删键），能清
    if pattern is not _UNSET:
        entry['pattern'] = slots
```

默认值保持"不传=不动" → CLI/老调用逐字节不变（他们那条"只增不改"的 golden 不会被
碰），界面改成显式传 `[]`。

## 3. 外部调研：通用"schema → 表单"这条路，查完是堵死的

### 3.1 Qt 界唯一的现成轮子，恰好缺我们最需要的那块

[`qt-jsonschema-form`](https://pypi.org/project/qt-jsonschema-form/)（PyPI，1.0.0）
是能找到的最贴近的一个：JSON Schema → Qt 表单，per-field 用 `ui-schema` 定制控件
（`ui:widget: colour / filepath / date`），校验错误直接显示。看着很合适，但它的 README
自己写着：

> **Unsupported validators**: Currently this tool does not support `anyOf` or `oneOf`
> directives. … Additionally, the `$ref` keyword is not supported.

而我们的清单**通篇是 union**：`pattern[].kind`（word / words / expr / number…）、
`clauses[].kind`（`CLAUSE_KINDS` 五种）、`block`（yes/no/possible）、`columns[]` 与
`pattern[]` 是两种不同形状的数组。union 不支持 = 生成器对我们最核心的两段直接投降。
另外：最后一版 **2023-02**、Development Status **4 - Beta**、还要多拖 `qtpy` +
`jsonschema` 两个依赖——和本项目"依赖越少越好"（`requirements.txt` 头一行）正面冲突。
同类的 [`pyqtschema`](https://www.piwheels.org/project/pyqtschema/) 更旧、更小。

**结论：不引。** 通用表单生成器的价值在"schema 写一次、界面自动长出来"，代价是
**布局不可控**——而这套界面恰恰是靠布局吃饭的（他们六版重构全在改信息架构）。

### 3.2 真正该抄的是"可视化 + 原文逃生口"这个组合

- Home Assistant：自动化有可视化编辑器，也能一键切 YAML（[社区讨论](https://community.home-assistant.io/t/visualize-scripts-coding-as-high-level-programming-language/840440/7)）；
- GitHub Actions：第三方做了 [workflow-editor](https://github.com/timoa/workflow-editor)，
  README 的原话就是"open a workflow (YAML)，view jobs and steps，edit job properties in
  a side panel，**save back to YAML**"——和我们要做的事一模一样。

本项目其实**已经有这个结构**：`dialog_learn.py` 的「项目清单」页会显示
`storygraph.rules.json` 的实际内容（806 行）。差一步：那一页是**只读**的。
把它变成"可编辑 + 校验 + 备份"，就等于给所有未来键开了一个**立刻可配**的口子，
不用每次等界面跟进（§4 的 L2）。

### 3.3 条件字段：抄 n8n 的 property dependencies

[n8n 的节点配置](https://github.com/czlonkowski/n8n-skills/blob/e037563e101749e630e6688d121d04529fe6ee7b/skills/n8n-node-configuration/DEPENDENCIES.md)
里，字段显不显示取决于另一个字段的值（选了认证方式才出对应输入框）。我们做
`body.allows` 正好需要这个：**块体勾了"有块"才显示允许清单**，否则整块藏起来。
现有表单里 `clauses` 选 `kind` 大概已经是这个套路，可以复用写法。

## 4. 建议：三层，按性价比排

### L0 · 对账判据（最该先做，一天内）

一条测试，钉死"后端会读的键 ⊆ 界面能写 ∪ 白名单"：

```python
FORM_KEYS = {'name','label','docs','block','columns','pattern','clauses', ...}
JSON_ONLY  = {'render'}          # 写清理由：读了但没有任何分支用它

def test_每个清单键都有归宿():
    读到的键 = 从 RegisteredStatement 字段 + _from_manifest + to_dict 推出来
    assert 读到的键 <= FORM_KEYS | JSON_ONLY
```

这条判据的正品案例就是它自己：**`body.allows` 现在会红**。以后谁加键没配界面，
CI 当场拦（和 `tests/test_schema_single_source.py` 一个思路，项目里已有先例）。

顺带把 `render` 从"忘了做"变成"**决定不做**"，写进 `JSON_ONLY` 的注释里——
占位键做成界面是给用户造假配置。

### L1 · 补一个入口 + 修一处 tri-state（一两天）

1. **`body.allows` 的可视化**：块体勾选后，出"这个块里允许写什么"——
   候选直接用项目里真实出现过的语句头（`vocabulary.statement_head_token` +
   `_BODY_VERB_HEADS` 那份白名单），多选框；默认全空 = 不校验（和现在一致）。
   写进 `declare_statement` 的 `body_allows` 参数。**这是纯增量，不动老路径。**
2. **tri-state 修复**（§2.3）：`pattern` / `columns` 用哨兵默认值，界面显式传 `[]`。
   配套判据：删光格子→保存→清单里 `pattern` 真没了。

### L2 · 原文可编辑（兜底，可后做）

「项目清单」页从只读变可编辑：`json.loads` → 结构校验（顶层对象、`statements` 是数组、
每条有 `name`）→ **备份** → 写。故意比表单松：表单管 90%，这一页管长尾和未来键。
风险隔离：写之前 diff 给人看，只允许改这一段。

### 明确**不做**

- ❌ 引 schema → 表单的通用生成器（§3.1：union 不支持 + 依赖红线 + 布局不可控）；
- ❌ 给 `render` 做界面（§1：无人消费）；
- ❌ 把 `body.allows` 做成"白名单校验"以外的东西——它是 WARNING（W122），
  按现有口径"少报胜过乱报"，别升级成错误。

## 5. 什么时候才该回头考虑通用生成器（判据，别凭感觉）

同时满足三条才值得：① 键的数量超过 ~30 且形状高度规整（没有 union）；
② 布局可以标准化（每行一个字段，不需要信息架构）；③ 有人愿意维护生成器本身。
现在三条都不满足——**键只有 10 个，其中 1 个还该是 JSON-only**。

## 6. 没查清 / 待定

- `aliases` 的编辑路径：现在靠"名字里写空格"，够用但没有"别名"这个字眼，
  用户可能不知道（要不要在名字栏加一行提示，待用户定）。
- L2 原文编辑要不要做成"只允许改当前这一条"（更安全）还是整份可改（更灵活）。
- `pattern` 清空之后，已经导出的章节里那些格子会变成"多余的位置参数"——
  重新导入时怎么报，需要一条对应判据（本轮没做）。
