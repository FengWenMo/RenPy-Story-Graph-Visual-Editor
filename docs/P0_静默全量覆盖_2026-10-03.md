报告日期：2026-10-03
严重性：**P0（静默数据毁坏）**

配套测试：`tests/test_p0_no_silent_full_regen.py`（**26 passed / 4 skipped**）+ `tests/test_product_python_syntax.py`（36）

## 1. 一句话

保存剧本时若增量补丁对不上，系统**不报错、不询问**，直接退回"全量重新生成"并
覆盖原文件——而全量生成只认得"拍"，`default` / `define` / `init python` /
`transform` / `screen` / 变量系统**一行都留不下**。

---

## 2. 根因链条（三层，缺一不可）

### 第 1 层　`_patch_note` 把失败降级成"换一种写法"

`storygraph/app/editor.py:1426`

```python
def _patch_note(self, text: str) -> dict:
    """试着走增量补丁；不行就全量重生成，并把原因写成一句人话。"""
    from storygraph.story.patcher import patch_export
    try:
        res = patch_export(self.beats, src, text, registry=self.registry())
        if res.ok:
            return {'used_patch': True, 'text': res.text, ...}
        reason = ('；'.join(res.reasons) or f'对位率不足（{res.coverage:.0%}）')
        return {'used_patch': False, 'text': text,          # ← 用回全量文本
                'text_note': f'全量重生成（增量未采用：{reason}）'}
    except Exception as e:                                   # noqa: BLE001
        return {'used_patch': False, 'text': text,           # ← 异常也退回全量
                'text_note': f'全量重生成（增量不可用：{e}）'}
```

`used_patch=False` 只是**换了个文本**，**不是中止**。原因被塞进 `text_note`
一句人话里，然后照写不误。

### 第 2 层　`export` 无条件落盘

`storygraph/app/editor.py:1421`

```python
write_generation(text, target, project_root=self.project_root)
return {'ok': True, ...}          # ← 注意：仍然是 ok=True
```

调用方（UI）拿到 `ok=True`，**看不出这一刀是全量重生成**。

### 第 3 层　`write_generation` 不检查目标是否已存在

`storygraph/story/generation_guard.py:369`

```python
def write_generation(text, out_path, *, review_on_block=True,
                     project_root=None, occupied=None):
```

全函数只判 **block 级语法/label 冲突**问题，**没有任何"目标文件已存在"的检查**。
实测往已有 .rpy 写，直接覆盖。

### 被误导的假设（这才是真正的设计错误）

`storygraph/story/patcher.py:109`（`PatchResult.ok` 的 docstring）：

> 覆盖率的门槛是 0.9（低于这个数说明源文件与表对不上，
> **退化成全量更稳**）；……宁可丢注释，也不能写出半对的脚本。

**"退化成全量更稳"这个前提是错的。** 全量生成丢的不是注释，是
`default` / `define` / `init python` / `transform` —— 丢这些，游戏直接起不来。

## 3. 复现（最小，可粘贴运行）

```python

import tempfile
from storygraph.parsing.renpy_parser import IncrementalRenPyAnalyzer
from storygraph.story.beat_build import beats_from_parse_result
from storygraph.story.excel_export import export_beats_to_excel
from storygraph.story.excel_import import import_beats_from_excel
from storygraph.pipeline.compile import compile_beats
from storygraph.story.generation_guard import write_generation

t = Path(tempfile.mkdtemp())
orig = t / 'chapter.rpy'
orig.write_text(
    'default score = 0\n\n'
    'init python:\n'
    '    def helper():\n'
    '        return 1\n\n'
    'label a:\n'
    '    e "原文台词"\n', encoding='utf-8')

a = IncrementalRenPyAnalyzer()
pr, _ = a.analyze(files=[orig], graph=None)
beats = beats_from_parse_result(pr)

res = compile_beats(import_beats_from_excel(t / 'c.xlsx'))
write_generation(res.rpy_text, orig)     # ← 没有任何拦截

print(orig.read_text(encoding='utf-8'))
```

```
    pass
    return
```

`default score`、`init python`、`def helper`、`label a`、台词 —— 全没了。

## 5. 修复方案

### 5.1 必须做（止住数据毁坏）

**A. `_patch_note` 失败时不要再返回全量文本**

改成让 `export` 能区分：建议让 `_patch_note` 在 `used_patch=False` 时
返回 `{'used_patch': False, 'blocking': [...]}`，`export` 见到 blocking
就**不写盘**，直接返回 `ok=False`：

```python
note = self._patch_note(text)
if note.get('blocking'):
    return {'ok': False, 'path': target,
            'blocking': note['blocking'],
            'note': note['text_note'], 'todos': 0}
```

UI 上把 blocking 显示出来，让人决定（是手工对一下表，还是接受全量并**明确勾选**）。

**B. `write_generation` 增加"目标已存在"护栏**

判据建议：目标存在 **且** 首行不是工具生成标记
（`# 由剧本表自动生成，请勿在此文件手工改动结构`）→ 判定为**手写文件**，
拒绝覆盖。例外：显式传入 `force=True`。

位置：`storygraph/story/generation_guard.py:369`，与现有 block 级门禁并列，
`written=False` + `review_path` 指向副本（沿用现有机制，不用新造）。

**C. 全量生成只许用于"新建文件"**

`cli.py:115` / `cli.py:290` 在目标已存在时，应当报"目标已存在，请改用增量
或换一个输出路径"，而不是覆盖。

### 5.2 顺手改（消掉误导）

`patcher.py:109` 那句 docstring「退化成全量更稳」改成：
「**调用方必须拒绝写入**，全量只许用于新建文件」。

### 5.3 逃生舱

给 `write_generation` 加 `force: bool = False`，CLI 加 `--force`。
人明确知道自己要覆盖时才覆盖。

## 6. 验收标准

1. patcher 失败 → 目标文件**逐字节不变**，返回 `ok=False` 且 `blocking` 非空
2. `write_generation` 到已有手写 .rpy → 不写盘，`written=False`
3. 写入**新**文件 → 仍然成功（不误伤）
4. 传 `force=True` → 允许覆盖
5. 正常小改动 → 增量成功，`default` / `init python` 等原样保留
6. `tests/test_p0_no_silent_full_regen.py` 全绿
7. 原有 1768 个测试不回归

### 改了四处

| 位置 | 改动 |
|---|---|
| `app/editor.py::_patch_note` | 补丁失败时返回 **`blocking=[原因…]` 且 `text=''`** —— 故意不给可用文本（给了就会有人拿它写盘，那正是事故形态） |
| `app/editor.py::export` | 见 `blocking` **且目标已存在** → `ok=False`、**不写盘**；另补上"检查 `write_generation` 的返回值"（以前直接丢掉，无条件报 ok=True） |
| `story/generation_guard.py::write_generation` | 新增 **`HANDWRITTEN_TARGET`** 护栏：目标已存在且首行无生成标记 → 拒写并留 `.blocked.rpy` 副本；新增 `force=` 逃生舱 |
| `cli.py` | `table xlsx2rpy` / `compile` 走新护栏；新增 **`--force`**；拦下时明确提示 `--force` |

### 三个刻意的判断（都是"别把护栏写成新的坑"）

1. **`target.exists()` 这个条件是必需的。**
   目标不存在时（新建章节），全量生成正是**唯一正确**的做法 ——
   不加这个条件会让"导出到新路径"彻底不能用。验收标准第 3 条
   （"写入新文件仍然成功"）就是钉这个的。

2. **判据是"首行有没有生成标记"，不是"文件已存在"。**
   只看"已存在"的话，"再导出一次"会被自己的护栏拦下 ——
   那比不拦更烦，且症状（"我明明是用工具生成的"）极难自查。
   `test_allows_overwriting_its_own_output` 守这条。

3. **标记只认逗号前那一段。**
   完整标记是 `# 由剧本表自动生成，请勿在此文件手工改动结构`，
   而人和测试写 `# 由剧本表自动生成` 就够了 —— 逗号后面那句是"叮嘱"，
   不是身份。要求整串相等的话，只写前半句的产物会被当成手写文件拒写。
   （**这条是我自己写的测试抓到的**：我先写了 `MARKER = '# 由剧本表自动生成'`，
   结果"再导出一次"红了。）

### 顺带修掉的一个隐患：标记现在是**单一真源**

`storygraph/core/vocabulary.py:GENERATOR_MARKER`。

渲染层**写**它、门禁**认**它 —— 两处字符串一旦漂移，护栏就认不出自家产物。
放 `core` 而不是那两个模块：`generation_guard` 已经 import 了 `beat_render`，
反向 import 会成环。`test_marker_is_a_single_source_of_truth` 直接断言两者相等。

### 一条"差点漏掉"的：`export` 丢掉写入结果

`export` 以前写的是：

```python
write_generation(text, target, project_root=self.project_root)   # ← 返回值扔掉
return {'ok': True, ...}                                          # ← 无条件成功
```

于是即使门禁拦下了，用户看到的仍是"导出成功"，以为产物在，
实际 `game/` 里什么都没有。现在改成检查 `art.written`。

**修这个的时候我自己踩了一次**：`'blocking': [self._issue_message(i) …]`
漏了 `self.`，一路活到运行时才 `NameError`。原因是原有用例都在
`export` 的**前一关**（补丁失败）就返回了，`write_generation` 的返回值
根本没被读到 —— **那条 return 没有覆盖**。
`test_export_to_handwritten_target_reports_blocking` 专门走那条分支
（目标设成已存在的手写文件，让补丁与语法门禁都通过），
并且我用"去掉 `self.`"变异验证过它确实会红。

## 10. 修完之后**手测才发现**的第二个面：护栏认不出自家产物

这一条值得单独记，因为**测试全绿了但它还是坏的** ——
原因是我只在 `write_generation` 那一层测，没经过 `export`。

### 症状

对一个由工具生成的文件**连续导出同一路径**：

```
第 1 次导出 → ok=True
第 2 次导出 → ok=False  「目标已存在且不是工具生成的（没有生成标记）」
```

也就是说"再导出一次"**必然失败**，而且提示还说"这是手写文件"——
用户会一头雾水："我明明就是用工具生成的。"

### 根因

`patch_export` 的合并策略是 **"保留原文那一行"**（那是它保住
`default` / `init python` 的办法）。于是补丁产物的**首行是源文件的首行**
（`default score = 0`），**没有生成标记**。

而标记以前只在**全量渲染**（`beat_render.render_beats_to_rpy`）里写。
补丁这条路写出去的文件因此**没有身份**。

### 修法

新增 `generation_guard.ensure_generator_marker(text)`：
首行没有标记就补上，有了就**一个字不动**。
放在 `generation_guard` 而不是 `beat_render`，因为
"补标记"与"认标记"（`_looks_handwritten`）是一对，必须同进同退。

`export` 在落盘前统一过一遍 —— **补丁与全量两条路都经过这里**。

### 教训（写进流程）

`test_allows_overwriting_its_own_output` 当时是绿的，因为它把
**自带标记的文本**直接喂给 `write_generation` ——
**它测的是护栏自己，不是真实导出路径**。
所以：**验收测试必须走用户真实经过的那条函数**
（这里是 `EditorSession.export`），否则测的是"我以为的路径"。

补的用例：`test_re_exporting_the_same_target_succeeds`（连续导出三次），
并用"去掉 `ensure_generator_marker`"变异验证过它会红。

## 11. 方案 3 收尾：默认安全 + 明确覆盖（2026-10-05 续七）

用户定的口径是「**先执行方案 1，方案 3 是最终目标**」。
方案 1（拒绝写盘 + 报错）在 §9 完成；这一轮把方案 3 补齐。

**全量单测 1964 passed / 5 skipped，0 failed。**

### 11.1 逃生舱贯通到每一层

| 层 | 改动 |
|---|---|
| `write_generation` | `force=` 参数（§9 已有） |
| `compile_table` / `export_table_to_rpy` | 加 `force=`，往下传 |
| `cli.py table xlsx2rpy` / `compile` | 加 `--force` |
| `EditorSession.export(target, force=False)` | 加 `force=` |
| `ui_qt.main_window.export_script` | 拦下时弹「覆盖手写文件？」对话框 |

UI 的对话框**说清会丢什么**（`default` / `init python` / `transform` …），
默认按钮是**取消**（这一刀不可逆）。

### 11.2 `force` 只越过一条 block，其余一律不越

这是方案 3 最关键的判断。`export` 现在返回 `codes`，前端靠它决定
要不要给"仍然覆盖"按钮（`ui_qt.main_window._overwritable`）：

| block 代码 | 能不能 force | 为什么 |
|---|---|---|
| `HANDWRITTEN_TARGET` | **能** | 产物没问题，只是目标是人手写的 —— 该由人决定 |
| `PYTHON_SYNTAX_ERROR` | 不能 | 产物**自己坏了**，覆盖只会把跑不起来的脚本写进 `game/` |
| `CJK_IN_IMAGE_TAG` | 不能 | 同上 |
| `LABEL_COLLISION` | 不能 | 同上（会让游戏起不来） |
| `PATCH_FAILED` | 不能 | 增量没配上，写出去就是丢内容 |

判据写在 `_overwritable()` 里而不是散在对话框里：`codes` 是
`EditorSession.export` 的公开契约，将来新增 block 代码时，
"能不能覆盖"必须是个**明确决定**，不能靠默认放行。

实测矩阵（`tools/_p0_accept3.py`，已删）：

```
1 原地导出（手写，默认）  ok=False codes=['HANDWRITTEN_TARGET']  default 还在
2 原地导出（手写，force） ok=True                               default 还在
3 导出到新路径            ok=True                               文件在
4 再导出同一路径          ok=True                               （幂等）
5 含手写错句的导出        ok=True   没有 `$ l oh`，原句保留
6 坏产物 + force          ok=False codes=['CJK_IN_IMAGE_TAG']   ← force 不越这条
```

> ⚠ 第 1 行**已于 2026-10-05 夜改口**（用户实测报）：增量补丁对上时
> 原地导出应当**直接放行**，见 §11.7。`HANDWRITTEN_TARGET` 现在只剩
> "要覆盖的是**别人的**手写文件"这一种触发面。

### 11.3 拦不拦的判据：`would_destroy_opaque`

第一版我写的是 `had_source`（"有源 .rpy 可增量"），**太粗** ——
它把「编辑 ch01、导出到 out.rpy」这种完全正常的操作也拦掉了
（`test_export_reflects_the_edit` 当场红）。

第二版改成 `target.exists()`，**也有问题**：

  · 新建章节时 `script_path` 为空 → 补丁必然失败，但全量正是唯一正确
    做法，拦了就没法新建文件；
  · 反过来，**目标就是源文件本身**（原地导出）时它一定存在，
    而那种情况恰恰最危险。

最终判据 `generation_guard.would_destroy_opaque(target, source_path)`：
**只看"覆盖它会不会毁掉工具不认识的内容"**，不管补丁为什么失败。

  · 目标 == 源 `.rpy` → True（作者手写的章节，几乎必然含第三类内容）
  · 目标已存在且无生成标记 → True（别人的手写文件）
  · 其余 → False（不存在 / 是工具生成的：覆盖毁不掉东西）

### 11.4 顺手把 `cli.py compile` 的重复实现收掉

`_cmd_compile` 以前自己又写了一遍 `import_beats_from_excel` +
`compile_beats` + `write_generation` —— 与 `pipeline.compile.compile_table`
是同一件事的两份实现（门禁字段名、`force` 传递都得改两处）。
现在委托给 `compile_table`。这是 `excel/cells.py:set_text`
"三份实现漂移后收敛"那条教训的同一类问题。

### 11.5 新增守卫：跨包不许用私有名

`test_package_layering.py` 加了一条 `test_no_private_names_cross_package`：
`from storygraph.<别的包> import _xxx` 一律红。

这是 P2-7 的直接推论（那次实测 `script_table` 门面 re-export 了 92 个
下划线名，而外部真正用到的只有 2 个）—— **下划线名一旦跨包使用，
它就已经是公共 API 了，只是没声明**，改名/删掉它会静默打断另一个包。

它当场找出 **7 处**（含我自己刚引入的 `_would_destroy_opaque`），
全部改成公共别名（做成别名而不是重命名：包内还有几十处调用，
一次性改名会把 diff 铺得很大、掩盖真正要审的改动；函数体只有一份，
不会漂移）：

| 别名 | 谁在用 |
|---|---|
| `split_show_items` / `join_show_items` / `split_hide_items` | `app/beats`、`pipeline/validate`、`excel_import`、`stage_snapshot` |
| `image_path_from_expr` / `image_solid_from_expr` | `app/stage` |
| `would_destroy_opaque` | `app/editor` |

白名单 `CROSS_PKG_PRIVATE_ALLOWED` 现在是**空的** ——
留空表是给"将来真有一处只能如此"用的：到那时必须写清理由，
而不是把测试放宽。

### 11.7 改口：**增量对上了就不许拦**（2026-10-05 夜，用户实测报）

§11.1 的矩阵第 1 行（"原地导出到手写章节 → 默认拦下"）**是错的**，
用户实测撞到并报到：

> 明明只是增量的对一个卡片的修改……为何只能全量导出不能增量导出了？
> 一般来说不应该是有多层嵌套的时候才全量吗？为何要阻止我拿新的文件
> 去替换旧的呢？

拦的判据用错了地方 —— 它看的是"**目标像不像手写文件**"（首行有没有
生成标记），而该看的是"**这一刀会不会丢东西**"：

| 情形 | 产物是什么 | 覆盖会丢什么 | 该怎么办 |
|---|---|---|---|
| 补丁对上 + 目标就是源 | 源文件全文，只换改过的那几行 | **什么都不丢** | **放行**（从前拦了 ← bug） |
| 补丁没对上 | 全量重生成（只认得"拍"） | `default` / `init python` / `transform` | 拦（P0 的核心，不变） |
| 底稿不是目标 | 甲章的全集 | 乙章的全部定义 | 拦（`merging_onto` 判） |

实测（用户自己的 `chapter0_0.rpy`，245 张卡逐张改一句话）：
**245/245 都是"对位 245/245 拍、改动 1 行"**，却 245/245 全被护栏拦下 ——
补丁算得好好的无损产物，被一条本该让路的护栏扔掉，用户只能看到一个
「覆盖手写文件？」对话框（**默认按钮是取消**）。

根因是**两处实现漏了一处**：CLI 那条路（`pipeline.compile.write_compiled`）
早就把"这份产物是在源 .rpy 上合并出来的"交给门禁了，`EditorSession.export`
没交。而且交给门禁的形式（布尔 `merged_from_source=True`）本身也不牢靠 ——
调用方声明一句"我走了增量"就能越过护栏，"编辑甲章、往乙章的手写文件上写"
会被静默放行。

修法（一处判据，两处调用）：

```python
# generation_guard.py —— 唯一判据
def merging_onto(out_path, source_path) -> bool:      # 底稿 == 目标？
    ...
if not force and not merged_onto_target and _looks_handwritten(out_path):  # 拒写
```

- `write_generation(merged_from_source=…)` 收的是**底稿路径**（不再是布尔）：
  门禁自己比"底稿是不是就是目标"，调用方无从搞错；
- `EditorSession.export` / `app.tables.apply_export` 都把底稿交下去；
- `app/tables.apply_export` 顺手改掉一句**驴唇不对马嘴**的报错：门禁拦下时
  它从前说"检查文件是否被占用"，现在说门禁给的那句。

守卫：`tests/test_export_acceptance.py`（1a 放行 / 1b 仍拒）、
`tests/test_p0_no_silent_full_regen.py::TestExportForceEscapeHatch`
（逃生舱改成"覆盖**别人的**手写文件"这个形状）、
`tests/test_cli_incremental_source.py::TestGuardInteractions`
（新增"声明走了增量也不许覆盖别人的文件"）。

`tools/acceptance_workflow.py` 第 ② 步从前写的是"先拦一次、用户点
「写入（增量）」再写" —— 它把**旧行为当成了正确行为**，所以这条缺陷在
验收脚本里跑了很久也没露头。现在它断言"**一次就写进去**"。

## 12. 拓展三条边界（2026-10-05 续八）

交付评审（`.workbuddy/memory/2026-10-04.md`）列了三条"必须让用户知道"的边界。
这一轮把它们各往外推了一格。**全量单测 2137 passed / 4 skipped / 0 failed**；
真实项目端到端 `tools/journey_check.py` **全部步骤通过**。

### 12.1 边界①：`build` 的"必然失败"是门禁**假阳性**

**不是产物坏了。** `generation_guard._python_syntax_issues` 把 `python:` 块体
**一行一行**丢给 `compile()`：

| 产物里的行 | 单行编译的结论 |
|---|---|
| `positions = [` | `'[' was never closed` |
| `]` | `unmatched ']'` |
| `for i, digit in enumerate(x):` | `expected an indented block` |

真实项目 `cli.py build` 报的 **10 条 `PYTHON_SYNTAX_ERROR` 逐条都是这类**。
把那份产物里 7 个块**整块** `dedent` 后编译，**一个都不错**
（复现入口：`tools/probe_python_block.py`；它的判据已改成"整块编译 +
四档分类"）。

**假阳性比漏报更贵**：它让 `build` 对真实项目永远失败，而且理由指向一个
不存在的问题 —— 人会照着假线索去改本来正确的代码。

修法：块体**整块**编译、`$` 语句**整条**编译（续行按括号/引号平衡分组，
复用 `beat_render._group_code_statements`）。块头形态同时扩到
`init python:` / `init N python:` / `python early:`（边界③之后它们也会出现在
产物里，必须一起查）。

守卫：`tests/test_python_syntax_guard_granularity.py`（6 种假阳性形态 +
3 条 `$` 续行 + 5 条真错必须仍拦下 + 1 条端到端"必须写得出去"），
用 `tools/mut_python_syntax_guard.py` 打回逐行编译**变异验证过会红**。

### 12.2 边界②：命令行也能走增量（`--source`）

`table xlsx2rpy` / `compile` 新增 `--source <这一章原来的 .rpy>`：
有源就走 `patcher` 增量合并，原文逐字节保留、只换改过的那几行。
判据只有一处（`pipeline.compile.merge_incrementally`）——
它同时决定"要不要保住第三类"和"那条手写护栏要不要让路"，
两处各判一次迟早一处改了一处没改，症状就是**静默丢掉 `init python`**。

**顺手把"能增量"的另一半补上了**：补丁对不上时若静默退回全量，
`--source X --out 新路径` 的目标是**新的**、`HANDWRITTEN_TARGET` 不适用
→ 源里的 `define` / `image` 在产物里没了而退出码是 0。
真实项目 `pomodorro.rpy` 实测丢 **37 处顶层语句**。

所以新增门禁 **`OPAQUE_LOST`**：产物缺了源文件的顶层语句就**拒写**并列出
行号 + 语句名（`write_generation(source_text=…)`）。`--force` 可越过
（降级为 warn，**仍然报出来** —— `CompileResult.guard_warnings` 存在的唯一理由
就是"写成功了"和"有没有话要说"必须分开承载）。

实测（真实项目，`--source`）：

| 文件 | 结果 |
|---|---|
| `whackamole.rpy` | 增量，改 2 行，13 处顶层语句全保住 |
| `ball_moving_game.rpy` | 增量，改 1 行，顶层语句全保住 |
| `pomodorro.rpy` | 补丁对不上 → `OPAQUE_LOST` 拒写（exit=1，**不写出残缺产物**） |

守卫：`tests/test_cli_incremental_source.py`（11 条）。

### 12.3 边界③：顶层 `init python:` 随表走，回到文件级

见 README 的"关键不变量 67"。要点：

- 解析器不再把顶层 `init python:` 当"未建模块"跳过 → `ParseResult.file_blocks`；
- 随第一张拍进隐藏列 `FileBlocks`（表只有"拍"一个单位）；
- `render_beats_to_rpy` 在所有 label 之前原样写回。

实测：`whackamole.rpy` 原文 2 个块 / 56 行块体 → 产物 **2 个块 / 56 行，
真丢代码 0**（`tools/probe_python_block.py`）。

守卫：`tests/test_file_level_opaque_blocks.py`（18 条）。

### 12.4 收尾时抓到的两个真问题（都是测试抓住的）

1. **`init python:` 空块体会写出半截块**：`init python:` 后面什么都不写是
   Ren'Py 语法错误。`join_file_blocks` 现在丢弃空块体
   （`test_empty_body_is_not_invented`）。
2. **"这一章没有解析出任何拍"这条原因没了**：边界③造的那张空拍让 `beats`
   非空，于是 `patch_export` 覆盖率 0% 却是**空 reasons** —— 调用方只拿到
   "没走增量"而不知道为什么。`patch_export` 现在补一条
   "渲染不出任何内容的拍"判据（`test_empty_chapter_reason_is_distinct` 抓到）。

### 12.5 边界之外，这一轮量出来的两件事（**没修，记着**）

- **行尾注释**（`x = 1  # 备注`）在词法器层被剥掉
  （`RenPyLexer._strip_inline_comment`，`test_real_project_regressions`
  有测试钉着"这是刻意行为"）。真实项目 minigame 的 `python:` 块里共 7 行
  这样丢的。**不属于三条边界**，但它确实是逐字保真的一个缺口。
- 单行 `python:` 块会被规范成 `$ x = 1`（真实项目 1 处）：语义等价，
  产物形状变了。

`tools/probe_python_block.py` 现在把这四档分开报
（在 / 行内注释 / 规范成 `$` / **真丢代码**）—— 不分开就会把"设计如此"
报成 bug，而**判据自己写错比没有判据更坏**（它会逼人去修一个不存在的问题）。
