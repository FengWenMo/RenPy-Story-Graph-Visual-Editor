## 1. P0-3 改名补丁 TOCTOU：计划之后文件被改过 → 旧全文覆盖回去

**位置**：`storygraph/assets/asset_extensions.py:402-441`（`apply_rename_patch`）

**攻击链**（探针 `_p0_audit_rename_probe.py` 攻击一，逐字输出）：

```
计划后盘上内容已变成（含程序员新加行）: True
apply 返回 ok = True
★ 程序员刚加的那句还在吗： False
★ 落盘内容是基于**过期读取**的旧全文： True
（程序员那一句只在备份里活着： True ）
```

**根因**：`plan_rename_patch` 把每个文件的 `old_text` / `new_text` 都算好塞进计划；
`apply_rename_patch` 直接 `write_text_atomic(fp, f['new_text'])`——
**不重读、不比对**。这是全仓唯一一个没有"写前复读全文比对"的原地改写点：
`control_route` / `control_branch` / `control_takeover` / `source_line_delete` /
`graph/commands` 的全部 undo/redo 都有这道守卫（对照面，第一轮已审）。

**窗口真实性**：UI 是**两段式**（`session_assets.asset_rename_plan` 不写盘 →
`dialog_asset_rename` 给人看预览 → 人点应用才 `asset_rename_apply`）。
人看预览的几分钟里，任何一方改那个 `.rpy`（程序员自己的 IDE、另一个工具实例、
git 操作）都会被打包吞掉。且 `apply` 返回 `ok=True`、**零警告**。

**为什么是 P0 而不是 P1**：用户的代码**回退**了（并发加的那行从 `.rpy` 消失），
且是 fail-unsafe（静默）。有 `.bak` 能救，但用户不知道要救。

**修法**（二选一，都不猜）：
1. `apply` 时对每个文件**重读**，当前内容 ≠ `f['old_text']` → 该文件拒写，
   结果里列出"计划之后被改过"的文件路径，其余文件照常写；
2. 或者拿当前内容**重算**替换（而不是用计划里的 `new_text`）——
   等价于把 plan 降级成"参数"而不是"全文快照"。

倾向 ①：与"要么全对、要么完全不动"的铁律同构，且能说出是哪个文件被改过。

## 2. P1-4 改名过度匹配：`$ bg = 1`、注释、字符串一起改

**位置**：`asset_extensions.py:357-359`（`_rename_pattern`，词边界正则）

**实证**（探针攻击二，改图片 id `bg` → `bg_new`）：

```
L2: '    scene bg classroom'   -> '    scene bg_new classroom'   ← 想要
L3: '    show bg'              -> '    show bg_new'              ← 想要
L4: '    $ bg = 1'             -> '    $ bg_new = 1'             ← Python 变量
L5: '    # bg 这是注释'        -> '    # bg_new 这是注释'        ← 注释
L6: '    play music "bg 音乐.mp3"' -> '    play music "bg_new 音乐.mp3"'  ← 字符串
```

**缓解已存在**：预览会列出所有 `changed` 行、用户确认后才写、有 `.bak` + 回滚
（`dialog_asset_rename` 三步都看得见）。所以定 P1 不定 P0。

**残余风险**：① 预览按"行"展示，编剧看不出哪行是代码；② id 是常见英文词时
（`bg` / `show` / `play` / `at`）命中面天然大；③ 字符串被改而运行时另有比较
（`config.x["bg"]` 之类）→ 游戏行为静默改变。

**修法**：把匹配限制在"资产引用位"——行首可选缩进后是已知引用动词
（`show` / `scene` / `play` / `queue` / `stop` / `hide` + 自定义语句参数位），
或至少：预览里把命中 `$` / `#` / 引号内的行**单独分组并加一句警告**
"这些看起来是代码/注释/字符串，确定要一起改吗"。

## 3. P1-5 混合换行文件导出后，没碰的行也被换行归一化

**位置**：`storygraph/story/patcher.py:3769`（`orig_lines = original.splitlines()`）
+ `:3938`（`text = '\n'.join(st.out_lines)`）

**实证**（探针 `_p0_audit_mixed_newline_probe.py`：前 4 行 CRLF、后 4 行 LF，
只改第 6 行一句台词后原地导出）：

```
导后各行换行符： [\n ×10]        ← 4 行 CRLF 全部变成 LF
- 第 0 行换行符被改：\r\n → \n（label ch01:）
- 第 1 行换行符被改：\r\n → \n（scene bg classroom）
- 第 2 行换行符被改：\r\n → \n（show ling happy at left）
- 第 3 行换行符被改：\r\n → \n（ling "第一句"）
```

**根因**：`splitlines()` 丢掉每行自己的换行符，写回时统一 `'\n'.join`；
`source_style.apply` 只能把全文翻成**一种**检测到的主导风格。
纯 CRLF / 纯 LF / BOM 文件都正确（第一轮探针 A/B 已验：CRLF 8→10、BOM 保留），
**只有混合换行**保不住。

**定级理由**：没改的行被静默改写字节——正踩用户口径里"没做到逐字节保真"。
Ren'Py 不在乎，但 git diff 会脏、用户的版本对照会乱。混合换行文件在
"从别处粘贴过的章节"里确实存在。

**修法**：`splitlines(keepends=True)` 保留每行 EOL，比较时剥、写回时按原行
自己的 EOL 还原；被替换/插入的新行用**它那一拍的原文最后一行**的 EOL
（或文件主导 EOL）。改动面集中在 `patch_export` 的读入与写回两处，
中间全部按"无 EOL 行"处理的逻辑不用动。

## 4. P1-6 资产表同步误删行：文件在，行没了

**位置**：`storygraph/assets/asset_registry.py:505-528`（`_missing_paths`）

**docstring 与实现三处矛盾**：
- `delete_rows_from_table:1087`：「**人工录入的行绝不走这条**（由侧车 `_autoscan.json` 判归属）」；
- `sync_asset_tables:761`：「⚠ **不做的事**：删行（表里有、磁盘上没了）」；
- 而 `_sync_prune_stage` 实际删、且 `_missing_paths` **不查侧车**；
  `:827` 的行内注释倒是说了实话：「现在**不再区分"谁加的行"**」——
  那是对用户 2026-10-05 原话的落实，**行为本身是按用户要求做的，不是 bug**。

**真正的 bug 是误删**（探针 `_p0_audit_autoscan_probe.py`，走真实打开路径
`sync_asset_tables(walk=FileWalkIndex(root))`）：

| 行形状 | 磁盘上文件 | 结果 |
|---|---|---|
| A 绝对路径指向项目内真实文件 | **在** | **删**（`walk.match:946` 直接拒绝对对路径） |
| B `game/tmp/hidden.png` | **在** | **删**（`_walk` 跳过 `_SKIP_SCAN_DIRS`） |
| C `game/cache/cached.png` | **在** | **删**（同上） |
| D `../sibling/shared.png` | 在 | 活（`_probe_outside` 兜底） |
| E 用户手写、真缺失 | 不在 | 删 + `.bak`（按用户要求，正确） |
| F 占位行（Notes=占位） | 不在 | 活（正确） |
| G 模板 `{image}.png` | 不在 | 活（正确） |

同一行走两条路裁决相反（A/B/C 三行都是 `walk.match=False`、
`resolve_thumb_source=True`）——`_row_file_exists` 用后者，
`_missing_paths` 用前者，**同一个"文件在不在"两个答案**。

**真机核查**（`_p0_audit_autoscan_real.py`）：`sr_general` 四张表 1942 行，
`walk` 判缺失 **0 行**（该删的早没了/都解析得到）——当前不触发，纯潜伏。
目录联接（junction，共享素材库）**安全**：`os.scandir` 会把 junction 当目录递归。

** surfaced 方式**：打开项目时 `window_graph_ops.py:590` 会播报
「**自动删除 N 条**（文件已经不在：images 3）」——对误删行这是**假理由**
（文件明明在）。备份是 `*.bak.xlsx` **固定名单代**，每次同步覆盖，
只保留上一代。

**定级 P1**：丢的是表里用户手写的元数据（Notes/Category/Tag），不是 `.rpy`；
有单代备份可恢复；需要"用户手写出绝对路径/跳过目录路径"才触发。
但按"会把用户整理过的数据弄丢"的口径，够 P1。

**修法**：
1. `_missing_paths` 对 `walk.match` 未命中**且路径是绝对路径/在跳过目录下**的行，
   退回磁盘探测（`resolve_thumb_source` / `_resolve_audio_source`）再判；
   探不到也不要删，标 `unusable` 让人自己决定；
2. 修掉 `:1087` / `:761` 两处过期 docstring（行为以 `:827` 注释为准，
   把"不查侧车"写清楚，别让下一个人被 docstring 骗）；
3. 备份改成带时间戳（或至少删除前把行内容写进返回结果，让 UI 能说清"删了哪几行"）。
