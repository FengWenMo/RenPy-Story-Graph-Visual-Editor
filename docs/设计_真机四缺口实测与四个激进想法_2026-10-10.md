## 第一部分：四个缺口的实测结论

### 缺口四（真机 headless）→ ✅ **完全通过，而且只要 7 秒**

| 指标 | 实测 |
|---|---|
| 8GB 项目上无头跑 `lint` | ✅ 跑通，**两次都是 7 秒**，无崩溃、无 SDL 依赖问题 |
| 体积影响 | 8GB 里大部分是 `build/`+图片 → **不影响 lint** |

> ⚠ **一个必须记住的坑（否则 CI 永远绿）**：`lint` **默认退出码是 0**。
> 只有加了 **`--error-code`**，有 finding 时才退 1。我第一次加了 → 1；第二次没加 → 0。
> **CI 里必须带 `--error-code`。**

### 缺口一（`--json-dump` 内容）→ ✅ 拿到真数据，但**缺 label**

真机产出 44KB：

| 段 | 条数 | 用途 |
|---|---|---|
| `location.transform` | **155** | ⭐ **`at` / `with` 的候选值**（正好回答"候选要手填"） |
| `location.screen` | 87 | 界面名 |
| `location.define` | 386 | `define` 变量名 |
| `location.callable` | 152 | 可调用对象 |
| **`location.label`** | **0** | ⚠ **官方 dump 不给 label** |

→ **label 要另取**：`renpy.get_all_labels()` 在真机给了 **106** 个。
→ 结论：`--json-dump` **值得进 CI，但不能当唯一来源**。

### 缺口二（`get_ordered_image_attributes` 可观测性）→ ✅ 可断言

真机实测（"给已选属性后，集合是否真收窄"）：

| `lan` | 38 | 给 `bg11_0` | 1 |
| `xing` | 28 | 给 `shock` | 3 |

→ 返回值**小、确定、可写死期望值** → 缺口二提的"加断言、不符就报警"**成立、成本极低**。

⭐ **副产品（重大）**：探针顺手把**分组名**读出来了 ——


## ⭐⭐ 最重要的一条更正：`lint` **会**校验属性引用

### 我上一轮说错了

上一轮我写进契约的是"**`lint` 不查属性**；`has_image` 也不是判据"。
依据是：最小工程里 `show lan 完全不存在` 没报错。

### 实测（决定性）

把那一行**单独**放（**去掉** `weather` 那行）再跑：

```
game/zz_bad_attr.rpy:2 'lan 完全不存在' is not an image.
→ 退出码 1
```

**`lint` 明确会拒非法属性引用。**

### 上一轮为什么得出错的结论

> `weather 雨 0.5` 是 **parse error**。**一旦发生 parse error，后面的语义检查（图像/属性/资源）根本不跑。**
> 于是我看到"零报错"，误判成"lint 不查属性"。

⚠️ **必须写进契约的操作规则**：

> **`lint` 没报 ≠ 没问题。必须先确认「没有 parse error」，否则一个语法错误会掩盖全部语义检查。**

（这和项目里既有的"前面的错误掩盖后面的判据"是同一个坑，只是换了层。）

### 顺带：真机 lint 报告里有**你项目现有的真问题**（不是我们造的）

```
game/chapter/chapter1_2.rpy:282  'lan sideeye' is not an image.
game/chapter/chapter1_2.rpy:294  'lan base_hand_up lose' is not an image.
game/chapter/chapter1_2.rpy:356  'ye uh' is not an image.
game/chapter1_4.generated.rpy:259 'lan base_hand_up lose' is not an image.
game/chapter1_4.generated.rpy:384 'cg cg05' is not an image.
game/chapter1_3.rpy:503          'bgm/lyj01.mp3' is not loadable
game/chapter1_1.rpy:171          The image tag 'bg7_0' is not the prefix of a declared image…
```

→ 这些是**引擎自己报的**、**带文件:行号**的、**可 CI 化**的一手清单。价值极高。

### 修正后的 oracle 表（覆盖上一轮）

| 要问什么 | 谁来答 | 实测证据 |
|---|---|---|
| 语句/语法成立吗 | **`lint`** | `weather 雨 0.5` → `expected statement.`，退 1 |
| **图像/属性引用合法吗** | **`lint` 也答** ✅ | `'lan 完全不存在' is not an image.` |
| 资源文件存在吗 | **`lint` 也答** ✅ | `'bgm/lyj01.mp3' is not loadable` |
| 组合兼容吗 | `get_ordered_image_attributes` | 30 → 3 |
| 属性词汇与分组 | `get_registered_image(tag).attributes` | `outfit: [clothes2, base_hand_up]` |
| ~~`has_image`~~ | ❌ **不是判据**（对不存在的组合返回 `True`） | 最小工程实测 |
| 前置条件 | **先确认无 parse error** | 见上 ⚠️ |

## 第二部分：四个"更激进"想法的评判（都尽量实测过）

### 想法一：把解析器当 oracle → ❌ **原形态不成立；改形态可用**

**实测**：

```
import renpy                      → OK（8.5.3+unofficial）
import renpy.parser               → ❌ ModuleNotFoundError: No module named 'renpy.cslots'
import renpy.cslots               → ❌ 同样
（先 import renpy 再试 → 仍然失败；且 module 'renpy' has no attribute 'config'）
```

**结论**：Ren'Py 的解析器**不是纯函数**，它依赖 `cslots` 这类**只有 launcher 引导后才存在**的东西。
**它只能在 SDK 自己的进程内**使用 —— 也就是**只能通过 `lint` / `run` / `test` 这类命令**。
所以"不启动引擎、不跑 headless、直接 import"这个卖点**不成立**。

⭐ **但有一条更干净的替代路**（实测存在）：
`renpy/arguments.py:285  def register_command(name, function, uses_display=False)`
→ Ren'Py **官方支持注册自定义 CLI 命令**，`uses_display=False` 表示不需要 SDL。
⚠ **待验证**：项目里的 `.rpy` 注册时机是否早于参数解析（内置命令是在 `arguments.py` 里注册的，很早）。
**所以这条路先别当定论，需要一次实测。**

### 想法二：`MODIFICATION:` 注释 → ⚠️ **可用，但它是"提醒"不是"契约"**

- 优点：**与代码同文件**，改代码时不可能不看见 → 抗漂移**远强于**另开一份声明文件。
- 与项目既有做法完全一致（本项目就是"**就近声明**"的思路）。
- ⚠ 但要知道它的上限：**它只覆盖"被改的那一处"**，而且注释**不是机器可读的稳定契约**。
- 必须配一条 CI：**解析器源码被改 + 邻近没有 `MODIFICATION:` → 红灯**。否则它会退化成"写了没人看"。
- 本项目现状：**没有 fork 引擎**，所以这条今天没有对象。**属于"如果将来真 fork 了"的预案。**

### 想法三：AST diff → ⚠️ **降级为"该重测什么的路标"**

- 前提是**引擎源码在项目里** —— `sr_general` **没有**（实测：无 `renpy/` 目录）。
- 即使有：diff 的产物是**代码变更**，不是**语法声明**。要变成契约，工具得**理解 `parse_show()` 被改了什么** —— 这是另一个量级的工程。
- ✅ **但它有一个便宜且实用的用法**：AST diff 一变 → **触发"重跑探针"**。
  即：**补丁不是契约，补丁是"该重测什么"的路标。**

### 想法四：让引擎生成"语法报告" → ⭐ **方向最对，而且我已经用等价形态跑通了**

**它给的 API 清单有几处是错的**（实测）：

| 想法四里写的 | 实测 |
|---|---|
| `renpy.parser.statements.keys()` | ❌ `renpy.statements.registry` **不是 dict**（真机报 "no dict registry"） |
| `renpy.list_images()` | ✅ 真机 **317** 张 |
| `renpy.get_available_image_tags()` | ✅ **235**（⚠ 但里面混着 `_hd_cut`/`afraid` 这类，**不是干净 tag 列表**） |
| `renpy.get_ordered_image_attributes(tag)` | ✅ 每 tag 全属性（`ling` 30 / `bg` 38 …） |
| `renpy.display.transform.transform_functions` | ❌ **不存在**（None） |
| 变换清单 | ✅ **改用 `--json-dump` → 155 个** |
| label 清单 | ✅ **`renpy.get_all_labels()` → 106 个** |
| `config.after_load_callbacks.append(dump_grammar)` | ⚠ 时机不对（load 后太晚；且它会挂在每次启动上） |

**但方向是对的**，而且我用 `init 999 python` 探针**已经拿到了等价结果**（317 图像 / 每 tag 属性与分组 / 106 label）。
**更干净的形态**（而不是手改 `renpy/__init__.py`）：

> **工具自己生成一份探针 `.rpy`，注入项目副本 → 跑 `lint` → 收割 JSON。**
> `lint` 期间 `init` 会执行（已实测）→ **零配合、不污染引擎、引擎升级不会丢**。
> 这比"让程序在引擎里加代码"好，因为**引擎源码改了会被覆盖**，而"工具生成探针"可以每次都重新生成。

## 第三部分：结论与建议

### 四个想法总评

| 想法 | 覆盖层级 | 成本 | 对本项目的判断 |
|---|---|---|---|
| 一 解析器 oracle | 语法合法性 | 极低（**若走 lint**） | **改形态=可用**；原形态（独立 import）**已实测不成立** |
| 二 MODIFICATION 注释 | 被改动的那一处 | 低 | 与"就近声明"一致；**今天无对象**，属预案 |
| 三 AST diff | 解析器文件的精确变更 | 中 | **降级为"该重测什么"的触发器**；前提（fork）不成立 |
| 四 引擎自画像 | 全部语法能力 | 中 | ⭐ **最有价值**；**用"注入探针 + lint"实现，不要手改引擎** |

### 推荐的组合（按"今天就能用 → 将来"排序）

1. **今天就可用、零配合**：`lint --error-code`（**7 秒**，同时覆盖**语法 + 图像/属性引用 + 资源存在性**）＋ `--json-dump`（155 transform / 87 screen）＋ 注入探针（属性词汇 + **分组** + 兼容候选）。
2. **下一步**：把上面三样包成**一次运行**，产出 `engine_facts.json`（可 diff、进版本库）；
   探针**挂在 lint 这条必经路径上** → 不会忘、不会过期。
3. **预案**：只有真 fork 引擎时，才启用 想法二（就近声明）+ 想法三（AST diff 当触发器）。
4. ⚠ **前提**：`lint` 的退出码必须带 `--error-code`；且**先确认无 parse error**，否则后面的检查会被掩盖。

### 对"缺口三"的正面回答（诚实）

- 探针**只覆盖你想得到的** —— 这一点两份反驳说得对，本轮也确认了（我第一次挑 tag 就挑错，探针直接空转）。
- **但"想得到"这件事可以被低成本喂饱**：`lint` 会把**项目里所有非法写法**都报出来（带文件:行号），
  **`discover_undeclared` 会把所有未声明的语句头报出来** → 两者合起来就是"该测什么"的清单。
- **仍然存在真正的盲区**：**从未被写过、也从未被引擎拒绝过**的语法，工具发现不了。
  这需要**人报一个名字**（最廉价的输入）。**这是路的上限，不粉饰。**
