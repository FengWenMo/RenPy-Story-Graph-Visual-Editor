# 答复：连线 / 补全 / 重载是什么；一个大 label 怎么 call 小 label（2026-10-22）

> 用户一次问了五个"我没搞明白"，逐个查代码回答。**不猜，都在源码里核过。**

---

## 一、连线是什么效果？生成新 rpy 还是增加新 label？

**都不是。** 连线就是一行 `jump` / `call` 语句。

- 图上一个方块 = 一个 `label`；
- 一条线 = 这两个 label 之间的跳转，导出时写在**起点 label 的末尾**：

```renpy
label chapter1_1:
    e "……"
    jump chapter1_2          ← 这条线

label chapter1_2:
    ...
```

`call` 会多一个 `from` 子句（Ren'Py 拿它区分存档点）：

```renpy
    call sub_scene from _call_sub_scene_1
```

**不新建文件、不新建 label。** 新建文件是「新建章节」或「导出」干的事。

---

## 二、「补全相关章节」= 按 call/jump 抓其他剧情图？

**对。** 源码里写得很直白：

> 把"图上被跳到、但还没导入"的文件一起导进来。
> 用户导入 `chapter1_1/1_2/1_3` 后，一点就把 `chapter_controller.rpy` 补进来，
> 9 条连线立刻出现。

判据是 `session.missing_chapter_files(graph)` —— 图上有条边指向 `label X`，
而 `X` 所在的文件还没导入 → 把它导进来。

## 三、「重载已导入章节」= 让无源变有源？

**不是。** 它的定义是：

> 重新解析**已导入的那些**文件（**范围不变**，用于跟上磁盘上的改动）。

也就是"我在 VSCode 里改了 `chapter1_2.rpy`，点一下让图跟上"。

### 「无源 → 有源」的正确做法（实测）

图上一个节点显示「（无源文件）」，说明它 `file_path` 是空的。两条路：

| 做法 | 结果 |
|---|---|
| 「➕ 导入章节 .rpy」选那个 rpy | **同名 label 会被合并**（节点数不变，`file_path` 填上）|
| 「新建章节」时把「写入文件」填好 | 建的时候就写文件，不存在"无源"这个状态 |

实测（`sss` 无源节点 + `sss.rpy`）：

```
先有无源节点 sss： 1 个节点
导入 sss.rpy 之后： 1 个节点（added=0）
  'sss'  file_path='…/game/sss.rpy'      ← 合并了，不是重复
```

所以**不要**为了"变有源"去删掉节点重建 —— 直接导入同名文件就会接上。

## 四、一个大 label 里 call / jump 小 label，再回来

### Ren'Py 本身的语义（这段必须说清，因为它决定工具该怎么做）

```renpy
label 大场景:            # 一个文件里可以有任意多个 label
    e "开场"
    call 小场景          # 执行 小场景，它 return 之后**回到这里**
    e "回到大场景了"
    jump 下一章          # jump 不回来
    return

label 小场景:
    e "在小场景里"
    return               # ← 这个 return 就是"回到 call 的下一条"
```

- **`call` 天然会回来**，因为 `call` 会在栈上记返回点；
- **`jump` 不会回来** —— 要回来得在小 label 里自己 `jump` 回大 label 的某个位置。

### 工具现在能表达什么、不能表达什么

| 想做的事 | 现在能不能 | 怎么做 |
|---|---|---|
| 一个 `.rpy` 里放多个 label | **能读**（导入时按 label 建节点，一个文件多章没问题） | 导入那个文件就会出多个方块 |
| 在一个已有 `.rpy` 里**新增**第二个 label | **能**（2026-10-21 加的） | 「新建章节」→「写入文件」填那个已有文件 → 末尾追加 |
| 两个 label 之间的 `jump` / `call` | **能** | 画一条线，选 jump / call（call 可填 `from` 标识） |
| **在一个 label 的中间**插一个 `call 小场景`（call 完继续往下） | **不能**（这是你问的核心） | 见下 |

### 为什么"中间 call"现在表达不了

工具把**一个节点 = 一个完整 label**，连线只连"label 的头"。所以
`call` 永远只能写在**起点 label 的末尾**（跳过去就不回来），
没法表达"跳到第 37 拍时 call 一下，回来接着第 38 拍"。

### 现在能用的替代做法（不用等改代码）

在**某一拍的「代码」列**里直接写 `call` —— 那一列是"原样透传"通道，工具不解析、不改写：

```
call 小场景 from _call_sub_1
```

导出的产物就是这一行，Ren'Py 照常执行并回来。

### 要彻底解决，得改哪里（这不是一天的事）

两条路，代价差很多：

| 方案 | 做法 | 代价 |
|---|---|---|
| **A. 拍级 call**（推荐） | 给拍加一种类型"调用"，渲染成 `call X from …` + 后面的拍照常跟在后面 | 中等：拍模型 + 渲染 + 补丁对位都要认这种类型；`from` 标识要稳定生成 |
| B. 让节点内可以嵌子图 | 图结构改成两层（label 里挂一个子流程图） | 大：整张图的数据结构、布局、导出都要动 |

**A 的关键难点**是 `from` 的稳定性：Ren'Py 要求同一个 `call` 语句的 `from` 标识
**跨版本不变**（否则老存档找不到返回点）。所以要有一个"这一拍的身份"可以
稳定派生（现在的 `LineId` 大致可用，但要在改拍序时保持不变）。
