### 1.3 引擎给了"位置"一个官方身份

Ren'Py 文档（label.html）原文：

> "If the optional `from` clause is present, it has the effect of including a label statement with the given name as the statement immediately following the call statement. **An explicit label helps to ensure that saved games with return stacks can return to the proper place when loaded on a changed script.**"

> "Publishing a game without `from` clauses for each `call` statement is dangerous... saves made inside the called label to become broken."

含义：**`call X from _call_Y` 的返回点本身就是一个具名 label**。位置不是玄学，它在引擎里有名字。
推论（两条都是工程事实）：
- 删掉这行 = 玩家在子场景里的旧存档回不来 → 删除必须提示；
- 加回来时**复用同一个 from 名** = 旧存档还能救回来 → 这是"删了再加 = 还原"的物理基础。

## 2. 三条裁决

### 裁决一：删边 = 删那一行，不做"只删线"

**今天的行为**：图边由 `flow_edges` 派生，`rebuild_source_edges` 第 135 行写着"源里有、图上没有 → 建一条"。
所以"只删线"下一轮刷新**必弹回** —— 那不是设计，是没做完。

**定案**：
1. 删边就是删剧本里那一行（call/jump 拍），走受控补丁；
2. **删前一律给 diff**（哪怕一行）—— 对象是策划，不是程序员；
3. 若这行是 `call`，额外一句：**"这行的 `from _call_xxx` 是存档返回点，删了会让在子场景里的存档回不来。"**
4. **不做"隐藏列表"** —— 那是第二条真相，违背"`.rpy` 唯一真源"（铁律 1）。
5. 只想让图干净 → 用**视图**（折叠无关节点 / 只看某条线），不动数据。

**行业对照**：Ink Graph（Obsidian）—— 删 link 就是删那一行；"A one-line delete happens at once and can be undone. **Anything bigger than one line is shown as a diff first.**"；删节点时 "Tunnels, threads, function calls... **cannot be redirected, so the delete is refused** and lists those places"。
**否决**：把"删线"和"删拍"做成两个动作（用户分不清，且删线会弹回）。

### 裁决二：位置不靠问，靠"线的起点看得见"

**今天缺的只有一件事**：边上不显示"第几拍"（`graph_canvas.py` 只画 `「选项」` 或 `if 条件`）。
数据其实全都在：`Edge.line_id`（哪一拍）、`Edge.from_clause`（引擎锚点）。

> ✅ **已补（2026-10-23 23:35，S0）**：边上现在写 `第 3 拍 · 「去屋顶」`，
> 悬停给"第 3 拍 / 共 4 拍 + 这一拍 + 上一拍 + 下一拍"。
> 手工草图（没有 `line_id`）**不编位置** —— 它在剧本里没有那一行。
> 点击跳转（双击边进卡片那一拍）留到下一版：那要处理切页/重载时序，
> 急了会出现"点一下界面乱跳"，比现在没有更糟。

**定案**：
1. 边的**起点钉在那一拍上**（线从卡片里第 N 拍的位置出发），边上标 `第 3 拍`，悬停给前一句/后一句。
   业界同款：InkVisual —— "A divert's wire leaves the card at **the exact line that writes `-> x`**"。
2. 删了再加 = **还原**：记 `(target, line_id, from_clause)`，加回时一键回原位、复用原名。
3. 弹窗**按"位置有几个可能值"开关**，不按动作开关：

| 落点 | 位置唯一吗 | 弹窗 | 默认 |
|---|---|---|---|
| 章末（编排层） | 唯一 | **不弹** | 章末 |
| 第 N 拍之后 | 多解 | 弹（拍列表 + 前后台词） | 上次的位置 → 当前选中的拍 → 章末 |
| menu/if 体内 | 还要选"哪个选项" | 图上不插 | 归分支文件（见裁决三） |

**回答"+ 号"**：不要。今天的画布**已经把 call 画成虚线**（`graph_canvas.py:377`），手工草图是点划线。
再叠一个 `+` 是第三种记号，只会增加解释成本。虚线 + 文字 `↩ 第 3 拍` 信息量更大。

### 裁决三（新结论）：三级不做"往源文件的 menu 里插 call"，做"分支外置"

之前九份报告都在讨论"怎么把 call 插进源文件的 menu 选项体"。**方向错了。**
那是侵入最深的一种写法（+5 行起），也最容易被用户骂"剧本被搞乱"。

**定案**：

```
menu 只有一个家：控制流文件（导演本）。
区别只在"谁来触发它"：

章末分支   → `_control` 里直接写 menu              源文件 +0 行
中途分支   → 源文件插一行 `call 选择点`，
             选择点（menu + 条件 + 变量）仍写在
             同一个控制流文件里                     源文件 +1 行
永不       → 把 menu 块写进剧本文件（演员本）
```

> ⚠ **术语订正（2026-10-23 22:50，用户指出）**：上一版写成"菜单放独立文件"，
> 容易被读成"要新建很多文件"。不对 —— **菜单放的是控制流文件，一个就够**。
> 你项目里 `chapter_controller.rpy` 已经在这么做了（图上的 `option_text` 边
> 一直就导出成 `_control` 里的 `menu:`，那条路是对的，不该改）。
> 所以这里的"外置"= 外置于**剧本文件**，不是外置于控制流文件。

```renpy
# 剧本文件（演员本）—— 编剧天天读的就是这个
label ch01:
    scene bg school
    e "早上好。"
    e "今天有件事想问你。"
    call ch01_choice from _call_ch01_choice_1     ← 唯一的入侵：一行，自带名字
    e "算了，先上课吧。"
    return

# 控制流文件（导演本）—— 章末 menu 和中途选择点都住这里，同一个文件
label ch01_control:
    call ch01 from _call_ch01_1
    menu:                        ← 章末分支：直接写，零碰剧本
        "看屋顶支线":
            call ch_roof from _call_ch_roof_0
    jump ch02_control

label ch01_choice:              ← 中途选择点：被剧本里那行 call 触发
    menu:
        "去屋顶":
            call ch_roof from _call_ch_roof_1
        "留下":
            call ch_stay from _call_ch_stay_1
    return
```

**为什么这是"最小侵入 + 最能读懂 + 防极端"三条同时满足**：
- 剧本里只多一行，且这行**自己解释了这里发生了什么**（`call ch01_choice`）；
- menu 改一百次、变量加十个，剧本一个字不动 —— 你担心的"一大坨变量塞进剧本"消失；
- 剧本损坏半径 = 1 行（受控补丁，逐字节保真照旧）；
- **不用新建文件**：所有分支都在已有的控制流文件里，符合项目现有约定。

**行业对照**（Lemma Soft / Fuwanovel 的 VN 结构最佳实践，原文）：
> "**Make one file containing flow control logic.** It exploits the difference between jump and call...
> This way the order of events is **purely controlled by one file and is not mixed into the story**."
> "In case a question is asked, **return just before asking it. Next you ask in the flow control** and branch according to the answer."
> "If you want to use flags... you test for flag conditions when figuring out which event label to call, **which is also done in flow control**."

这和你项目的 `chapter_controller.rpy` 是同一个架构 —— 你不是"理论上可行"，你已经在这么做。

**所以"控制流 .rpy 还需要吗"**：不但需要，**它就该是分支和判断的家**。
"剧本是演员本、控制流是导演本"这句话，比"图编辑器要不要碰源文件"重要得多。

## 6. 别人怎么写，我不可能都想到——四档出口、三档降级、不替人重构

### 6.1 引擎对"坏习惯"是完全沉默的（实测）

`probe_exits.py` 跑了三个样本，**全部 `ok=True`，零语法错、零警告**：

| 样本 | 引擎说的话 |
|---|---|
| 章末落空（最后一句是台词） | **一个字不说** |
| 章末 `jump` | 一个字不说 |
| `menu` 嵌在 `if` 体内 | 一个字不说 |

而官方文档写得很清楚，落空是**会真的跑歪**的：

> "If there is no jump statement at the end of the block associated with the label, Ren'Py will continue on to the next statement."（quickstart）
> "it simply continues on to the following label block... **as if the label statements weren't there at all**."（language wiki）

**结论：靠引擎报错来发现"写法不规范"是不成立的。发现是工具的活。**

### 6.2 真机：最危险的不是 menu，是没写出口

全项目 58 个 label 的出口：

| 出口 | 个数 | 说明 |
|---|---|---|
| `return` | 24 | 干净 |
| `jump` | 24 | 这章自己写了"去哪" |
| **落空 / 以 `$` 或台词结尾** | **10** | 引擎不报，玩家会顺路撞进下一个 label |

`chapter3_1.rpy` 就是真落空：最后一句是台词 `"...先好好休息，这次就听他一回。"`，
后面没有 `return`。**它今天能跑，是因为碰巧它是文件里最后一个 label；哪天有人在后面追加一个 label，这章就会莫名其妙撞进去。**

### 6.3 写法不是无限的：只有两个轴需要区别对待

| 轴 | 取值 | 工具要不要改行为 |
|---|---|---|
| **章末出口** | `return` / `jump` / `call`(+return) / 落空 / menu 收尾 | **要**（决定能不能包 `_control`） |
| **分支位置** | 章末 / 段落末（走控制流文件）/ 内联在台词中间 | **要**（决定能不能在图上插） |
| 声明放哪 | 同文件 / 独立 / 分散 | 只记录，不改行为 |
| 控制流放哪 | 有 / 无 / 同文件 | 只记录，不改行为 |

**四档 × 三档 = 12 种组合**，不是无限种。`tests/fixtures/placement/` 的七个样本已经覆盖了骨架
（`expected.json` 里的 `declarations` / `control_flow` / `content_globs` / `declaration_style` 四个键）。

### 6.4 探测 → 清单 → 分派（"我怎么知道"的答案）

```
打开项目
  ↓ 只读扫描（不写盘）
  · 每个 label 的最后一条有效语句 → 出口四分类
  · menu/if/while 的缩进层级与宿主 → 分支三分类
  · default/define 的落点 → 声明形态
  · 有没有 _control / 独立 flow 文件 → 控制流形态
  ↓
给人看一眼：「我读到你是 A 形状（声明独立 / 控制流独立 / 章末全 return），对吗？」
  ↓ 人确认 → 写进 storygraph.rules.json 的 placement（**一次**）
  ↓
之后全部按清单分派，不再问
```

新增文件出现**新形状**时才提示一次；形状没变就永远不问。
`Conventions` 现在**已有** `placement` 字段 + `placement_source`（`declared` / `detected`），
两者分开记 —— 报告里能说清"这是你说的还是我猜的"。

两条**必须记住的判据**（写代码时校准出来的）：
- `define gui.x` / `define config.x` **不算**项目声明 —— 不排除的话，任何项目的
  `gui.rpy` / `options.rpy` 都会被当成"声明文件"；

  （names / chars / flags）是人工按语义排的，算法读不出来；文件系统字母序
  （chars / flags / names）同样对。所以测试比集合，其余三项比字面值。

### 6.5 三档降级：坏习惯不会让工具瘫痪

| 用户怎么写 | 图的权限 | 卡片的权限 | 提示 |
|---|---|---|---|
| 干净（章末 return + 分支独立） | 全功能（拖线即写） | 全功能 | — |
| 内联 menu / if 在台词中间 | **只画、只读** | 全功能（menu 拍可改） | "这段分支在剧本里，图只能看" |
| 章末 `jump` | **只读**（改目标可以，加边不行） | 全功能 | "这章的出口写在剧本里" |
| 章末落空 | 报警（红） | 全功能 | "这章没有出口，会撞进下一个 label：`xxx`" |

**这是这套设计的核心：不是"改造用户"，是"按用户的写法决定自己能用多深"。**

### 6.6 "分离"（把内联 menu 抽到控制流文件）到底做不做

**能读出 → 必须做；能分离 → 做，但只作为显式动作，绝不自动。**

| | 识别（只读） | 分离（改写） |
|---|---|---|
| 风险 | **零** | 改字节 + 改结构 + 动存档位置 |
| 什么时候做 | 每次打开项目 | 用户右键点"把这段分支抽到控制流文件" |
| 前置条件 | 无 | diff 预览 → 确认 → 跑 lint → 可撤销 |
| 失败后果 | 无 | 剧本被改坏（所以必须可撤销） |

**为什么不能自动分离**：
1. 抽取是**重构**，等于工具替用户决定项目结构 —— 违背"本工具不猜语义"；
2. 选项体里可能有 `scene`/`show`/`$`，搬出去**语义等价但可读性变了**（"演员本"里少了这段演出）——
   这是创作判断，不是工具能定的；
3. 在 menu 里存的旧档，抽取后回不到原处。

**存量项目默认不动**（只标记、只降级），新项目默认分离。想批量改造就是另一个独立工具，不进主流程。

### 6.7 章末 `jump` / `call` 的精确规则

| 章末最后一条 | 能包 `_control` 吗 | 为什么 | 图上 |
|---|---|---|---|
| `return` | ✅ | 标准出口 | 出边可拖（写 `_control`） |
| `jump X` | **❌** | 包一层 `call 这章` 后，`jump` 直接穿出，**永远回不到 `_control`** | source 边，只读；能改目标，不能加边 |
| `jump 自己` | ❌ | 原地循环（等事件/重试），不是"去哪" | 画成回到自己的边，标注"循环" |
| `call X`（末尾，之后无语句） | **❌** | ⚠ **Ren'Py 没有隐式 return**：call 回来之后没有语句了，一样落空 | 标红；建议补一行 `return` |
| `call X` + `return` | ✅ | 这才是正常写法 | 虚线回环 + 出边 |
| `menu` 收尾 | ❌ | 出口由每个选项各自决定，不能用一个目标代表全体 | 每个选项各一条边 |
| `$ renpy.full_restart()` / `quit()` | ❌ | 终局，没有"下一步" | 不出边 |
| **`$ renpy.jump(x)` / `renpy.call(x)` / `jump expression x`** | ❌ | **静态判不出去哪** —— 那是运行时的事 | **标"运行时决定"，只读；不报落空** |
| 台词 / `show` / `comment` 收尾 | ❌ | 落空，会撞进下一个 label | 标红 |

> ⚠ **第三层边界（2026-10-23 23:55，用户指出）**：`renpy.jump(变量)` 这一档曾被我
> 归进"落空"——**那是错的**。判不出来的东西就不能编一个分类给它。
> Ink Graph 敢拒绝删除 function call，是因为它**确知**会破坏返回栈；
> 我们对 `renpy.jump(x)` 没有这种确知，正确动作是承认不知道。
> 现在它单独一档 `EXIT_DYNAMIC`：`is_risky=False`（不是缺陷）、`can_wrap=False`（不知道去哪），
> 降级清单里单独一条 `dynamic_exit`，和"这些章没有出口"分开报。
> ⚠ `$ renpy.jump("b")` 虽然参数是字面量，**也归这一档** —— 那是 Python 表达式，
> 解析一半比不解析更危险。

> ⚠ **订正（2026-10-23 23:00，写代码时发现自己写错了）**：上一版把"末尾 `call`"
> 写成"✅ 可包（call 回来再 return，正常）"——**错**。
> Ren'Py 的 label 末尾**不会**自动 `return`：`call sub` 回到原行之后，
> 如果后面没有语句，label 就结束了，一样落空。所以"末尾 call 无 return"
> 归到风险档，不归到安全档。

判定算法（只读，四条）：
1. 取 label 内最后一条**有效**语句：**跳过空行和注释**（`comment` 也是 Statement，
   但它不改变执行流 —— 真机 `fc_play` 末尾就是一段 `## ----` 分节注释，第一版被它骗了）；
2. `return` → 可包；`jump` → 不可包；`call` → **不可包**（见上）；
   终局调用（`full_restart` / `quit`）→ 不可包；
3. 最后一条带着"所属菜单选项" → 归 `menu` 档，**逐个选项**列出出口，不拿最后一条代表全体；
4. 以上都不是 → 落空，找同文件下一个 `label` 名，报"会撞进 `X`"；没有下一个 → "落到文件末尾"。

实现：`storygraph/story/exits.py`（`LabelExit` / `ExitsReport` / `project_exits`），
判据测试 `tests/test_label_exits.py`（24 条），命令行 `python cli.py exits <项目>`。

> 真机结果（`sr_general`，23 文件 / 56 label / 1.0s）：
> `return` 22 / `jump` 21 / **落空 8** / `menu` 4 / 终局 1；
> **6 个章没有出口**（含 `chapter3_1`），17 个章出口写在剧本里，4 个章以选项收尾。
> 这三类就是"图只能用多深"的开关 —— 工具降级时**必须**把它们说出来。

## 9. 三层边界（2026-10-23 23:55，补充：工具到底管到哪一步）

> 起因：用户指出我只有两层（降级 / 不降级），漏了第三层。
> 正确的边界是三层，**"用户非要乱搞"的答案不是堵死所有写法，而是让工具在每种写法下都不撒谎**。

| 层 | 面对什么 | 工具的动作 | 今天的实现 |
|---|---|---|---|
| **① 操作层面拒绝** | 做了会**确定**破坏东西（删 `call ... from` → 存档返回点没了） | 拒绝，或强提示并列出原因 | ✅ S1（确认框点名 `_call_xxx`；`jump` 不提示） |
| **② 权限降级 + 静态报警** | 静态**能判定**的坏形状（落空 / 章末 jump / 内联 menu） | 图上收回写权限，标红/标黄，卡片仍可用 | ✅ `ExitsReport.degradations()`（blocked / readonly） |
| **③ 能力边界声明** | 静态**判不出来**（`renpy.jump(变量)` / `renpy.call(变量)` / `jump expression`） | 明说"运行时决定"，只读，**不报落空** | ✅ `EXIT_DYNAMIC` + `dynamic_exit` 降级条 |

**判据一句话**：能判定的就判定，不能判定的就说不能判定 —— **绝不把"不知道"塞进一个错误的分类**。

为什么第③层必须单独存在（不是洁癖）：
- 报错了，用户会去改一段**本来没问题**的代码；
- 报警一旦出现假阳性，后面所有真报警都会被当噪音；
- 而"我不知道"是一条**可验证的陈述**——它永远不会错。

✅ 第①层已落地（S1）：删 `call X from _call_Y` 的确认框写明"玩家在「X」里存的档就回不到原处了"；
删 `jump` 不提示（`D2`）。删完图上的线由拍重新派生，**不会再弹回来**。

## 10. S2 的架构校准：为什么选择点不住 `*_control.rpy`

安全性来自"没人碰它"，不是来自"它叫控制流"。

| 文件 | 谁写 | 会被整份重写吗 |

| 剧本 `.rpy` | 导出（增量补丁） | 否（逐行配对替换） |
| `*_control.rpy` | 导出控制流 | **是** |
| `*_choices.rpy` | 只由 `apply_choice_point` 写（新建走门禁、追加原子读改写） | 否 |

## 11. S3：导出控制流前的守门（实测到一个 P0）

### 11.1 P0：只导两章就导出，会冲掉第三章

```

第 2 天：只导入 ch01/ch02 → 再点一次导出

原因：`export_to_renpy` 按**当前这张图**整份重生成，图里没有的章就被抹掉。

**这是 S3 真正的价值**：不是"把线写进 `_control`"（导出器本来就会写），

### 11.2 守门的三条判据

| 情况 | 动作 | 为什么 |

| 文件里有 `X_control`，图里既无 `X` 也无 `X_control` | **拒写**，列出缺的章 | 整份重生成会抹掉它们 |
| 文件里有**不叫 `*_control`** 的 label | **拒写**，列出它们 | 说明有人手写过；整份重生成会删掉（与 S2 同源） |

接在 `EditorSession.export_control_flow` 里，所以 **UI / CLI / 任何入口都过这一关**，
不是某条按钮的私货。

理由：图里没有这些章 —— 写下去会把它们在这个文件里的控制流整块抹掉
```

### 11.4 一个顺带发现

`discover.labels_in_file` 的正则**不认中文 label**（真机 `第一章` 就是中文）。
守门要用"这个文件里到底有什么"，所以本模块自己用一条**更宽**的正则扫，
并在代码里写明"用途不同，不是两套判据"。

## 12. L7 完整版 + 形状落清单（本轮最后两件）

### 12.1 "摆好的版式回来了"需要三步，不是一步

W1b 只做了第 2 步，所以重开软件仍然是"图是空的，版式无从可贴"。

| 步 | 做什么 | 在哪儿 |
|---|---|---|
| 1 | 记住"这个项目的图由哪些文件组成" | `session_store.remember_graph_files`（**用户级**，相对路径） |
| 2 | 打开项目时**重建同一张图** | `window_graph_ops._restore_graph_files` |
| 3 | 把版式贴上去 | W1b 已有 |

三条前提缺一不做：**图必须是空的**（用户手上已有工作时不许自动重置）、
`auto_open` 开着（关掉记忆的人就是不想要）、记录里的文件**现在还在**。

判据：`tests/test_graph_restore.py` 11 条。

### 12.2 形状要能落到清单里，但只能由人触发

`Conventions.placement` 原来只有"探测"这一半。现在补了写入口：

```bash
python cli.py shape <项目> --write
```

**为什么不自动写**：探测是"我看到的"，写进清单就变成"这个项目就是这样"。
自动落盘等于把猜测洗成事实 —— 所以只给人一个显式按钮。

它只写四个键（`declarations` / `control_flow` / `content_globs` /
`declaration_style`），别的段一个字不动；清单 JSON 坏了就**拒写**。

判据：`tests/test_conventions_placement.py` +4 条。

### 12.3 故意没做的两件（会干扰用户测试）

| 项 | 为什么先不做 |
|---|---|
| 加边交互（E1 零弹窗 / E2 告知型面板） | 要动 `AddEdgeDialog` 与 `add_edge` 两条主路径；用户马上要统一测，这时候改交互会让"是新增的 bug 还是本来就那样"说不清 |
| 视图折叠 / 只看某条线（D3） | 纯界面增量，价值低于上面两件；等真实使用反馈再定形态 |

## 13. E1/E3 + D3：接线落点与视图过滤（2026-10-24）

### 13.1 拖一条线，落点由**剧本结构**决定

```
章末最后一条           落点                     问不问
─────────────────────────────────────────────────────────
return                插在 return 之前          不问（唯一）
台词 / 舞台            接在末尾                  不问（唯一）
jump / call / menu    已有去向 → 两个"去哪"了    要问
在块体里（nest_path）   分支归卡片，图上不插       不问（不做）
起点不是当前载入的章     插不了                     只提示
```

**最后一条最重要**：插拍依赖 session 在那一章。起点不匹配时**不许**画一条
"看起来写进去了"的线 —— 那种假象比报错难查得多。

**"在块体里"这条是实测补上的**：章末 `menu` 的最后一拍是
`nest_path='menu:1>B'` 里的那个 `return`。只看 `raw == 'return'`
会判成"插在它前面"，一插就插进选项体了（和那个 P0 同源的错）。

### 13.2 为什么默认是 `jump`

章末接线的绝大多数意图就是"这一章完了去下一章"。要 `call`
（带返回点）就走卡片里的「↳ 插入控制流卡」，那里能填 `from`。

### 13.3 D3 是**视图**，不是删除

「🔍 只看选中模块的连线」只改 `visible`：
- 再点一次恢复；
- 重建图（连线/刷新）之后过滤**仍然在**（否则用户白点）；
- **一条边都不删** —— 删线在 S1 之后会删剧本那一行，两件事不能混。

### 13.4 E2 的完整面板**暂缓**（有数据支撑）

"途中接线 → 告知型面板（选插在第几拍 + 前后台词预览）"没做完整版，
`ambiguous` 时退回原来的 `AddEdgeDialog`。

理由不是偷懒：`cli.py exits` 扫真机 8 章，**6 章以 `return` 收尾**，
1 章 `jump`（`mini_game_flipcard`），1 章 `menu`（`puzzle`）。
真正会走到 `ambiguous` 的场景在真实项目里很少 —— 先看它到底会不会被撞上，
再决定那个面板长什么样，比现在凭空设计一个更靠谱。

## 14. 事故复盘：我把拖线搞坏了（2026-10-24 11:25 → 11:50 修好）

### 14.1 现象

用户："你的 UI 改坏了，无法拖线链接。"

### 14.2 根因（一句话）

**`import_chapters` 只建图、不载入拍。** 而 E1 的落点判断要先看"这一章的拍"。

于是最常见的路径——**打开项目 → 导入章节 → 直接拖线**（没进卡片页）——
`session.beats` 是空的，每一次拖线都判成 `not_loaded`，
而我的分支是"只弹一句提示就 `return`"。

**界面上就是：拖了完全没反应。**

### 14.3 修法

`not_loaded` / `ambiguous` / `cannot` **一律退回画草图**，只在状态栏说清
"这一章没打开，只能画草图"。

> **"不能写剧本" 和 "不给你连线" 是两件事，不能混。**
> 画草图是无害的；静默什么都不做，是最坏的一种"反馈"。

三条兜底全加上：`plan_wire_landing` 抛异常 → 画草图；`_apply_wire` 失败 → 画草图；
`cannot` → 画草图。

### 14.4 更该记的：**我的测试当时是绿的**

第一版测试写的是：

```python
assert not host.add_edge_calls, '插不了就不该假装能插'
```

这条断言把 bug 钉成了**预期行为**。测试全绿，用户一拖就发现坏了。

教训：**判据要从"用户会怎么用"出发，不能从"我刚写了什么"出发。**
后来改成两条反向断言（`test_not_loaded_still_draws_a_sketch` /
`test_just_imported_without_opening_still_connects`），并把"真窗口端到端"
也加上了 —— 只有真窗口才走得到"导入章节但没载入拍"这个状态。

### 14.5 顺带发现一个既有竞态（不是这次引入）

6 个测试文件一起跑时，进程稳定 `access violation` 崩溃：

```
线程：thumb_loader → prune_thumb_cache → Path.__init__
主线程：Garbage-collecting
```

`thumb_loader._schedule_cache_prune` 把缓存清理丢进
`QThreadPool.globalInstance()`，窗口 `close()` 之后线程还在跑；
进程 GC 时撞上就崩。**真机上"快速关开窗口"也可能撞到。**

测试侧已加 `_drain_threads()`（close 后等线程池）；
**产品侧的正解是"退出时不跑清理 / 改到空闲时跑"，待做。**
