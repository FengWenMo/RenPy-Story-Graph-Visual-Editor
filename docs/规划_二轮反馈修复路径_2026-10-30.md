### 2.3 ③ 「过场没有注册（项目自己写的自定义写法）」

**现状链路**

- `$ renpy.transition(Dissolve(0.1), layer="master")` 解析成 `StatementKind.PYTHON` → `Beat.code`（CodeBlock），
  只在卡片**折叠的高级区**里能看到（`app/editor.py:90,105`；`ui_qt/main_window.py:631-667`）。
- 工具的"过场"模型只有 `Beat.with_`：只由 `show/scene/hide … with` 子句或 Stage 列 `[转场]` 写入
  （`story/beat_build.py:709-770`）；预览的淡入只看它（`app/stage.py:129-161`、`ui_qt/stage_preview.py:1319-1324`）。
- 结果：`chapter1_1` 208 拍里 24 处代码过场，预览**只淡了 1 次**（那 1 次来自唯一一处
  `hide ... with dissolve`）；`chapter3_1` 35 处独立 `with`，预览 0 次淡入；Excel「转场」列全空，
  `coverage_of_beats` 还把覆盖率记成 T0（**假绿**）。
- "未注册提示"核实：工具**从未提示过**——`describe` 不看 Python 语句，`discover_undeclared(sr_general)=[]`、
  `unknown_statements` 全仓为空。用户是看到"转场列空 / 卡片看不见 / 预览硬切"得出的结论（或"想注册没入口"）。

**为什么现有四条"教它"机制都装不下它**（`03_transitions.md §4.2`）

1. `storygraph.rules.json` + `StatementRegistry`：按**开头词**匹配，且只收"未建模的原生语句"——`$` 开头是 Python；
2. `cds_registry.py`：读项目 `renpy.register_statement(...)`，只读、无参数列，本项目 0 处；
3. `dsl` 的「配置_词表」工作表：只有注释承诺，**没有读取实现**；
4. 卡片"自定义动作/语句参数格"：只支持头行字段或 raw 叶语句，`code` 没有分支；动态列名还要求 ASCII 标识符
   （`renpy.transition` 的点号进不去）。

**修改建议（三档，`03_transitions.md §五`）**

| 档 | 做什么 | 改字节 | 工作量 |
|---|---|---|---|
| **A（建议先做）** | 新纯函数模块 `story/transition_expr.py` 识别 `$ renpy.transition(...)` / 独立 `with …` / 行内 `with`；`StageFrame` 派生 `transition_expr/时长`；卡片摘要/「当前舞台」显示一行"过场：Dissolve 0.1（master）"；预览按**字面量时长**做淡入（如实标"近似实现"） | **否**（纯读） | 1~1.5 天 |
| **B1（随后）** | 把它注册成**可编辑技术语句**：复用现有动态列机制（卡片参数格 + Excel 列自动长出），只改 `Beat.code` 里那一行、定点回写、同步 `ordered`；**不能**复用 `Beat.with_`（会重复执行） | 零改动零写；改值只动一行 | 2.5~3.5 天 |
| C | 通用"项目适配包/映射"声明技术调用形状、随包分发 | 同 B | 5~7 天；**建议等第二例出现再做**，别先发明一门没人用的配置语言 |

**判据方向**：`tests/test_transition_expr.py`（识别纯函数 ~10 条：表达式/层/时长/注释/多行/认不出不猜）、

### 2.4 ④ 立绘分类有问题 + 「只有文件名是角色名的可以匹配」

**用户原话对应**：`流溪：「立绘怎么一堆单独的分类，什么 relaxing，resigned」/「这不都是凌的表情吗」`；
`sorano：「只有文件名是角色名的可以匹配」「不能直接放立绘图，直接放角色那个头像图就能动」`。

**实测（本轮只读复现，`.pip-tmp/plan/probe_group_stats.py` / `probe_sprite_match.py`）**

- 选择器一共 **145 个分组**，其中 **137 个是「立绘：」**；**110 个分组只有 1 张图**——
  `立绘：resigned`、`立绘：refusing`、`立绘：qing` … 全是 `cc_preview/<角色>/<表情>.png` 行
  （Tag 空 → 按资产 ID 猜成独立 tag → 每个表情一个分类）。
- 真正按角色聚合的只有 6 组：`lan 45 / ling 48 / xing 41 / ye 50 / toto 4 / dororo 3`。
- 选中后的 spec（`app/picker.py::image_spec_of`）：有 Tag → `tag 属性`（`ling refusing` ✓）；
  **没 Tag → 直接拿资产 ID**（`refusing` ✗）。
- 卡片能不能出"三个可调属性"取决于 spec 的第一个词是不是**已知角色 tag**
  （`ui_qt/sprite_grid.py:463,640-660` → `beats.attr_slot_rows`）：`ling refusing` → `表情/服装/位置` 三格 ✓；
  `refusing` → 0 格（只剩兜底表情格+位置）。实测 1719 行里只有 **228 行**能出属性格。
- 于是正好复现用户观察：`cc_preview/avatar/lan.png`（资产 ID 恰好是 `lan`）**能匹配出三格**；
  而 `cc_preview/avatar/ling.png`（ID 是 `avatar_ling`）和 `cc_preview/ling/refusing.png`（ID 是 `refusing`）
  **都不能**——也就是"只有文件名恰好是角色名的能匹配"。真正带「标签」的 8K 立绘行（`ling refusing`）
  本身是能匹配的，但它们和 159 张预览副本混在同一个列表里，分类又被拆成 110 个单图组，
  很难找到、很容易误选预览图。
- 更严重：选中预览图后 `cards_to_show` 会原样写出 **`show refusing`**（实测），
  而引擎里没有 `image refusing` —— 这一行在游戏里运行时是"找不到图"（当前没有门禁/提示）。

**根因（编号供实现引用）**

- **R1 没有"图像 → 角色/属性"的唯一真源**：只认资源表「标签」列 + 资产 ID 猜，**不看路径**
  （`cc_preview/<角色>/<表情>.png`、`images/characters/<角色>/**` 的文件夹本身就写着答案）。
- **R2 分类按 tag 生成**：Tag 空的行被 `_guess_image_tag` 拿 ID 当 tag → 110 个单图分类
  （`app/beats.py:1369-1459`）。
- **R3 选中不校验"能不能上舞台"**：缩略图按资源表 Path 能显示，于是"看起来加上了"，
  属性全无、保存后写出非法 `show`。
- **R4 用途不区分**：立绘 / 背景 / CG / 界面 1193 张全部进同一个选择器（`pick_image` 只有 `types=['image']`），
  找不到、容易误选。
- **R5 资源表两套行**：8K 真立绘（Tag 非空）+ `cc_preview` 副本（Tag 空、159 行）同时列出，
  同一张脸出现两次，用户分不清哪行才是能写进 `show` 的。

**修改建议：新增"资产身份解析"（唯一真源），分四步**

1. **纯函数模块 `storygraph/assets/asset_identity.py`**（不碰 UI）：
   `resolve_image(row, project_root, mapping, known_tags) -> Identity(kind, tag, attrs, source)`。
   判定顺序（**只认字面量，不模糊匹配**）：
   ① 映射表精确覆盖 → ② 映射表路径规则 → ③ 资源表「标签」列（且必须是已知角色 tag）→
   ④ **路径里出现已知角色 tag 的目录段**（如 `cc_preview/ling/`）→ ⑤ 文件 stem 恰等于角色 tag
   → ⑥ 认不出 = `unknown`（**不猜**）。
   `kind ∈ sprite | bg | cg | ui | preview | avatar | other`；`source` 记"映射/标签列/文件夹/未知"（对照表要显示）。
   已知角色 tag 来源：`characters.xlsx` 的「立绘 tag」+ 引擎事实里带属性的 tag + 语句表 `show` 的候选。
2. **选择器重构**（`app/beats.py::categorize_assets` + `app/picker.py` + `ui_qt/asset_picker.py`）：
   - 分组 = 角色优先：`立绘：凌（ling）` 里放这个角色的**所有表情**（按属性排序），不再每个表情一个分类；
     `预览图`/`头像` 单独归到「角色预览图（不能直接上舞台）」，不再混进立绘；
   - 背景 / CG / 界面 各自成组；「全部」加"只看立绘 / 只看背景 / 只看 CG"过滤（`pick_image` 加用途参数）；
   - 条目显示 **人话名**：角色显示名（`凌跃捷`）+ 属性词（可映射中文），原始 ID/路径放 tooltip。
3. **选中即校验**（`asset_picker.accept` + `sprite_grid._on_add/_on_click`）：
   - 预览图/头像被选进"立绘"时：如果映射/推断能对到**真立绘**行（`ling refusing`），直接给规范 spec（并在提示条里说明"已用对应的立绘"）；
     对不到就**拒绝**并给一句话（"这是角色预览图，不是立绘；请选『立绘：凌』里的 xxx"）；
   - 卡片加**警告条**：spec 的 tag 不是已知角色 tag 时，显式写"这张图不是立绘/未知角色 tag"，并给"按文件夹推断/改选"入口；
   - 保存/导出前把这类行报出来（走既有"舞台可疑行"门禁的同一套路），**不许静默写出 `show refusing`**。
4. **（与⑥同源）映射表覆盖**：见 §2.6。

**判据方向**：`tests/test_asset_identity.py`（~15 条：Tag 优先、文件夹推断、`cc_preview/avatar`、
`_hd_cut` 这类下划线开头、同图两行、未知不猜、source 标注）；改 `tests/test_picker_and_refresh.py`
的分类断言（单图分类不得再出现、`立绘：ling` 内含表情）；`test_ui_qt.py` 选择器"选预览图被拒/映射到真立绘"；
真机探针：再跑一次 `probe_group_stats.py`，要求「立绘：」分组 = 角色数（4~6），单图分组 ≤ 个位数。

**工作量**：2~3 人日（含测试）；风险：改选择器分组会动 `test_picker_and_refresh` / `test_ui_qt` 若干断言（同一提交内改）。

### 2.5 ⑤ UI 宽窄 / 别拖横向滚动条

**实测（offscreen 探针，`05_ui_width.md`）**

| 右栏状态 | 立绘卡数 | 卡片最小宽 | 横向滚动条 |
|---|---|---|---|
| 窗口 1142（当前能缩到的最窄） | 0 / 1 | 380 | 无（视口 420） |
| 同上 | **2** | **519** | **有（max=99）** ← 用户截图形状 |
| 同上 | 3 / 4 | 721 / 832 | 有 |
| 手动把分栏拖成 `[700,250]` | 0 | 380 | **有（视口 229）** |

**根因**：① `sprite_grid.py:784` 写死 `_cols = 4`，每多一张卡 +202px；② 空卡片被「高级区」按钮
51 字长文本压出 **356px 地板**（`main_window.py:714-719`，+边距=380）；
③ **窗口最小宽 1142px** = 导航 dock 200 + 卡片页顶部动作条 920（`main_window.py:2333-2396`）——
窗口根本不能变窄，右栏最多 420，与①叠乘。

**修法（`05_ui_width.md` §三）**：Phase 1 速赢（0.5 天）：高级区短文本 380→365、「选择…」→24px「⋯」+tooltip、
当前舞台 288→240、默认窗口 1600→1360 ⇒ 卡片地板 **317px**；Phase 2 主修（1 天）：网格列数随宽度自适应
（4 张卡 832→2 列 428）+ 右栏最小宽兜底（**拖到卡片刻度就停，结构性保证不出横向条**）+ 双击「展开卡片」；
Phase 3（0.5~1 天）：5 个结构按钮收进「⋯ 结构」菜单 + crumb 换省略标签 ⇒ 窗口最小宽 **1142→726**，实现"UI 宽窄可变"。
**不建议**：强制关横向条（静默裁切）、给卡片 `setMinimumWidth(0)`（没用）、整体缩放（字太小）。
**判据**：新增 `tests/test_ui_width.py`（卡片 `minimumSizeHint ≤ 340`；窗口 `≤ 900`；
逐拍把右栏压到 340 断言 `horizontalScrollBar().isVisible() == False`；网格列自适应）；同步改
`test_ui_fit_and_flow.py:141-150`、`test_stage_thumb.py:436-440`、`test_prewarm.py:53-67`。合计 2~3 天。

### 2.6 ⑥ 映射表：查询 / 对照 / 修改 / 随包分发

**定位**：项目级"项目适配"文件（与 `storygraph.rules.json` 同一个模式：**跟项目走、可提交、可 diff**），
让做《千连万理》的人（或别的项目开发者）自己维护"哪张图是哪个角色的哪个表情"；
工具在**没有映射**时按文件夹推断（§2.4 第 1 步），映射只做**覆盖/纠正**。

  "name": "千连万理 · 资源映射",
  "characters": {

### 2.7 ⑦ CG/BG 无法调节大小 + 8K 图能不能正常显示

**直接回答"8K 能正常显示吗"（分三处，别混）**（`07_cg_bg_scale.md §〇/§五`）

| 位置 | 行为 | 数字 |
|---|---|---|
| 选择器缩略图 | **能**：统一解到 104×74，不整张进界面 | 冷缓存 8K **781ms/张、峰值 +134MB**；磁盘缓存热 7~24ms；14 线程并发最坏瞬时 **3~4GB**（低内存机器有 OOM 风险） |
| 卡片小图 / 演出预览（引擎排版） | **能显示但不缩放**：原图像素贴左上、超出裁掉 | 8K bg 只露左上 1920×1080；4K CG 只露左上 1/4 |
| 引擎 / 游戏本身 | **能加载，但 Ren'Py 不会自动缩放**：无 `at` 就按原像素裁切；要正常显示必须 `fit`/`zoom` 变换 | SDK `layout.py:873`；作者已写 `bgfit: fit "cover"`、`cg38402160: zoom 0.5` 并在脚本里用了 |

> 结论：**不是"图太大显示不出来"，而是工具预览没按引擎语义处理尺寸**；而且引擎里同样需要 `at`。
> 项目作者已经写了变换（`scene … at bgfit` 10 处、`show cg … at cg38402160/bgfit` 13 行），
> **是预览没跟上**，不是游戏里没写。

**根因（预览侧三条，均实测）**

- **R1 CG 层丢了几何**：舞台快照的图层只存图名（`story/stage_snapshot.py:179-184`），
  `_draw_layers` 永远原图像素贴 `(0,0)`（`app/stage_render.py:485-510`）⇒ 4K CG 只露左上 1/4；
  chapter1 621/1022 帧有 CG，带 `at` 的约 598 帧全错。
- **R2 BG 变换双重丢失**：① `scene_at` 不参与快照累积（`app/stage.py:283`；当前只 13 帧有值，
  按引擎语义应有 320 帧带 fit）；② `story/atl.py` **不解析 `fit`**（注释里明写忽略），
  `bgfit` 退化成"按名字猜居中贴底原尺寸"——实测 `box(2304×1296)=(-192,-216,2304,1296)`；
  ③ 卡片没有 `scene_at` 显示/编辑入口（只有 Excel 背景列 `图@变换` 或高级区手打）。
- **R3 内存/耗时**：`_load_scaled` 解码目标=原图、`lru_cache(maxsize=48)` 按**张数**缓存：
  8K 单张 132.7MB → 理论最坏 **6.37GB**；实测 8K 立绘首帧 **1547ms / 峰值 581MB**，
  8K 当背景 768~834ms / 峰值 547MB。

**修法（推荐路径，`07_cg_bg_scale.md §十/§十一`）**

- **P0 预览层补引擎语义（2~3 天，不改用户字节）**：
  ① `atl.py` 支持 `fit / nearest / xsize / ysize / xysize / anchor`，`Placement` 携带 `fit`，按"屏幕=包含区域"算 box；
  ② 快照累积 `scene_at`（持续状态）与 `layer_at`（show 时记、hide 清），`StageFrame` 带出；
  ③ `_draw_background / _draw_layers` 统一走 `placement.box`；
  ④ `_load_scaled` 解码目标封顶（≤ 屏幕/可见区域）+ 缓存按**字节预算**（如 256MB）。
- **P1 只读提示/试穿（1~2 天）**：卡片/预览显示一行人话："背景 bg7_0 2304×1296 → 屏幕 1920×1080
  （无 at：游戏里会裁切 / 有 fit 变换）"；提供"试穿项目已有 transform"下拉（只改内存 override，不写盘）。
- **P2 用户确认后写 at（1~2 天）**：把选中的 transform 写进 `scene_at` 或该 CG item 的 `at`；
  **只允许引用项目已存在的 transform**，diff 确认、可撤销、走既有补丁门禁。
- **明确不做"预览自动 fit"**：游戏里没写 fit 会裁，预览却铺满 = 预览骗人（违铁律 #9）。
- **方案 D（独立"图层/大小"编辑器：z-order / behind / 铺满/适应/自定义 zoom）3~5 天，先不做**，
  等 A/B/C 落地后按反馈决定。

**判据**：新增 `tests/test_stage_render_scale.py`（无 at 裁切 / fit cover / fit contain / zoom / **继承** /
layers 的 at 生效 / 多图层叠序，用像素采样断言）、`test_stage_snapshot_scene_at.py`（state 含 scene_at/layer_at、

### 2.8 附带：「GitHub Star 提示连不上，但其实我能打开」（已修，2026-10-30）

**这不是用户网络问题，检测逻辑确实有错**（`ui_qt/github_star.py`，本轮实测）：

- 本机 `urllib` 已认到系统代理（`http://127.0.0.1:80`），仓库页实测 **200 OK（1.45s）**；
- 但 `probe_repo` 超时只有 **2.5s**（`PROBE_TIMEOUT`），实测同一条网络连续 5 次里**就有 1 次 >6s**——
  2.5s 必然偶发误报"连不上"；
- `probe_repo` 把**任何** `HTTPError`（404/403/429/500）都当"连不上"（`github_star.py:138-148`）：
  网络其实是通的，用户若在浏览器登录着（私有/改名仓库）照样能打开；
- 没 token 时探测失败**就不开浏览器**（`:327-345`）——而浏览器走系统代理/PAC，往往能打开。
  现有测试 `test_offline_says_so_and_does_not_open_a_dead_page` 把旧行为钉住了，需要一起改。

**改法**：点一下**立刻打开浏览器**（本机动作、不联网），探测挪到后台只做提示；
探测"任何 HTTP 响应都算网络通"；超时 6~8s、失败重试一次；文案改成
"已打开仓库页（网络自检没通过，浏览器里若打不开多半是代理/网络）"。判据：`test_github_star.py`
改旧断言 + 新增"404 也算通 / 超时仍开页 / 点一下立即返回"。工作量 0.5 天。

**✅ 已落地（2026-10-30）**：`PROBE_TIMEOUT` 2.5 → 7 s、失败重试一次；`HTTPError` 全算网络通；
点一下先同步开页面、探测只补提示；`TIMEOUT` 3 → 8 s。测试 20 → 30 条，
`python -m pytest tests/test_github_star.py -q` 全绿（3 轮）；真机探针：不存在的仓库
（HTTP 404）现在判"通"。
