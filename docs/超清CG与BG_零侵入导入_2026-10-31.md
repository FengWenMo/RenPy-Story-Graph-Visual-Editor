# 超清 CG / BG 的零侵入导入

> 状态：**方案待评审**（2026-10-31）  
> 触发：导入 4K 素材时，"要不要在 `show` 里加 `at`"这件事逼着工具去改用户的 `.rpy`  
> 相关：`docs/真源与优先级_设计决策_2026-10-31.md`（层序与准入四问）、`MEMORY.md` 铁律 1/3/6

---

## 一、一句话结论

**超清不是"脚本问题"，是"资产声明问题"。**

一张 4K 图在 Ren'Py 里放不下，不是因为它需要 `at sg_fit`，而是因为**引擎不知道它是 2 倍图**。告诉它这件事有三个地方可写：文件名、目录名、`Image()` 的 `oversample` 参数。**前两个完全不碰 `.rpy`。**

所以本工具的正确姿势是：

> **能靠"文件/目录"表达的，绝不写进脚本；能靠"读"解决的，绝不写。**



---

## 二、为什么超清总把人往"改代码"上推

Ren'Py 的默认语义是：**像素尺寸 = 逻辑尺寸**。

> *"By default, the pixel size of an image defines the size it will take up when displayed. For example, if an image is 1920x1080 pixels, and the game is configured, using `gui.init()`, to run at 1920x1080, the image will fill the entire screen."*  
> —— [Displaying Images · Oversampling](https://www.renpy.org/doc/html/displaying_images.html)

于是 3840×2160 的图，在 1920×1080 的游戏里会被当成 **3840×2160 的逻辑尺寸** —— 溢出、只露左上角。

工具看到这个现象，本能反应是"我得帮它缩一下"，而手上最顺手的工具是 `show ... at xxx`。**这就是侵入的起点**：用"某一行演出"去修"一张资产的属性"。

**这是层次错位**：分辨率是资产的属性，不是这一拍的属性。把它写进 `show` 行，等于把"这张图多宽"记在"第 200 拍"上 —— 换个地方用同一张图，就得再写一遍。

## 三、Ren'Py 给了三条零代码路径（官方原文）

| 机制               | 写法                              | 官方依据                                                                                                                |
| ---------------- | ------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| **文件名**          | `bg room@2.png`                 | *"Oversampling is automatically enabled if the image ends with an '@' followed by a number, before the extension."* |
| **目录名**          | `images/@2/bg room.png`         | *"A directory can also specify how much to oversample images inside it."*                                           |
| **`Image()` 参数** | `Image("bg.png", oversample=2)` | *"Oversampling can also be enabled by giving the `oversample` keyword argument to `Image()`."*                      |

三条路径里，**前两条不需要碰任何脚本**，第三条需要写一条 `image` 定义（属于"要写代码"，但写的是工具自己的 sidecar）。

### 三个必须记住的细节

**① `@N` 不属于 image name**

`bg room@2.png` 注册出来的图像名仍然是 `bg room`，`@2` 是被识别并剥离的后缀。所以 **`show bg room` 一个字都不用改**。  
（社区实证：F95 用户改用 `@2`/`@3` 命名后 *"no need to edit Ren'Py .rpy files, it works flawlessly"*）

**⚠ 但对本工具有代价**：我们的资产 ID 来自文件名（`_image_id_from_name` → 空格转下划线）。改名会让 ID 从 `bg_room` 变成 `bg_room@2`，资源表、映射、卡片全跟着变。**这是工具侧的成本，不是引擎侧的成本。** 这个区分决定了我们该选哪一档（见 §五）。

**② 自动过采样的触发条件是"游戏被缩放"，不是"配置了高分辨率"**

> *"if the **game is scaled** by more than 1x and less than or exactly 2x, Ren'Py loading `eileen happy.png` will look for `eileen happy@2.png`"*

窗口放大也算缩放。而且查找顺序是**从大到小**（>2× 时找 `@4` → `@3` → `@2` → 原图）。

**③ `@2` 是"声明"，不是"开启高清"**

`@2` 的意思是"这张图的像素是逻辑尺寸的 2 倍"。标了它，4K 图会按 1920×1080 显示（正确）；**不标它，4K 图按 3840×2160 显示**（溢出）。

它不会让 1080p 的图变清晰 —— 那需要真的换素材。

## 四、最关键的一条区分：超清 ≠ 适配

这两件事经常被混成一件，混了就会误以为"超清必须写 transform"：

|               | 症状                                 | 解法                                   | 碰脚本吗   |
| ------------- | ---------------------------------- | ------------------------------------ | ------ |
| **超清（分辨率）**   | 4K 图按 4K 逻辑尺寸显示，溢出屏幕               | `@2` / `images/@2/` / `oversample=2` | **不碰** |
| **适配（比例/裁切）** | 图的比例和屏幕不一致（3:2 的 CG 放 16:9），要铺满就得裁 | `fit "cover"` / `zoom` / `xysize`    | 要      |

**一张 4K 且比例正确的图，声明过采样之后就完美满屏，一行脚本都不用改。**

只有当"比例不对 / 要局部放大 / 要故意留黑边"时才需要 transform —— 而那些**不是超清问题，是构图决策**，本来就该由创作者决定，不该由工具自动施加。

**这条区分能把侵入面砍掉一大半**：真实项目里绝大多数 4K 素材（16:9 的背景、按屏幕比例出的 CG）只要声明过采样就完事。

## 五、侵入性阶梯：五档，默认停在最低可行档

| 档 | 做法 | 动什么 | 引擎效果 | 工具代价 | 风险 | **报警下限** |
|---|---|---|---|---|---|---|
| **L0 只读** | 工具识别 `@2` / `@2/` 并按显示尺寸预览，导出**一字不改** | 什么都不动 | 已正确 | 补目录识别 | **无** | `none` |
| **L1 移目录** | `game/images/@2/xxx.png` | 移动文件，**文件名不变** | 正确 | 补目录识别 | 极低（git 里是"移动"） | `none` |
| **L2 改文件名** | `xxx@2.png` | 文件名变 | 正确 | **资源 ID 变**，映射要跟着改 | 中 | **`hint`**（0 引用）→ `notice`（有引用） |
| **L3 定义层 sidecar** | `image xxx = Image("xxx@2.png", oversample=2)` | 新增 `image` 定义 | 正确 | 要查重、要指纹守卫 | 中高（可能覆盖用户语义） | **`notice`** → `confirm`（覆盖用户定义） |
| **L4 注入 at** | 改 `show` 行 | **直接改用户代码** | 正确 | —— | 高 | **`confirm`**（永远，逐处） |

**"报警下限"这一列不是装饰**：L2 及以上一律不许静默执行，级别怎么浮动见 §5.5。L0/L1 允许 `none`，是因为它们不改身份也不改代码。

### 为什么 L1 应该排在 L2 前面

同样正确、同样零代码，但**目录级不参与 image name**（图像名只由文件名决定），所以：

- 资源 ID 不变 → 资源表、映射、卡片、跨章引用全不动；
- git 里显示的是"文件移动"，不是"删除 + 新增"（后者会让 code review 和 blame 全断）；
- 想反悔，把文件移回去就行。

**L2 的"改名"在引擎侧完全安全，但在我们这边是连锁反应。** 所以能移目录就别改名。

### L3 有一个材料里没提的风险

`image` 语句默认按 **init priority 500** 执行，而官方明确：

> *"Images defined using the image statement **take precedence over** those defined by the image directory."*

所以工具在 sidecar 里写 `image bg room = Image(...)`：

- 如果用户**也**定义过 `image bg room`，后执行的赢 → **用户的定义被静默顶掉**；
- 而且 `image bg room` 是**全局命名空间**，改它会改变**所有** `show bg room` 的含义 —— 影响面比"改某一行"更大。

从"不改字节"看是干净的，从"不改语义"看是脏的。**所以 L3 必须配 `sg_*` 那三条护栏：查重（用户已定义就不写）+ 指纹守卫 + 引用存在性。**

### L4 只在一个条件下允许

比例真的不适配、且用户明确要求"这张要铺满/要裁切"时。这时写的是**构图决策**，不是超清处理，必须由人触发，不能自动。

---

### 5.5 L2–L4 的报警：档位决定下限，后果决定上浮

**L2 以上一律不许静默执行**（它们动的是"身份"或"代码"），但**报警强度不能一刀切**——同样在 L2，"改一个 0 引用的孤立图"和"改一张被 87 处引用的背景"完全是两件事。所以：

> **档位只给"最低线"，实际上报级别由**算得出的事实**决定。**

四档：

| 档 | 表现 | 拦不拦 | 用在哪 |
|---|---|---|---|
| `none` | 什么都不显示 | 不拦 | L0 / L1 |
| `hint` | 操作按钮下方一句话（不弹窗） | 不拦 | **L2 的最低档**：改名的 ID 无引用、映射无条目 |
| `notice` | 黄色横条 + 可展开的影响清单 | 不拦，但要点"继续" | L2 有引用；L3 纯新增定义 |
| `confirm` | 红色确认，必须勾选一句具体后果 | **拦** | L3 覆盖用户已有定义；**L4 永远** |

#### 各档的最低线（低于这条线就是 bug）

| 档位 | 最低线 | 理由 |
|---|---|---|
| **L0** | `none` | 只读，没有任何副作用 |
| **L1** | `none` / 可选 `hint` | 移动文件不改代码；如果开了"移动后原始路径写进备注"则给 hint |
| **L2** | **`hint`**（不许 `none`） | 它会改**身份**：资源 ID 变、映射可能失效。哪怕 0 引用也要让人知道"我改了它的名字" |
| **L3** | **`notice`**（不许 `hint`） | 它往项目里**新增代码**，而且是全局命名空间的 `image` 定义 |
| **L4** | **`confirm`**（永远，无例外） | 它**直接改用户的 `.rpy` 行** |

**关键点：L2 的 `hint` 与 L0/L1 的 `none` 之间只差一句话，但这一句话是"知情权"——不能省。**

#### 上浮规则（同一档位内部）

```
L2:  引用数 = 0 且 映射无条目        → hint
     引用数 > 0 或 映射有条目        → notice（列出数字与行号）

L3:  项目里无同名定义                → notice（"新增一条 image 定义"）
     同名定义在工具 sidecar、内容相同 → hint（"已存在，不会重写"）
     同名定义在工具 sidecar、内容不同 → notice（"会重写自己生成的那条"）
     同名定义在**用户文件**里          → confirm（"会覆盖 script.rpy:41 的 image bg room"）

L4:  任何情况                        → confirm（逐处，不是整批一次）
```

#### L4 比 L2/L3 多三条硬要求

它是唯一改用户 `.rpy` 的档位，所以确认框不能只说"有风险"：

1. **给出用户能理解的坐标**：不是"会影响 3 处"，而是"第 200 拍（`chapter3_1.rpy:412`）的 `show bg room`"；
2. **逐处确认，不许整批勾一次**：一次确认覆盖 N 处 = 出事时无法定位是哪一处被默许的；
3. **逐处可撤**：每一处都要能单独还原成原文，不能"一键全撤"却撤不干净。

#### 防误报：宁可降档，不许升档

| 情况 | 正确做法 | 错误做法 |
|---|---|---|
| 引用数算不出来（解析失败） | 降为 `hint` 并注明"未能统计引用" | 升为 `notice` 说"可能有风险" |
| 映射文件读不出来 | 不报"映射会失效" | 默认假设有映射 |
| 同名定义扫不出来 | 报 `confirm`（保守） | 报 `notice`（乐观） |

**最后一行是唯一的例外**：查"用户是否已有定义"这件事，**查不到时必须按"有"处理**（升档），因为漏报的代价是静默覆盖用户代码，而不许误报的代价只是多一次确认。

#### 判据

| 判据 | 反例（必须红） |
|---|---|
| L2 改 0 引用的图 → `hint`（不是 `none`） | 无声执行 = 违反知情权 |
| L2 改 87 处引用的图 → `notice`，且理由里的数字是 87 | 写"若干处" = 假报 |
| L3 项目无同名定义 → `notice` | 报 `confirm` = 误报（把新增当覆盖） |
| L3 用户有 `layeredimage bg room` → `confirm` | 漏扫 layeredimage = 静默覆盖 |
| L4 任何情况都是 `confirm`，且逐处 | 整批一次确认 = 责任不可追溯 |
| 报警算出的数字 == 修复实际改的数字 | 两处各算一遍 = 迟早对不上 |

## 六、零侵入的边界：能走到哪

**"零侵入源代码"在 L0 和 L1 是成立的** —— 一行 `.rpy` 都不动。

但它有两个边界要如实说：

1. **L1 仍然动了文件树**（移动文件）。对"代码零侵入"成立，对"项目零改动"不成立。要不要接受，取决于团队对 git 历史的在意程度。
2. **L0/L1 只能解决"超清"，不能解决"适配"**。比例不对的图，怎么都得有一条 transform —— 那不是侵入，那是创作。

所以真正的目标是：

> **把"必须改代码"的场景，从"所有 4K 图"压缩到"比例真的不适配的那几张"。**

## 七、本工具要怎么改（具体到模块）

### 7.1 先补一个硬缺口：`oversample_of` 不认目录

现状（`storygraph/app/stage_render.py:843`）：

```python
_OVERSAMPLE_RE = re.compile(r'@([1-9][0-9]*)$')

def oversample_of(path) -> int:
    """这张图在引擎里的超采样倍数（没有 / 认不出 = 1）。只看文件名。"""
    stem = Path(str(path)).stem
    m = _OVERSAMPLE_RE.search(stem)
```

**它只看文件名，不看目录。** 于是 `game/images/@2/bg room.png` 在工具眼里是 1 倍，在引擎眼里是 2 倍 —— **预览和实际差一倍**。

这是 L1 方案的**前置条件**：不补它，移目录之后工具的画布就是错的。

补法（判据很硬）：

```python
def oversample_of(path) -> int:
    """文件名 @N 与目录 @N **都算**，取最大（引擎也是这个语义）。

    认不出 = 1（不猜）。
    """
    p = Path(str(path or ''))
    by_name = _match_at(p.stem)
    by_dir = max((_match_at(part) for part in p.parts[:-1]), default=1)
    return max(by_name, by_dir, 1)
```

**判据**：

- `images/@2/bg.png` → 2
- `images/@2/bg@3.png` → 3（取大）
- `images/bg@0.png` / `bg@x.png` → 1（不猜，与现有 `@0`/`@x` 不认的口径一致）
- 三处调用点（背景 / 立绘 / 图层）结果一致

### 7.2 检测层（只读，永远可跑）

新增一个纯函数，回答"这张图该不该标过采样"：

```python
# storygraph/assets/asset_oversample.py
def oversample_advice(path, pixel_size, logical_size) -> Advice:
    """这张图建议用几倍过采样；不需要就 None。

    判据只有一条：**像素尺寸是逻辑尺寸的整数倍（±2px 容差），且倍数 ≥ 2**。
    比例不符（3:2 的图放 16:9）→ 不是"超清不够"而是"比例不适配"，
    这里**不**给过采样建议（那是 transform 的事，见 §四）。
    """
```

返回 `Advice(need=2, reason='3840×2160 = 1920×1080 的 2 倍')` 或 `None`。

**这一层不写任何东西**，只出结论。结论进：

- 资源表的一个**只读列**「建议过采样」（或 tooltip，不新增列也够）
- 卡片右侧尺寸提示行（现在已经有 `800×600@2（引擎按 400×300 画） → 屏幕 400×300` 那种）

### 7.3 建议层（人点才动文件）

界面上给一个明确动作，措辞要说清代价：

> **「这张是 2 倍图，但没声明。建议移到 `images/@2/`：**  
> **文件名不变、脚本不用改、资源 ID 不变。**」

点"移动"才动。**默认动作只有一种：移目录（L1）。**

改名（L2）**要做**，但摆在第二个位置，而且必须过一次影响面报告（§5.5 下限是 `hint`，有引用时升 `notice`）：

> **「改名会把资源 ID 从 `bg_room` 变成 `bg_room@2`：**
> **87 处 show/hide 引用它、映射里有 3 条，改完这 90 处都要复核。**
> **（按钮：仍然改名 / 改用移目录）**」

**为什么默认不是改名**：引擎侧两者完全等价，但改名会让**我们自己的** ID 连锁——资源表、映射、卡片、跨章引用全跟着变。移目录不碰文件名，所以这一串连锁根本不会发生。见 §五。

### 7.4 落盘层（只有 L3 才写代码）

只有一种情况会碰代码：**比例不适配，且用户选了"按这个比例铺满"**。

这时也不写进 `show` 行，而是写进 `sg_transforms.rpy`（`story/sg_transforms.py` 单入口），并且：

1. **查重**：项目里已有能表达同一几何的 transform → 复用，不新增；
2. **指纹守卫**：文件被人改过（sha256 不符）→ **abort，不覆盖**；
3. **引用存在性**：`at sg_fit_cover` 引用了不存在的定义 → 报 E305。

这三条是 `sg_*` 已有的纪律，这里只是复用，不新增机制。

## 八、判据（可测试）

| 判据          | 怎么验                                                                           |
| ----------- | ----------------------------------------------------------------------------- |
| 目录级过采样识别正确  | `oversample_of('images/@2/bg.png') == 2`；`@2` 目录 + `@3` 文件名 → 3；`@0`/`@x` → 1 |
| 显示尺寸统一走一处   | 背景 / 立绘 / 图层三处的 `display_size` 结果一致（现在已统一，加目录后要复验）                            |
| **L0 不改字节** | 一个含 `bg@2.png` 的项目：打开 → 预览 → 导出，`.rpy` 逐字节不变                                  |
| **L1 不改字节** | 把图移到 `images/@2/` 后：`.rpy` 仍逐字节不变，且预览尺寸变了（证明工具读到了）                            |
| 建议只在"整数倍"时给 | 3840×2160 @ 1920×1080 → 建议 2；3000×2000 @ 1920×1080 → **不建议**（比例不符）            |
| L3 查重       | 项目已有 `image xxx` 时，不生成同名定义                                                    |

**最重要的一条是第二行和第三行**：它们是"零侵入"的可执行定义 —— 不是靠注释承诺，是靠"导出前后字节相同"。

## 九、不要做什么（反面教材）

| 做法 | 为什么不行 |
|---|---|
| **原地重烤图片**（把 4K 缩成 1080p 再存） | 丢质量、不可逆；而且这是改用户的资产文件（侵入性的最重形式） |
| **自动**给每行 `show` 注入 `at` | 把资产属性记在"某一拍"上；同一张图换个地方用就得再注入一次。**用户显式点的那一处可以（L4），自动的永远不行** |
| **自动**改名 `xxx@2.png` | 引擎安全，但我们的资源 ID 会变 → 资源表/映射/卡片连锁。**用户显式改名 + 过影响面报告可以（L2），自动的不行** |
| **把 `config.physical_width` 当单图解法** | 它是**全局**配置（整个游戏换分辨率），不是"这张图要超采样" |
| **看到 4K 就自动处理** | 有些项目就是 4K 逻辑分辨率（`gui.init(3840, 2160)`），那种图**不需要**过采样。必须先比"逻辑尺寸"，不能只看像素数 |
| **批量一次确认 N 处改动** | 出事时无法定位是哪一处被默许的（§5.5 的 L4 硬要求） |

**注意"自动"两个字**：L2/L3/L4 本身**要做**（工具要全面），反对的是**不经人确认就跑**。每一档都必须先过 §5.5 的影响面报告。

最后两行尤其重要：

- **判断依据是"像素 vs 逻辑尺寸"的倍数，不是"像素大不大"**。4K 图放在 4K 游戏里是完全正常的。
- **报警的强度由后果决定，不由档位决定**（§5.5）。同样是 L2，0 引用是 `hint`，87 处引用是 `notice`。

---

## 十、落地顺序

L2/L3/L4 **要做**（工具要全面），但每一档都必须先过影响面报告（§5.5）才允许落盘。

| 顺序 | 做什么 | 为什么排这里 |
|---|---|---|
| **P0** | `oversample_of` 认目录（§7.1） | L1 的前置条件；不补它，移了目录工具算错 |
| **P0** | `oversample_advice()` 纯函数 + 卡片提示行（§7.2） | 只读，零风险，立刻能回答"这张要不要处理" |
| **P1** | 「移到 `images/@2/`」动作 + 影响说明（§7.3） | 第一次真正动文件，需要明确的代价提示 |
| **P2** | **影响面 API**（§5.5）：`rename_impact` / `define_impact` | L2/L3/L4 的**共同前置**——没有它，后三档一律不许接线 |
| **P3** | **L2 改名**：检测漂移 + 修复映射（§5.5 的档位下限 `hint`） | 身份层改动，可逆，但要报告 |
| **P4** | **L3 定义层**：比例不适配时才写，复用 `sg_*` 三条护栏 | 唯一往项目里加代码的一档 |
| **P5** | **L4 注入 `at`**：逐处确认 + 逐处可撤 | 唯一改用户 `.rpy` 的档位，最后做 |
| **—** | 不做：原地重烤素材、批量一次确认 | 见 §九 |

**P2 是关键路径**：影响面 API 不做，L2/L3/L4 就只能"先做功能后补报警"，那是本轮讨论明确否掉的形态。所以它排在三个档位**之前**，不是之后。

---

## 十一、给用户的一句话

**这个工具处理超清的正确方式，是"认出来 + 告诉人"，而不是"帮你改代码"。**

- 图已经命名对了（`@2`）→ 工具读对就行（L0）；
- 图没命名但尺寸是整数倍 → 建议移目录，**文件名和脚本都不动**（L1）；
- 图的比例真的不对 → 那是构图，由人决定，工具只负责把 transform 写进它自己的文件里（L3）。

**`.rpy` 从头到尾只写逻辑名，永远不碰。**

## 十二、附：这套"检测层 + 多级提示"已经在别处用上了（2026-10-31 夜）

写这份方案时还不知道它会被复用。当天晚上做"本景还有几处单独改写"时，
`story/override_advice.py` 直接照这套骨架落地了 —— 顺手验证了 §7.2 / §5.5
不是纸面设计：

| 这里的形状 | 那边的落法 |
|---|---|
| §7.2 检测层是**只读纯函数**，永远可跑 | `override_advice(beats, source, kind=, tag=)` 不写盘、不改 Beat、不删行 |
| §7.3 建议层是"人点才动"，默认动作只有一个 | 那边**默认什么都不做**：只报数，连"点一下合并"的按钮都不给（合并 = L4 删行） |
| §5.5 四档 `none/hint/notice/confirm` | 用前三档：0 处 `none` / 1–2 处 `hint` / ≥3 处 `notice`；`confirm` 留给以后真正写盘的那一步 |
| §5.5 "算不出来**降档**，不许升档" | 统计失败 → `hint` + "统计不出"，**绝不当 0 处** |
| §5.5 唯一例外：查"用户是否已有定义"查不到时按**有**处理 | 同一条精神：不知道 ≠ 没有（沉默就是撒谎） |
| §八 判据"报的数字 == 修的数字" | 那边落成一组跨层判据：数出来的每一拍，在舞台快照里确实改了那个 `at` |

所以 §十 那个落地顺序（P2 影响面 API 先于三个档位）也被印证了一次：
**先有"数得准的只读结论"，才谈得上让人按下那个按钮。**
