## 一、P0-2 自动保存 / 崩溃恢复

### 1.1 边界（先把它钉死，不然会越做越大）

这一层只做一件事：**把"内存里的这一章"整份抄到用户目录，崩了下次能拿回来。**

- **不代替导出**：不写用户的 `.rpy`（那要过安全门禁），也不改"改拍 → 导出才落盘"
  这条既有语义。恢复之后状态栏照样是「● 未导出」。
- **不写进项目仓库**：`%LOCALAPPDATA%/StoryGraph/autosave/`，与
  `session_store` / `ai_settings` / `crashlog` 同一处约定。项目里那份要进 git、
  要评审，"我这一分钟改到哪了"不该污染 diff。
- **不自动恢复**：只问一句。替用户决定"这就是你要的"正是丢东西最典型的方式 ——
  她可能已经在编辑器里改过那段了。

### 1.2 存什么：整章，不是差量

```
%LOCALAPPDATA%/StoryGraph/autosave/<项目键 12 位>/<章节键 12 位>.json
{ "version": 1, "root": "…", "chapter": "…", "chapter_rel": "game/script/ch01.rpy",
  "saved_at": "2026-10-23T00:12:03", "source": {"hash": "…", "size": …},
  "dirty": {"changed": 3, "added": 1, "removed": 0}, "total": 284,
  "file_blocks": "init python:\n    …", "beats": [ {…全部字段…}, … ] }
```

差量（只存改过的几拍）看起来省，但它要求"改过的拍能被无歧义地定位"，而定位靠的
`seq` / `line_id` 恰恰是插卡删卡时最先变的东西 —— 一条对不上，剩下全要猜。
整章则永远能还原成**能直接导出**的状态。

实测（`tools/_probe_autosave.py`，真机 `chapter1_4.rpy`）：284 拍 →
**270 KB / dump 3 ms / load 3 ms / 重建 6 ms**，往返之后 **284 拍渲染逐行相同**、
`_beat_edits_print` 全部一致。1800 拍的章节约 1.7 MB / 20–30 ms —— 30 秒一跳，
打字时感觉不到。

原子性：`*.tmp` + `os.replace`。半截 JSON 比没有快照更坏 —— 它会让人以为"恢复过了"。
章节顶层块（`file_blocks`）走 `write(extra=…)` **并进同一次写**，不是"写完再补一刀"
（补写要读-改-写，中途断电会留下"拍在、块没了"的半份快照）。

### 1.3 恢复 = "未导出"，不是"已保存"（这条最要紧）

```
恢复 → beats 被替换 → mark_edits_dirty() → 状态栏「● 未导出」
     → 用户看过 → 点「⤓ 导出 .rpy」→ 那一刻才落盘
```

`take_edits_baseline()` **不能**在恢复之后调：那会把"内存比磁盘新"抹掉，用户
看一眼以为已经写回文件了，随手一关就真丢了 —— 正是这条功能要防的事。
基线（`_saved_prints`）仍然停在**磁盘**那一版，所以 `unsaved_edits()` 报出来的
是"快照比磁盘多了/改了什么"，一句谎都没有。

`line_id` **不许重排**：它是协作库那一行的主键（拍级三路合并的地基）。
恢复时顺手 `_renumber()` 会让同一句换一个新编号，协作那边就看不出"这是同一句"。

### 1.4 源文件变过 → 行号清零

快照记了写它那一刻源文件的 sha1。恢复时拿**现在**的文件比：

- **一样** → 拍的 `src_first/src_last` 仍然有效，导出走增量补丁，未改的行逐字节保留；
- **不一样**（崩溃之后被谁动过）→ 行号**清零**，交给 `patcher._fill_missing_src`
  按内容重新对位。

拿旧行号硬写 = 把改动写到**别人的行上**，而且补丁会报"成功"。

### 1.5 假警报的两次消除

"改了又撤销回去再崩"和"崩在导出成功的下一瞬"，这两种情况下快照与磁盘**没有差别**。
那时弹"有 1 拍没导出"是假警报，而假警报会训练用户闭眼点"恢复" —— 真出事那天也闭眼点。

1. `_recovery_is_noop(entry)`：把快照里的拍重建出来、和**磁盘那一版**逐拍比
   `beat_edits_print`（与导出同一条路渲染）。一样 → 不问，直接清掉。
2. 定时点发现**已经干净了**（撤销回原样 / 刚导出）→ `autosave_clear()`。
   没有这一步，第 1 条就永远是"事后诸葛亮"：快照是在撤销**之前**写下的，
   重启时它确实比磁盘多东西。

### 1.6 界面

- **状态栏**（`AppStatusBar.set_autosave`）：`⏱ 自动保存 00:12`。成功也显示钟点 ——
  一个看不见的自动保存，体验上等于没有这个功能；失败显示 `⚠ 自动保存失败` +
  原因（悄悄失败比没有更坏）。
- **问句**（`_ask_recovery`）：正文是"哪一章 · 改了几拍 · 什么时候存的"，
  三个按钮「恢复这些改动 / 不要了，丢掉 / 稍后（这次先不管）」。
  源文件变过时主按钮改成「仍然恢复（可能盖掉新改动）」并先说清会盖什么。
- **菜单**「🧰 更多工具 → 🕘 上次没导出的改动…」：列这个项目**所有**快照
  （可能改过两章），可恢复或全删。
- **恢复后停在第一处改动**那一拍（difflib 对齐，1800 拍约 160 ms）——
  停在第一拍等于让她自己在 1800 拍里找，"恢复成功了"这件事她不会相信。

### 1.7 谁来写

`window_recover.RecoverMixin`：30 秒一跳，**只在"可见窗口 + 脏"时写**；
导出成功 / 关窗时选了"不保存" / 关窗时本来就没改动 → `autosave_clear()`。
看不见的窗口（测试 / 嵌入 / 启动失败清理）既不写也不弹。

## 二、P0-3 协作锁接线

### 2.1 为什么"锁"值得接（而不是留着当摆设）

`push` 的规则是**被锁着就拒绝提交**（不静默覆盖）。可如果没人上锁，这条规则
永远不触发 —— 两个人照旧同时改同一句，后提交的那个在 `push` 时才发现。

锁的价值不在"挡住别人"，在于**先手**：我改这一句的这 15 分钟里，你提交它会被拒，
而不是我的改动被静默覆盖。

### 2.2 三层，规则一个字没改

```
collab.collab_store     lock / renew_lock / unlock / lock_range / locks   （不动）
        ↑ 薄壳
app.session_collab      collab_lock / collab_unlock / collab_lock_range / collab_locks
        ↑ 界面
ui_qt/dialog_locks.py   「🔒 协作锁（谁在改哪几句）」
        ↑ 入口
window_graph_ops        _more_tools_menu() 的一行 + show_collab_locks()
```

对话框做四件事：**看**（哪一句 · 谁 · 还有几分钟 · 是不是我的）、**占**
（锁住当前这一拍 / 锁住整章）、**收**（续租我的 / 解锁选中的 / 强制解锁）。
强制解锁只有所有者能做，做了进审计。

新加 `collab_store.lock_summaries()` 给列表带**台词摘要**：只显示 `ch01.0007`
人认不出来。`locks()` 的形状不动（CLI 与导出还在用）。

### 2.3 两个实现陷阱（都有用例钉着）

1. **`if self._session:` 遇到 `EditorSession.__len__`** —— 会话没载入章节时
   `len()` 是 0，于是它 falsy。对话框里那句 `self._session.collab_locks(...) if
   self._session else {}` 于是永远走 else 分支，列表永远是空的，**看起来像"没人锁"**。
   改成 `is not None`。
2. **`int(getattr(self, '_loaded_idx', -1) or -1)`** —— **第 0 拍是 0**，
   `0 or -1` 会把它当成"没载入"。于是"锁住当前这一拍"永远回一句
   "先选中一句再回来"，而且看起来一切正常。

### 2.4 顺手堵的一个洞：读锁列表**不许建库**

`collab_store.connect()` 会 `mkdir` + 建库 + 跑 DDL。那对"提交 / 建库"是对的，
对"看一眼锁列表"却是灾难性的：用户手填错一个路径，工具就在那儿悄悄造出一个
空协作库，界面显示"没人锁"。所以 `session_collab.collab_locks` 先判 `is_file()`。

## 三、复核 rename：两个洞（都是"改名被自己的编辑器撤销"）

D3' 的三段式（`plan` → `apply(confirm=)` → `rollback`）确实接进了 Qt，但**顺序**
没人管：

1. **顺序闸**（`dialog_asset_rename._block_if_unsaved`）：手上这一章还有未导出的
   改动时**拒绝改名**。反过来的后果是"先改名、再导出 → 会话把自己那份（还带着
   旧名字）写回去"，而且导出报"成功"。只在"这次改名确实会改到手上这一章"时拦
   （`_touches_current_chapter`）—— 别的章节被改名与这一章无关，不该被无关的改动卡住。
2. **写盘后重读**（`window_assets._after_asset_rename`）：改名成功之后，若当前章在
   `modified` 里就 `load_script(…, goto_card=False)`。不重读的话，卡片页捧着改名前的拍，
   下次导出同样把旧名字写回去。

判据：`tests/test_asset_rename_ui.py` 新增 5 条（脏拦住 / 干净放行 / 别的章节不拦 /
`on_applied` 拿到结果 / 窗口只在"当前章被改过"时重读）。

## 七、给"50 人"这条线的下一步建议

1. **先把写盘路径做扎实**（这一轮做的）；下一步是 **P0-1 三路合并** ——
   它的前提是"每一拍有稳定身份"，这一点在 `line_id` + 自动保存"不重排"
   这一刀之后比之前更稳。
2. **"状态"比"锁"更接近团队流程**：锁解决"同时改"，状态解决"到哪一步了"。
   `set_status` 已经实现（含权限与审计），接线成本与这一轮的锁基本一样。
3. **崩溃恢复的下一步不是"更频繁"，而是"关窗也留一份"**：现在关窗选了
   "不保存"就是真的不保存（用户明确表过态，我们不该偷偷留着）。
   如果团队要"每天下班前自动留一份"，那是一条**项目设置**，不是默认行为。
