## 1. 根因：`clicked(bool)` 被当成槽的第一个位置参数

### 症状

用户原话：「「插入卡片」与「插到前面」效果现在完全一样，插入卡片应当在当前
我选中的卡片条目下往下一条插入，而不是往上一条插入」。

### 定位

语义层是**对的**（`EditorSession.insert_beat(idx, after=True/False)` 一直正确，
`test_editor_session_behavior` 也一直绿）。缺陷在**接线**：

```python
# ❌ 修之前
self._insert_btn.clicked.connect(self.insert_card)          # insert_card(after=True)
# QPushButton.clicked 的签名是 clicked(bool checked = False)
# PySide 把这个 bool 当**第一个位置参数**喂进去 → 实际调 insert_card(after=False)
```

也就是说：**「插入卡片」按钮一直在执行「插到前面」**。两个按钮的落点自然一样。

### 同一类的另外 4 处（静态审计查出来的）

| 位置 | 槽 | 被喂 `False` 之后 |
|---|---|---|
| `_save_layout_btn.clicked` | `save_layout(target=None)` | 不弹「另存为」→ 拿 `False` 当路径 → `TypeError: ... not 'bool'` |
| `_load_layout_btn.clicked` | `load_layout(source=None)` | 同上（不弹「打开」） |
| `_export_flow_btn.clicked` | `export_control_flow(target=None)` | 同上 |
| `act('➕ 新章节', self.add_node)` | `add_node(at=None)` | 不走"放视野中央"→ `float(False[0])` → 点了没反应 |
| `act('🔗 连线', self.add_edge)` | `add_edge(from_id=None)` | 不走"用画布选中的模块"→ 拿 `False` 当节点 id |

**为什么原来的测试没抓到**：`test_ui_qt` 里那两条是**直接调方法**
（`window.insert_card(after=True)` / `(after=False)`）—— 缺陷在接线处，
用例绕开了接线。这是本仓库第三次踩"测试绿了 ≠ 缺陷被钉住"
（前两次：单测停在 `beats_from_parse_result()`；空 label 用例不走 Excel）。

### 修法（两处收口 + 一处检查）

1. **按钮**：`clicked.connect(lambda: self.slot())`（5 处，含插入卡片）。
2. **工具栏**：在 `act()` 这个**唯一入口**里统一包一层
   `a.triggered.connect(lambda _checked=False: fn())` —— 以后往工具栏挂回调
   不会再踩同一个坑。
3. **检查**：`tools/audit_qt_signal_slots.py` —— 静态判据：
   *"槽的第一个可选参数的默认值不是 `False`（Qt 发的就是 `False`）就报"*。
   它**跨文件解析**（槽常在和接线不同的 mixin 里），并且能识别
   `act()` 已经包过 lambda 的情形（把包装去掉会重新报，双向变异验证过）。

### 判据

| 文件 | 内容 |
|---|---|
| `tests/test_qt_signal_wiring.py` | **10 条**：点真按钮 / 触发真 `QAction`，断言落点、断言行数、断言对话框收没收到 `None` |
| 变异验证 | 把 5 处接线改回裸 `connect` → **7 条红**；只把 `act()` 的包装去掉 → `add_node`/`add_edge` **2 条红** |

## 3. 验收时撞到的真缺陷：**第二次原地导出必然失败**

这不是用户报的，是我按流程走第二遍时撞到的 —— 而它正好落在**最常用的一条循环**上：

```
改一句 → 导出 → 再改一句 → 再导出     ← 第二次断
```

**症状**：第二次导出报 `PATCH_FAILED：对位率不足（0%）`（换个样本是 50%），
文件不动、用户不知道下一步做什么。

**根因**：第一次写回之后，**磁盘上那一份**已经是新内容（补丁插了几行、首行多
了生成标记），而内存里的 `src_first/src_last` 还是**改动前**那份文件的。
`_recover_ranges` 见"拍上已经有行号"就**跳过重算** → 对位率掉下去 →
补丁失败 → P0 那条"目标就是源文件"的护栏拒写。

**修法**：原地导出成功后按**刚写出的那份文件**重贴行号
（`session_export._resync_source_ranges`）。只同步行号，不动内容 ——
内容以内存为准，而磁盘刚刚正是按内存写的。

**判据**：`tests/test_export_acceptance.py::test_7_two_in_place_exports_in_a_row`
（P0 验收矩阵新增第 7 条）。变异验证：去掉重贴 → 该条红，且**产物丢掉
`default score` / `transform my_tf:`**（截图式的失败证据）。

顺带把"拦下时不告诉你怎么办"补上了：`PATCH_FAILED` 现在附三条能走的建议
（重新载入这一章 / 换个路径导出 / 备份后明确覆盖）。

**为什么最终选了"重新解析"而不是"重贴行号"**（走过的弯路，记下来）：
第一版我用 `recover_source_ranges`（解析磁盘 + difflib 对拍）贴行号，
它在最需要它的那个场景上**是错的** —— 解析器会把"注释 / `call screen` +
紧随其后的台词"吸成**一张**拍，而内存里是**两张**，对齐于是给出**交叠区间**
→ 对位率 50%（whackamole 实测）。合并**本来就知道**每一拍写到了哪几行，
但把它报出来要动 `patch_export` 里"替换 / 插入 / 删除"三套坐标系的换算
（全仓最危险的一段）。"内存 := 解析(磁盘)"是**零启发**的：磁盘就是真源
（契约 A1），解析器怎么读、内存就怎么存，两者永远一致。

## 7. 三条缺口的消除（2026-10-05 续）

主题一句话：**让软件自己解决，而不是回头提醒用户**。所以三条都不是"加一句
更清楚的警告"，而是把"会出问题的那件事"从根上消掉；"报错"只留在**兜底**位置。

### 7.1 UI 的导出也能说出"丢了哪几行"

**做法**：`EditorSession.export` 把**源文本**交给 `write_generation`
（`source_text=self._source_text_for_guard()`）。那条门禁的判据本来就是
"源里有、产物里没有的顶层语句"，不给源就无从说起 —— CLI 一直传了，编辑器一直没传。

**判据**：`tests/test_file_level_opaque_blocks.py::TestEditorExportNamesTheLoss`
（3 条：指名道姓 / force 放行但仍报 / **反面对照**——保真时不许拦）。
变异验证：把 `source_text` 改回 `None` → 第 1 条红。

### 7.2 只有注释/代码的拍不再"对不上位"

**症状**：改一句 → 导出 → 再改一句 → 再导出，**第二次必失败**
（`PATCH_FAILED：对位率不足 0~50%`），而提示没告诉用户下一步做什么。

**根因**：第一次写回之后磁盘变了（补丁插了行、首行多了生成标记），
内存里的 `src_first/src_last` 还是**改动前**那份文件的。

**做法**：原地写回成功后**重新解析刚写出的那份文件**（内存 := 磁盘，
契约 A1 的直译）。零启发 —— 不用猜行号、不用 difflib 对拍。
（第一版正是用对拍，在"注释卡 + 台词卡"这种粒度变化上给出交叠区间、
对位率 50%；走过的这条弯路写在 §3 末尾。）

**连带**：`resync_after_export` 让卡片列表跟着刷新（拍数变了才动，
不打扰最常见的"改一句再导出"）。

**判据**：`tests/test_export_acceptance.py::test_7`（变异：去掉重解析 →
产物丢掉 `default score` / `transform my_tf:`）+ `tests/test_qt_signal_wiring.py`
的两条列表跟随用例。

### 7.3 第三类内容**整个顶层区间**随表走

**做法**：解析器按**原文**收下整个顶层区间
（`renpy_parser._top_level_region` → `TopLevelRegionNode` → `ParseResult.file_blocks`），
渲染时在所有 label 之前原样写回。覆盖 `define` / `default` / `image` /
`transform` / `screen` / `style` / `init:` / `translate` / `init python` / 文件头注释。

**路上踩到的三个真问题**（都有用例钉住）：

| 问题 | 现象 | 修法 |
|---|---|---|
| **Excel 单元格 32767 上限** | 真实文件的顶层区间 38492 / 50426 字符，塞进隐藏列**静默截断**到 32767 | 改走**隐藏表**「文件级保真」，一行一格（`FILE_BLOCK_SHEET`）；老表的隐藏列仍可读（只读兜底） |
| **`init python:` 块里夹着顶格注释** | `ball_moving_game.rpy` 就是 `init python:` / `# 类/对象设置` / `    class GridCell:`；注释被当成新的一段 → 块头丢了，产物里出现悬空缩进 | 顶格注释在"块头以 `:` 结尾"时**并入当前段**（Ren'Py/Python 都忽略整行注释的缩进） |
| **基准缩进被顶格注释拉到 0** | 去缩进失效 → 渲染后 `import random` 变 8 格、注释 4 格 → **unexpected indent**，`init python:` 整块语法坏 | 基准只看**结构性行**（注释不参与）；缩进小于基准的行原样保留不切片。这一条是 `PYTHON_SYNTAX_ERROR` 门禁**拦下来**的（`journey_check` 第 2b/5 步），没有静默写出去 —— 门禁在这里正好证明了它的价值 |

**判据**：`tools/probe_opaque_fidelity.py`（40 个真实文件逐个走
`.rpy → 拍 → xlsx → 读回 → 渲染`，顶层语句丢失 **0 处**；改之前 4 个文件 / 219 处）；
`tools/journey_check.py` 第 8 步两条路都 `[PASS] … 丢 0/13 处`（改之前全量丢 11/13）；
`tests/test_file_level_opaque_blocks.py` 26 条（含"超长往返不许截断"、
"注释夹在块中间缩进不许算错"、"块体为空不许写半截块"）。

**副作用（好的那种）**：`OPAQUE_LOST` 门禁从"每次全量都拦人"退化成**兜底** ——
哪条路又漏了才会响。这正是"软件自己解决"的样子：把人从警告里解放出来，
同时不放弃"沉默地丢东西"这条底线。

## 8. 追查：「导出控制流」那两个菜单项，说法对不对？（2026-10-05 追加）

有人报："「导出控制流」两个菜单项全部失效"，理由是

```
window_graph_ops.py:462   lambda: self.export_control_flow(wrapper=True)
window_graph_ops.py:464   lambda: self.export_control_flow(wrapper=False)
而签名是 (self, target=None, wrapper=None) —— wrapper 是第二个位置参数，
于是 False 落进了 target：str(False) → 当路径写盘 → 根目录长出名叫 False
的文件 → 紧接着 Path(False).is_file() 抛 TypeError。
```

**结论：症状是真的，归因是错的。** 分三段说清。

### 8.1 症状确实存在（有物证）

仓库根目录里今天还躺着一个名叫 `False` 的文件：

```
False   178 字节   创建 / 修改时间 2026-10-04 17:56:52   git 里是未跟踪状态
内容：前 6 行就是控制流产物 ——
      # 由剧情编辑器自动生成的控制流（请勿手动修改跳转部分）
      label a_control:
          call a
          jump b_control
```

也就是说：**确实有一次导出把 `False` 当成了路径**，而且写成功了。

### 8.2 但那两个菜单项不可能是凶手

菜单项的写法是 `export_control_flow(wrapper=True/False)` ——
**关键字传参按名字绑定**，`wrapper` 排第几位都不可能落进 `target`。
把 `wrapper` 改成关键字专用（`*`）是**加固**，不是修 bug：
改之前那两行本来就是对的。

**实测**（`tools/probe_flow_export_bool.py`，点真 UI、桩掉文件对话框）：

```
A `export_control_flow(wrapper=True)`  → 对话框弹了；产物有
A `export_control_flow(wrapper=False)` → 对话框弹了；产物有
```

两个菜单项**都正常**，与"全部失效"相反。

### 8.3 真正的原因：Qt 把 `bool` 顶进了第一个位置参数

`QPushButton.clicked(bool checked = False)` / `QAction.triggered(bool checked = False)`
—— 槽的**第一个位置参数**收到的就是这个 `False`。而当天那条接线是：

```python
self._export_flow_btn.clicked.connect(self.export_control_flow)
#                                          ^ 直接 connect → export_control_flow(False)
```

`False` 落进 `target` 之后，槽里的判据是

```python
if target is None:      # ← 不是 `if not target`
```

而 `False is None` 是 `False` → **"没给路径就弹另存为"那条分支被绕过** →
`False` 被当成路径一路送到会话层 → `str(False)` = `"False"` → 工作目录里
多出那个文件。**这才是那份报告描述的现象，只是接线点认错了。**

（会话层现在有 `isinstance(target, (str, Path))` 硬护栏 → 就算绕过也只会
报"导出路径不是路径"，不再写垃圾文件。）

### 8.4 修了什么

| 层 | 改动 | 为什么 |
|---|---|---|
| 接线（早已修） | `clicked.connect(lambda: self.export_control_flow())`；`act()` 统一包 lambda | 让 Qt 的 bool **根本没机会**进槽；静态审计 `tools/audit_qt_signal_slots.py` 守着 |
| **槽的入口（本次）** | 新增 `ui_qt/qt_args.drop_qt_bool`，5 个槽的入口先用它：`save_layout` / `load_layout` / `export_control_flow` / `add_node` / `add_edge` | "任何一条路径把 bool 送进来"都按"没给"处理 —— **自愈**（该弹对话框就弹），并留一笔 `swallow` 痕迹。只丢布尔：别的错类型照旧往下走、该炸就炸 |
| 注释（本次） | 更正 `window_graph_ops.export_control_flow` 的 docstring 与 `session_graph` 的说明 | 那两处把原因写成"`wrapper` 第二个位置参数串位"，会误导下一个人（**报告不照单全收**） |
| 物证（本次） | 删掉根目录那个 `False` 文件 | 它是已修 bug 的残渣（内容与时戳已抄进本节存档） |

**实测（修之后同一个探针）**：

```
B `export_control_flow(False)`（= 裸 connect 的等价物）：
     没抛异常；对话框**弹了**；按用户选的路径正常写出
```

**判据**：`tests/test_qt_signal_wiring.py::TestQtBoolIsNeverAnArgument`
（5 条：只丢布尔 + 5 个槽都接了兜底 + bool 进来照常弹对话框 + add_node 不炸 +
add_edge 退回"画布选中"）。变异验证：去掉那 5 行 → **4 条红**。

**顺带纠正一处判断**：`graph_canvas.zoom_by(at=…)` 与
`window_keyboard._remove_shortcuts` 里的 `if … is None:` **不是**这一类
（前者从没接过信号、`at` 由滚轮事件显式传；后者那个 `target` 是循环变量），
所以没给它们加兜底 —— 判据要落在"真会收到 Qt bool 的槽"上，不是见 `is None` 就加。

### 8.5 那个"加固"改坏了一个调用方（完整性起见记一笔）

`wrapper` 改成关键字专用**不是纯增量**：它动了一个公开方法的签名，
而**有人按位置传参** —— 跑全量测试当场红了两条：

```
TypeError: GraphOpsMixin.export_control_flow() takes from 1 to 2
           positional arguments but 3 were given
```

来自 `tests/test_main_window_snapshot.py` 的黄金快照驱动：

```python
_public(win, 'export_control_flow', str(cf), None)      # ← wrapper 走了位置
```

**产品代码里没有第二个位置传参的调用方**（扫全文确认：UI 的调用点要么只传
`target`、要么 `wrapper=…`；`session_graph.export_control_flow` 是另一个方法）。
所以只有测试这一处 → 改成 `wrapper=None`，并给 `_public` 加上 `**kwargs`
支持关键字专用参数。**黄金快照不需要重新录** —— 改回关键字之后记录的
仍是原来的值（这本身就证明了那个 TypeError 是位置传参造成的）。

**教训**：改签名要扫**全部**调用方（`grep 'export_control_flow('`），
否则改的人只看到"更安全了"，看不到别人已经断了。而这次替我们扫出来的是
黄金快照 —— 它红了两条，一条报 `TypeError`、一条报"文件没生成"。
