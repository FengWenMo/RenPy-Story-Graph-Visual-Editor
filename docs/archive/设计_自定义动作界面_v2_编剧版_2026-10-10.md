# 设计方案：让**编剧**也能看懂的自定义动作界面（v2）

> **这一版要解决的问题**（用户 2026-10-10 截图评审，原话）：
> > 坏了……作为一个程序我都看不明白你写的东西……我不会用！！！你更别提编剧了……
> > 而且你这个参数表非常丑，一旦遇到多个参数一点也不方便，一行只能显示一个……
> > 而且 with，window,pause 一类的不都是默认的关键字吗？emm……你确定你这个工具的
> > 通用性足够强？？？而且你说的这个候选值其实非常繁琐！有多少动作我也不知道，
> > 都在表格内部的……这样吧……重新设计它，先写一版新的设计方案……让这个界面做到
> > 编剧也能听懂

v1 的三个病（逐条对着截图认）：

| # | 病 | 证据 |
|---|---|---|
| ① | **用词是实现者的语言** | `语句名` / `参数（会成为表格列）` / `attr_groups` / `rules.json` / `Describe` / `T1 通用行` / "候选值" —— 编剧一个词都不认识 |
| ② | **参数表一行只显示一个，而且被裁切** | 截图里参数区只有 `mood / 神态 / （空）` 一行，字被切成两半；想加 3 个参数要拖小滚动条 |
| ③ | **把内置关键字当"工具不认识"** | 表里赫然写着 `with`(39) / `window`(9) / `pause` / `I` —— 这些是 Ren'Py 内置语句，`with/pause/window` 甚至是**工具自己已经声明过参数**的叶语句 |

③ 已实测确认（`tools/probe_discover_noise.py`）：

```
工具**认识**的语句头里： with=True  window=True  pause=True  play/show/scene/hide=True
工具**自己声明过参数**的叶语句： ('with', 'pause', 'window')
→ 它们出现在"待声明"列表里，是**我的发现闸门漏了**，不是项目缺声明。
```

### ③ 已经造成真实后果（2026-10-10 真项目核查）

真项目 `sr_general` 的"待声明"列表**一共只有 3 行**，其中两行是噪声：

```
with    x39   ← Ren'Py 内置（转场）
window  x9    ← Ren'Py 内置（开关对白框）
l       x1    ← 是那句台词 `l oh "3"` 被误读成动作
```

更严重的是：**真项目根目录下已经有一份被这个界面误导着写出来的声明**
（文件创建时间 2026-10-10 19:47）：

```json
{"statements": [{"name": "pause", "label": "等待",
                 "columns": [{"name": "pause", "label": "等待"}]}]}
```

`pause` 是 Ren'Py **内置**语句（`pause 1.0`，时长本来就是它的参数），
**根本不需要声明** —— 是工具把人教错了。这一条从"体验问题"升级为
**"工具在输出错误的知识"**，必须在 v2 里堵死（§六 闸门①②）。

⚠ 另外要注意：`with`/`window`/`pause` 的高计数很多来自 Ren'Py **模板/界面文件**
（`screens.rpy`、`eyes_tracker.rpy` 这类）。它们不是剧情章节，本就不该出现在
"要认识哪个动作"里 —— v2 的发现还要**跳过模板/界面文件**（或至少标注来源文件，
让人一眼看出"这是模板里的"）。

## 一、先定"谁在用、在哪用、要什么"

| 角色 | 他关心什么 | 他不关心什么 |
|---|---|---|
| **编剧** | "我要在剧情里让林月见换泳装"、"这句台词的表情换成生气" | 语句名、参数名、JSON、表格列、T1/T3 |
| **程序/技术策划**（第二用户） | 一次定义、全项目复用、可评审可 diff | 每个参数的长解释 |

**所以主路径必须是"从剧情出发"**：编剧在卡片上想加一个动作 → 界面给出**能选的动作清单**（用中文名）→ 他要填的每一项都有**例子和候选** → 点"加进这一拍"。

**声明**这件事是**副产品**：编剧第一次用 `swim_suit` 时，界面顺手问一句
"这个动作工具还不认识，给它起个中文名、告诉我它要填什么，以后就能在下拉里选"
→ 答完落成一份文件（可评审、可 diff），**从此所有人（包括编剧）都只用下拉**。

## 二、界面的三段式（一屏看得完，不用左右对照）

v1 是"左=发现 / 右=填表"的双栏，编剧不知道该看哪边。v2 改成**单栏三段**：

```
┌─ 让工具认识一个新动作 ─────────────────────────────────────────────┐
│                                                                    │
│ ① 要认识哪个动作？                                                   │
│    ┌──────────────────────────────────────────────────────────┐    │
│    │ ● swim_suit   "泳装切换"   用了 12 次   例：swim_suit 林月见 "泳装" │
│    │ ○ rainy      "下雨"       用了 3 次    例：rainy 0.5          │    │
│    └──────────────────────────────────────────────────────────┘    │
│    （只列**真正不认识**的动作；内置的 with/window/pause 已经会了，不在此列）│
│    没找到？[ 手动输入动作名… ]                                       │
│                                                                    │
│ ② 给它起个编剧看得懂的名字                                            │
│    在编辑器里显示为：[ 泳装切换          ]   ← 编剧就点这个           │
│    一句话说明（可空）：[ 换角色立绘/服装         ]                    │
│                                                                    │
│ ③ 这个动作要填什么？（工具已经从你写过的 12 次里猜出来了，改改就行）      │
│    ┌────────────────────────────────────────────────────────────┐  │
│    │ 第 1 项  名字[ 角色  ] 例[ 林月见 ▾ ]   ☑ 只能填这些：林月见 沈青 │  │
│    │ 第 2 项  名字[ 服装  ] 例[ 泳装   ▾ ]   ☑ 只能填这些：泳装 校服  │  │
│    │ 第 3 项  名字[ 表情  ] 例[ 开心   ▾ ]   ☐ 随便填               │  │
│    │                                        [＋ 再加一项] [－ 删这项]│  │
│    └────────────────────────────────────────────────────────────┘  │
│                                                                    │
│ ④ 以后在编辑器里长这样（下面这块就是**真实控件**，编剧能直接试）          │
│    动作 [ 泳装切换 ▾ ]  角色 [ 林月见 ▾ ]  服装 [ 泳装 ▾ ]  表情 [ 开心 ▾ ]│
│                                                                    │
│                              [ 就这样，教会它 ]   [ 算了 ]           │
└────────────────────────────────────────────────────────────────────┘
```

要点（每条都对着一个病）：

- **① 只列不认识的** → 治病 ③。闸门：`词表认识的` / `工具自己声明过的` / `说话人 + 台词被误当动作` 三种一律不列。
- **② 中文名是主字段**：编剧看到的、选的、说的都是中文名；动作名（`swim_suit`）**收进"技术细节"小字**，可展开不可默认展开。
- **③ 每一项一行、竖向排版**（不是三列表格）：一行装"第几项 + 名字 + 例子 + 是否限定"，**多少项都放得下**（滚动的是这个区，不是整页）→ 治病 ②。
- **例子与候选都是从真实脚本里抠出来的**（见 §三）→ 治"有多少动作我也不知道"。
- **④ 现场预览真实控件**：编剧在按下之前就能点点看，不用想象。

## 三、关键机制：**从真实脚本反推"这个动作要填什么"**

这是"编剧也能懂"的技术支撑 —— **不让任何人手填参数名**。

对每个待认识的动作，扫它在项目里**真实出现过的那些行**，按 Ren'Py 的写法反推每一项：

| 脚本里长这样 | 反推出的一项 | 界面上的话 |
|---|---|---|
| `"泳装"`（引号包着） | 第 1 项，例值 `泳装` | 名字默认「服装」？→ 不猜，默认 `第1项`，让编剧改名 |
| `mood=happy` | 名字 `mood`，例子 `happy` | 名字直接可用（作者自己写的） |
| `0.5` / `3`（裸数字） | 名字 `时长`？→ **不猜**，默认 `第2项`，标"数字" | 编剧改名 |
| `林月见`（裸词，且是角色表里的 ID） | 名字默认「角色」，候选=角色表 | 编剧一眼认出来 |

**候选值**（"只能填这些"）的来源，按可信度从高到低：

1. **同一个动作在项目里出现过的所有值**（`swim_suit` 出现 12 次 → 收集到
   `泳装/校服/便装/浴衣`）—— 这是最贴合项目的，**不需要用户手打**；
2. 若那一项是**角色**（值命中角色表 / 被引号包着且像人名）→ 候选 = 角色表的显示名；
3. 若那一项取自**资源表列**（例如 `Tag=` 的取值）→ 候选 = 该列去重值；
4. 用户在界面里**补充**（第一版先给出 1–3 的结果，手输只是补充手段）。

⚠ 判据：**猜不出就不猜**。默认名字用「第N项」，宁可让编剧改一次，也不要猜成
`intensity` 这种他看不懂的东西。

## 四、"有多少动作"这件事要能被回答

编剧的诉求是"我不知道有哪些动作可用"。所以除了"发现不认识的"，还要有
**一个可浏览的清单**（同一个窗体的第二个标签页，或主界面另开）：

```
┌─ 动作清单（本项目） ─────────────────────────────────────────┐
│ 编剧看到的名字      动作名        要填什么              谁在管      │
│ 泳装切换           swim_suit    角色 服装 表情         本项目声明   │
│ 下雨               rainy        强度                  本项目声明   │
│ 淡入淡出           with         效果                  工具自带     │
│ 停一拍             pause        时长                  工具自带     │
│ 显示/隐藏对白框     window       show/hide             工具自带     │
│ 播放音乐           play         音乐 淡入淡出          工具自带     │
└──────────────────────────────────────────────────────────────┘
                                     [ 导出这张表给编剧 ]
```
- **工具自带的**（`with`/`pause`/`window`/`play`/`show`/`scene`/`hide`/`menu`/`jump`…）
  也列出来，并且**标注"工具自带"** —— 这样编剧才知道"原来这些不用声明，本来就能用"。
- 一栏"谁在管"把 **本项目声明** 与 **工具自带** 分开，直接回答"通用性够不够"这个问题。
- 「导出这张表给编剧」= 一份 Markdown/CSV（中文名列在前），编剧不用装工具也能看。

| v1（截图里的） | v2（编剧看的） | 备注 |

| 中文名 | 在编辑器里显示为 | —— |

## 六、要做到"通用性足够强"，这一版要补的闸门（判据）

| 闸门 | 规则 | 判据 |
|---|---|---|
| 内置语句不进"待认识" | `statement_head_token(t) ∈ RENPY_KNOWN_HEADS` → 不列 | 真机与样例：`with/window/pause/play/show/scene` 都不出现 |
| 工具自带参数的叶语句不进 | `head ∈ LEAF_ARG_HEADS`（`with/pause/window`）→ 不列 | 同上（`pause` 曾出现在 v1 列表里） |
| **已声明的内置语句要能被纠正** | 若清单里出现内置语句的声明 → 动作清单里标 **"这个其实不用声明"**，并提供**一键移除** | 真项目现有的 `pause` 声明能被指出来并清掉 |
| 模板/界面文件降权 | `screens.rpy` / `*_tracker.rpy` / `options.rpy` 这类不算"剧本里的写法"（至少标出**来自哪个文件**） | `with x39` 的来源能被看见，不再被当成剧本用法 |
| 说话人+台词被误读的不进 | 该行**没被任何分支接住**、且形状像 `名字 属性 "台词"` → 归到"疑似写错"，**不给"声明"动作** | `l oh "3"` 命中；给的是"这行像台词/说话人写错了"的提示 |
| 只出现一次且名字极短（≤2 字符）的 | 列出但**标注"可能只是写错了"**，默认不选中 | `l` 落在此类 |
| 候选值来源 | 真实出现过的值 → 角色表 → 资源表列 → 手输 | `swim_suit` 12 次 → 4 个服装候选，无需手打 |
| 猜不出不猜 | 反推不出名字的项默认 `第N项`，**绝不生成英文臆测名** | 裸数字项默认名 ≠ `intensity` |

## 八、验收（编剧视角，人拿着这份单子就能验）

### V2-1 落地记录（2026-10-10）

| 做了什么 | 结果 |
|---|---|
| `_is_builtin_head()`：词表已知 ∪ 容器头 ∪ `with/pause/window` 叶语句 → **不列** | 真项目"待认识"列表 **3 → 0**（`with x39` / `window x9` 消失） |
| 语句头必须是合法标识符（首字符不能是数字/符号） | `$`/数字开头的东西不再混进来 |
| `_looks_like_dialogue()`：**先问角色表** | `l oh "3"` 判成"**这是台词**"（`l` 是角色「蓝」的 ID，真项目 `script.rpy:94`） |
| 每条候选带 `files`（来源文件）+ 样例带 `文件名:行号` | 看得到 `with` 那类计数来自哪个文件（模板/界面文件一目了然） |
| `declared_builtins()`：指出"这条其实不用声明" | 真项目那条 `pause` 被准确指认 |
| `remove_statement()`：先备份 → 再移除；空清单删文件 | 真项目已清理：`storygraph.rules.json` 删掉，**备份留在 `storygraph.rules.backup/`** |

⚠ 两个当场抓到的自己的错（都值得记）：
① `_looks_like_misread_speaker_line` 只按"名字≤2字符 + 行里有引号"判，
   把 `l oh "3"` **误诊成"你可能写错了"** —— 而 `l` 是角色表里的角色，
   那是台词。**骂错人比不提示更糟**，所以判据先问角色表，措辞也改成陈述事实。
② `Statement.source` 是 `(路径, 行号)` **元组**，我按纯路径取 → 样例显示成
   `ch01.rpy', 2)` 这种垃圾（判据当场抓到）。
