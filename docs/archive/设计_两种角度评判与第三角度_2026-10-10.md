# 两种角度的客观评判 + 第三个角度
### —— 反推（扫描）vs 定义驱动，谁更适合这个工具？

> 2026-10-10 ｜ 触发：用户提出两个角度，并给出一张对比图，结论倾向"定义驱动"。
> 本文**不照抄那张图**：它有几条是对的，有两条是误导的，还漏了一条最关键的。
> 全篇仍然遵守"说人话 + 每个观点附理由"的约定。

---

## 一、先把问题归一：这两个角度**不是二选一**，是一条环的两半

你说的两件事其实在回答**两个不同方向**的问题：

| 角度 | 它在回答 | 方向 |
|---|---|---|
| **方案一 扫描反推** | "已经在脚本里写下的东西，工具怎么读懂" | **向后看**（原文 → 工具） |
| **方案二 定义驱动** | "新内容怎么被写出来" | **向前看**（定义 → 产物） |

它们在软件工程里有正式名字，叫 **往返工程（Round-trip Engineering, RTE）**。
而 RTE 的权威定义里有一句话，正好用来纠那张图的偏：

> **"往返工程常被错误地定义成'同时支持正向和反向工程'。真正的特征是：
> 让两个各自演化的产物，通过**增量更新**互相反映对方的变化。"**
> —— Wikibooks / TU Tampere 硕士论文（见 §八）

**为什么这句话重要**：它意味着"扫描"和"生成"**不是对手，而是同一条流水线的两端**；真正决定成败的不是选哪端，而是**中间那份"规则"从哪来、怎么保证它不过期**。

**结论（先说这一条）**：所以正确的问法不是"选方案一还是方案二"，而是
**"规则的真源放在哪、由谁维护、过期了谁来报警"**。这才是三个角度的分水岭。

## 二、逐条评判那张对比图

### 说得对的（我认同）

| 图里的观点 | 为什么对 |
|---|---|
| 方案二"**冷启动**（新项目）不依赖历史样本" | 真的。没有样本时方案一什么都推不出来。 |
| 方案二"**开发者写的是生成器**，不必处理无穷无尽的写法" | 真的，而且这跟本项目已有的结论一致：**生成比解析简单**。解析要面对"有人多打了个引号"，生成只按模板拼。 |
| 方案二"**新动作来了加一行**" | 真的，这是它最大的成本优势。 |
| 一句话概括那两句（"学会一门还在变化的方言" vs "按官方术语表说话"） | 这个比喻很准，**而且它指出了要害：谁是"官方"**。 |

### 是误导的（必须纠正）

**误导一："真源在哪"这一行搞错了层。**

图里写：方案一真源"分散在历史脚本里"，方案二真源"集中在定义文件中"。

**但这件事在本工具里根本不成立** —— 本项目的**一号铁律**是 `.rpy` 是唯一真源、逐字节保真。
**内容**的真源**永远是剧本**，方案二永远拿不走它。

那方案二集中起来的是什么？是**"形状"（schema）**：这个动作叫什么、要填几项、每项什么候选。
**内容真源 ≠ 形状真源**，这是两层，不打架。图里把它们并列成"真源之争"，是拿苹果比橘子。

**误导二：把方案二的成本说成"免费"，漏掉了它自己的死穴 —— 漂移。**

图里方案二那一行写："程序改了语法 → 改定义表里一行模板"，语气像是举手之劳。
**但真正的问题是：谁来记得改？改了怎么知道改对了？**

定义表是**人手维护**的，引擎代码是**程序手改**的，这两份东西**没有任何机制保证同步**。
半年后程序给 `swim_suit` 加了一个参数、改了一个参数名，定义表还是旧的 ——
于是工具**自信地**按旧定义生成字符串，产出"工具觉得对、引擎不认"的垃圾。

**这正是整个 API 工业界（Protobuf / GraphQL / OpenAPI）最贵的一课**：
它们的方法是 **schema-first（契约先行）+ CI 里卡漂移**，原文说得很重：

> "契约不能在实现里**静默漂移**，因为实现是从契约生成的、或对契约校验的。"（见 §八）

**所以图里方案一那一行"程序改了语法 → 需要重新扫描、重新反推"，被写成了缺点，其实它是解药** ——
**扫描就是那个漂移探测器。** 没有它，方案二的过期你永远发现不了。

**漏掉的一条（最关键）：方案二的产物，工具自己验不了。**

方案二说"生成器只读定义表，拼字符串"。可如果定义写错了（少一项、参数名拼错），
工具**没有任何能力发现**，因为它**本来就不懂这门语法**。
所以方案二必须配一个"**写出去、让引擎/lint 检查**"的回路 —— 这一点图里完全没有。

## 三、三个角度的本质：**"规则从哪来"**

把两个角度放到一根轴上，第三个角度自己就浮出来了：

| | 角度一 · 反推 | 角度二 · 定义驱动 | **角度三 · 契约驱动** |
|---|---|---|---|
| 规则从哪来 | 从**示例**里归纳 | 由**人**手写声明 | 从**宿主（引擎）**读 |
| 学术名 | 语法归纳（grammar inference） | 声明式/模式驱动（schema-first） | 宿主注册表 / 框架契约（framework API） |
| 靠什么 | 统计 | 承诺 | **权威** |
| 冷启动 | ❌ 无样本即失效 | ✅ 定义即起点 | ✅ 引擎就有 |
| 会不会漂移 | 不适用（它就是探测器） | ⚠️ **会，且没人发现** | ✅ 结构上不会 |
| 会不会过度泛化 | ⚠️ 会（多列/少列都可能） | 不适用（人写的） | 不适用 |
| 谁来维护 | 没人（自动） | **人（易忘）** | 程序（写引擎时顺手） |

**关于角度一，学术界已经给了结论**（正好印证"让编剧确认"是对的做法）：

- 从样本推断 DSL 语法**是可以成功的**，但**必须有负样本 + 人来纠正**，否则会"过度泛化"（推出多余规则）或"欠泛化"（漏规则）；
- 推断**通用编程语言**的语法至今"对现有算法来说太复杂" —— 但 **DSL 更小更简单，成功率高**；
- 最新研究（Autogrammar）已经转向"**文档 + 执行日志**一起学"，而不是只看样本 —— **也就是：回到契约/说明上去**。（见 §八）

**所以三个角度不是三选一，而是三件事各就各位：**
> **角度一是"探测器"，角度二是"写作面"，角度三是"权威源"。**

## 四、第三个角度具体是什么：**契约驱动**

一句话：

> **规则的真源不是历史脚本、也不是人手写的定义表 —— 而是引擎自己公布的那份声明。
> 定义表是它的"人话翻译 + 缓存"，扫描是它的"校验器"。**

**机制（正反两向共用同一份契约）**：

```
        引擎自己公布的契约（Ren'Py CDS / Unity-Yarn 命令特性 / 你写的清单）
                              │   （这是唯一真源）
              ┌───────────────┴───────────────┐
              ▼                               ▼
      向下：定义 → 控件 → 拼串          向上：定义 → 识别 + 校验
      （编剧在这边写作）                （读老脚本 + 对用法报警）
              └───────────────┬───────────────┘
                              ▼
                    扫描真实脚本：发现 + 验漂移
```

**这个角度的强处，正好补掉前面两个角度的死穴**：
- 方案二会漂移 → **契约就是引擎的代码本身**，程序改引擎时顺手就改了契约，结构上没法漂；
- 方案一没样本就失效 → **契约不依赖样本**，冷启动没问题。

**它不是我编的，文献里有两条独立出处**：

1. **往返工程文献**：最可行的一种 RTE 是"**框架 API**"形态 ——
   > "**API 规定了框架被正确使用的所有方式**，因此可以**精确、完整地**识别代码里的 API 用法，也能生成正确的用法代码。"
   （Wikibooks: Round-trip Engineering）
   —— 这就是"引擎为源，正反两向都变精确"。

2. **API 工业界（schema-first）**：
   > "把**机器可读的契约**作为唯一真源……实现由它生成或对它校验……**契约就不能在实现里静默漂移**。"
   （Contract & Schema-First Design / Protobuf·GraphQL·OpenAPI 的 CI 门禁）

**而且这个角度正好是"能迁 Unity"的那把钥匙**：因为跨引擎的注册机制**就是**契约本身 ——
Ren'Py 用 `renpy.register_statement(...)`；Yarn Spinner 用 `[YarnCommand]`；Naninovel 用 `[CommandAlias]`。
**同一个思路，三个引擎都有。** 你昨天问"凭什么撑 Unity 迁移"，答案就在这里：
**谁做了契约，谁就能被任何引擎读懂。**

## 五、结论：哪个更符合**这个**工具

**分三层回答，不是单选。**

### 主干 = 角度二（定义驱动）
**理由**：你这个工具的真实瓶颈是 **"编剧写剧本"**，不是"工具读剧本"。
写作面要的是"点几下就有控件"；生成（读定义 → 摆控件 → 拼串）**比解析简单得多**；
冷启动不依赖样本。行业同构：**Naninovel 声明命令 → 编剧用 `@command`；Yarn 写定义文件 → 编剧有补全**。
**"让工具学会一门还在变化的方言"确实是错的思维 —— 写作面应该按"官方术语表"说话。**

### 上游 = 角度三（契约驱动）
**理由**：定义表**不该是人手写的**（会忘、会漂），最好**由引擎/程序产出**。
这也是唯一能同时做到"不漂移 + 冷启动 + 跨引擎"的形态。
**对你这一个项目**：真机 `sr_general` 里**目前 0 个 CDS** —— 所以这条今天还没有输入。
但它是**方向**：工具应该**主动提示/引导程序"给自定义语句加一句注册"**（一句 `renpy.register_statement`，成本极低，收益是工具永久认识它）。

### 护栏 = 角度一（扫描），**只做两件事**
1. **发现**：扫出"你在用、但还没声明"的写法（这就是"有多少动作我也不知道"的答案）；
2. **验漂移**：声明说"要填 2 项"，可真实脚本里出现了第 3 项 → **报警**。

**它绝不能当真源** —— 因为归纳会过度泛化，而"猜错就是改剧情"。
**它只在"人点头"之后才有资格变成定义。**

### 一句话结论
> **写作面用方案二，规则来源用角度三，方案一降级成"发现器 + 漂移探测器"。**
> 三者共用一份契约，所以"读一套、写一套"在结构上不可能发生。

## 六、这对你的项目具体意味着什么

**好消息**：这三件东西**你的项目已经有了，只是地位没摆正**。

| 角度 | 项目里是谁 | 现在的地位 | 应当的地位 |
|---|---|---|---|
| 角度三 契约 | `story/cds_registry.py`（读 `renpy.register_statement`） | 已做，但藏在体检报告里，没人知道 | **提升为定义的首选来源 + 界面上明确提示"让程序加一句注册"** |
| 角度二 定义驱动 | `storygraph.rules.json` 的 `statements[]` + `spec_args` 动态列 + 卡片参数控件 | 已做，但界面是"程序话" | **主干：唯一入口，全中文** |
| 角度一 扫描 | `statement_registry.discover_undeclared()` | 已做，被当成"另一个入口" | **降级为后台：只负责"发现"和"报警"，不当真源** |

**所以真正的改动不是"从方案一改成方案二"**，而是**给三者排座次 + 补上那个缺的门禁**：
- 定义表 → 产物的路已有；
- 扫描 → 定义的"建议"已有；
- **缺的是"定义 ↔ 真实脚本"的对账门禁**（声明说 2 项、脚本里有 3 项 → 报），
  以及**"定义 ↔ 引擎契约"的对账**（CDS 说 3 项、定义说 2 项 → 报）。
  **这两个"对账"才是防漂移的东西，也正好落在本项目"要么全对要么完全不动"的既有哲学上。**

## 七、你必须接受的一件事（诚实说）

走上"定义驱动为主干"，就等于承认：**你多了一份要维护的东西（定义/schema）**。

这是有代价的，工业界的代价清单是公开的：
- 定义会**过期**；
- 定义错了，工具会**自信地生成错的东西**；
- 所以必须配 **CI/构建时的漂移门禁**，否则半年后没人敢信它。

**换来的东西是值得的**：冷启动、跨引擎、编剧能用、程序改一处全项目跟着变。
但**前提是那个门禁真的做出来** —— 只做"定义 → 生成"、不做"对账 → 报警，
**一年后你会得到一份漂亮的、但和引擎对不上的定义表**，那比现在更糟。
