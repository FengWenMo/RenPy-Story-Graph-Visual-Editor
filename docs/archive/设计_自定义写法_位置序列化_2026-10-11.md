# 设计：把「自定义写法」从**扁平表单**改成**位置序列**（2026-10-11 程序员撞墙记录）

> 用户（程序员本人）拿 `show 小明 泳装 开心` 去填现有表单，**从第一步卡死到第三步**，
> 最后给出诊断原话：
>
> > "它的根本错误在于：你试图用一个**扁平的键值对表单**，去描述一个
> >  **复杂的树状语法结构**。"
> > "这就好比你想教人做菜，但你的表单只给了三个填空：'食材'、'调料'、'火候'，
> >  却没有地方让你写'先放油还是先放盐'。"

## 一、他卡在哪（逐条，全部要修）

| # | 卡点 | 说明 |
|---|---|---|
| 1 | **"语句名"填什么** | `show` 是引擎原生指令 —— 填它会不会**覆盖**引擎的 show？还是填 `show 角色 服装 神态`？还是 `swim_suit`？**卡死**。界面没告诉他"这一行会被怎么切" |
| 2 | **"剧本里怎么写" vs "表格那一列显示什么"** | 他填出三张卡（小明/角色、泳装/服装、开心/神态），但**这三张卡是平的** |
| 3 | **顺序** | 竖着排的三张卡，凭什么对应 `show 角色 服装 神态` 而不是 `show 服装 角色 神态`？ |
| 4 | **类型** | `小明` 是**变量**、`泳装/开心` 是**枚举** —— 输入框里都是中文字符串，工具怎么知道？ |
| 5 | **"词组（可选·高级）"** | 猜是正则捕获组或枚举分类，但**没有地方写 `swim_suit` 这样的匹配词** |
| 6 | **"验证它能跑"报错** | 因为他根本不知道工具期望的数据结构长什么样 |

## 二、病根（一句话）

**表单是"键值对"（unordered keys），而 `show 小明 泳装 开心` 是"位置序列"（ordered slots）。**
用键值对表达序列 ⇒ 顺序、可选、类型全都无处安放 ⇒ 用户只能猜。

## 三、重新设计：**位置序列**（Sequence of Slots）

### 3.1 核心数据结构（纯数据，先于界面）

```python
pattern = [
    {'kind': 'keyword', 'text': 'show'},              # 固定关键字
    {'kind': 'variable', 'column': '角色'},            # 变量（谁说话/谁出场）
    {'kind': 'choice',  'column': '服装', 'group': 'outfit'},   # 枚举（候选值来自词组）
    {'kind': 'choice',  'column': '神态', 'group': 'expression'},
    {'kind': 'optional', 'text': 'at', 'column': '位置'},        # 可选段
]
```

**顺序 = 列表顺序**（不再靠"竖着排"猜）；**类型 = `kind`**（不再靠中文字符串猜）；
**候选值 = `group`**（词组就是"这一格的可选值集合"）。

### 3.2 界面必须回答的三个问题（在**填的时候**就答，不是写文档）

| 用户的问题 | 界面怎么答 |
|---|---|
| "`show` 填哪儿？会覆盖吗？" | 顶部先问**"你要改的是哪种？"**：<br>① 引擎自带的写法（`show` / `say` …）→ **给它加列**，**不覆盖引擎**；<br>② 我们自己的新写法（`swim_suit` 这类）→ 新建一条 |
| "这三格对应哪三个词？" | **实时切行**：给一行样例（`show 小明 泳装 开心`），界面把它**切成色块**，每个色块贴上"第 N 格"的标签；填错顺序时**当场看出来** |
| "工具怎么知道 小明 是变量、泳装 是枚举？" | **每一格自己说**：格子的类型是**选出来的**（固定关键字 / 任意变量 / 从这些里选），不是猜的 |

### 3.3 界面的形状（草稿）

```
你要改的是：  ( ) 引擎自带的写法 show   ( ) 我们自己的新写法 ____
样例（从剧本里粘一行）：  show 小明 泳装 开心          [ 试切 ]

切出来的样子：
   ┌────────┐ ┌──────┐ ┌──────┐ ┌──────┐
   │ show   │ │ 小明 │ │ 泳装 │ │ 开心 │
   │固定关键字│ │ 角色 │ │ 服装 │ │ 神态 │
   └────────┘ └──────┘ └──────┘ └──────┘

每一格（按顺序）：
  1. show    [固定关键字 v]  文字[show]
  2. 小明    [变量 v]        表格列[角色]
  3. 泳装    [从这些里选 v]  表格列[服装]  可选值来自词组[服装 v]
  4. 开心    [从这些里选 v]  表格列[神态]  可选值来自词组[表情 v]
  (+ 加一格   − 删这一格   ↑ 上移  ↓ 下移)

结果预览（会写进清单的东西）：见右栏
```

**关键差别**：`＋加一格` 是**插入到序列里的某个位置**，不是"再加一条键值对"；
每格有 `↑↓`（顺序是能改的，不是靠拖时间）。

### 3.4 「词组」的定位（回答卡点 5）

词组 = **"这一格允许哪些词"的集合**，可以复用：

```python
groups = {
  'outfit':     {'label': '服装', 'options': ['泳装', '校服', …]},
  'expression': {'label': '表情', 'options': ['开心', '害羞', …]},
}
```

⇒ 界面上它**挂在格子上**（"可选值来自词组[服装]"），而不是一个飘在下面的独立表格。
`swim_suit` 这种"内部写法 vs 中文词"的映射，就写在词组里（`泳装 → swim_suit`）。

## 四、⚠ 一条必须先回答的产品决定（卡点 1）

`show` 是**引擎内置**。本工具**绝不覆盖引擎**（§12.1/§12.6 的边界）。
所以"给 `show` 加列"这件事的正确实现是：

- **工具侧**：在 `storygraph.rules.json` 里给 `show` 声明**列**（`角色/服装/神态`）
  + 把候选值挂到词组上 —— 这是**编辑器的事**（表里多几列、下拉多几项）；
- **引擎侧**：`show` 本来就是引擎的，**不需要也不应该**再注册一次；
- ⚠ 若有人真想**替换**引擎的 `show`（CDS 覆盖内置），那是**另一件事**，
  并且必须走**最高级警告**（形状不保证，N5）—— 界面上要单独一栏，绝不与"加列"混在一起。
