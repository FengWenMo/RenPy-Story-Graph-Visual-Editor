## D3'：AssetEngine 是否接进 Qt？

**建议：先不接，把确认闸门做好再说。**

### 理由

**1. 当前 AssetEngine 在生产中确实不可达，这是事实**

你的文件已经确认：`AssetEngine._apply_changes` 只被 `_apply_rename_patch` 调用，而 `AssetEngine` 在 `ui_qt` 生产路径中从不构造（asset_registry.py:1758 自己写明）。这意味着当前 D3 的风险是**潜在的，不是线上风险**。在能力悬空的状态下，接进 Qt 等于把一个未经验证的写入路径直接暴露给用户。

**2. 确认闸门有成熟的工程模式可以直接借鉴**

搜索到的资料中，多个项目采用了“预演-确认-回滚”的三段式契约：

- **Ghost Files** 在提出文件变更时先显示一个半透明的预览，让你看到结果长什么样，批量操作时可以分组预览、检查样本后再信任整个模式。
- **Nomi** 的桌面代理平台要求“配置 → 预览计划 → 批准”，永远先展示它打算做什么。
- **Backtrack AI** 是文件系统上的事务执行层，把自然语言意图转换成经过验证的行动计划，带预览、审批和确定性回滚。
- **Zudo-Tauri** 的模式是：把输出先暂存到临时目录，让用户接受或取消——接受才覆盖原文件，取消则原文件保持不变。

这些模式的核心契约是一致的：**默认不碰用户的原始文件，先展示 diff 或预览，确认后才写入，且写入必须可回滚。**

**3. Qt 侧有现成的原子写入和逐字节回滚方案**

搜索结果中出现了 Qt 的 `QSaveFile` 原子写入模式：失败的写入不会破坏原始文件；同时有 `undoLastApply` 恢复编辑前的精确字节。这可以直接复用到你现有的门禁体系里。

### 落地步骤建议

1. **先把 `_apply_rename_patch` 改成“算 diff → 返回调用方 → 确认后写”** 。这是 M2 的核心改动，且不依赖 Qt 接入，可以在当前无 UI 的环境下用测试直接验证。
2. **用测试驱动确认闸门的完整性**：断言“未确认时不产生任何写操作”“确认后写入的字节与预览一致”“回滚后字节逐位还原”。
3. **确认闸门通过全量测试 + 真实项目复验后**，再决定是否接 Qt。届时决策点变成：“确认闸门的 API 是否足够稳定，可以直接暴露给 UI？”

**为什么这个顺序是对的**：如果你先接 Qt 再接闸门，用户会在一段窗口期内直接触发未受保护的写入路径——这正是 D3 当前“不可达”状态所避免的。先做闸门，再接 UI，风险窗口为零。

## D4'：Stage 列走方案 A（结构化候选）还是方案 B（每指令一列）？

**建议：方案 B，每指令一列，复用 spec_args 范式。**

### 理由

**1. Excel 数据验证在单个单元格内无法实现“多值选择”**

这是方案 A 的根本障碍。多个来源确认：Excel 的数据验证下拉列表**只能绑定到单个值**，一个单元格内无法通过数据验证让用户从多个候选中分别选择。有讨论明确指出：“你没法在一个单元格里用数据验证做多值选择。一个单元格里放多个值本身就不好处理。我只会用每行多列的方式，按用户可能选择的最大项数来排。”

你的 D4 问题定义就是“Stage 一格多指令”——这正是数据验证覆盖不到的区间。方案 A 想拆成“位置 / 转场 / 停顿 / 音频动作”四个结构化候选，但它们在 Excel 单元格层面仍然是**并列的文本**，Excel 原生数据验证无法对“逗号分隔的多个值”分别提供下拉。

**2. 方案 B 复用已有范式，而不是发明新范式**

你已经在用 `spec_args` 的动态列范式。方案 B 把 Stage 拆成“每指令一列”，本质上就是**把动态列范式扩展到演出指令的维度**。这意味着：

- 不需要在 beat_model 里新增一套 `StageCandidate` 数据结构；
- 不需要在 excel_export 里新增一套针对 Stage 的特殊 DataValidation 逻辑；
- 列投影 / 列注册的既有路径可以直接承载。

**3. 从数据模型的角度，“行便宜，列昂贵”的原则需要辩证看**

有一条搜索结果给出了一个有用的判断框架：“行便宜，列昂贵”——但这里的“列昂贵”指的是**数据库物理 schema 的变更成本**，而不是 Excel 数据模型的列。在你的场景里：

- Stage 的指令类型（位置/转场/停顿/音频）是**已知且有限**的，不是用户自定义的无限维度；
- 每指令一列是**显式 schema**，比“一格多指令”的隐式 DSL 更容易被 `project_conventions` 的 learn/describe 路径理解；
- 列数增加是可接受的——50 人的策划团队面对的是几十列的演出配置表，不是几十万列的数据库表。

**4. 方案 A 的“改动小”是假象**

方案 A 看起来改动小，是因为它只需要在现有 Stage 列上加数据验证。但一旦你开始拆“位置 / 转场 / 停顿 / 音频动作”，你就已经在做**结构化解析**了——这恰恰是方案 B 用列结构直接表达的东西。方案 A 相当于“先让用户写自由文本，我再解析成结构化数据”；方案 B 是“让用户直接在结构化字段里填写”。后者在工程上更干净，在 UX 上对策划也更明确。

### 落地步骤建议

1. **先定义 Stage 的指令类型清单**：位置、转场、停顿、音频动作——确认每种指令的参数是什么。比如位置可能需要 (x, y) 或预设点名称，转场可能需要时长和缓动类型。
2. **为每种指令创建对应的动态列**，复用 `spec_args` 的列投影机制。每列绑定该指令参数类型对应的数据验证。
3. **保留 Stage 列作为“复合视图”** ：在 Excel 里保留一个只读的 Stage 列，把每指令列的值拼成人类可读的字符串，方便策划一眼看到完整演出。但这列不参与数据验证和回写——它是展示层，不是数据层。
4. **在 beat_model 里更新 `SINGLE_LINE_BEAT_FIELDS` 的定义**：把 Stage 从“多行指令”类别中移出，替换为各指令列的单行字段。

**风险提示**：方案 B 的列数会显著增加。需要在 Excel 导出时考虑列分组或折叠，避免策划被几十列淹沒。可以用“指令类型”作为一个可折叠的分组标题行来组织。
