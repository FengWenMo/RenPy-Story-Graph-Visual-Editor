## 第 1 题 ｜ 行身份配对 + 行数守恒的最小差异替换 ⭐⭐⭐

> **出处**：`storygraph/story/patcher.py :: _replace_matched` / `_line_key` / `_same_thing_unless_rewritten`
> **为什么最值钱**：这是整个项目最独特的算法。它回答了工具链最核心的命题——
> **程序生成的代码要改用户已有的代码时，怎么做到"最小惊讶"**。
> 可迁移到任何代码生成器、格式化器、数据库迁移工具、配置同步器。

### 关卡 A · 最简版

**一句话**：给定原文的一个区间和生成器产出的一批新行，把原文每一行尽量换成
"同一件事"的新行；换不了就原样保留。**行数必须不变。**

**输入**
```
old_lines = ['show a happy', 'x "你好"', 'hide a']
gen_bodies = ['x "你好吗"', 'show a sad']
```

**期望输出**
```
['show a sad', 'x "你好吗"', 'hide a']     # hide 没配对上 → 原样保留
changed = 2
```

**你要写的**
```python
def replace_matched(old_lines, gen_bodies):
    """返回 (新行列表, 改动数, 没落地的生成行)"""
```

**最简化的"同一件事"判定**：只比**第一个词**（指令动词）。
`show a` 可以配 `show b`，`x "..."` 只配 `x "..."`。
配对时一对一：一个生成行只能被消费一次。

**自测（先别看代码，把这几条想清楚）**
- `gen_bodies` 为空 → 输出必须**逐字节等于** `old_lines`
- 两者内容完全一样 → 输出等于输入，`changed == 0`
- 原文有 2 行 `x "..."`，生成器只有 1 行 → 第二行保留原文（不能一对多）
- 原文 1 行、生成器 3 行 → 多出的 2 行报"未落地"

### 关卡 B · 升级版（对齐真实约束）

原实现加了 6 道闸，每一道都对应一次真实事故：

1. **台词配对要求说话人一致**。`lyj "…"` 不许配 `jc "…"`——否则改 A 的台词会写到 B 身上。
   立绘同理，要求 tag 一致（`show ling` 只配 `show ling`）。
2. **认不出身份的行 → 永不替换**。key 退化成 `('other', 原文)`，只和逐字相同的行配对。
   注释、`if`、`menu`、未识别语句因此**天然不会被改坏**。这是"宁可不动，不可改错"。
3. **内容一致 → 保留原文那一行**。`'什么都不改，产物逐字节等于原文'` 这条硬契约就是从这来的。
4. **只差空白 → 保留原文**。原文 `jc  "…"`（两个空格）、生成器 `jc "…"`——Ren'Py 两者等价，
   改它没好处，却让每次导出的 diff 多出一堆"看起来没改"的行。
   *真实收益*：`chapter0_0`（满篇双空格）从"每次导出 10+ 行差异"变成"原文不动 = 0 行差异"。
5. **立绘换名时词数必须一致**。`ling close_happy` ↔ `ling_close_happy` 是生成器的"规范化"，
   不是作者改动——**那是把能跑的脚本改坏，不许换**。
6. **缩进只来自原文**：`_indent_of(原行) + 新内容`。结构不是补丁该管的事。

**验收标准**
- 改一句台词 → diff **正好 1 行**
- 什么都不改 → 输出 == 输入（逐字节）
- 拿 `chapter1_2.rpy`（214 拍）跑一遍：什么都不改时差异 0 行

**思路提示**（不是答案）
- 把 `gen_bodies` 按 key 分桶成 `dict[key, [候选…]]`，消费时用 `(key, 下标)` 记 `used` 集合，
  一对一就自然成立了。
- 每一道闸都是"先判能不能换，再决定换不换"，顺序不能反。

## 第 2 题 ｜ 缩进敏感的分块：物理行 → 逻辑行树 ⭐⭐⭐

> **出处**：`storygraph/parsing/renpy_parser.py :: RenPyLexer._build_tree` / `_flatten`
> **为什么值钱**：这是**所有 Python 风格 DSL 解析器的第一步**。YAML、Ren'Py、
> 任何靠缩进表达结构的语言都走这条路。算法本体只有十几行，优雅得值得背下来。

### 关卡 A · 最简版

**一句话**：把 `(文本, 缩进)` 序列建成父子树。

**输入**
```
[('a', 0), ('b', 4), ('c', 8), ('d', 4), ('e', 0)]
```

**期望输出**
```
a
├── b
│   └── c
└── d
e
```

**你要写的**
```python
def build_tree(flat):   # flat: [(text, line_no, indent), ...]
    """返回根节点列表"""
```

**核心**（如果想不出来，这一条可以直接看）：维护一个单调栈，`root.indent = -1`。
对每个新行：`while stack[-1].indent >= indent: pop()`，挂到 `stack[-1]` 下，再 push 自己。

**自测**
- 缩进回退到 0（`e` 的情形）
- 缩进不连续：`0 → 8 → 4`
- 空输入、只有一行
- 第一行就有缩进（畸形输入，别崩）

### 关卡 B · 升级版（对齐真实约束）

真实 lexer 在建树前还有一步 `_flatten`，那里才是坑最多的地方：

1. **整行注释要保留含缩进的原文**，不能存 `stripped`。
   *真实事故*：`    #anchor(0.5, 0.5)` 被双重去缩进啃成 `    hor(0.5, 0.5)`——
   **注释的 `#` 被吃掉了，变成非法 ATL 代码**，产物跑不起来。
2. **三引号字符串跨行合并**。`"""..."""` 没闭合就一直往下吃。
3. **反斜杠续行**：数尾部 `\` 的**奇偶**。偶数个是转义过的反斜杠，不是续行。
4. **括号计数跨行合并**：但必须**跳过字符串里的括号**——`"("` 不算真的开括号。
5. **行内注释剥离必须按行做**。
   *真实事故*：原本"遇到第一个 `#` 就截断"，对**已合并的多行语句**就是从第一个 `#`
   起把后面**所有行全删掉** → 括号永远配不平 → 合并循环一路吃到底 →
   **整个文件被并成一条逻辑行，里面所有 label 全丢**。
6. **安全阀**：合并行数上限（项目里 120）。括号计数万一被奇葩代码骗了，
   也不能一路并到文件末尾把后面所有 label 吃掉。宁可留一条超长语句 + 警告。

**验收标准**
- 真实项目 88 个文件 36,688 行：**0 解析失败**，耗时 < 1s
- 解析后 `label` 数量 == 源文件里肉眼可见的 label 数量（第 5 条如果写错，这个数会暴跌）

**思路提示**
- 第 4、5 条是耦合的：括号计数必须在"剥离注释之后"做，而剥离必须按行。
  想清楚**处理顺序**，这题就通了。

## 第 3 题 ｜ ATL 变换链的求值：带参数的链式调用 + 单位判定 ⭐⭐☆

> **出处**：`storygraph/story/atl.py :: eval_number` / `_eval_node` / `_from_def` / `_props_of`
> **为什么值钱**：这是一个**安全的小型表达式解释器**（AST 白名单求值，不用 `eval`），
> 加上一套**单位系统**。可迁移到 shader 参数系统、动画曲线、配置 DSL。
> 编译原理的浓缩版。

### 关卡 A · 最简版

**一句话**：写一个安全的算术表达式求值器。支持常量、变量、加减乘除、
整除、取模、幂、一元负号。**不许用 `eval`。**

**输入 / 输出**
```python
eval_number('z * 1.00', {'z': 0.30})   # → 0.3
eval_number('400 + 20 * 2', {})        # → 440.0
eval_number('1.03', {})                # → 1.03
eval_number('__import__("os")', {})    # → None（必须拒绝）
```

**你要写的**
```python
_ALLOWED_NODES = (...)   # 白名单，想清楚该放哪些

def eval_number(expr, env):
    """求值失败一律返回 None，绝不抛异常、绝不 eval"""
```

**自测**：`1/0`（除零）、未知变量、`'true'` / `'false'`、空串、语法错误。
**失败必须返回 `None`**，不能抛——调用方要靠 `None` 降级。

### 关卡 B · 升级版（对齐真实约束）

1. **白名单之外的 AST 节点一律拒绝**。`Call` / `Attribute` / `Subscript` 都不能放——
   项目源码里的表达式是不可信输入。
2. **transform 链式调用**。真实项目是这么写的：
   ```
   transform f21:
       focus(320)
   transform focus(x=640, z=0.30):
       xcenter x  xoffset 400  ypos 1.03  zoom z*1.00
   ```
   要把 `320` 绑到 `x`，`z` 用默认值，再进 `focus` 体内求值。**跟调用链、绑参数**。
3. **单位判定：整数 = 像素，小数 = 屏幕比例**。`ypos 1.03` 是 103% 屏高，不是 1.03 像素。
   ⚠ 坑：链式绑定拿到的 `320` 是 float，**代回源码时必须还原成整数形式**，
   否则像素值会被误判成比例。
4. **一行多个属性 + 缓动前缀**：
   `easein .25 xcenter x zoom z*1 alpha 1.00` → 要跳过 warper 名和它后面的时长。
5. **只取"最终静止态"**：`on show:` 那些事件块不算。
6. **算不出来就返回 `None` 让上层降级**，绝不硬猜。
   *（反面教材：原实现曾按首字母猜位置 `i/f/l/r → 0.35/0.65/0.25/0.75`，
   导致 `f21`/`f22` 都算成 0.65 叠在一起，`zoom 0.30` 完全没体现。）*

**验收标准**
- 真实项目：`f21 → x=0.375`、`f22 → 0.708`、`i11 → 0.542`、zoom 0.30（与手算一致）
- 与游戏存档里的真实截图对比：取景一致

## 第 4 题 ｜ 有向图分层布局（Sugiyama 简化版）⭐⭐☆

> **出处**：`storygraph/graph/layout.py :: layout_graph`
> **为什么值钱**：经典图算法，任何 DAG 可视化、依赖关系图、状态机图都要用。
> 这题的价值在于**处理脏输入**——真实剧情图是有环的（章节互相跳转）。

### 关卡 A · 最简版

**一句话**：给一个 DAG 分层（最长路径法），层内排布不重叠，输出每个节点的 `(x, y)`。

**输入**
```python
nodes = {'a': ..., 'b': ..., 'c': ..., 'd': ...}
edges = [('a','b'), ('a','c'), ('b','d'), ('c','d')]
```

**期望**：`a` 在第 0 层，`b`/`c` 第 1 层，`d` 第 2 层；层内不重叠。

**你要写的**
```python
def layout_graph(graph, start_id=None, layer_gap=180, node_gap=60, max_iter=10):
```

**自测**：单节点、孤立节点、菱形、链状、多个入度为 0 的节点。

### 关卡 B · 升级版（对齐真实约束）

1. **有环怎么办**——剧情图必然有环（章节互跳、回头跳转）。
   做法：Kahn 拓扑排序，把导致环的边**反向**（记进 `reversed_edges`）。
2. **自环单独剔除**（`u == v` 不参与拓扑，否则入度永远降不到 0）。
3. **层内顺序用重心法迭代**：按相邻层邻居的平均位置排序，迭代若干轮。
4. **迭代上限**（`max_iter=10`）：不收敛也要停，不能死循环。
5. **起点优先**：有 `start_id` 时它排在同层最前。
6. 边的**端点取块中心**（不是块的边缘），因为块不透明。

**验收标准**
- 真实控制流图（40+ 节点）不出现同层块垂直重叠
- 布局结果稳定：同样输入两次，输出一致

## 第 5 题 ｜ 补丁的整体校验：改完还是不是"同一个程序" ⭐⭐☆

> **出处**：`storygraph/story/patcher.py :: _verify_patch` / `_unescaped` / `_content_lines`
> **为什么值钱**：这是"生成式工具"的**验证层**。可迁移到任何 codegen、重构工具、
> 迁移脚本。核心思想是：**宁可退回保守方案，也不产出半对的结果。**

### 关卡 A · 最简版

**一句话**：给定原文和补丁后的文本，检查"该有的台词一条都不少"。
用**多重集**（计数）比较，不是集合——两句相同的台词，少一句也要抓出来。

**你要写的**
```python
def verify_patch(text, original, beats, blocks):
    """返回不通过的原因列表；空列表 = 通过"""
```

**自测**
- 原文 2 句相同台词，产物只剩 1 句 → 必须报错（用 `set` 会漏掉这个）
- 台词被改了内容 → 报错
- 什么都没改 → 通过

### 关卡 B · 升级版（四道查 + 语义等价）

1. **① 能重新解析回来**——写临时文件跑一遍自己的 parser。
2. **② 台词多重集包含**（关卡 A 的内容）。
3. **③ 生成器要的每一条内容行都在产物里**。
   这条最能抓"区间错位、改到别人的行上"这种隐蔽错误。
4. **④ `label` / `return` 的数量不许变少**（结构不许被啃掉）。

然后是最微妙的部分——**什么叫"一样"**：

5. **转义差异不算丢**。同一句话，原文可能写成单引号无转义
   `'file "c:\\a.py", line 24'`，生成器写成双引号带转义
   `"file \"c:\\\\a.py\", line 24"`——**Ren'Py 读出来一模一样，但逐字节不同**。
   只按字节比会把这种行判成"丢失"，于是**整章白白退回全量重生成**
   （注释被冲掉、还会因重新分组少一拍）。这就是 `_unescaped` 存在的原因。
6. **菜单选项的结尾冒号要容忍**：源文件里是 `"A":`，生成器只产 `"A"`
   （冒号是 `menu:` 结构的语法，不是内容）。

**验收标准**
- 真实项目 `chapter1_2`：416/416 条生成内容全部命中（不误伤）
- 人为把某拍的行号改错 → 必须被第 ③ 条挡下，返回 `ok=False`

## 第 6 题 ｜ 源行号恢复：按内容把两个序列对齐 ⭐⭐

> **出处**：`storygraph/story/patcher.py :: recover_source_ranges` / `_align_key`
> **为什么值钱**：本质是**序列对齐**（近似 LCS）。可迁移到 source map 生成、
> 增量编译的行号映射、任何"元数据丢了要靠内容找回"的场景。

### 关卡 A · 最简版

**一句话**：两个序列，元素有各自的 key。找出"相等段"，把源序列元素身上的
属性（比如行号）搬到目标序列对应元素上。

```python
src = [k1, k2, k3, k4]     # 带 line_no
new = [k1, k3, k4]         # 没有 line_no（表里的拍删了一条）
```
→ `new[0]` 拿到 `src[0]` 的行号，`new[1]` 拿 `src[2]`，`new[2]` 拿 `src[3]`。

**自测**：目标多了元素（插入）、目标少了元素（删除）、完全对不上。

### 关卡 B · 升级版（对齐真实约束）

1. **先按 `label` 分组再对齐**。跨 label 对齐没有意义，也对不准。
2. **对齐键不含正文**——这样"用户改了台词"照样能对齐上。
   （反过来，如果把正文放进 key，改一句台词就对不上了。）
3. **插入的拍**：没有对应源拍 → 给一个**插入点**（前一拍末行之后），
   交给插入通道处理，而不是当"替换"。
4. **删除的拍**：记进 `dropped`，让调用方退回全量。
5. **`autojunk=False`**：`difflib.SequenceMatcher` 默认会把"出现次数过多的元素"
   当垃圾忽略，重复元素多的序列（大量空台词拍）会被误判。
6. **只读源文件，不改表结构**。
7. ⚠ **运行期元数据陷阱**：任何"只在这两个字段存在时才跑"的检查，
   在编辑器那条路上会被**静默跳过**（载入章节 → 删卡片 → 导出 = 删掉的拍还在文件里）。
   删拍检测必须每次都做。

## 第 7 题 ｜ 持续状态传播：演出状态机与"只输出增量" ⭐⭐

> **出处**：`storygraph/app/stage.py`、`storygraph/story/beat_render.py :: _stage_lines`
> **为什么值钱**：Ren'Py 的 `show` / `at` 是**持续状态**（不像代码里的局部变量）。
> 这个模型可迁移到动画系统、时间轴、撤销栈、任何"状态持续到被显式改变"的系统。

### 关卡 A · 最简版

**一句话**：一串演出指令（`scene` / `show` / `hide` / `play`），
逐拍算出"当前舞台状态"，但**只输出与上一拍相比的变化量**。

**输入**
```
拍1: scene bg_classroom, show ye happy at i11
拍2: （无舞台指令）
拍3: show ye sad
```

**期望产出**
```
拍1: scene bg_classroom / show ye happy at i11
拍2: （什么都不输出）
拍3: show ye sad
```

**自测**：`scene` 清空所有立绘；同角色换表情；`hide` 之后再 `show`。

### 关卡 B · 升级版（对齐真实约束）

1. **继承的值不许物化**。立绘位置若来自继承，界面要显示 `i11（继承）`，
   但**保存时不许把它写进这一拍**——用户点一下 chip 才算"改了"。
   *（反面教材：把继承值物化后，原本持续的位置被写死，后续改动全部错位。）*
2. **必须幂等**。`hydrate` 跑两次结果必须一样。
   *真实事故*：`hide cg03` 被吸两次变成 `hide cg03; cg03`。
3. **`beat.at` 是"整拍兜底位置"**：只套给**没写 `@位置`** 的 show。
   如果所有立绘位置不一致就同步它，会**给别的立绘凭空套上位置**（立绘错位）。
4. **原生真迹原样输出**：作者手写在 Stage 列里的原生代码，逐字保留；
   结构化列里那份只是影子，不进渲染。

**验收标准**
- `beat → cards → show` 往返**一个字都不许变**
- 真实项目：连续 `apply_current_beat` 后重新渲染，产物与源 .rpy 舞台指令逐条相同
  （历史实测 chapter1_2 71/71、chapter1_3 89/89，0 丢 0 多）

## 第 8 题 ｜ 分支条件推导：让每条边互斥且完备 ⭐⭐

> **出处**：`storygraph/parsing/renpy_parser.py :: GraphBuilder`、
> 契约测试 `tests/test_pipeline_batch.py::TestBranchConditionsAreLogicallyCorrect`
> **为什么值钱**：小而美的命题逻辑题。可迁移到控制流分析、状态机导出、
> 决策表生成。也常被拿来做笔试题。

### 关卡 A · 最简版

**一句话**：把 `if / elif / else` 翻译成**互斥且完备**的边条件。

```
if a:      → 边1: a
elif b:    → 边2: b and not a
else:      → 边3: not a and not b
```

**你要写的**
```python
def branch_conditions(clauses):
    """clauses = [('if', 'a'), ('elif', 'b'), ('else', None)] → 条件列表"""
```

**自测**：只有 `if`；`if / else`；四分支；条件为空串。

### 关卡 B · 升级版（对齐真实约束）

1. **AST 路径与 Statement 路径必须同一套规则**——项目里有两条构图路径，
   规则一漂移就出现"图里看到的 ≠ 导出的"。
2. **`menu` 的文字与条件要分离**：选项**文字**进 `option_text`，**条件**进 `condition`。
3. **用区间分析验证完备性与互斥性**（写成测试，不是靠肉眼）。
4. **`call X from Y` 的 `from` 子句必须一路保住**。
   它是 Ren'Py 的**存档点标识**：同一个 label 被多处 call 时靠它区分存档属于哪一处，
   丢了就是"语义等价但老存档回滚"。
5. **去重键不要带 `from_clause`**——同一个 `(from, to, type, cond, option)` 就是同一条边，
   带上它会让两条解析路径各建一条（实测边数翻倍）。
   正确做法：基础键去重 + 谁抓到 `from` 就补到那条边上。

## 第 9 题 ｜ 引用判定索引：从 O(N×M) 到 O(N+M) ⭐

> **出处**：`storygraph/assets/asset_registry.py :: resolve_references`（`AssetIndex`）
> **为什么值钱**：性能工程的基本功。简单，但**不做就会在真实数据上卡死**，
> 而且这类错误在测试数据上完全看不出来。

### 关卡 A · 最简版

**一句话**：N 个引用（比如脚本里的 `"bgm/night.mp3"`），M 个资产记录，
判定每个引用指向哪个资产（找不到就报"缺资源"）。

```python
def resolve_references(refs, assets):
    """返回 [(ref, asset_or_None), ...]"""
```

**先写 O(N×M) 的朴素版本**，再用真实数据量感受一下它有多慢，然后改成哈希索引。

**自测**：引用写法与资产路径不完全一致（大小写、分隔符 `/` vs `\`、有无扩展名）。

### 关卡 B · 升级版（对齐真实约束）

1. **一次建索引，多次查询**。⚠ 项目里真实踩过：在循环里调用而没传 `AssetIndex`，
   退化成 O(引用 × 资产)，真实项目直接卡住。
2. **别名要认**。真实项目里图片名常常**只写在脚本里**：
   ```
   definitions.rpy:146   image bg bg11_0 = "images/bg/bg11.png"
   ```
   Ren'Py 是照脚本认的（`scene`/`show` 查的就是这张声明表）。
   *实测代价*：只查资源表时，1537 拍里有背景的 **349 拍是黑的**。
3. **三级回退**：资源表 → 脚本 `image` 声明（含 `image black = "#000000"` 这种纯色）
   → 磁盘按名字找。**每一级都验文件真的存在**。
4. **找不到时给"是不是想写这个"**：唯一前缀匹配才建议，并列第一就不猜。
   *（真实项目里大量"缺资源"其实是作者把长文件名手写截断了。）*

## 第 10 题 ｜ 缩略图优先级调度队列 ⭐

> **出处**：`storygraph/ui_qt/thumb_loader.py :: ThumbLoader._pump` / `focus`
> **为什么值钱**：并发调度 + 取消 + 去重的组合拳。工程价值高，
> 也是"用户体验优化"的标准套路（可视区优先、预取不插队）。

### 关卡 A · 最简版

**一句话**：一个任务队列，每个任务有优先级，最多同时跑 K 个；
一个跑完就按 (优先级, 先来后到) 补下一个。

```python
class ThumbLoader:
    def request(self, key, priority):  ...
    def _pump(self):                    # 补位
```

**自测**：优先级抢占、并发上限、空队列、同一 key 重复请求。

### 关卡 B · 升级版（对齐真实约束）

1. **后来的请求顶掉排队中的同 slot 旧请求**（只保留最新）。
   换表情连点会连发多个请求，旧的没必要再解。
2. **防抖只对"同一 slot 连续被改"生效**——每个 slot 都先白等一个周期，
   等于一屏 N × 120ms，首屏会肉眼可见地慢。
3. **`focus()` 必须把"窗口内、还没有图"的全部格子提上来**，不能只提这一次新请求的。
   *真实踩坑*：每次都多留"上 1 行、下 3 行"作缓冲，滚到下一屏时那一屏**早就排过队了**，
   只提新请求等于 `focus([])`（谁都没提）。
4. **预取永远不许插队**（`PRIORITY_BACKGROUND`），且预取只填缓存、不回调。
5. **结果回来要核对 key**。同一个 slot 换内容会连发多个请求，
   不核对就会出现"旧结果顶掉新回调，还把旧图缓存到新键上"
   （表现：换了内容图不出来）。
6. **预取键必须和真正的请求完全一致**（同一条路径解析 + 同一个尺寸），否则预取等于白做。

**验收标准**（实测口径）
- 选择器首屏出图：4.28s → 1.76s（2.4×）
- 换到相邻拍（预取命中）：冷 408ms → **10ms**
