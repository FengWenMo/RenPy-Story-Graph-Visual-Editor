# 复核与修正：契约驱动的"致命前提"到底杀死了什么

> 2026-10-10 ｜ 触发：用户指出"契约驱动"有致命前提 —— 你们的程序**不用 CDS 注册**，
> 而是直接改解析逻辑 / 往已有语句的参数序列里插东西，所以"引擎公布的声明"根本不存在。
> 并给出三条弱点（契约粒度不够细 / 数据流方向冲突 / 扫描是滞后指标）。
>
> **本文先做实测，再答。实测结果改变了整个结论** —— 而且**推翻了我上一轮的一部分说法**。

## 一、你的批评：三条弱点我全部接受

### 弱点一：契约的粒度不够细 —— 对

`register_statement` 能声明的只有**语句名 + 有没有块**；参数的语义形状写在 `parse` 函数里，
**是代码不是数据**。`lint` 的判据也是程序写的，不是机器可读的 schema。
**对"新增语句"这一类，契约永远是部分契约。**

**但要补一句**：这个弱点**只对"新增语句"成立**。
对**属性 / 变换 / 图片 / 标签**这些*引擎原生可枚举*的东西，粒度问题**不存在** —— 它们是完全可枚举的（见 §二）。
你这一个项目，命中的恰好是后者。

### 弱点二：数据流方向冲突、优先级没定义 —— 对，我确实没写清

我上一轮用"上游"这个词是含糊的。必须写成规则（见 §三）。

### 弱点三：扫描是滞后指标 —— 对

扫历史脚本确实滞后：编剧还没用过的新写法，扫不出来。
**但 Ren'Py 自带实时 oracle**，可以不用等（见 §二）。代价是你说的那句"需要额外工程"，
但那是"写一个一次性导出脚本"，不是"无限行为探测"。

## 二、关键发现：Ren'Py 自带一套**可枚举、可校验**的属性注册表

这是本次复核最有价值的东西。官方 API 里现成就有：

| API | 它给你什么 | 正好解决你哪个抱怨 |
|---|---|---|
| `renpy.list_images()` | 全部已定义图像（tag + 属性，空格分隔的字符串） | "有多少写法我不知道" |
| `renpy.get_available_image_tags()` | 全部 tag | 同上 |
| `renpy.get_ordered_image_attributes(tag, attributes=(), sort=None)` | **返回一组属性，按"适合展示给用户"的顺序排好；且只给与给定属性*兼容*的那些** | **"候选值非常繁琐、要我一个个手填"** |
| `renpy.has_image(name, exact=False)` | 这个名字合不合法（**成员测试 = 裁判**） | "验漂移" |
| `renpy.get_registered_image(name).attributes` | `layeredimage` 的每个属性，带 `.group` / `.attribute` | "服装/表情怎么分开" —— **分组名也在引擎里** |
| `renpy.sh lint --error-code` | 官方静态检查；**出错退出码 1**，文档明说"useful for CI systems" | CI 门禁 |
| `layeredimage` 的 `group` / `attribute` | 属性的**分组结构**（声明的，不是猜的） | 同上 |

**这就是你最初那句抱怨的正式答案：**

> "你说的这个候选值其实非常繁琐！有多少动作我也不知道，都在表格内部的，却要我手动一个个填上去……"

**候选值根本不该由人填 —— 该问引擎要。**
`get_ordered_image_attributes(tag)` 返回的**就是**"这个 tag 下合法、兼容、且按展示顺序排好的属性"。
我上一轮让你/项目去"声明候选值"，对你的项目来说**是绕远了**。
（顺带：分组名 `outfit`/`expressions` 也是 `layeredimage` 里声明的，工具不用自己发明。）

## 三、修正后的四级阶梯（不是"契约 vs 不契约"）

你说"契约驱动"只有三种形态（A 注册 / B 声明文件 / C 行为探测）。**漏了最要紧的一级**：

```
① 引擎原生可枚举的东西        图片 / 属性 / tag / 变换 / 角色 / 标签
   来源 = 引擎自带 API          renpy.list_images() / get_ordered_image_attributes() / …
   ✅ 零配合成本 · 不漂移（它就是引擎本身）· 你的项目 99% 靠这一级
        ↓ 没有覆盖到？
② 程序用标准注册               renpy.register_statement(...)（CDS）
   来源 = python early 块       ✅ 不漂移（改注册=契约自动更新）｜❌ 要求程序愿意用
        ↓ 没有？
③ 程序真改了引擎源码           来源 = 引擎补丁本身
   · 3a **引擎补丁即契约**：diff 你的引擎 vs 官方上游 → 直接得到语法增量（Ren'Py 是 Python，可 diff）
   · 3b **就近声明**：让程序在补丁旁边写一行声明（不是另开一份文件 → 抗漂移远强于独立声明文件）
        ↓ 都没有？
④ 归纳 + 裁判 + 人确认         扫历史脚本推断形状 + 用 lint/has_image 当裁判 + 人点头
   ⚠ 滞后（要有样本）、会过度泛化 → **只能当"发现"和"报警"，永不当真源**
```

**关键在于**：你指出的"致命前提"**只杀死第 ② 级**，不构成整条路的致命伤 ——
因为 **①** 不需要任何配合，**④** 有引擎 oracle 兜底。

**而你的项目现在站在第 ① 级**（没有任何语句级魔改），这是**最好办的一级**。

## 四、三个弱点的处置（对应 §一）

### 处置一：粒度不够 → 承认它，但**标出每一段的出处**

定义表里每个字段标 `来源`，只允许三类：

| 来源 | 例子 | 谁说了算 | 在定义表里 |
|---|---|---|---|
| **派生**（从引擎/契约读的） | 有哪些属性值、参数名、是否有块 | 引擎 | **只读，不许在本项目改** |
| **人工**（人加的语义） | 中文名、分组归并、候选过滤、例子、说明 | 人 | **可编辑 —— 这才是"你的"** |
| **内容** | 台词、演出 | `.rpy` | 不在定义表里 |

⚠ **这个"派生 vs 人工"的分法不是新发明** —— 项目里已有两处同款先例：
`core/capability.py` 的 `Provenance`（declared / host-registry / shape / builtin）、
以及资产表的 `update_keys=`（脚本权威字段 vs 人写的 `Category`/`Notes` 一律不动）。
**套用既有模式即可。**

### 处置二：优先级 —— 写死三条，消除"三向漂移"

1. **形状 → 引擎/契约。** 引擎说有几个字段就是几个；定义表里这些字段**只读**。
2. **语义 → 人。** 中文名/分组/说明只在定义表，**引擎不许覆盖**（引擎压根不知道这些）。
3. **内容 → `.rpy`，永远唯一真源。**

**对不上时不是"谁赢"，是"报错"** —— 绝不静默挑一个。
例：引擎说 `swim_suit` 不存在，可选修表里有它 → **报"这个词引擎不认识"**，不是默默用它。
这正好落在项目既有的"**要么全对、要么完全不动**"哲学上。

### 处置三：滞后 → 用引擎 oracle 把"滞后"变"实时"

- **不需要等样本**：直接 `list_images()` / `get_ordered_image_attributes()` 枚举全部合法值（覆盖"新增"）。
- **不需要跑游戏**：`lint --error-code` 一条命令给你"哪些地方引擎不认"。
- **落地形态**：一个**一次性导出脚本**（在 Ren'Py 里 headless 跑）→ dump 成一份
  **可 diff 的缓存文件**（如 `storygraph.engine_facts.json`）→ 进版本库。
  **引擎改了 → 这份文件跟着变 → diff 出来就是"漂移报告"。**

⚠ 诚实说代价：这一步**需要引擎侧跑一次**（你说的"需要额外工程"是对的），
但它是一次性的、可进 CI 的，**不是"无限行为探测"**。

## 五、结论：我上一轮的结论要修哪几处

| 上一轮我说的 | 修正后 |
|---|---|
| "主干=定义驱动，上游=契约驱动，护栏=扫描" | **改成"四级阶梯"**（§三）—— 因为"契约"不止一种，最高一级是**引擎原生枚举**，而它零成本 |
| "定义表集中形状真源" | **定义表里形状是派生的、只读**；人只能加语义（§四处置一） |
| "扫描是漂移探测器" | **扫描只是滞后的那一半**；实时的那一半是**引擎 oracle**（§四处置三） |
| 用 `swim_suit lyj "泳装" intensity=3` 当例子 | 那是我编的**示意图**；你的项目里这类东西是**属性**，走第 ① 级，不用契约 |

**一句话修正**：
> **不是"先有契约，工具才能工作"；而是"先看引擎自己会不会说，会说的就用引擎的，
> 不会说的才要人教"。Ren'Py 在"属性"这件事上非常会说 —— 我们之前问错人了。**

## 六、现在就能做的最小动作（不写产品代码，先验证）

1. **写一个一次性 dump 脚本**（在 Ren'Py 里跑）：
   输出 `list_images()` / `get_available_image_tags()` / 每个 tag 的 `get_ordered_image_attributes()`
   / 每个 `layeredimage` 的 `group` 名 → 存成 `storygraph.engine_facts.json`。
   **验收**：这份文件里应当出现 `clothes2` / `base_swimsuit` / `outfit` / `expressions`。
2. **拿它当候选来源**：卡片/表格的属性下拉**直接读这份缓存**，不再靠人填。
   项目已有的 `attr_groups` 降级成"改名/合并"的**覆盖层**（引擎给的是真分组）。
3. **门禁**：`lint --error-code` 进 CI；`engine_facts.json` 进版本库（引擎改了就 diff）。
4. **只有在第 1~3 步都覆盖不到时**，才回头问"要不要推程序用 CDS"。
   —— **在确认第 ① 级能覆盖多少之前，先别急着推程序改工作流。**
