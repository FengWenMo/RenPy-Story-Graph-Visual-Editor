# 调研 3：自定义模块面板该怎么办（最头疼的那块）

> 用户 2026-11-07：
>
> > Unity 就不能兼容折叠吗？完全可以吧！所以实际上我们的拍可以先做成类似于 Unity 的元素……
> > 然后有些复合的东西可以略微折叠，**最为关键的……自定义模块的那个面板怎么办？**
> > 这个可是非常头疼啊……卡片编辑器现在的 UI 其实还好，最关键的就是自定义模块……再搜一下

---

## 0. 先纠正我上一轮的一个错误

我把"缩进"和"折叠"说成了对立面 —— **这是错的**。Unity 完全能折叠：

- IMGUI：`SerializedProperty.isExpanded` + `EditorGUILayout.Foldout(...)`
- UI Toolkit：`Foldout` 元素，嵌套 Serializable 类**默认就是可折叠的**
- `[FoldoutGroup("高级", expanded: false)]`（Odin）就是"默认收起"

正确的说法应该是：**默认展开 + 缩进表层级；只有"复合的、不常改的"才折叠。**
Unity 的 Inspector 是"全展开的一列"，折叠是**例外**，不是默认。

---

## 1. 自定义模块面板为什么头疼：一句话根因

> **它逼人直接编辑底层数据结构。**

我们现在的表单要求人构建 `pattern`（位置序列）、`clauses`（子句表）、`columns`
（列名 / 候选 / positional / multi）—— 这些是**我们代码里的模型**，不是编剧脑子里的东西。

搜到的那篇"用 Odin 给策划做 Context Editor"的实战文章，第一条经验就是这句：

> **「为策划设计工具时，最大的禁忌是直接暴露底层数据结构。他们不需要知道 List 是什么。」**
> 应该通过 `[ShowInInspector]` / `[HideLabel]` 做一层**视图模型**，
> 把"暴击率"和"暴击伤害"放进一个叫**"暴击属性"的折叠组**，
> 远比直接显示两个浮点数字段友好。

对照我们：**"这一格是 / 这一列叫什么 / 可以多值 / 可以不填 / 只能从这些选"
就是"直接显示底层数据结构"。** 五个正交决定平铺在一张卡上，人每次都要重新想一遍。

## 2. 搜到的两条可直接照搬的做法

### 2.1 一个格子 = 一个对象，**先选类型，只显示该类型的字段**

Unity 的 `[SerializeReference]` 子类选择器（多个第三方实现说法一致）：

```csharp
[Serializable] public abstract class Effect { public float duration = 1f; }
[Serializable] public class Damage : Effect { public int amount = 10; }
[Serializable] public class Slow   : Effect { public float multiplier = 0.5f; }

[SerializeReference] private Effect onHit;
```

编辑器里的行为（原文）：

> "onHit draws a **dropdown listing Damage and Slow**. Choosing one creates an instance
> and **the fields of that instance draw underneath, in a foldout**."

**这正是我们"格子类型"该有的交互**：
选「从候选选」→ 只出现"列名 + 候选"；选「固定字」→ 只出现"哪几个字"。
**不是**现在这样：把 5 个控件全摆出来，让人自己判断哪几个有意义。

### 2.2 给非程序员的工具，三条设计原则（Odin 实战）

那篇给策划做工具的文章，目标写得非常具体：

| 原则 | 原文/做法 | 我们的对应 |
|---|---|---|
| **一眼看出"该动哪里"** | 左 Categories / 右内容；"a feeling of **opening Excel**" | 已有左侧分类（发现/已声明/词组/清单）✅ |
| **就地编辑、不跳文件** | `[InlineEditor(Expanded = true)]` 就地展开引用的对象 | 缺：声明完看不到"卡片上什么样" |
| **留自由但难改坏** | `[ReadOnly]` 锁 ID/内部 flag；`[InfoBox]` 给说明；`[HideIf]/[ShowIf]` 按情况隐藏 | 缺：`positional` / `header` 这些内部键全暴露给编剧 |

还有一条（CSDN 那篇数值策划工具的经验）值得记：

> "**中央数据区**用 `[TableList]` 显示所有可配置的表，支持**就地编辑、排序、拖拽**…"
> "**侧边预览面板**：选中一行时，在右侧展开该物品的详细属性，并给一个即时预览。"

**"列表 + 右侧预览"** 是这类工具的标准形制，我们现在是"列表 → 跳页 → 表单"，
中间少了一环。

## 3. 我们面板的具体病灶（逐条对到文件）

| 病灶 | 位置 | 编剧感受到的 |
|---|---|---|
| 每格 5 个控件平铺 | `param_editor.FieldCard`（这一格是 / 这一列叫什么 / 可以多个 / 可以不填 / 只能从这些选） | "我到底要填几个？" |
| 类型用下拉但**不改变可见字段** | 同上 | 选了"固定字"，还要面对"候选列表"这种无关控件 |
| `pattern` / `clauses` 是**两个平行概念** | `_build_form_page` 第 2 步 + 第 3 步 | "位置格和复杂子句有什么区别？" |
| 没有**结果预览** | 全页 | 声明完不知道卡片会长什么样，只能回去点一遍 |
| 内部键暴露 | 高级区 / `positional` / `header` | 一堆"参数名/列名/header"分不清 |
| 保存后要**重新打开**才知道对不对 | `_save_statement` → 刷新表格 | 试错成本高 |

## 4. 建议的三个改动（按性价比排序）

### 改动 A：格子改成"一行一格"，类型决定显示哪些字段（最高优先）

```
[任意文字 ▾]  [喊话        ]  必填 ☑            ×
[从候选选 ▾]  [强度        ]  候选 1 2 3 5      ×
[固定字   ▾]  [at          ]  剧本里原样出现    ×
                                        [+ 加一格]
```

- 类型只有三个（任意文字 / 固定字 / 从候选选）——`multi`（可多值）变成行内一个勾；
- **`必填` = 现在的"可以不填"反过来说**（编剧只关心"这个空能不能空着"）；
- 选"固定字"时，"候选"那一格**不出现**（对应 `[SerializeReference]` 的 foldout 行为）。

### 改动 B：右边加一块**实时预览卡片**（第二优先，但它才是"对应"的解药）

用户反复说"UI 和自定义模块一定要对应"。**最好的"对应"是让人在配置时看见结果。**

```
右侧：卡片上会长这样
  mycue
  喊话  [闪电]
  强度  [3]
  位置  [left]
```

改左边任何一格，右边立刻变。技术上不难：`build_declaration()` 的产物
喂给现有的 `dynamic_spec_columns()` + `BeatCardEditor._add_spec_cell` 就能画出来 ——
**因为它已经是"声明的消费者"了**，等于把卡片那套复用一遍。

### 改动 C：`pattern` 与 `clauses` 合成"一格一格"，子句只是"带关键字的一格"

现在人要在两个地方想"这算位置格还是子句"。合成后：

```
[at ▾ 固定字] [位置 ▾ 任意文字] …
```

即：**子句 = 一个"固定字 + 值"的组合格**，界面上仍是"一行一格"，只是多一个
"它前面有个固定词"的勾。`pattern` / `clauses` 留在 JSON 里，界面不再分两段。

---

## 5. 实施顺序（建议）

| 步 | 做什么 | 风险 | 观感收益 |
|---|---|---|---|
| 1 | 格子改"一行一格"+ 类型驱动可见字段（改动 A） | 中（要动 `FieldCard`，有地狱测试守着） | 大 |
| 2 | 右侧实时预览（改动 B） | 低（复用现有渲染，只读） | **最大** |
| 3 | `pattern`/`clauses` 合并显示（改动 C） | 高（涉及声明结构） | 中 |

先做 1 + 2：**A 让填写变简单，B 让结果可见**。C 可以等前两个稳定了再说，
因为它动的是数据契约，不是展示层。
