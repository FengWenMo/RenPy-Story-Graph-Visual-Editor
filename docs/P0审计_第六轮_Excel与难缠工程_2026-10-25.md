# P0 审计 · 第六轮（2026-10-25 傍晚）：换角度 —— **用户的另一份资产是 Excel**

> 前五轮盯的一直是 `.rpy`（字节、行、回执）。这一轮的问法变了：
>
> **"如果我不是在改他的剧本，而是在改他的表呢？"**
>
> 本项目的产品前提是"对着表格编排演出"（`game/asset_tables/*.xlsx`、
> 每章一份 `.xlsx`），那么**工作簿就是用户的第二份源码**。而工具对 `.rpy`
> 已经有一整套判据（逐字节、备份、拒写、门禁），对 `.xlsx` 却几乎为零。
>
> 另一半动机来自你的一句话："真机没打到只是这个真机项目过于简单"。
> 所以这轮还补了一个**难缠但完全合法**的工程做矩阵测试（`sr_general`
> 里没有 menu、没有 if/elif、没有点号 label、没有重复台词）。

## 1. P0-E：一次「生成演出表」= 把用户的 Excel 清空重建

### 1.1 复现（`tools/_p0_audit_round6_xlsx.py`，修前）

```
① 首次摊表 → 16 张表
② 策划在同一份工作簿里：
     · 加一整页「角色设定」（小雨 / 17 岁，怕水 / 妈妈 / 出场三章）
     · 在 Beats 加一列「配音状态」（已录 / 待录）
     · A2 标黄 + 批注「这句要重录」
     · 冻结首行
③ 脚本改一句 → 再点一次「生成演出表」

[FAIL] A 自己加的「角色设定」页还在      ← 没了
[FAIL] B 自己加的「配音状态」列还在      ← 没了
[FAIL] C 那一格的批注还在                ← 没了
[FAIL] D 那一格的底色还在                ← 没了
[FAIL] E 冻结首行还在（还被改成 G2）      ← 变了
[FAIL] F 覆盖前留了备份                  ← 一份都没有
汇总：0/6 通过
```

### 1.2 根因

`export_beats_to_excel()` 第一行是 `wb = openpyxl.Workbook()`，最后一行是
`wb.save(output_path)` —— **整份新建再覆盖**。而它是"表"这条路上
**唯一**的写入口（`open_rpy_as_table` / `generate_table` / CLI `rpy2xlsx`
全走它）。

有意思的是，代码里早就有过同一个教训、但只修了一半：

```
# asset_registry._write_script_tables
# ⚠ 已存在的表只追加，绝不整份重写（2026-10-05 实测踩到）：
#    重建 images 时如果顺手 write_dict_to_excel(characters.xlsx, …)，
#    会把用户手工维护的角色表整张覆盖（实测：手写的 hand_made 那行没了）。
```

—— 资源表那边学会了"append-only"，剧本表这边还在"整份重建"。

### 1.3 修法：重建工具那几张，人的东西带走

新模块 `storygraph/story/xlsx_preserve.py`，四件事：

| 做什么 | 怎么判"是人的" |
|---|---|
| 快照用户自加的**整页** | 页名不在工具白名单（`Beats` / `Candidates_*` / `词表` / `舞台快照` … 11 张） |
| 带走整页的**值 + 样式 + 批注 + 列宽 + 合并 + 冻结** | 逐格复制 `_style` |
| Beats 里用户自加的**列** | 表头不在工具列集合里 → 按 **`LineId`（隐藏的"行号"列）** 回填，行增删也对得上 |
| Beats 上**人标过**的格子（底色 / 字色 / 批注）+ 冻结窗格 | 按 `LineId` + **表头名**定位（工具可能新加动态列，列号会右移） |
| **覆盖前备份** | `ch1.bak-20261025-155226.xlsx`，保留最近 3 代 |

为什么按 `LineId` 而不是行号：脚本改一句，行号就漂了；而"这句要重录"
是**跟着那句话说**的。为什么按表头而不是列号：`with 的转场` 这类动态列
会让列号整体右移。

备份的意义是兜住 openpyxl 搬不动的东西（图表 / 透视表 / 切片器）。
**不静默**：保住了什么、备份在哪、有几行对不上，都进日志与 CLI 回执。

### 1.4 复测

```
[PASS] A 自己加的「角色设定」页还在
[PASS] B 自己加的「配音状态」列还在（值 ['已录','待录'] 一一对应）
[PASS] C 那一格的批注还在（'这句要重录'）
[PASS] D 那一格的底色还在（00FFF2CC）
[PASS] E 冻结首行还在（A2）
[PASS] F 覆盖前留了备份
汇总：6/6 通过
```

额外钉了一条：**未知列不许影响导回** —— 带「配音状态」列的表照样能
`import_beats_from_excel` 读到正确的 3 拍（判据 `test_unknown_column_does_not_break_import`）。

## 3. 点号 label：工具自己示范、自己导不出去

`ui_qt/window_nodes.py` 的新建 label 对话框原话：
"新 label 名（**可以用点号**，如 `main.route`）"。
而 `patcher._LABEL_LINE_RE = r'^(\s*)label\s+([A-Za-z_]\w*)(.*)$'` —— `\w` 不含点：

* `label main.route:` 认不出是 label 行 → 补丁把它当正文 → 整章一句都对不上 →
  导出被拒（"1 句台词在补丁结果里找不到"）；
* 同一份文件在 `pipeline/statement_probe.py` 里早就是 `[A-Za-z_][\w.]*`（对的）。

修法：`[A-Za-z_][\w.]*`；顺手把 `choice_point` 的前缀校验也统一
（`[A-Za-z_][\w]*(?:\.[\w]+)*`）：`main.route_choice_1` 在 Ren'Py 里完全合法。

复测：

```
=== 点号 label（main.route）===
  OK   点号 label 拍=2
  OK   点号 + 行尾注释
```

## 4. `removed_count` 恒少算：一条判据静默失效的连锁

P0-D 的回执里那句"删掉了 N 行"，数量取的是 `PatchResult.removed_count`。
`removal_note` 里有个兜底（`count or len(preview)`），所以回执**看起来是对的**。

直到这轮加"表比源码旧"的判据时才发现：`removed_count` 在所有
"拍内跟着删掉的行"场景里**恒为 0**。

```python
# 修前
removed_count=(removed_lines + shrunk_total)   # shrunk_total 是 patch_export 的局部变量
```

`shrunk_total` 在 `patch_export` 里只初始化（3853 行）、从不累加 ——
真正的累加在另一个对象上（`st.shrunk_total`，3675 行）。

后果链：`removed_count=0` → 我新写的 `staleness_note(removed_count=0)` 直接返回空
→ "表比源码旧"这句话永远不出现 → 用户又回到"丢了行、不知道为什么"。
**一个少算的数字，能让三条判据同时哑掉。**

修法：`removed_lines + st.shrunk_total`。修后同场景
`removed_count=2`、`stale_note` 正常出现。

## 5. 隐藏列「来源指纹」（你批的那条）

### 5.1 它解决什么

"表过期"从前只有一条**间接**证据（2026-10-21 那条守卫：源里有台词被判删、
同时表里有句子在源里找不到）。而"只丢了 `$ flag = True` 这种行"时没有台词
被删 → 守卫不响 → 分不清"表旧了（丢了别人的行）"还是"用户清空了那一格"。

隐藏表「表信息」新增一行：

| 项 | 值 |
|---|---|
| 来源文件 | `…/game/ch1.rpy` |
| 生成于 | 2026-10-25T16:07:58 |
| 工具 | Renpy_Story_Graph_Editor |
| **来源指纹** | `19488a2653fedbae`（`sha1(原始字节)` 前 16 位） |

### 5.2 它的用法（刻意的边界）

只在**这次真要删行**（`removed_count > 0`）时说话：

```
增量补丁：只改了 4 行，原文其余部分逐字节保留；**删掉了源文件里 2 行**
（表里已经没有对应内容）：$ flag = True / play music "bgm.ogg" fadein 1.0；
**这张表比源码旧**（源码在摊表之后又被改过）：这次删掉的那几行很可能是
别人刚写的，不是你清空的。先把这一章重新载入（表会拿到新行）再导出。
```

**为什么是"说清楚"而不是"拦住"**（这是本轮唯一一个我主动收窄的地方）：

* 指纹匹配时不该拦 —— 那是用户自己清空了一格，拦住会把常用路堵死；
* 指纹不匹配时也不该拦 —— 因为**工具自己写回 `.rpy` 之后，指纹立刻变旧**
  （源码被我们改了）。真拦的话，正常节奏会变成"每次导出都要先重新摊表"，
  用户会开始闭眼点"仍要覆盖"——那比不拦更危险。
* 所以它只做一件事：**把"为什么丢了行"从猜变成事实**，并且指出下一步
  （重新载入这一章）。真正的兜底是 `removed_count` 的精确点名（§4）。

老表（没有指纹）→ 不猜、不报，行为与从前一致。

## 6. 没修的（逐条给理由）

| 项 | 级别 | 为什么 |
|---|---|---|
| `app/tables.export_character_table()` 整份重写 `characters.xlsx` | P2 | **没有调用点**（只在 `__all__` 里）。真接上线就会重演 P0-E，所以留了记录；建议下次要么删掉、要么改成 append-only（`_write_script_tables` 已经那么做了） |
| `write_asset_excel()` 在"资源表坏了"时整份重建 | P1 | 只在**表格解析失败**时走（正常表走早退），且重建前 `_quarantine_broken_tables` 会把坏表隔离留档。要根治得给资源表也做"保住用户列"，工作量与 P0-E 相当，建议单独一轮 |
| `collab pull` 整份重写 xlsx | P2 | 同步工具的固有语义（拉取即覆盖），与 git 同类；已有 `collab_status` 提示 |

| `format_compile_result` 与 `_report_incremental` 一次导出两段回执 | P2 | 两段现在说的是同一件事（都点名删行 + 都提"表旧了"），只是啰嗦 |

## 8. 一句话

前五轮我在守**"不弄坏他的剧本"**；这一轮守的是**"不弄坏他的工作台"**。
而这一轮最贵的一条教训是：**一个少算的数字会让三条判据同时哑掉**——
所以"回执里的每个数都必须是真算出来的"，不是排版问题，是安全问题。
