# 拍模型加作用域：把循环体升到 T0（设计与分期）

> 状态：**方案已定，未实施**（2026-10-07 第三轮）。
> 这一轮做掉了 CST 加固 / 幂等收尾 / 每参数一列 / `camera` 接住；
> 循环体升 T0 是唯一没做的，它也是四项里唯一"改拍结构 + 改核心渲染"的。

## 1. 现状（D2 做到了哪一半）

`while` / `for` 现在是 `StatementKind.LOOP`：

```
text   = 整块原文（渲染的真相）
header = 头行（可编辑，藏在隐藏列 LoopHeader）
body   = 块体各行（逐字，相对缩进）
```

拍上是"**一张拍承载整块**"（`Beat.opaque` + `Beat.loop_header`），渲染走
`emit_opaque()`：**头行改了就替换首行、没改就逐字吐原文**。

于是能力等级是 **`T0b`（内置 IR + 块体逐字）**，不是 `T0` —— 这正是当初刻意的
诚实（`core/capability.py`：「不许拿'接住了'冒充'完全理解了'」）。
要升 `T0`，块体必须成为**可结构化编辑的拍**，而那需要拍模型回答一个问题：

> 这一拍**在哪个块里**？循环体会重复执行，扁平的一维语句流表达不了。

## 2. 为什么它不便宜（先摆清代价，再谈方案）

| 维度 | 现状 | 升 T0 之后 |
|---|---|---|
| 拍的数量 | 循环 = 1 张拍 | 循环 = 1 张头拍 + N 张块体拍 |
| 渲染 | 逐字吐原文（**结构上**不可能改到别人的排版） | 每张块体拍各自渲染、再整体缩进一层 |
| 增量对位 | 1 个身份（整块） | N+1 个身份，每个都要能配回源行 |
| 老表（只有 `LoopHeader` + `Opaque`） | —— | **必须继续能读**（走旧的逐字路，等级退回 T0b） |

真机（`sr_general`）里 **只有 1 处循环、块体 2 行**（`mini_game1.rpy` 的游戏
主循环）。所以这一项是**为架构做的**，不是为眼前的数据做的 —— 收益要在
"以后写循环的人能像编辑台词一样编辑循环体"上兑现。

⚠ 历史教训：`menu` 那次同规模的改动分了 **B 阶段一/二/三** 三轮才收口，
中间踩过"半截菜单"（多吞/少吞一拍 = 静默改剧情）。**循环体同样会踩这个坑，
而且比菜单更隐蔽**：少吞一拍 → 那拍跑到循环外面**只执行一次**；多吞一拍 →
它被**执行多次**。两种都不报错。

## 3. 方案（与菜单那套同构，不发明新机制）

已经有的零件（**全部复用**，这是方案可行的关键）：

- `core/nest_path.py`：块路径 DSL（`if:1>menu:2>A>if:3`）+ `join_nest` /
  `split_nest` / `body_chain`；
- 隐藏列 `Nest`（`Beat.nest_path`）：结构位随表走，渲染器**已经**按它建树；
- `beat_render.split_beat_units()` / `_take_menu_run_by_path()` /
  `render_menu_block()`：**扁平拍 → 嵌套块**的整套做法。

### 步骤 1 · 解析：块体也产出语句，标上结构位

`_stmt_loop` 现在只造一个 `LoopNode`（头 + 逐字块体）。改成：

- `LoopNode` 增加 `body_nodes`（把 `line.subblock` 按**正常分派**递归解析出来的
  AST 节点，而不是当文本抄一遍）；
- `ParseResultBuilder._walk` 在 `LoopNode` 分支里：**先**给头行一条语句
  （`StatementKind.LOOP`，payload 只留 `header` + `text`（头行原文）），**再**
  以 `nest_path=join_nest(外层, f'loop:{n}')` 递归 walk `body_nodes`；
- `counters['loop']` 与 `counters['if']`/`['menu']` 同一套（label 内文档序）。

判据：`while "x"` / `for "台词"` 仍是台词（**已有**，别弄坏）；
`while cond:` 的块体里 `$ a` / `call x` / 嵌套 `if` 都各自成为一条语句。

### 步骤 2 · 拍：头变"组头"，块体成普通拍

`beat_build._emit_loop` 拆成两件事：

- 头行 → 组头拍（**像 `_emit_menu` 那样**：`kind` 仍是内部标记，带
  `loop_header` + `nest_path`，`opaque` **为空**）；
- 块体语句 → 走**正常 handler**（`_emit_say` / `_emit_python` / …），
  它们的 `nest_path` 由 `mark_struct` 转发（已有机制）。

⚠ **兼容线**：老表里 `loop_header` 非空**且** `nest_path is None` → 那些拍还是
"一张拍承载整块"，渲染走逐字路，等级 `T0b`。这条兼容线**必须有判据**。

### 步骤 3 · 渲染：加一个 `loop` 单元

`split_beat_units()`：

```python
if _is_loop_head(beats[i]) and plan['known'].get(label):
    run, i = _take_block_run_by_path(beats, i, 'loop')
    units.append(('loop', run))
```

`_take_block_run_by_path` 就是把 `_take_menu_run_by_path` 里的 `menu:{k}`
换成参数化的段名（**同一份实现，参数化**，不是复制一份 ——
复制一份 = 两套边界判据 = 迟早漂移）。

`render_loop_block(run, indent)`：

```python
lines = [f'while {header}:']            # 头行原文/编辑后的头行
for kind, unit in split_beat_units(run[1:], use_paths=True):
    lines += _render_unit_lines(unit, indent + '    ', ...)
```

**递归**要保住：循环里套菜单、菜单选项体里套循环，都靠 `split_beat_units`
的递归（菜单那条路已经这么做了）。

### 步骤 4 · 等级与报告

`capability_of`：`raw_kind='loop'` 时，**看这一拍有没有结构化的块体**：

- 头拍 + 块体拍都在（`nest_path` 齐）→ **`T0`**（"结构化列全功能编辑"成立）；
- 只有 `Opaque`（老表 / 结构位缺失）→ **`T0b`**（与今天一致）。

`coverage_of_beats` 要跟着改（它现在靠 `loop_header` 认循环；
升 T0 之后"头拍 + 块体拍"要算成一份，别让覆盖率虚高 —— **这是最容易自欺的
一处**）。

## 4. 判据（先红后绿）

改 `tests/test_loop_model.py`（它现在钉的是"必须 T0b"，要改成"**两种形态各自
成立**"）：

1. 结构化循环：`while cond:` 头 + 块体台词/`$`/`call` 各自成拍，**等级 T0**；
2. 老表形态（只有 `LoopHeader` + `Opaque`）：等级 **T0b**，逐字节不变；
3. **不误伤**：`while "x"` / `for "台词"` 仍是台词；
4. **边界不多不少**（菜单那次的教训，用真机形状做夹具）：
   - 循环体后面那一句**不许**被吸进循环（吸了 = 执行多次）；
   - 循环体里最后一句**不许**掉到循环外（掉了 = 只执行一次）；
   - 嵌套：循环里套菜单、菜单里套循环，逐层缩进正确；
5. **没改就逐字节**：`t0 → t1` 允许排版归一，`t1 == t2 == t3`
   （`tools/audit_idempotence.py`，真机 53 个文件必须仍全绿）；
6. **增量**：`--source` 那条路对含循环的章节仍能配对（`tools/journey_check.py`
   第 8 步 + `tests/test_incremental_export.py`）。

## 5. 风险与回退

- 最大风险：**边界不多不少**（第 4 条）。菜单那次的 "半截菜单" 是静默改剧情，
  循环这边更隐蔽 —— 判据必须先写，且夹具要"脏"（选项体/块体里夹注释、空行、
  相邻同构块）。
- 第二大风险：**增量对位**。循环体从 1 个身份变成 N+1 个身份，配对键变了。
  回退点：`Beat.opaque` 那条逐字路**不许删**（它是老表与新代码的共同底线）。
- 回退策略：完成步骤 1~2 之后**先不切渲染**（`split_beat_units` 仍走老路），
  用对拍器（`nest_placement_conflicts` 那套）比"结构化推出来的摆法"与
  "老路摆法"是否一致；全绿再切渲染 —— 这正是 B 阶段一/二的顺序。
