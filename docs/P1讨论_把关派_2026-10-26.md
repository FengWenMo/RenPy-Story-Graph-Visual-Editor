## ① 无标题 menu 加标题（从无到有）

### 判词：**只修报错体验**（通道扩展缓修；主路径不动）

### 现象残骸（实测）

仅两种形状仍被拒，拒因都是同一句"1 处新增内容没能落进产物"：

```
[FAIL] B  无标题 + extras `set seen`        （菜单块里有非标题行）
[FAIL] B2 无标题 + extras `$ seen_x = 1`    （同上）
[FAIL] H  `menu:  # 备注`（行尾注释）从无到有
```

而**有标题 + extras 改标题是 PASS 的**（J/K 形状）——说明 extras 本身
不挡路，挡路的只是"从无到有"与它们的组合。根因在
`patcher._replace_matched`（`storygraph/story/patcher.py:1577`）的窄判据：
整段换标题要求 `old_lines[1:]` / `gen_bodies[1:]` **全部**是 caption 行，
extras 行不是 → 判据不过 → 走普通配对 → 新标题行落不了地。
H 同理：`_MENU_HEAD_RE…endswith(':')` 对 `menu:  # 备注` 不成立
（`_norm` 不去行尾注释）。

### 修的话，最危险的那条岔路

**放宽"其余行全是 caption 行"的判据**（允许 extras 混在 gen_bodies 里一起
整段换）。那一步会毁的字节是：`set seen` / `$ seen_x = 1` 这类**菜单块里的
用户语句**——它们会被算进"标题区间"整段替换掉，或被挤到错误的行位。
`extras` 在 `beat_build` 里是**逐字节保留**的设计（`MenuNode.extras` 的
docstring 明说"从前 `_parse_menu` 遇到就跳过——静默丢弃，行为悄悄变了"），
任何让它们动起来的修法都是往回走。

次危险：修 H 时顺手把 `_MENU_HEAD_RE` 放宽到"去注释后以冒号结尾"——
若还原时把行尾注释丢了/复制了两份，就是 P0-9 注释通道踩过的坑
（`_menu_head_caption_merge` 里那段"照抄会写出两份"的教训）。

### 红线（修成这样必须拒）

- 若产物里 extras 行（`set seen` / `$ …`）与原文**不逐字节相同**（内容或
  相对行位变了）→ **必须 `ok=False`**。
- 若"从无到有"插的标题行落进了 extras 之间（与渲染顺序不一致）→
  **必须 `ok=False`**。
- 若 `menu:  # 备注` 的行尾注释在产物里消失或重复 → **必须 `ok=False`**。
- 以上任一做不到时，保持现状的拒绝 + 说清"菜单块里有代码行/行尾注释，
  加标题请用全量重写这一章"，**不许硬写**（铁律 2/3）。

### 参照物

`_replace_matched` 的注释块通道（`patcher.py:1490` `_comment_run`）：
"整段换"的先例，判据收窄到**恰好一处连续注释块**才动手，其余不猜——
① 的死角修复应当照抄这个纪律：只认"extras 恰好全部在标题区间之外"
这一种形状，别的继续拒。

## ② 真机复杂文件上移动拍被拒

### 判词：**不修**（重排判据一个字都不许放宽）+ 只修报错体验

### 现象残骸（实测）

`tools/_p1debate_gate_move_stats.py`，真机 `script_pomo.rpy`（55 拍）：

| 移动距离 | 成功率 | 拒因大头 |
|---|---|---|
| 1 | **52%**（28/54） | 挪过结构块头 11 / 结构拦截 5 / 认不出的行 3 |
| 2 | 36%（19/53） | 挪过结构块头 13 / 认不出的行 6 |
| 3 | 31%（16/52） | 挪过结构块头 16 / 认不出的行 5 |
| 5 | 28%（14/50） | 挪过结构块头 16 / 认不出的行 8 |

被拒的分三类：

1. **该拒的（大头）**：挪过 `if`/`elif`/`else:`/`screen`/`menu` 选项头、
   跨 label、块头单独搬——这些全是**改剧情/改结构**，拒因已说人话
   （"挪出分支后条件不再生效——那是改剧情，不是排版"，`patcher.py:3113`）。
2. **审计点名的痛点**："重排段里有认不出的行"（约拒因的 15–30%）——
   那些行是 `image overworld = …`、`define persistent.pomoscript = True`、
   `jump pomo_script2`、`$ renpy.pause(hard=True)`：**不属任何拍的顶层行**
   夹在两拍之间。`_plan_reorders`（`patcher.py:3093`）要求重排段的空隙
   "只许空行/注释"，于是被拒。
3. 校验兜底："N 句台词在补丁结果里找不到"——重排产物对不上，**必须拒**
   （铁律 2 的第二道门）。

### 不修的理由（毁什么数据、谁能救回来）

空隙里那些"认不出的行"**恰恰是位置敏感的**：
`$ renpy.pause(hard=True)` 是暂停点、`jump` 是去向、`define` 是初始化顺序。
让拍**绕着它们换位**，等于把暂停点/跳转点与台词的相对顺序改掉——
文件字节一个没坏，**剧情语义被改了**。这违反铁律 1 的精神
（不归己的行虽然没动，但它归属的"顺序语义"被工具改了），
而且**没有任何回执能发现**：diff 里这些行原封不动，坏的是它们的邻居。
用户救不回来——他自己都不一定知道顺序被换了。

"移动等于不可用"不成立：相邻移动一半能过，过不去的多半是**该拒的**。

### 红线

- 若重排后，重排段空隙里任何非空非注释行的**相对顺序**（相对段内拍）发生
  变化而回执未点名 → **必须 `ok=False`**。
- 若放宽空隙判据的实现里，出现"认不出的行原地不动、拍绕行换位"或
  "认不出的行跟着某一拍走"两种策略中的任何一种 → **必须 `ok=False`**
  （两者都是猜，铁律 3）。
- 移动涉及带条件的拍、跨 label、过块头 → 保持 `ok=False`（现状正确）。
- 报错体验可修：把"重排段里有认不出的行"升级为**点名是哪几行**
  （例：`$ renpy.pause(hard=True)` 不属于任何拍）+ "请先把这些行移出
  重排范围，或用全量重写这一章"。

### 参照物

`_plan_deletions`（`patcher.py:3146`）的纪律："只动该动的那几行，凡是
拿不准的一律放弃（退回全量）"——删行通道当年为了不删坏结构宁可整份放弃，
移动通道没有理由更松。`_plan_branch_deletion`（只动必须动的几行）同源。

## ③ 改 if 条件被拒

### 判词：**不修**（elif / 嵌套 / 清空保持拒绝；单层与链头已修）+ 报错已达标

### 现象残骸（实测）

```
[PASS] 单层 if 条件        → 只动 `if flag:` 一行
[PASS] 链头（elif 链）条件 → 只动 `if a == 1:` 一行，elif/else 逐字节不动
[REJ]  elif 支条件         → 拒因具体（展平累积条件没法一行表达），文件未动
[REJ]  嵌套 if 条件        → 拒因具体（累积条件含外层），文件未动
[REJ]  清空条件            → 拒因具体（拆结构），文件未动
[被拒] 真机 elif 支台词改条件 → 文件未动
```

"导出到 `build/renpy/` 可用" = 全量重写这条出路是通的，用户没有被困死。

### 不修的理由

elif 支在表里存的是**展平后的累积条件**（`(b) and not ((a))`），文件里是
一行 `elif b:`。用户改的那一格没法机械映射回一行——要映射就得**猜**
"用户想改的是哪一层"（`_split_negation` 只认两种形状，认不出就更得猜）。
猜错 = 改剧情。另一条岔路是把整条链重写成平铺 `if`——那是改用户没碰过的
结构行，违反铁律 1（P0-10 的审计判据原话："`elif`/`else`/`if` 行逐字节不动"）。
嵌套同理：累积条件含外层，光改内层一行写不出用户填的那句话。
清空条件 = 拆掉一层 `if` = 结构改动，从来就不该增量做。

### 红线

- 若条件改动导致 `if`/`elif`/`else`/`menu:` 等**结构行**（含缩进）在产物中
  变化（链头那一条 `_plan_condition_rewrites` 白名单内的除外）→
  **必须 `ok=False`**。
- 若从累积条件反推分支条件时分解**不唯一** → **必须 `ok=False`**（铁律 3）。
- 若"清空条件"被实现成增量删 `if` 行（而非拒绝）→ **必须 `ok=False`**。
- 全量重写路径（`build/renpy/` 导出）必须始终可用；报错必须继续指路
  （现状的 `_condition_hint` 已按 elif/嵌套/清空分了三种说法，达标）。

### 参照物

`_chain_renumber`（`patcher.py:2679`）：删支之后条件重算**在模型侧对账**、
文件里作者的结构行一个字节不动——"条件的事在模型侧解决，结构行不许碰"
的先例。`_plan_label_renames` 同理（单开一条通道、只在确定归属时改）。

## ④ `write_asset_excel` 表坏了才整份重建（有隔离备份）

### 判词：**修**——但修的不是"重建时保住内容"，而是三件事：
**收窄触发条件 + 回执必须点名损失 + 原件永不删除**。
**禁止**抢救式半解析。

### 现象残骸（实测，`tools/_p1debate_gate_asset.py`）

```
实验 B（images.xlsx 字节写坏）：
  坏文件 openpyxl 读不出（BadZipFile）
  → 改名 images.broken-20261026-*.xlsx，新表从扫描整份重建
  → 用户的「配音演员」列 /「分类说明」页 / 批注：哪都没有
     （broken 文件本身也读不出——字节就是坏的，物理上取不回来）
  → 回执：repaired=['images.broken-….xlsx'] 提了改名去向，
     **只字不提"手写内容没进新表"**
实验 C（music 坏、images 好）：好表不陪葬 ✅（人手内容保住）
对照 A（表能读 + 扫描）：列/页/批注全保住（P0-F 已修）
  附带发现："记了文件但文件不存在"的手写占位行会被删
  （P0-F 刻意判据"表跟随磁盘"，future2 被删 / future1 留）——
  设计内，不列入本次议题
```

### 为什么必须修（用户的先例约束）

P0-F 的现场，用户对**同一类问题**（资源表被整份重建）的原话是：
"**不要做隔离备份（这解决不了根本问题）**"，要求直接保住。
④ 现在走的恰恰是被否决过的那个形状：**隔离改名 + 整份重建**。
（P0-F 后来修的是"表能读"这条路——`xlsx_preserve` 直接保住，已验证。
④ 是它的边界外：表**读不出**。）

### 但有一条物理事实必须说清

**表坏了（zip 损坏）时"直接保住"在技术上不可能**——openpyxl 读不出坏 zip，
拿不出内容就谈不上保住。所以"修 ④"不等于"让坏表也能保住内容"。
把关派接受的修法只有：

1. **收窄触发**：只在"这张表确实读不出（BadZipFile 级）"时才隔离+重建；
   能 `read_excel_rows` 读出来的表一律走 P0-F 的保住通道
   （实验 C 已证明现状如此——这条要**钉成判据**，防止未来回退）。
2. **回执必须点名损失**（这是本轮最大的缺口）：
   "images.xlsx 读不出来（BadZipFile），已改名为 `images.broken-*.xlsx`；
   新表从扫描重建，**你在旧表里手写的列/页/批注没能带过来**
   （那份文件坏了读不出）；请用 Excel 打开 `.broken` 文件试试修复。
   ——而不是现在这样只报一个文件名。
3. **原件永不删除**：`.broken-*.xlsx` 留档是对的，保留；但**不许**出现
   "清理旧备份"之类的顺手删除。

### 修的话，最危险的那条岔路

**给坏 zip 做抢救式半解析**（抠 `sharedStrings.xml` / 逐格猜内容再写回新表）。
抠出来的东西必然不完整（样式、公式、合并格全丢，部分行可能残缺），
写回去就是**"半对"的产物**——正好踩铁律 2（要么全对、要么完全不动）。
第二个岔路：把 `parse_asset_tables` 的**任何**异常（钩子炸、路径错、
临时锁）都当"表坏了"走隔离+重建——误伤能读的表。
隔离判据必须钉在"`read_excel_rows` 这张表抛异常"上（现状已是，钉住它）。

### 红线（若…则必须 ok=False）

- 若某张表 `read_excel_rows` **读得出**，却被隔离或重建且人手内容
  （列/页/批注/手写行）丢失 → **必须 `ok=False`**。
- 若重建路径在未确认"这张表读不出"之前就整份新建覆盖 → **必须 `ok=False`**。
- 若回执只报"已修复/已重建"而不点名"哪张表、原件在哪、旧表手写内容
  没带过来" → **必须 `ok=False`**（铁律 6 的同款判据：不许用"成功"
  掩盖损失）。
- 若任何"抢救式半解析"的实现写出**部分**行/列 → **必须 `ok=False`**，
  整份放弃（铁律 2）。

### 参照物

1. **P0-F 的 `xlsx_preserve`**（`storygraph/story/xlsx_preserve.py`）——
   "表能读"时的直接保住，正是用户批的方向；④ 是它的边界条件，不该
   另起一套"半保住"。
2. **P0-B 的 `SourceNotUtf8`**（第五轮）——"坏载体宁可拒写、把原件
   一个字节不动地留给用户"的先例。④ 的对应姿势是：**坏表不硬救、
   说清楚、原件留给人**，不是"尽力恢复"。
3. `removal_note`（P0-D）——"删了什么必须点名"的唯一实现纪律，
   ④ 的回执应当照这个模式做成**一处实现、所有出口同一句话**。

## 五、绝对不该修的是哪条：**② 的重排判据放宽**

四条里只有一条，"修成功了"会**静默毁用户剧情**且事后无从发现——②。

- ①③ 的死角是**可用性**问题：拒了，文件没动，用户有全量重写这条出路；
  修好了顶多多敲一次键盘，修错了也只动标题/条件那一行，红线可判。
- ④ 是**安全**问题：正在丢数据，必须修；且修法有明确的物理边界（能读就保，
  读不出就留原件+点名）。
- ② 不同：它守的"空隙只许空行/注释"是在保**顺序语义**。一旦为了让移动
  可用而放宽，产物 diff 里**看不出任何异常**（认不出的行字节原封不动），
  坏的是它们与台词的相对顺序——暂停点、跳转点、初始化顺序被悄悄换位。
  用户、代码评审、金标测试三方都发现不了。这种"修"只有一个方向：
  从"宁可拒"滑向"猜一个"，而铁律 3 说得很清楚——**猜一个名字比说
  不知道坏得多**。

如果实现派和产品派都想动 ②，请先回答：
"空隙里那行 `$ renpy.pause(hard=True)` 该跟谁走？"——答不上来就不许动。

## 六、判词总表

| # | 判词 | 一句话理由 |
|---|---|---|
| ① | **只修报错体验**（通道扩展缓修） | 主路径已修；extras/行尾注释死角拒得对，硬修会动 `set seen` 这类用户字节 |
