## 2. 项目结构

### 2.1 分层存在，但契约没有自动化守卫

项目文档（README 与记忆）明确写了单向依赖契约：

> core ← parsing/excel ← assets/story ← pipeline ← ui，story 层不许顶层 import pipeline

实测包间依赖，发现 **4 条违约，其中 2 条是顶层硬依赖**：

| 违约边 | 类型 | 位置 | 性质 |
|---|---|---|---|
| `graph → app` | **顶层** | `graph/commands.py:4`、`graph/editor_utils.py:7` | 可接受（见下） |
| `pipeline → app` | **顶层** | `pipeline/renpy_exporter.py:2` | 可接受（见下） |
| `assets ↔ story` | 延迟 | `assets/asset_engine.py:375` | 环状 |
| `parsing ↔ graph` | 延迟 | `parsing/renpy_parser.py:116` | 环状 |
| `pipeline ↔ story` | 延迟 | `story/script_table.py:284` | 环状 |

**需要修正我自己的第一判断**：`graph → app` 与 `pipeline → app` 依赖的是 `app/notify`，那是**设计正确的通知端口**（模块文档明令"禁止在本模块里 import 任何 UI 框架"）。这是依赖倒置，不是泄漏。

但**真正的问题在别处**：

1. **没有任何测试守卫依赖方向**。契约写在文档里，靠人自觉。`grep -rl "depend\|依赖\|架构" tests/` 没有一条架构守卫测试。契约 14 因此是一条"口头契约"。
2. **`app` 包是职责混杂的篮子**：`notify`（端口）、`editor`（1843 行 EditorSession，UI 无关会话）、`beats`（1051 行选项计算）、`stage`（984 行）、`thumbs`、`tables`、`asset_panel` 全在同一个包里。`ui_qt/main_window.py` 顶层 `from storygraph.app.editor import EditorSession`——说明 `app` 既不是纯 UI（`ui_qt` 才是），也不是纯领域（`core`/`story` 才是）。**命名模糊 = 边界模糊**。
3. **`story/script_table.py` 门面 re-export 私有函数**（`_absorb_native`、`_hydrate_audio`、`_split_image_name`…）。这是**封装倒退**：私有 API 经公共门面固化为公共契约，以后重构 `_hydrate_audio` 就会破坏 `script_table`。门面文档写得很好，但这件事做反了。

### 2.2 值得肯定的结构决策

- `story/` 已从 3.8k 行上帝模块拆成 12 个模块 + 兼容门面，环靠延迟 import 压住
- `notify` 端口让后端不依赖前端框架，无头环境零副作用（这是对的）
- `generation_guard` 让"落盘"只有一个入口，`validate` 承诺不写盘
- Git log 显示"修复双IR问题"是最新提交，`Node.statements` 已收敛为结构化真源

## 3. IR 层：合理之处与根本缺陷

### 3.1 做得对的地方

`core/statement.py`（557 行，零依赖）质量高于平均：

- `kind` 用字符串常量类而非 Enum，与 Excel 列直接对应——这是**有理由的**选择
- 每种 kind 显式定义哈希输入，不用 `canonical(payload)`
- `validate_hash_contract()` 自检加字段忘了同步哈希的坑
- `__hash__` 与 `__eq__` 同源（用 `_freeze` 而非 `content_hash`），注释里明确解释了为什么不能用 content_hash
- `MARKER = '\x01'` 的来历写成了事故复盘（三处硬编码 → 收敛到一处）

### 3.2 根本缺陷：IR 是"语句流"，不是"语句树"

`Statement` 是**扁平**的：`kind + payload + condition`。15 个 kind 里没有任何一个能表达"包含子语句"。

后果在真实数据上直接暴露。Ren'Py 的 `menu` 是**嵌套块**：

```
menu:                 ← 块
    "选项A":           ← 分支头
        jump b        ← 分支体（属于选项A）
    "选项B":
        jump c
```

而 Beat 是扁平拍，`render_beat_to_rpy` 是**单拍渲染器**。实测：

```
输入：menu 块（2 选项）
输出：
    label a:
        "选项A"        ← 变成裸旁白！
        jump b         ← 无条件执行
        "选项B"
        jump c         ← 永远不可达
    return
```

**`menu:` 块整个消失**，选项变成旁白台词，第一个分支无条件跳转，第二个分支死代码。

这不是"丢失了一条语句"，是**把交互结构压成了顺序流**。游戏能启动，剧情全错，且不报任何错。

### 3.3 同一根因的第二症状：else/elif 靠 `not()` 展开

真实项目解析出的 `condition` 长这样：

```
player_score == game_rounds
not ((player_score == game_rounds))                          ← 这就是 else
(breakline == 2) and not ((breakline == 1))                  ← 这就是 elif
(breakline == 3) and not ((breakline == 1) or (breakline == 2))
```

`elif` / `else` **不是被建模，而是被"展开"成前一条件的否定合取**。这是把树形分支压扁成一维条件链的典型手法。代价：

- 条件含副作用或非布尔语义时会算错
- 嵌套 `if` 无法表达
- 一旦某个谓词被改写，`not(...)` 链不会同步更新

### 3.4 弱类型 IR 的代价：加 kind 会静默漏改

`payload` 是 `dict`，15 个 kind 共用一个 dataclass。数据与行为没有绑定：

- 描述 kind 的声明有 **4 份**：`_HASH_FIELDS` / `_FACTORY_FIELDS` / `validate_statement.required` / 各工厂方法签名
- `validate_hash_contract()` 只串联了其中 2 份
- **实证缺口**：`_FACTORY_FIELDS[CALL] = ('target',)` 漏了 `from_clause`，而 `make_call` 实际写入 `from_clause`——自检没抓到，因为 CALL 不参与哈希就被跳过了

于是"新增第 16 种 kind"要改 N 处，**编译器不会提醒你漏改**。这正是 menu 在渲染层漏实现却没有被任何机制拦下的原因。

### 3.5 其他 IR 层问题

| 问题 | 位置 | 严重性 |
|---|---|---|
| `MARKER='\x01'` 把元数据编码进数据文本 | `statement.py:31` | 中（注释承认是 hack，payload 形状优先于类型清晰） |
| `content_hash` = md5 前 8 位（32 bit） | `statement.py:228` | 中（10 万条量级生日碰撞概率极高；未说明为何 md5） |
| `MENU_OPTION` 哈希前缀是 `'menu'` 不是 `'menu_option'` | 历史兼容 | 低（注释已说明是刻意决策） |

## 4. 模块深度与模糊性

### 4.1 深度：细，但转换层是过程式的

1354 个函数中位 12 行 = 粒度健康。但转换层不是按 kind 表驱动，而是巨型 if/elif：

- `_parse_statement`：375 行，cc=59（所有语句类型的分派都在一个函数）
- `render_beat_to_rpy`：194 行，cc=37
- `beats_from_statements`：337 行，cc=78

**"数据驱动的 IR + 过程式的分派"是错配**。若每个 kind 自带 parse/render，加 kind 只需加一处，漏实现会立刻在运行期报"没有 render 实现"，而不是静默降级。

### 4.2 模糊性清单

| # | 模糊点 | 证据 |
|---|---|---|
| 1 | 音频三套表示并存 | `beat.bgm` / `beat.sfx`（文本，"真相源"）与 `music`+`music_params`+`music_action`、`sound`+`sound_params`+`sound_action`（结构化） |
| 2 | 读了不存在的列 | `beat_model.py:778-782` 读 `MusicAction` / `SoundAction`，但 22 列表头里没有这两列 → **死代码**，永远回落到默认 `'play'` |
| 3 | Beat 35 字段 vs 22 列 | 13 个字段无列承载，其中包含 **`condition`** |
| 4 | `app` 包定位不明 | 端口 + 会话 + 选项 + 缩略图混装 |

## 5. 实测效果（真实项目）

### 5.1 解析能力：0 失败

41 个文件全部解析成功，产出 3803 条 Statement，降级率 5.8%。

```
say 1874   comment 495   python 464   show 397   raw 221
hide 92    scene 71      play 64      extend 35  jump 32
return 25  menu_option 20  call 8     menu 5
raw 构成：screen 129 / unmodeled 81 / call_screen 11
```

解析层面**是扎实的**。

### 5.2 端到端往返：真实丢失 2.0%，但高度集中

测法：原文 → parse → beats → **xlsx** → beats → compile → re-parse，比对 Statement 多重集（归一化空白，排除纯空格差异）。

| kind | 原文 | 真实丢失 | 丢失率 |
|---|---|---|---|
| menu | 5 | **5** | **100%** |
| menu_option | 20 | **20** | **100%** |
| call | 8 | **7** | **87.5%** |
| raw | 221 | 11 | 5.0% |
| python | 464 | 22 | 4.7% |
| show | 397 | 5 | 1.3% |
| say | 1874 | 6 | 0.3% |
| comment / scene / hide / play / extend / jump / return | — | **0** | 0% |
| **合计** | **3803** | **76** | **2.0%** |

**总量 2% 看着不错，但分布致命**：丢失 100% 集中在**分支结构**上——这正是视觉小说的命脉。

### 5.3 三个已确认缺陷（P0 / P1）

**P0-1　menu 块在往返后整体消失**
复现：2 选项 menu → 产物 `"选项A"` / `jump b` / `"选项B"` / `jump c`，无 `menu:`，第二分支不可达。
影响：游戏可启动、无报错、剧情错误。

**P0-2　`Beat.condition` 不落 Excel**
`to_row()` 返回的 22 个值里没有 `condition`，`from_row()` 也不读。
实测 `mini_game1.rpy`：往返前 7 条条件 → 往返后 **0** 条；产物 `if` 行数 5 → 1。
影响：所有 `if` 分支被抹平为顺序执行。注意：**渲染层 `beat_render.py:329` 是正确的**，丢在序列化层，所以 `.rpy → .rpy` 不出错，一经过 Excel 就丢。

**P1-3　台词尾部空格被吃掉**
`'元神，启动！ '` → `'元神，启动！'`，`chapter0_0.rpy` 一处 116 条。
严重性**低**（不影响语义），但与项目自己定的"逐字节不变"契约冲突。

### 5.4 为什么 1731 个测试全绿却没抓到

**测试只测了 A→B 半程，没测 B→Excel→B' 全程。**

`tests/test_script_table.py`：

```python
def test_condition_from_if_block(self, write_rpy):
    beats = beats_from_parse_result(result)
    assert beats[0].condition == 'love > 5'      # ← 止步于此

def test_menu_option_becomes_own_beat(self, write_rpy):
    beats = beats_from_parse_result(result)
    assert beats[0].kind == KIND_MENU_OPTION      # ← 止步于此
```

两条都断言到 `beats_from_parse_result` 就结束，**没有导出 Excel、没有回导、没有重新编译**。所以"Excel 双向同步"这条**对外承诺的核心能力**，测试覆盖的是它的前半段。

做过 `export_beats_to_excel` 的只有 5 个测试文件，其中断言 menu/condition 的条目基本为零。

**结论：测试数量（1731）不等于测试有效性。缺的是"往返不变式"这一整类测试。**

## 7. 总体判断

**结构分层合格，工程纪律高于平均，IR 层的抽象层级不够。**

项目已经跨过了"能跑"的门槛（解析 0 失败、降级率 5.8%、1731 测试、生成门禁、协作锁），现在卡在的是**抽象层级的天花板**：用扁平的语句流去表达本质上是树的剧本结构。这个选择在过去是省事的（Excel 天然是二维表），代价现在开始兑现——分支结构在双向同步中静默损坏。

最需要优先做的不是加功能，而是**补一类测试**：往返不变式。因为它一旦存在，P0-1 和 P0-2 会在补上的当天自动暴露。
