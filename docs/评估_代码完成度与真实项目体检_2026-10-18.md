## 0. 先说结论

**这套东西的骨架是对的，工程纪律在同类项目里罕见；但"产物正确性"这一环没有闸门，导致它在真实项目上会静默改坏脚本。**

具体三句话：

1. **能用的部分是真能用**：常规章节（台词 / 旁白 / show / scene / menu / 跳转）走增量补丁往返，
   你的真机项目 52 个写盘文件里，**22 个在剥掉"首行生成标记 + 空行"后逐字节完全相同**，
   其余的差异也只有空行和换行符 —— 保真不是吹的。
2. **不能用的地方很致命**：一旦碰上官方示例级别的写法（`menu:` 块内 caption、`call` 带参数、
   `u"..."`、块内顶格注释、带 BOM 的文件），产物**过不了引擎 lint**，而工具自己不会发现
   —— 因为它构建/导出**从不跑引擎**。
3. **离"50 人工业化"还差一层**：Excel 之间没有活引用（0 个公式）、协作库没有并发控制、
   多引擎导出是 JSON 示意。这三件恰好是你产品定义里最核心的三件。

一句话：**它已经是一个"能陪你一个人干活"的工具，还不是一个"能交给 50 人团队"的工具。**

## 3. 六条 P0：会把能跑的脚本改坏

> **【2026-10-19 复核结论】** 本节六条已在 `c186241` 结案，逐条复核见 §9。
> 其中 **P0-6 的前提是错的**（`u"..."` 原文本身就过不了引擎），已更正 —— 见 §9.2。

> **先说一件比这六条更要紧的事**：全量测试 **4945 条全绿**，这六条一条都没被拦住。
> 原因不是测试写得少，是**判据的口径**：现有测试验的是"工具自己前后一致"
> （往返稳定、金标指纹、列对账），而"引擎能不能解析这个产物"从来没进过判据。
> 这就是为什么"全绿"和"跑不起来"可以同时成立 —— 闸门建在错的环节上。

判据统一：**原文合法 → 工具处理 → 产物不合法 / 语义变了 / 内容丢了**。
下面每一条都在最小样本上复现过，不是读代码猜的。

### P0-1 带 BOM 的文件，产物被引擎判语法错

- **现象**：原文 UTF-8 BOM 开头，产物把 `\uFEFF` 写到了**第一个内容行**的行首：
  `\uFEFF# This file demonstrates...`。这一行不再是注释，变成了一条语句。
- **引擎判词**（`the_question` / `tutorial` 实测）：
  ```
  File "game/indepth_text.rpy", line 3: expected statement.
      ﻿
      ^
  ```
- **影响面**：`tutorial` 23/23 个文件带 BOM，`the_question` 4/5 个，你的 `sr_general` 5/55 个。
  Windows 上的中文项目用记事本/VS Code 保存成 UTF-8-BOM 极常见。
- **为什么没被发现**：工具从不跑引擎；而自己的 `validate` 也没查"产物能不能解析"。

### P0-2 `menu:` 块内 caption 被写成 `menu "标题":`，引擎直接 parse error

- **原文（官方示例写法，最常见的一种）**：
  ```renpy
  menu:
      "As soon as she catches my eye, I decide..."
      "To ask her right away.":
          jump rightaway
  ```
- **产物**：`menu "As soon as she catches my eye, I decide...":`
- **引擎判词**：
  ```
  File "game/script.rpy", line 34: expected ':' not found.
      menu "As soon as she catches my eye, I decide...":
           ^
  ```
- **为什么**：Ren'Py 的 `menu` 头只接受 label 名 + 参数，不接受字符串。
  解析器把块内 caption 合并到了头部（`renpy_parser_stmts.py:191-195`），渲染时照着写出去（`beat_render.py:1794`）。

### P0-3 块内出现顶格注释 → 整段结构错乱

- **原文**：
  ```renpy
  label start:
      python:
          import random
  # 顶格注释
          def f():
              return 1
      e "after"
  ```
- **产物**：
  ```renpy
  # 顶格注释
          def f():
              return 1
      e "after"

  label start:
      $ import random
      return
  ```
- **性质**：`label start:` 被挪到文件末尾，`def f()` 被提到顶层并且缩进错乱。
  这不是"排版变了"，是**脚本结构被重排**。真机项目里作者自己写过这种注释，
  修复只覆盖了顶层区间，没修缩进建树那一层。

### P0-4 `call label(args)` 的参数被丢掉

- **原文**：`call foo(1, two=True) from _call_foo` + `label foo(a, two=False):`
- **产物**：`call foo from _call_foo`
- **后果**：被调方声明了参数、调用方不传 → Ren'Py 运行时直接报参数错误。
  这是从"能跑"改成了"跑不起来"，而且方向是**不可逆的语义收缩**。

### P0-5 `show expression` 里的分号把一条语句撕成两条

- **原文**：`show expression holo("a;b")`
- **产物**：
  ```renpy
  show expression holo("a
  show b")
  ```
- **为什么**：`Show/Hide` 的多值用 `;` 分隔，切分时**不认引号**（`beat_stage_parse.py:70`）。
  用户写一个带分号的表达式就中招，而 `expression` 恰恰是程序最常用的逃生舱。

### P0-6 `u"..."` / `r"..."` 被当成说话人

- **原文**：`u"统一"`（Python 的 unicode 前缀，Ren'Py 支持）
- **产物**：`u "统一"`
- **后果**：旁白变成"角色 u 说「统一」"，运行到这句就是 NameError。

## 6. 建议的修复顺序（按"每修一条能挡掉多少事故"排）

**第一优先：给产物加一道引擎闸门**
在任何写盘前，把产物丢给 SDK `lint`（你有 `engine_collect` 的基础设施，隔离工程也已经写好了）。
这一条能一次性挡住 P0-1/2/4/5/6——它们全是"引擎会报、工具不会报"的错。
成本低、收益最大，而且能防止未来的同类退化。

**第二优先：修词法层的三条（P0-1 BOM、P0-3 顶格注释、P0-5 分号）**
都在 `renpy_parser.py` 的 lexer/`_flatten`/`split_show_items` 里，改动面小，
但每一条都是"静默毁脚本"。

**第三优先：P0-4 `call` 参数 / P1-2 中文说话人**
这两条决定"程序敢不敢用这个工具"——程序最常写的就是带参数的 label 和中文说话人。

**第四优先：Excel 的"活引用"（P1-6）**
这是你产品定义里最独特的一条，现在只做到一半。真要做，方向不是"多写几张 sheet"，
而是把 Beats 的关键列改成 `=VLOOKUP`/跨表引用 + 让派生表用公式重算，
这样才叫"表格之间相互连通"。

**第五优先：写回闭环 + 预览实时化（P1-7/8）**
这两条不修，策划的工作流永远是"改完导出、进游戏看"，工具只是个更漂亮的编辑器。

### 11.2 新发现的硬伤：协作基线会被自己的数据撑爆

**现象**：三方合并只在「库刚 `import-ir`、还没有人 push 过」时有效。一旦有人 push，第二次 pull 的基线就坏了。

**证据链（全是我这轮跑出来的）**：

| 步骤 | 观测 |
|---|---|
| ① 库刚导入 | 每行 payload 中位数 **622** 字符，无 `FileBlocks` |
| ② 第一次 pull 出的表 | `BasePayload` = **651** 字符，`_parse_base` 正常 |
| ③ 某人 push 一次 | `book.0045` 的 payload 变成 **69,341** 字符，其中 `FileBlocks` **64,000** 字符 / **3,827** 行 |
| ④ 第二次 pull 出的表 | `BasePayload` = **32,767** 字符（Excel 单元格上限），JSON 在 char 592 处被切断 |
| ⑤ 这时再 push | `read_collab_sheet` 的 `base` = **None** → 退化成两方比较 |

- 表格协作的第二次开始，全部退化成「revision 变了就冲突」——正是这轮想消灭的假冲突。

- 不会毁文件：从库 `export_ir_from_db` 再渲染，`define s` / `default book` 各出现 **1 次**，
  `screen` 23 个（来自 screens.rpy），没有重复。所以是"协作退化"，不是"内容污染"。

1. **`FileBlocks` 不进单行 payload**：它是文件级数据，要么进库的独立表
   （`file_blocks(file_id, block_no, text)`），要么只挂在「每章第一拍」并**单独存**，
   不要跟着每一拍的 payload 走。
2. **写 `BasePayload` 时设长度闸门**：超过 ~30,000 字符就不写，并在「协作信息」里

   现在的行为是**写一个被 Excel 静默截断的坏 JSON**，比不写更糟。
3. 退一步：超长时只存 `ContentHash`，至少能判断「我没改这一行」，

### 12.1 32767：一个数、一种处置

| 协作冲突界面 | 两栏直接显示全文 | 每边显示前 300 字 +「共 N 字 · 看全文」；**提交的仍是全文** |

### 12.2 协作：第二次起失效 —— 根因与修法

根因不是算法，是**数据放错了地方**：`FileBlocks`（整份顶层 define/screen/init）
被 `attach_file_block_text` 挂到第一拍、又被 `_beat_to_payload` 塞进那一行 payload。
一行 64KB，pull 时 JSON 抄进 `BasePayload` 单元格 → 被 Excel 截成 32767 →
`_parse_base` 拿到半个 JSON → `None` → 降级两方比较 → 字段级明细消失。

修法两层：

1. **`FileBlocks` 离开行 payload**（schema 2）：独立表 `file_blocks`，**整库一份**
   （`LIBRARY_BLOCKS` 空键）。`pull` / `export_ir_from_db` 挂回第一拍；
   `push` 空文本不动库里那份。老库自动迁移（`meta.file_blocks_split`）。
2. **`BasePayload` 永远塞得进一个格子**：`_base_cell_text()` 先试原文 JSON，
   超预算（`32767 - 1500`）就改存**每字段 sha1 摘要**（`{'__hashes__': …}`）。
   三方合并只问"这一格还是我拉取时那样吗"——相等性判断，摘要就够，
   合并语义一字不差；连摘要都放不下 → 写空 + 明确报"没有基线"，**绝不写半个 JSON**。

## 14. 三条修完，又挖出第四条（2026-10-18 深夜，`605ef97` 之后）

### 14.1 P0 结案：去重键不再看"内容"

`beat_render._collect_file_blocks` 改成**只看"整段是否与上一段完全相同"**：

```python
out, prev = [], None
for b in beats or ():
    parts = split_file_blocks(getattr(b, 'file_blocks', ''))
    if not parts:
        continue
    key = tuple(p.strip() for p in parts)
    if key == prev:            # 同一份块被挂了两次（复制行 / 表格重复登记）
        continue
    prev = key
    out.extend(parts)
```

判据从"这一条以前出现过"换成"这一段与上一段一模一样" —— 单条相同只说明
"同一个符号在文件里出现了两次"，那是作者的结构。真机实测**除了 2 个 `}`，
还多吃了 33 条 `##` 与 12 条 `####…` 横线**（它们不影响语法，只是把文件
结构悄悄抹平了，所以没人报）。

守住的两头：`tests/test_file_blocks_not_deduped.py`（6 条）—— 三个 `}`
必须都在、重复的分隔注释必须都在、真重复（两张拍各带一份）仍然只写一次。

### 14.2 冒出来的 P0′：`show …:` 的 ATL 块体**一直在丢**

修完 `}` 后引擎 lint 继续往下跑，报出 35 处：

```
File "game/script.rpy", line 19742: show statement expects a non-empty block.
```

现场（`chapter3_1.rpy:20`）：

```renpy
show lan agreeable at right:      →   show lan agreeable at right:
    zoom 0.15                              ← 块体（zoom / yoffset）没了
    yoffset 200                        with dissolve
```

根因：`_stmt_show` / `_stmt_scene` 只建模**头行**，`line.subblock` 里的 ATL
属性没有任何载体 → 解析时静默丢掉；产物剩一个空块头 → Ren'Py 加载即报错。

修法是**结构性判据**（`renpy_parser._parse_statement` 的守卫）：
解析出来的节点**有没有块体载体**。有（`menu` / `if` / 循环 / `camera` /
`transform` / `layeredimage` / 未建模块）→ 照常；没有 → 整块交给
`_stmt_unmodeled` 逐字保真（`UnknownBlockNode` → `Beat.opaque`）。
**看不懂就别拆**，拆一半比不拆危险。

顺带把 `show` / `scene` 加进 `RENPY_FLOW_BLOCK_HEADS`：它们不是"项目自定义
语句"，是 Ren'Py 标准写法 —— 该算 T2（认识形状、逐字抄对），不该催用户去教工具。

> 能力账要如实记：可编辑覆盖率 **100% → 98.0%**（1757/1792）。
> 那 2% 从前被算成 T0，可渲染时块体是**丢的** —— 100% 是假的，98% 才是真的。

### 14.3 P1 结案：闸门改成"看出处"，不是"看措辞"

`engine_lint` 现在只认两种**出处**，都不看那句话长什么样：

| 引擎输出 | 含义 | 处置 |
|---|---|---|
| `File "game/script.rpy", line N: …` | 加载/编译**抛了异常**，脚本没读进去 | **阻塞** |
| `game/script.rpy:N …` | 脚本读进去了，这是 lint **检查**的意见 | 不阻塞 |
| 只有 traceback 帧（`…, line N, in xxx`） | `init python` 把 lint 跑崩了 | **阻塞** |

`{` was never closed` / `'(' was never closed` / `style property … is not known`
全部落在第一类（以前它们被 8 个措辞漏掉）。第三类是这轮补的：`init python`
抛异常时引擎**不中止 lint**、退出码还是 0，从前会被当成"语法通过"。

判据的来源是 `tools/probe_lint_messages.py`：14 条**真实引擎输出**样本
（正常 / 未闭合括号 / 缩进 / 表达式 / 缺图 / 缺角色 / 缺 label / 缺音频 /
样式属性 / init 抛异常 / 自定义语句），改判据前后各跑一次比对归属。
单测不依赖 SDK：`tests/test_engine_lint_gate.py` 直接喂录下来的 raw。
