## 〇、两把尺（先立换算率，再看四条）

1. **"绕路"要按"这人会不会写代码"折算**。50 人里约 40 人不写代码。
   任何要求"去 `build/renpy/` 比对文件再放回去"的出路，对这 40 人按 **0 条出路**计。
   **拒因里写着出路 ≠ 用户有出路**。这是排优先级的第一把尺，四条都拿它量。
2. **这四条都不静默**（都有报错、拒绝时字节不动）——所以它们是 P1 不是 P0。
   讨论的不是"要不要止血"，是"值不值得把'报了错'变成'能干活'"。
   守住"不静默"是及格线，不是终点：报错说谎（指错出路）比报错更伤，
   见 ① 的"三条出路"实测。

## 二、逐条（谁在痛 / 判词 / 半修接受度 / 优先级 / 便宜替代）

### ① 给无标题 menu 加标题（从无到有）→ 补丁拒

**1. 谁在痛**：编剧/文案为主，策划次之。场景：章节里先写好选项、后补一句
"你要去哪里？"——纯文案补全动作，不含任何结构意图。裸 `menu:` 是真实项目
最常见的 menu 写法（多智能体测试报告 §3.4 自己也点了这条）。**每次**给裸
menu 补标题都撞；50 人团队的文案产出节奏下，周级多次到数十次。
撞见的报错是"1 处新增内容没能落进产物"+ 三条出路（`session_export.py:402`）。

**2. 判词**：**修**。理由只有一条就够：这是文案日常动作，被拒 = 这个功能对
40 个不写代码的人**等于不存在**。而且它比 ②③ 更恶劣的地方在于——**三条出路
对这个场景全是死路**：
- "① 重新载入这一章再导出（行号过期是最常见的原因）"——本场景不是行号过期，
  重载多少次都一样拒，**这条提示在说谎**；
- "② 导出到 `build/renpy/` 比对之后放回去"——比对 .rpy 是程序的活，40 人按 0 计；
- "③ 原地覆盖刻意关掉"——直接封死。
用户依次试完三条全失败后的感受不是"工具谨慎"，是"工具骗我"。
这违反"拒因要说人话"的另一半：**指不到真出路的话，等于没说**。

**3. 只修一半行不行**：**不能**。只把拒因改漂亮（说人话不改行为）解决不了
任何事——用户要的不是更温柔的拒绝，是那一行标题落进文件。对这种
"高频 + 无绕路 + 窄修有先例"的组合，半修是浪费一次上下文切换。
唯一可接受的"半"：对账确认已窄修后**收口**（回归网钉住六形状 + 真机抽查），
不再往"任意新增行都能插"泛化——泛化是无底洞，增量补丁的边界就是"不猜"。

**4. 优先级**：**1**。频率最高的日常动作 × 绕路价值为 0 × 修复成本已被证明
很低（窄通道六形状判据在库，`patcher.py:1566` 起）。项目自己的历史也投过票：
第三轮审计"给修的人的顺序"就把 menu 标题排第一（"高频编辑直接被拒，
用户体验最差"）。**若对账发现判据是红的，今天就该修它**；若是绿的，
第 1 名的预算转给 ② 的绕法验证与报错体验。

**5. 更便宜的替代方案**：无。这个现象级没有绕路可教（见 2 的三条死路）。
已修状态下更便宜的动作是**不作为**——别为"万一还有别的新增行形态"提前建
通用插入引擎；等真机全量扫描（审计 §六.4）报出真实命中率再说。

---

### ② 真机复杂文件上移动拍被拒（"重排段里有认不出的行"）

**1. 谁在痛**：**策划**为主（"对着卡片编排演出"就是他们的核心工作流，
调顺序 = 排戏），编剧次之（叙事顺序调整）。场景：在分支密集、带自定义语句/
注释的复杂章节里挪一拍。频率：编排期几乎每天动顺序；复杂章节是分支作的
**常态**不是例外，周级数次。痛感分三支，别混在一起谈：
- 普通拍互换——开发日志记为**已能挪**（真机 9 种移动实测 3 种落盘）；
- 跨 `if`/`elif` 块头的挪——**拒得对**（台词出分支 = 条件不生效 = 改剧情）；
- 重排段里混着"认不出的行"（块头/裸注释/未建模语句）——**仍然整段拒**，
  这才是"移动等于不可用"的残余现场。

**2. 判词**：**只修报错体验**（行为缓修，且只缓修"opaque 行挡道的普通重排"
这一支）。跨结构那支**不修**——修了就是让工具猜"挪出分支算不算改剧情"，
违反"工具不猜语义，意思由人标注"；那一刀的正确语义是**人来承担**。
"带认不出的行整段挪"也不做（同理，那是猜这些行归属谁）。
欠的是：拒因点名**卡在哪一行**（现在"认不出的行"分支已经举例了，
`patcher.py:3123`，但只给了全量这一条死路）+ 给一条**人能走**的绕法。

**3. 只修一半行不行**：**能接受**，而且这就是当前的正解。理由：
拒绝本身是安全的、正确的（审计原话"安全"）；痛点不在"被拒"，
在"拒了之后不知道怎么办"。把话说清 + 给绕法，策划就能继续干活；
硬做行为修反而要用"猜行归属"换体验，赔三护栏里的"不猜语义"。

**4. 优先级**：**2**。策划核心流的残余缺口，频率高；但修复形态轻（文案 +
一条已验证的绕法），且行为修要过语义评审，不能挤到 ① 前面。
若 ① 对账转绿，本条顶上第 1。

**5. 更便宜的替代方案**（用户问的"复制粘贴 + 删原卡"就在这里答）：
- **现成零成本的**：拒因里已经给了——"要挪请先在卡片上清掉这一拍的条件，
  或者用全量重写"。把"清条件再挪"做成绕法指引即可：清条件 = 人显式承担
  语义变化，正是"意思由人标注"的正解，不花一行代码。
- **"复制内容到目标位置插卡 + 删原卡"（拆移动为插入+删除）**：
  **值得教，但必须先验证再教**。风险在插入端：含 opaque/自定义语句的拍
  复制过去，会不会又撞"新增内容没能落进产物"？没验证就写进拒因 =
  教用户跳坑（又一条说谎的出路）。验证成本低（一个探针），先跑它。
- 都不成立时，兜底出路是全量导出 `build/renpy/` + 人工放回——对 40 人
  按 0 计，只能算程序的退路，不进文案。

### ③ 改 if 条件被拒（条件改动走全量）

**1. 谁在痛**：策划为主（调分支条件是编排-测试-调优循环里的高频动作：
改阈值、换 flag、重构判定），程序次之（每次被找去当"人肉全量器"）。
频率：调优期日级。现状分层：单 `if` 与**链头**已能增量改一行（开发日志
§二十四.3 + `test_p0_round4.py::TestConditionEdit` 6 判据）；
`elif`/`else` 支、嵌套 `if`、清空条件仍拒，拒因已说人话
（"改链头那一支可以增量；这一支请全量重写这一章"）。
绕路是"全量导出 `build/renpy/` 比对放回"——程序级，40 人按 0 计。

**2. 判词**：**缓修**——先上便宜替代，行为修排队；**"把累积条件自动写回
elif 行"永远不修**（那是猜语义：表里存的是展平后的累积条件，工具不知道
用户想写哪一行原文，硬写就是替用户编剧情）。
为什么缓不急：链头增量已覆盖最高频形态（大部分条件调整动的就是链头/单 if）；
elif 支的痛是真的，但不是"每天卡死"级。

**3. 只修一半行不行**：**能**。现状（链头增量 + 说人话 + 全量出路存在）
已经是可工作的半修。对程序，全量导出是十分钟的事；对策划，只要拒因
说清"改这一支要走全量、按钮在哪"，至少不堵死。真正不该省的是下面的
便宜替代——那才是把策划的痛也消掉的一步。

**4. 优先级**：**3**。残余痛真实但频率中等、有出路（尽管是程序级）；
便宜替代成本低，可搭 ② 的报错体验一起做。

**5. 更便宜的替代方案**：**让 elif 的条件按"原文行"编辑**——条件格
直接显示源文件里那行 `elif love < 2:` 的原文，用户改的就是这个字符串，
工具整行替换（与链头已有的 `_plan_condition_rewrites` 同一刀）。
零语义猜测：工具不翻译、不展开，**意思由人标注在原文上**；改一个阈值
（`< 2` → `< 3`）非程序员完全可操作，改不动结构（拆 elif）自然会改崩、
被 lint/校验拦下——那是诚实的失败。比"自动写回累积条件"便宜一个量级，
且合哲学。若嫌格子太代码味，退一步：拒因卡片上给"一键全量导出到
`build/renpy/` 并打开目录"（UX 建议 3 的卡片形态，见 §五）。

### ④ `write_asset_excel` 表坏了才整份重建（有隔离备份）

**1. 谁在痛**：维护资源表的策划/美术（`images.xlsx` 里的"配音演员"列、
手写占位行、批注底色都是他们的工作台）。场景：资源表**解析失败**
（文件真损坏/格式异常；Excel 开着锁住的成因要单独验证是不是也走这支）
→ 坏表挪成 `*.broken-<时间戳>.xlsx`（`asset_registry._quarantine_broken_tables`）
→ 按扫描结果整份重建。频率：**月级或更低**（表真坏了才触发）。
痛感：新表里没有手工维护的列/行/批注（它们在隔离副本里），
当天工作流断一次，要人工搬回来。

**2. 判词**：**只修报错体验**（行为**不修**）。三条理由：
- **行为本身是对的**：表都解析不出来了，"重建出一张能用的表"是用户继续
  干活的唯一方式；拒绝重建 = 工具直接罢工。
- **"直接保住"在这里物理上做不到**：`xlsx_preserve` 那套（快照人的列/页/
  批注再还原）前提是表**读得出来**；坏表恰恰是读不出来。
  把 ④ 的标准定成 `xlsx_preserve` 级，是要从损坏文件里抢救内容——
  那是数据恢复工程，不是产品需求。
- **"不要做隔离备份，这解决不了根本问题"那句话的适用面要划清**：
  它反对的是**常态覆盖**（表好好的、扫描一遍就重建）——那一刀 P0-F 已改成
  "直接保住"（`write_dict_to_excel` 按 ID/真实文件保住人的列、行、底色、批注，
  8/8 判据）。④ 是**病态重建**（表已不可用），隔离副本是**仅存**的保全手段，
  两者不可混为一谈。拿常态的标准压病态的路径，只会逼出假修复。

**3. 只修一半行不行**：**能——半修就是唯一该做的**。修行为既不可能也
不值得；真正欠的是**回执说人话 + 恢复指引**：哪张表坏了、为什么（解析异常
原文）、隔离到了哪个文件、**重建后少了什么**（"你的『配音演员』列 12 行
在隔离副本第 3 列"）、怎么搬回来。现在的隔离动作本身没错，错在用户
得自己考古。

**4. 优先级**：**4**（最低）。频率最低 × 有兜底（字节不丢，能手动救）×
常态那刀已修。不值当为它开一轮 P0-E 级工程。

**5. 更便宜的替代方案**：回执做成"恢复指引卡"（上面 3 的内容），
零行为改动；若想再进一步，重建时**尽力抢救可读的页/列**（openpyxl
换参数重读、按页 try）能救多少算多少并在回执报数——但这是锦上添花，
救不了就明说"救不了"，**不许静默少报**。不做"坏表不重建"的选项。

## 三、优先级排序（投资顺序）

| 序 | 项 | 一句话理由 |
|---|---|---|
| **1** | ① 加标题 | 最高频的编剧日常 × 绕路价值 0 × 窄修已证明便宜；若对账仍红，今天就修 |
| **2** | ② 移动拍（残余） | 策划核心流残余；先做"清条件再挪"指引 + 验证"复制+删原"绕法 + 拒因指路，行为修缓 |
| **3** | ③ 改条件（残余） | 链头已覆盖高频；上"elif 原文行编辑"这个便宜替代就基本消痛，自动写回不修 |
| **4** | ④ 坏表重建 | 月级频率 + 隔离兜底 + 行为正确；只把回执做成恢复指引 |

排序逻辑一句话：**先把"每天卡人、无绕路"的清掉（①），再给"每周卡人、
有绕路但指不清"的指路（②），然后用便宜替代收编"有人肉绕路"的（③），
最后给"月级、有兜底"的补文案（④）。**

## 四、最不该修的是 ④

**④（行为面）最不该修**。"表坏了整份重建"看着最像"毁用户工作台"，
但拆开看：触发条件月级、隔离副本保住了全部字节、重建是唯一能让人继续
干活的行为、"直接保住"在读不出的表上物理不成立。为它投 P0-E 级工程 =
为月级频率付日级成本，且修的是一个本来就对的行为。
它唯一欠的是回执说人话——那是文案，不是修复。

顺带钉一条**子项级的"不该修"**（给 gatekeeper 把关用）：② 的
"跨结构移动"**永远不该修成能挪**。台词挪出 `elif` 分支 = 条件不再生效
= 改剧情；工具替用户做这个决定就是猜语义。正确产品形态是现在这样：
拒绝 + 说清"那是改剧情，不是排版" + 把决定权交回人（清条件再挪 /
全量重写）。修它 = 用三护栏里最贵的一条（不猜语义）换一条便利。

## 五、拒因出口怎么借力 UX 建议 3（不重复该建议本身）

UX 建议 3（"现象 + 可点位置 + 怎么修"卡片）已定为最优先项，此处不重提；
只说 ①②③ 的拒因**接上去时各自的"怎么修"一栏该写什么**——这是卡片文案
的落点，也是本讨论唯一要求的接口：
