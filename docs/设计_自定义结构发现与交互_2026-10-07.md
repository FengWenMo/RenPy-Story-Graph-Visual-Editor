# 设计：工具如何得知「自定义结构」，以及要不要 index 层 / 适配器

日期：2026-10-07 · 状态：**设计草案（待你拍板）** · 关联：`docs/设计_自定义语法适应架构_2026-10-07.md`（CST）

---

## 0. 先把问题切对：三类"不认识"

把"工具不认识的东西"分成三类，**接法完全不同**（混在一起谈就永远谈不清）：

| 层 | 例子 | 工具能不能自己知道 |
|---|---|---|
| ① **语法级** | `mycue "闪电" intensity=3:` —— 有头行、有参数、有块体 | **能**（形状检测）。这是 CST 现在做的事 |
| ② **结构级** | 块的**语义约束**：哪些参数必填、参数取值范围、块体里允许出现什么、能不能嵌在别的块里 | **不能猜**，只能被**声明**或**反射** |
| ③ **语义级** | "这一步在游戏里是什么意思"（提示 / 战斗 / 存档点） | **永远不该猜** —— 猜错比不知道更贵 |

结论：CST 收尾在 ①；要往前走，必须解决 ② 的**得知途径**与人机接口。③ 只允许"人标注"，工具只做展示与检索。

---

## 1. 四种"得知"途径：对比后取组合，不取单选

| 途径 | 怎么得到 | 优点 | 代价 / 风险 | 定位 |
|---|---|---|---|---|
| **A 自动推断** | 形状检测（现有 `story/statement_registry.py` 的 shape detection） | 零配置、当场可用 | 只能得到"像什么"；参数名/类型/约束**猜不出**；必然有误判 | **只做分类与保真降级**（现状是对的，不要加码） |
| **B 项目内声明** | `storygraph.rules.json` 的 `statements[]`（已有雏形） | 精确、可评审、**进版本库**、能被 diff | 要人手写；与代码里的 CDS 会**漂移** | **主路径** |
| **C 运行时/静态反射** | `renpy.register_statement` 的实参（CDS）；静态扫描 `scan_project_cds`（已有） | **不会漂移**（真源就是程序员的代码） | 要能扫到/跑到；CDS 只给"形状"，给不了"意图" | **主路径的补充**：发现 + 校验声明 |
| **D 交互式教学** | 工具问、人答（表里/卡片里"这是什么"） | 不用写配置文件；当场生效 | 一次性人力；**必须落盘**否则白教 | **载体**：把人的回答**落成 B** |

**一句话结论**：
> 主路径是 **B（声明）**；**C** 负责"发现 + 防漂移"；**D** 是让人顺手把答案变成 B 的入口；**A** 只做分类与降级，不许拿来当结构真源。

**最重要的约束**：无论走哪条路，得知的结果都必须**落成一份可评审的文件**（`rules.json` 的 `statements`，带 `source: cds|rules|guess` 与时间）。
只存在内存里的"工具知道"不算知道 —— 程序员改代码、工具改内存，两边第二天就对不上。

## 2. 接口草案：`describe` 协议（工具 ↔ 程序员）

三档，从轻到重，**第一档现在就该做**：

### 2.1 `describe --json`：把"工具以为的结构"摊开
```
python -m storygraph.cli describe --json
```
输出（每个自定义语句一条）：
```json
{ "name": "mycue", "label": "闪电提示",
  "source": "cds",                  // cds | rules | shape-guess
  "block": true,                     // 有没有块体
  "head_re": "mycue\\s+(?P<text>...)",   // 工具认头行用的判据
  "columns": [ {"name":"intensity","label":"强度","positional":0,
                "choices":["1","2","3"],"required":true} ],
  "fidelity": "T0b",                 // 这类结构工具能保到什么程度
  "evidence": {"file":"game/ch.rpy","line":50,"count":7},
  "warnings": ["块体里有 2 处工具不认识的语句"] }
```
**为什么先做它**：它是所有"交互调节"的地基 —— 没有它，人和工具无法对齐"你到底以为什么"。
而且它天然可进 CI：`describe --json > 现状.json && git diff --exit-code 现状.json`
就能抓住"代码改了、工具的认知没跟上"。

### 2.2 声明文件（唯一真源，人写/工具写同一份）
```json
{ "statements": [ {
    "name": "mycue", "label": "闪电提示", "block": true,
    "source": "cds",
    "columns": [
      {"name": "intensity", "label": "强度", "type": "int",
       "positional": 0, "required": true, "choices": ["1", "2", "3"]},
      {"name": "target", "label": "目标", "type": "str",
       "choices_from": "characters"} ],           // 命名锚点，不写代码
    "body": {"allows": ["say", "show"], "min": 1}
} ] }
```
要点：
- **声明里只填数据**（名字/标签/类型/候选来源/约束），**不填代码**；
- `choices_from` 是**命名锚点**（`characters` / `transform` / `images` / `music`），
  由工具解析成候选 —— 项目侧不需要写任何 Python；
- `source` 记来源，`describe` 与 `validate` 都据此报"声明与 CDS 不一致"。

### 2.3 校验规则的扩展点（"调节"真正发生的地方）
`validate` 现在报的是通用问题（空台词、缺资源…）。要让自定义结构**可调**，需要能从声明**生成**规则：
- 必填参数缺失、参数取值不在候选里、`positional` 位置写了多余 token；
- 块体里出现了 `body.allows` 之外的语句；
- 声明与 CDS 的签名不一致（改了代码没改声明 / 反了）。

这一层才是"与程序员直接交互调节"的落点：**改声明 → 工具行为立刻变**（列出现/下拉/校验/渲染/保真档），
而且每一次改动都**可评审、可回滚**（进 git）。比任何 GUI 都可靠。

## 3. 要不要 index 层（像 git）？—— 要，但不是"内容寻址"

**先认清现状**：我们**已经有一个 index 层**了 —— 隐藏列（`Ordered`/`Nest`/`CodeBlocks`/`StageOrder`/`OpOrder`）
就是"真状态"，Excel 只是它的**视图**。所以问题不是"要不要加"，而是"这一层缺什么"：

| git 里的东西 | 我们的对应物 | 现在缺什么 |
|---|---|---|
| index（暂存区） | 隐藏列（真状态）+ 表（视图） | **schema 没有单一定义**：列定义散在 `BEAT_FIELDS` / `_HEADER_ALIASES` / `EXPORT_COLUMNS`，靠判据钉住不漂移 |
| blob/object store | `Beat` 的字段 + `ordered` | 撤销栈只在内存（`app/session_table.snapshot`）；`collab_store` 是雏形，没接上 |
| `git diff` | `ContentHash`（行级）+ 审计工具 | 只有行级指纹，没有**拍级**结构化 diff |
| `git merge` | 无 | 没有"表 vs 源码 vs 上次表"的**三路合并**；冲突策略不存在 |

**建议（按性价比排序）**：
1. **`schema.json` 单一定义**（列名/中文表头/类型/保真档/别名）→ 由它**生成** `BEAT_FIELDS`、`BEAT_HEADERS`、`_HEADER_ALIASES`、`EXPORT_COLUMNS`。
   收益：一次性消掉一类"改了一处忘了另一处"的漂移；成本低；**现在就该做**。
2. **会话级快照落到 `collab_store`**（已有表结构）→ 崩溃/换机不丢"未导出"的编辑。
3. **拍级三路合并**：留到真有并发编辑需求时再做（现在做等于给一个不存在的场景写复杂逻辑）。

**一句话**：index 层的下一步不是"新加一层"，而是把**已有那一层**的 schema 定义收成一份。

## 4. 适配器要吗？—— 要，但粒度是"结构的种类"，不是"每个语句"

**反例（不要走）**：为每个自定义语句写一个 Python 适配器 `MycueAdapter(StatementAdapter)`。
后果：插件地狱；与 CDS 必然漂移；每个项目都要写代码 —— 与你"让工具自动得知"的目标相反。

**正例（已经在做，继续收）**：
| 适配器 | 形态 | 已有的雏形 |
|---|---|---|
| 形状 → 列/下拉/折叠 | **声明式形状表**（数据，不是代码） | `story/spec_args.BUILTIN_ARG_SCHEMAS`、`rules.json: statements[].columns` |
| 候选来源 → 资源表 | **命名锚点** `choices_from` | `'transform'`（已用）、`characters`/`images`/`music`（待补） |
| 结构 → 保真档 | **能力推导** `capability_of(structured=…)` | `story/capability.py`（T0/T0b/T1a/…）—— 应改成**从声明推导**，别散在代码里 |
| 结构 → 渲染 | 渲染器**按结构位**归组 | `beat_render` 的 `Nest`/`loop`/`camera`/`unified_plan` |

**判据（判断一个适配器该不该写）**：如果它只对**一个项目的某一个语句**生效 —— 不写，改成声明；
如果它对**一类结构**生效（"有块体的自定义语句""带位置参数的标准语句"）—— 写，且只写一份。

## 5. 落地顺序（每步独立可验收）

| # | 做什么 | 验收判据 |
|---|---|---|
| 1 | `cli describe --json`（把"工具以为的"摊开） | 真机跑通；输出可 diff；`git diff --exit-code` 进 CI |
| 2 | 列/下拉/保真档**全部从声明推导**（缺声明 → 降级并**点名**） | `rules.json` 改一行 → 表的列与下拉跟着变（真机验证） |
| 3 | "教一次"入口（表/卡片上人答 → 落成 `statements[]`） | 在教学入口填的形状，导出的表立刻出现对应列 |
| 4 | 校验规则从声明生成（必填/取值/块体允许） | 造一个违规脚本 → 校验报出**声明里那条**规则 |
| 5 | `schema.json` 单一定义（index 层第 1 件） | 生成物与现有 `BEAT_FIELDS`/表头**逐字节一致** |
| 6 | 会话快照落 `collab_store` | 杀掉进程重开，未导出的编辑还在 |

前 4 步合起来就是你问的"工具如何得知自定义结构 + 如何与程序员交互调节"：
**能看见（1）→ 能声明（2）→ 能顺手教会（3）→ 能被检查（4）**。

---

## 6. 明确不做（以及为什么）

- **不猜语义（③）**：`mycue` 是"提示"还是"战斗"——工具永远不写进数据，只让人标注。
- **不做"每个语句一个适配器"**：粒度错，必然漂移。
- **不把 index 层做成内容寻址（git 的 blob hash）**：我们的真源是 `.rpy` 与隐藏列，
  再加一层哈希寻址只会增加同步点，收益是 0。
- **不做拍级三路合并（第 6 步之前）**：没有并发场景时它是纯负债。
