# 嵌套结构位 与 行尾注释：实测 + 可修方案（2026-10-05）

问的是「这两个能不能都修？病根是不是同一个（结构位不进表）？B 方案
（升级成随表隐藏列）能不能让它们进表但默认隐藏？」

**答案：两条都能修，B 方案对第一条（结构）正是对的修法；但两条的病根
不是同一个机制** —— 一个"表里没地方放、只能靠猜"，一个"词法器阶段就扔了"。
先把实测摆出来，因为它推翻了三个流传的说法。

复现命令（都在 `tools/`，只写 `%TEMP%`，不碰真实项目）：

```bash
python tools/probe_nesting_min.py       # 最小复现：if>menu / menu>if / if>if>menu
python tools/probe_nesting_inline.py    # 全量 vs 增量：结构 + 行尾注释
python tools/probe_structure_risk.py    # 真实项目里各有多少处
```

---

## 1. 三个说法要更正

| 流传说法 | 实测 | 证据 |
|---|---|---|
| "嵌套 > 3 层不支持，**validate 会显式报错、不静默降级**" | ❌ **validate 一个字都没说**（`exit=0`，只有 W110 角色表空 / W304 图入口）。这是**静默产出坏脚本** | `probe_nesting_inline.py` 末段 |
| "深度 3 是分界线" | ❌ **跟"深度"没关系**。坏的是**菜单选项体**：选项体里有 >1 条语句或含块就坏，**2 层就坏**；而纯 `if` 嵌套到多层反而走"条件合取"近似（能跑、语义大体等价） | `probe_nesting_min.py` |
| "行尾注释要加列才能存（所以没救）" | ⚠️ 只对**一半**。label **外面**的 185 行现在**已经安全**了（上一轮的顶层保真把它们逐字带走）；label **里面**还剩 **12 行**有风险 | `probe_structure_risk.py` |

### 最小复现：`menu>if`（两层，就坏了）

原文 → 全量产物：

```renpy
menu:                        menu:
    "选项":          →           "选项":
        if flag:                     pass          ← 选项体被掏空
            e "选了且 flag"      if flag:           ← 提到 label 级：
        e "选项内收尾"               e "选了且 flag"     **不管选没选都会执行**
                             if True:
                                 e "选项内收尾"
```

`if>menu` 也不对（`menu` 之后的、仍在 `if` 里的那句，被吸进了最后一个选项体）。
**产物语法合法、能跑、validate 0 错 0 警 —— 改的是剧情语义**（本仓库最贵那一类）。

### 真实项目里的暴露面

```
菜单块 7 个 / 选项 24 个 → **复杂选项体 3 个**（2 个文件：script_pomo 2 / pomodorro 1）
行尾注释：label 里 12 行（5 个文件）；label 外 185 行（已安全）
纯 if 嵌套 ≥2 层：109 处 —— **不是缺陷**（合取近似），只是说明"深度"不稀缺
```

所以：**结构那条是真缺陷但罕见（3 处）**，一旦踩到就是静默改剧情；
**注释那条面很小（12 行）**，但修起来最便宜。

## 2. 病根：两个不同机制（用户说"同一个"—— 设计层面近似，代码层面不是）

### ① 结构位：不是"没进表"，是"**塞进了一个一维字符串，信息量不够**"

现在的做法（`beat_render.stamp_menu_bodies`）：

```python
# 菜单组的边界靠 condition 兜底判定（`_menu_member` 是 .rpy 侧的结构位，
# Excel 里存不下）……把选项体里**空条件**的拍写成 `True`
#（语义等价，Ren'Py 里 `if True:` 永远成立）之后，条件就成了可判定的结构信号
```

也就是说：**有人已经试过"把结构位塞进表"** —— 塞进了 `Condition` 列，
用 `True`（在选项体里）vs 空（在菜单外）当判据。问题不是"没进表"，
而是这个编码**只有 1 bit**：分不出**哪个**选项、也分不出**多深**；
选项体里一旦有第二条语句或嵌套块，信号就塌了。

配套的识别逻辑全在 `beat_render`：`_take_menu_run` / `_menu_segments` /
`_is_menu_foreign` / `_expected_body_condition` / `_condition_is_refinement`
（按 `and` 拆原子做集合包含）。**全是推断**，没有任何一处拿到真结构。

### ② 行尾注释：**词法器直接扔掉**，IR 里根本没有这个字段

```python
accumulated = self._strip_inline_comment(accumulated)   # renpy_parser 477
flat.append((accumulated, line_no, indent, False))
```

`_strip_line_comment` 只返回"代码部分"，注释文本**没有被存到任何地方**。
所以下游再怎么改都没用 —— 这不是"表里没地方放"，是"源头没留下"。
（label 外面的之所以现在安全：上一轮的顶层保真走的是**原文行**，绕过了词法器。）

## 3. 方案 B（结构位进表）—— 推荐，但按阶段走

> **阶段二 ✅ 已实施**（2026-10-05，见 README 不变量 76）：渲染器**优先用结构列**
> 建树（`use_paths=False` 是给对拍器留的老路开关）。实测 40 个真实文件
> 两条路**逐字节不变**（对 HEAD worktree 比对）；而老推断摆错的
> `menu>if` / `if>menu` / 交错选项体三个形状**修对了**且顺序与源码一致。
> **阶段三 ✅ 已实施**（2026-10-05，见 README 不变量 77）：`stamp_menu_bodies`
> 的函数体与调用点都删了 —— 表里不再有我们补的 `True`，产物里不再有那层
> `if True:`，而且**过表产物与直接渲染现在逐字一致**；老表（无 `Nest` + 有
> `True`）仍然渲染正确。原计划的"退掉 `stamp_menu_bodies` 的 `True` 打标
> （`Nest` 已经扛得住那件事）"这一条已完成，余下的把 `_menu_member` 降成解析期内部量（它本来就不进表，
> 现在只服务于"老表 / 源码侧的对拍与兜底"）。
>
> **阶段一 ✅ 已实施**（2026-10-05，见 README 不变量 75）：解析器写 `nest_path`
> → 隐藏列 `Nest` → 对拍器 `nest_placement_conflicts` → `NEST_CONFLICT`（warn）。
> **行为零变化**（`tools/render_hash.py` 实测 40 个文件两条路逐字节一致），
> 且**阶段一的验收判据已达标**：真实项目 0 处不一致、0 条拍缺结构位。
> 下面保留原始设计说明（阶段二/三还没做）。


用户提的形状是对的：**新隐藏列，工具维护，和 `StageOrder`/`OpOrder`/`CodeBlocks`
同一档**。具体设计：

### 3.1 列里放什么：**块路径**（materialized path），不是树、不是 JSON

```
（空）                     = label 顶层
if:1                      = 该 label 第 1 个 if 块里
if:1>menu:1>A             = 那个 if 里的 menu 的第 1 个块的第 A 个选项体里
if:1>menu:1>A>if:2        = 再深一层
```

* 段 = `<块类型>:<同类型兄弟序号>`，选项体用 `A`（匿名，按顺序编号）；
* 只用**路径**就够渲染：相邻行共享前缀 → 建树（等价于邻接表存树的标准做法）；
* 人可读（和 `Stage` 列同风格），出问题能一眼看懂，不是黑盒 JSON。

### 3.2 谁写谁读

| 层 | 改动 | 说明 |
|---|---|---|
| 解析 | `renpy_parser._walk` 给 `Statement` 加 `nest_path`（**它本来就知道真结构**：`LogicalLine.subblock` 就是树） | 不加解析，只是把已有的结构记下来 |
| 模型 | `beat_model`：`Beat.nest_path` + `BEAT_FIELDS` 加一列 `Nest`（**24 → 25**），进 `HIDDEN_BEAT_COLUMNS` | 与 `StageOrder` 同档 |
| 渲染 | `split_beat_units` / `_take_menu_run` / `_menu_segments`：**有 `nest_path` 就按它建树**，没有才退回今天的推断 | 推断降级为兜底 |
| 退场 | `stamp_menu_bodies` 的 `True` 写入可以退掉（或留成兼容壳） | 顺带说明为什么以前必须写 |

### 3.3 迁移：**先双写 + 对拍，别一次换掉**

这一步同时就是"止血"（见 §5）：

1. **阶段一（半天）**：解析写 `nest_path`、表里存列，**渲染仍然用老推断**，
   但每次渲染把"老推断的结果"和"结构列说的"**对拍**，不一致就报一条
   **门禁问题**（指名道姓：哪个 label、哪几行、两种结构各是什么）。
   行为零变化 → 刚验收过的往返契约不会被打断；真实项目那 3 处会**立刻现形**。
2. **阶段二（半天）**：渲染优先用 `nest_path`（列空时退回推断，老表照样能读）。
3. **阶段三（半天）**：把 `probe_nesting_min.py` 的三个用例、以及真实项目
   40 个文件的**结构指纹**全绿之后，退掉 `stamp_menu_bodies` 的写入。

### 3.4 风险面（老实说）

* `BEAT_FIELDS` 又要动（我刚把它从 25 改到 24，再 +1）→
  `test_dsl_compile` / `test_roundtrip_invariants` 的列契约要一起改；
* 隐藏列定位、`_ui_project` 与黄金快照（`test_main_window_snapshot`）；
* `_menu_member`（内存侧）与 `nest_path`（表侧）两份真相要明确主从：
  **`nest_path` 是唯一的表侧真源，渲染只认它**；`_menu_member` 退成解析期内部量。

工作量：**1–2 天**（含用例），与之前估的一致。

## 4. 方案 C（行尾注释进表）—— ✅ **已实施**（2026-10-05）

> 四层都接上了：词法器 `LogicalLine.inline_comment`（只认单行）→
> `Statement.inline_comment`（动态属性）→ `Beat.inline_comment` + 隐藏列
> `Inline` → 渲染贴回原行。规矩是"**说不清就不贴**"：多行逻辑语句不采集；
> 一拍多行时只有"前面全是块头"才贴最后一行。
> 真实项目 label 内带注释的拍 **4/4 保住**，原地增量**不重复**。
> 见 README 不变量 78；用例 `tests/test_inline_notes.py`（15 条）。
> 下面保留原始设计说明。


1. **词法器保留**：`LogicalLine.inline_comment`（新建字段，**不动 `.text`** ——
   现有上百条判据都建立在"text 是代码"上）；
2. **带到拍上**：`Statement` / `Beat` 各加一个字段（`inline_comment`）；
3. **写回**：`render_beat_to_rpy` 在对应那一行尾贴上 `  # 注释`；
4. **进表**：隐藏列 `Inline`（逐行属性，与 `StageOrder` 同档）。

**边界情况（设计上必须选一边）**：一拍可能对应多行（menu 头、多行 `raw`/`code`），
一格字符串放不下"每行一条注释"。三个选项：

* **只存 1:1 的拍**（台词/跳转/单行 raw）——覆盖实测那 12 行里的绝大多数，
  多行拍退回"原文保真通道"（顶层块已经安全）；
* 存"行内序号→注释"的小映射（`2:注释; 4:注释`）——完整，但可读性下降；
* 不给注释进表，改成"改动过的那一行才丢"时**报一句**（属于 §5 的做法）。

建议先做第一个 + 第三条兜底。工作量：**半天**。

## 5. 方案 A（止血）：把"静默"变成"看得见" —— ✅ **已实施**

> 已按本节落地（2026-10-05）：`generation_guard.menu_structure` / `structure_loss`
> \+ `STRUCTURE_LOST`（**warn**，不拦）+ `RenPyLexer.tokenize_text`；
> 用例 `tests/test_structure_gate.py`（12 条），现场证据
> `tools/probe_structure_gate_cli.py`。下面保留原始设计说明，只有一处与实现不同：
> 级别定为 **warn 而非 block** —— 因为"结构变了"也可能是人**有意**改的，
> 只比"源 vs 产物"分不出，而假阳性比漏报更贵。理由写在
> `structure_loss` 的 docstring 与 README 不变量 74 里。


**判据不能用"深度 ≥ 3"**，两个理由都很硬：

1. **漏**：真正坏的是"菜单选项体有第二条语句/嵌套块"，**2 层就坏**；
2. **误报**：纯 `if` 嵌套在真实项目里有 **109 处**，而它是设计内的近似
   （合取），报它就是刷屏 —— 而刷屏的警告等于没有警告（本项目已有教训）。

**该用的判据：结构指纹不一致。** 源和产物都用**现成的** `RenPyLexer`
（`LogicalLine.subblock` 就是树，不用新写解析器）算一份"每个 label 的
块头序列（类型 + 深度）"，忽略文本内容，逐 label 比对：

```
label nest:  if(1) say(1) if(2) say(2) menu(2) option(3) say(4) …
```

不一致 → 新增门禁代码（例如 `STRUCTURE_LOST`），与 `OPAQUE_LOST` **同一形状**：
`write_generation` 里拦、列出"哪个 label 第几行、期望什么/实际什么"、
`--force` 降级为 warn（仍然报）。

* 它同时是 §3.3 阶段一的"对拍器"，所以**不管先做 B 还是先做 C，A 都不白做**；
* 它拦的是"结果不对"，与"推断为什么错"解耦 —— 以后新增结构形态也照样兜得住。
工作量：**半天**。

## 6. 建议的顺序

| 顺序 | 做什么 | 工作量 | 为什么这个顺序 |
|---|---|---|---|
| 1 | **A：结构指纹门禁** | 0.5 天 | 现在那 3 处是**静默**的（实测 validate 0 错）；先让它现形，且它是 B 阶段一的对拍器 |
| 2 | **B 阶段一：结构列双写 + 对拍** | 1 天 | 开始真正修，但行为不变，不碰刚验收的往返契约 |
| 3 | **B 阶段二/三：渲染改用结构列 → 退掉 `True` 打标** | 1 天 | 结构那条彻底解决（含"选项间插拍归属"、"选项体到哪结束"） |
| 4 | **C：行尾注释进表** | 0.5 天 | 独立，随时可插队；面只有 12 行，但便宜且能一次做干净 |

**不建议做的**：

* 树列塞 JSON（可读性归零，出问题没法人工核对）；
* 一次性把渲染换成结构列再补用例（那正是"刚验收完就动往返契约"的最坏形态）；
* 按"深度"下判据（漏 + 误报，见 §5）。
