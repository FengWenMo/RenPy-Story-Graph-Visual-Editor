# 不安全因素审计：会改坏别人项目代码的 P0/P1

> 2026-10-25 · 范围：导入 → 解析 → 编辑 → 导出全链路的**落盘安全**
> 判据（用户口径）：会把代码改坏 / 侵入性特别强 / 存在不必要侵入 / 没做到逐字节保真
> 方法：静态枚举全部落盘点 + 4 个对抗探针真实跑 `EditorSession` 循环 + 既有测试基线复跑

## 0. 审计方法与基线（先说判据从哪来）

## 2. P0-1：选择点追加 = 整份文件换行改写（探针 1 实锤）

**代码**（`storygraph/story/choice_point.py`）：

```python
229    # —— 追加：保留原文件每一个字节，只在末尾接一段 ——
230    from storygraph.story.paths import write_text_atomic
232        old = target.read_text(encoding='utf-8')        # ← 裸读：CRLF 被折成 LF
236    sep = '' if old.endswith('\n\n') else ('\n' if old.endswith('\n') else '\n\n')
238        write_text_atomic(target, old + sep + plan.block)   # ← 无风格还原，LF 写回
```

**为什么是 P0**：这正是本项目自己审计过并修掉一整轮的那类 bug（2026-10-18 审计 P0-1：
"打开再导出逐字节不变"；`source_style.py` 的模块 docstring 原话："审计实测：tutorial 的
23 个脚本里 23 个都是 CRLF，而工具写出来的是 LF —— 逐字节相同率 0/23"）。
patcher / `write_generation` / `compile.py` 三处都修了，**追加路径是漏网的一处**。

**实测**（探针 1，BOM+CRLF+手写注释的选择点文件，插入第二个选择点）：

```
before CRLF 行数 = 4   →   after CRLF 行数 = 0
原有每一行都原样还在 = False      # 4 行全部因换行被改写
```

**触发路径**（UI 常态，不是边角）：卡片页「插入选择点」→ `window_card.py:888`
`apply_choice_point(plan, root)` **立即落盘**。用户第一次插入生成 LF 文件 → 在 VS Code /
记事本里手改选项（Windows 编辑器默认存 CRLF）→ 第二次插入 → 整份文件换行被改写。
git diff 表现为"整个文件变了"，用户看到的就是"工具又在改我的文件"。

**为什么测试没抓到**：`test_choice_point.py:137 test_append_keeps_existing_bytes`
的意图正是"已有内容必须逐字节保留"，但样本是 **LF 文件** —— 换行维度完全没覆盖。

**修法**（与 `control_route.apply_control_init` 同款，三行）：

```python
from storygraph.story.source_style import read_text as _read_src
old, style = _read_src(target)                 # 剥 BOM、统一 LF，同时拿到风格
...
write_text_atomic(target, style.apply(old + sep + plan.block))
```

顺带：`except OSError` 漏了 `UnicodeDecodeError`（见 P1-2），追加前应像
`apply_control_init` 那样核对"文件还是计划时那一份"。

## 3. P0-2：BOM 文件被自家门禁误拒（探针 2/4 实锤）

**代码**（`storygraph/app/session_export.py:530-544`）：

```python
541        return Path(p).read_text(encoding='utf-8')      # ← 不剥 BOM
```

这份 `source_text` 交给 `write_generation` → `opaque_loss(source_text, text)`：
源文第一行是 `'\ufeff# 文件头注释…'`（或 `'\ufefflabel ch01:'`），而产物里 BOM 早已被
`source_style.read_text` 剥掉 → 门禁判"第 1 行顶层语句没有出现在产物里" →
`OPAQUE_LOST`（block）→ **拒写**。

**实测**（探针 2/4，同内容三形态，只改一句旁白后原地导出）：

| 文件形态 | 结果 |
|---|---|
| 无 BOM（CRLF） | ok=True，只改该改的行 |
| BOM + 首行注释 | **ok=False，codes=['OPAQUE_LOST']** |
| BOM + 首行 label | **ok=False，codes=['OPAQUE_LOST']** |
| BOM + 空首行 | **ok=False，codes=['OPAQUE_LOST']** |

即：**凡是带 BOM 的章节文件，卡片页原地导出必然被拒**。报错文案还反过来指责用户
"有 1 处顶层语句没有出现在产物里……全量重生成会丢 define"——而真相是守卫自己拿的
源文没剥 BOM。

**为什么是 P0（虽 fail-safe）**：不毁数据（拒写方向是安全的），但
① Windows 中文项目 BOM 极常见（本仓库自己的审计：真机 5 个文件带 BOM、官方 tutorial
23/23 全带）；② `overwritable()`（`window_export.py:78`）只放 `HANDWRITTEN_TARGET`，
`OPAQUE_LOST` **没有逃生舱**，用户除了改文件编码无路可走；③ "改一句台词导不出去"
= 核心循环对该形态文件 100% 断。

**为什么是三处漏一处**：`pipeline/compile.py:294` 和 `app/tables.py:234` 都用
`source_style.read_text`（剥 BOM）并留着注释"带 BOM 的第一行会与产物对不上 → 误报
（2026-10-18 审计 P0-1 的连带修）"——`session_export` 这条**同样的修法漏掉了**。
`tests/test_audit_p0_regressions.py` 只覆盖了渲染层与 `source_style` 本身，
没有覆盖 `_source_text_for_guard`。

**修法**（一行，与另两处对齐）：

```python
from storygraph.story.source_style import read_text as _read_src
return _read_src(p)[0]
```

回归判据：BOM+CRLF 文件原地导出 ok=True，且除改过的那行外逐字节不变
（探针 2 的 A 例已是这个判据的阳性对照）。

## 4. P1 明细

### P1-1 UI 表格导出不过程引擎闸门（`app/tables.py`）

`export_table` → `apply_export` → `write_generation(...)`（342-346 行）**不传
`engine_lint`**；而 CLI `table xlsx2rpy`（`cli.py:362`）、`build`（`build.py:208`）、
卡片页导出（`session_export.py:483`）都传。同一个"表 → .rpy"操作，界面这条路不过
"引擎能不能解析这份产物"的闸门。其余守卫（手写护栏 / OPAQUE_LOST / label 重名）仍在，
所以是 P1 不是 P0；但按本项目"同一件事两处实现、漏一处就是事故"的既有教训
（cli.py:342 注释原话），这里该收口。修法：`apply_export` 透传 `engine_lint=True`，
并按 `compile.py:342-356` 的样式带上 `declared_heads_near` 与 lint 项目根。

### P1-2 非 UTF-8 文件：静默 0 拍 + 未捕获异常（两条路）

- `renpy_parser.py:234`：解码失败 `return []`（最底层静默）；
  `session_table.py:332 load` 不检查 `pr.errors` → 探针实测 GBK 文件
  **"load ok，拍到 0 张"**，界面就是一张空卡片列表，没有任何"这个文件不是 UTF-8"的解释。
  导出会被 PATCH_FAILED 拦下（fail-safe，字节未动），但用户先被空列表误导。
- `choice_point.py:233`：`read_text(encoding='utf-8')` 抛 `UnicodeDecodeError`
  （`ValueError` 子类），而 `except OSError` 接不住 → 冒到 `window_card.insert_choice_point`
  （888 行无 try）→ Qt 槽内未捕获异常。

修法：load 时把 `pr.errors` / 解码失败变成一句人话（"这个文件不是 UTF-8，Ren'Py 只认
UTF-8；另存为 UTF-8 再导入"）；选择点追加改走 `source_style.read_text` 并补
`UnicodeDecodeError` 分支。

### P1-3 选择点新文件无生成标记（潜伏）

`apply_choice_point` 新建路径用 `FILE_BANNER`（不含 `GENERATOR_MARKER`）过
`write_generation`。今天没有流程会重写这个文件（工具独占，`test_choice_point.py:178`
守着"控制流导出不吃选择点文件"），所以不炸；但一旦将来任何"重算选择点"功能走
`write_generation`，第一件事就是被 `HANDWRITTEN_TARGET` 拒写。建议创建时加
`ensure_generator_marker`，与 `control_takeover.py:258` 的做法一致。

## 5. 审过**没有**问题的（证明覆盖面，也是回归时的对照面）

- **写入架构**：`WRITERS` 单落盘点登记（`test_single_write_entry.py` 3 passed）；
  `write_text_atomic` 原子写 + `newline=''` 零翻译 + BaseException 清临时文件；
  `write_generation` 的 block 级门禁（Python 语法 / 中文图像名 / label 重名 /
  OPAQUE_LOST / 引擎 lint）+ `.blocked.rpy` 只落 `build/review/` 绝不进 `game/`。
- **原地改写一律"全文复读比对"**：`control_route`（锚点行比对）、`control_branch`、
  `control_takeover`（写前核所有文件、失败回滚）、`source_line_delete`、
  `graph/commands.py` 全部 undo/redo —— "文件在计划之后又被改过就拒写"这个模式
  在每个落盘点都在，且读回用 `source_style.read_text`、写前 `style.apply`。
- **增量补丁**：`patch_export` 表过期守卫、`_verify_patch`、trust_ranges 收紧；
  BOM/CRLF 在 patcher 与 `write_generation` 两层都有还原。
- **新建章节**（`window_nodes._write_new_chapter`）：同文件重名拒写、修复流程先
  `find_label_files` 全项目查重、追加按目标文件载体风格还原。
- **引擎隔离**：`engine_lint` / `statement_probe` / `isolated_project` 全部写临时目录，
  不碰用户项目；缩略图缓落在 `%TEMP%`；autosave 落用户 home。
- **非 UTF-8 / 非法字节整体 fail-safe**：探针 F' —— 拒写、一个字节都没动
  （问题在"不解释"，不在"敢写"）。
- **MCP / AI agent**：写盘工具（declare）dry-run + 备份 + diff；`host_validate`
  执行项目代码要显式 `trust=True`。

## 6. 修复顺序建议

1. **P0-2**（一行修 + 一个回归测试）：收益/成本比最高，且让"官方 tutorial 全量 BOM
   文件"重新可导出。
2. **P0-1**（三行修 + 把 `test_append_keeps_existing_bytes` 扩出 CRLF/BOM 参数化）：
   止住"每次插入选择点都可能整份改写用户文件"。
3. **P1-2**（两处）：把"不是 UTF-8"从静默变成一句人话。
4. **P1-1**：`apply_export` 收口引擎闸门。
5. **P1-3**：创建时补生成标记。
