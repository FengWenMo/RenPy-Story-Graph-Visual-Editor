## 二、G1：带子句的 `show` 被吞掉（P0）✅ 已修

### 现场

```rpy
label start:
    show e happy
    show bg library with dissolve
    "台词"
```

打开这一拍的卡片（`beat.show = 'e happy; bg library with dissolve'`），**什么都不改**，导出：

```rpy
label start:
    show e happy with dissolve     ← with 挪到别人头上
    "台词"                          ← bg library 整条消失
```

`tools/audit_fidelity_gaps.py::g1_clause_show` 输出：

```
G1 载入：beat.show = 'e happy; bg library with dissolve'
G1 卡片：['e happy']                 ← 卡片里根本没有 bg library
G1 提交后：beat.show = 'e happy'
G1 结论：❌ with 那条没了
```

### 为什么会这样

工具里有两个"数组 → `show` 文本"的函数，语义**不一样**：

| 函数 | 保留复杂子句？ | 谁在用 |
|---|---|---|
| `app/beats.py::apply_sprite_rows` | **保留**（`kept = [i for i in ... if i['clause']]`） | 只有 `remove_sprite` 和旧路径用 |
| `app/beats.py::cards_to_show` | **不保留**（只拼 `image` + `@位置`） | **卡牌保存/翻页走的正是这条**（`session_table.apply`：`b.show = B.cards_to_show(cards)`） |

而 `beat_sprite_rows` 会把 `clause` 形态的项**跳过**（`if item.get('clause') ... continue`），所以卡片数组里天生没有它们。`session_table.apply` 又用 `if show: b.show = show` **整体替换**，不是"拼回去"。两边一夹，子句那条就蒸发了。

### 为什么测试没抓到

`tests/test_card_editor.py:517` 有一条专门写"复杂子句（behind/as/onlayer）不进数组，但**重建时不能丢**"—— 它测的是 `apply_sprite_rows`。**真路径用的是另一个函数**，那个函数没有这条判据。这是"判据从函数出发、不是从用户路径出发"的老毛病（和 E1 拖线事故同源）。

### 修法（建议）

`cards_to_show` 不能独立承担写回，应该在 `session_table.apply` 那一层做"覆盖不了的原样带回"：

```python
new_show = B.cards_to_show(cards, self.symbols)
keep = [i for i in split_show_items(b.show) if i.get('clause')]
if new_show or keep:
    b.show = join_show_items([...结构化的...] + keep)
```

判据（先红后绿）：把 `audit_fidelity_gaps.g1_clause_show` 转成 `tests/`：`show e happy` + `show bg library with dissolve` → 提交 → 导出 → 断言产物里 `show bg library with dissolve` **逐字节还在**，且 `show e happy` **没有**被加上 `with`。

## 三、G2：`show expression` 丢了关键字（P0）✅ 已修

### 现场

```rpy
    show expression holo("lan base") at i11
```

提交后 `beat.show` 变成 `'holo("lan base")@i11; e happy'`，导出：

```rpy
    show holo("lan base") at i11
```

Ren'Py 会把 `holo("lan` 当图像名、`base")` 当属性 —— 这一行**必然报错**（lint / 启动都能看到），而且不是"少了点参数"，是"整句语法坏了"。

### 根因

`beat_sprite_rows` 只排除了 `clause`，没有排除 `is_expression`（`_parse_show_expression` 返回的项 `clause=''`、`is_expression=True`）。于是表达式被当普通立绘：`image.split()[0]` 切出 `holo("lan` 当 tag，写回时 `expression` 前缀没人负责还原。

### 修法

两条路，选一条并写死判据：

1. `beat_sprite_rows` 跳过 `is_expression` 的项（卡片不显示它们，写回时和 clause 一样原样带回）——**推荐**，改动最小，和 G1 的修法共用同一个"原样带回"通道；
2. 卡片模型带上 `is_expression`，`cards_to_show` 还原前缀（要处理表达式里的空格压缩）。

⚠ 注意 `test_roundtrip_invariants.py:1281` 已经有 `show expression holo("lan base") at i11` 的用例，但它测的是**只读往返**（不经过卡片提交），所以一直是绿的。这条用例要么补一步 `apply`，要么另开一条。

## 四、G3：中文/日文角色名 → 每导一次多一行（P0）✅ 已修

### 现场

```rpy
label start:
    凌跃捷 "第一句"
    凌跃捷 "第二句"
    return
```

把第一句改成 `第一句（改）` 后导出：

```rpy
label start:
    凌跃捷 "第一句（改）"
    凌跃捷 "第一句"          ← 旧行还在
    凌跃捷 "第二句"
```

再导一次：

```
    凌跃捷 "第一句（改）(改)"
    凌跃捷 "第一句（改）"
    凌跃捷 "第一句"
    凌跃捷 "第二句"
```

**线性恶化**，内存里的拍数也一起涨（3 → 4 → 5），因为导出会回读产物。

### 根因（一行正则）

`story/patcher.py:552`：

```python
_SAY_RE = re.compile(
    r'^(?P<who>[A-Za-z_][\w.]*)?\s*(?P<q>"|\')(?P<body>.*)(?P=q)$')
```

`who` 只认 **ASCII 开头**的标识符。中文说话人匹配失败 → `_line_key` 落到 `('other', 原文)` → 改了正文之后键就变了 → 补丁认为"这是一条新内容"→ **插入新行**；而旧行的键也不匹配了 → 被当"未知块"原样保留。

有意思的是**解析器认中文说话人**（`RenPyParser` 给出的 `payload={'speaker': '凌跃捷', ...}` 完全正确），所以这是工具内部两套口径打架：解析侧认，补丁侧不认。

### 为什么测试没抓到

`tests/` 里没有任何"非 ASCII 说话人 + 改动 + 导出"的用例；真机项目 sr_general 的角色 tag 是英文（`ling`/`ye`），所以金标也覆盖不到。**而用户画像里的中文小团队直接用中文角色名是很自然的事**（Ren'Py 基于 Python 3，中文标识符合法）。

### 修法

1. `_SAY_RE` 的 `who` 改成 Unicode 标识符：`[^\W\d]\w*(?:\.[^\W\d]\w*)*`；
2. 同一口径还有 `beat_model.py:3078` 的 `_RE_SAY_WHO`（`^(?:[A-Za-z_]\w*(?:\.[A-Za-z_]\w*)*\s+)?`）—— 两处必须一起改，否则"读得出说话人、配不上行"的老问题会以另一副脸回来（这正是项目自己总结的"同一件事两套解析"）。
3. 顺手查 `patcher.py:1006` 和 `1073` 那两处 `_SAY_RE` 用法（一个判"是不是台词行"、一个判"只有一条台词"），放宽后要确认不会把 `voice "x"` 之类吞进去 —— 已有 `_VERB_RE` 优先 + `_KEYWORD_SPEAKERS` 兜底，风险不大，但要有用例。

判据：`audit_fidelity_gaps.g3_nonascii_speaker` 转测试，断言"导出后拍数不变、产物里旧台词只出现 0 次（改过的只出现 1 次）"。

## 五、P1 项（会咬人，但不是"立刻坏"）

**P1-1 控制流守门只认 label 名。**
`story/control_write.py::plan_control_write` 的三条判据里，第二条是"文件有 `X_control` 但图里没有 `X`"→拒。它不检查**同名 label 里的内容是不是工具生成的**。用户在 `ch01_control` 里手加一句 `$ persistent.seen_ch1 = True`（很常见），导出后整份重生成，这行静默消失。文件头有"请勿手工改动结构"的标记，算告知，但对"别人的项目"仍是侵入。

*建议*：守门加第四条 —— 同名 label 块内若出现"不像生成物"的行（非 `call/jump/return/menu` 且没有生成缩进指纹），列出并让用户选"保留/覆盖"，而不是只报名字。

**P1-2 手改 Stage 会清空全部结构化字段。**
`session_table._apply_stage` 判定"用户手改了"之后，把 `scene/show/hide/at/with_/transform/stage_order` 全清空，只留文本，期待 `hydrate_from_dsl` 重建。好处是不重复（历史 P0 的正解），代价是**hydrate 认不出的部分就没了**。实测 `[停顿] 1.0` 会被保住（走 `stage_only_ops`），但会**改写成 `pause 1.0`** —— 中文 DSL 变成原生代码。这不是数据丢失，是"用户写的话被换了一种说法"。

*建议*：手改分支改成"能重建的重建，剩下认不出的原文照抄"（复用 `stage_only_ops` 的思路），别整段清空。

**P1-3 首次导出插 2 行标记。** `# 由剧本表自动生成，请勿在此文件手工改动结构` + 空行。对有 git 的项目是纯噪声（每次"第一次导出"都会有 diff）。*建议*：只在目标文件**已有**该标记时更新它；首次插入前问一次，或者写进 `.storygraph/` 的旁注而不是脚本。

**P1-4 翻页即提交。** `window_card.apply_current_beat` 在换拍时会把表单提交进内存（合理，为了不丢当前编辑），但它同时也把 G1/G2 的破坏带进来了 —— 用户"只是翻过去看看"也会中招。*建议*：G1/G2 修好之前，这条路径要能"只读不写"；修好之后也不必改（提交本身没坏，坏的是写回函数）。
