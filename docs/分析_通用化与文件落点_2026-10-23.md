# 分析（订正）：工具要通用，不能绑死 sr_general 的三件套（2026-10-23）

> **订正**：上一篇 `分析_变量归置与三件套_2026-10-23.md` 说"真机已经长成了你想要的样子"——
> **因果讲反了**。用户指出：
>
> > 错了……这个工具是给我的项目专门服务的……现在你需要把工具变得通用，
> > 可拓展到所有项目，并不是只有这个项目……
>
> `sr_general` 的 `definitions.rpy` / `chapter_controller.rpy` 是**工具围着它做出来的形状**，
> 不是"所有项目该有的形状"。通用化要做的是：**原则通用、落点跟随项目**。

---

## 一、问题重述：通用 ≠ 让所有项目长成 sr_general

| | 不是这个 | 是这个 |
|---|---|---|
| 通用化目标 | 让所有项目都建 `definitions.rpy` + `chapter_controller.rpy` | 任何项目**已有的**结构，工具都能认、能跟、能写对地方 |
| 变量归置 | "必须写进 definitions.rpy" | **必须写进"声明该在的地方"**——那地方是哪，问项目 |
| 控制流层 | "必须叫 `_control`" | **必须与内容分离**——分离出的文件叫什么、放哪，跟项目约定 |

**原则是通用的**（声明与内容分离、控制流与内容分离、剧情时刻不搬），
**落点是项目的**（文件名、目录、命名习惯）。

---

## 二、真机只是四种形状之一

不同 Ren'Py 项目的真实形状（公开项目/教程/商业作里都能见到）：

| 形状 | 变量声明在哪 | 控制流在哪 | 例子 |
|---|---|---|---|
| **A. 三件套** | `definitions.rpy` 集中 | `chapter_controller.rpy` 独立 | `sr_general`（工具围着它做的） |
| **B. 官方模板** | `script.rpy` 开头 + `gui.rpy`/`options.rpy` | 各 label 末尾 `jump` 内联 | Ren'Py 新项目默认 |
| **C. 分文件但混写** | 每个 `.rpy` 自带 `default`，散落各处 | 各章末尾 `jump` 内联 | 常见中型项目 |
| **D. 纯文本流** | `00_variables.rpy`（数字前缀） | `jump` 内联，或 `call` 子过程 | 社区推荐写法 |

**工具今天对 A 友好，对 B/C/D 可能就"没有用"**——这正是用户 2026-10-05 说的：

> "若是程序自定义了一个结构，而编剧用这个编辑器编辑时发现：你没有适应到它的
> 自定义结构怎么办？**他会立即退出，因为工具没有用！**"

---

## 三、基础设施其实已经有了——只差"文件落点"这一维

`storygraph.story.project_conventions` 已经是三层机制：

| 层 | 现有内容 | 管什么 |
|---|---|---|
| **① 认形状** | `detect_conventions()` | 立绘姿势、transform 形状、路径基准 |
| **② 清单声明** | `storygraph.rules.json`（项目根/game 下） | 覆盖自动识别；`statements`、`attr_groups`… |
| **③ 不认识就明说** | `unknown_statements()` | 扫出工具不认识的语句头，写体检报告 |

**缺的是把这三层扩到"文件落点"**。`Conventions` 现在有 `poses / pose_labels /
path_bases / auto_fixes`，**没有**：声明写哪、控制流写哪、生成物叫什么。

### 要加的维度（提案）

```json
// storygraph.rules.json 增加 placement 段
{
  "statements": { "...": "..." },
  "placement": {
    "declarations":     "game/definitions.rpy",
    "control_flow":     "game/chapter/chapter_controller.rpy",
    "generated_suffix": ".generated",
    "content_globs":    ["game/chapter/*.rpy"],
    "comment_style":    "#"
  }
}
```

| 键 | 含义 | 没声明时怎么认 |
|---|---|---|
| `declarations` | 变量 `default`/`define` 写到哪 | 扫"声明密度最高、台词密度最低"的文件；都没有则**问一次**并写进清单 |
| `control_flow` | 控制流骨架写到哪 | `files_look_like_control_flow()` 认出来的文件；或 `_control` label 聚集处 |
| `generated_suffix` | 工具生成物命名 | 项目里已有 `*.generated.rpy` / `*_control.rpy` 的习惯 |
| `content_globs` | 内容文件范围 | 其余 `.rpy` |

**声明覆盖识别**——和现有 `storygraph.rules.json` 同一条规则（用户 2026-10-05 定的）。

## 四、原则不变、落点可变（通用化后的规则）

| 原则（**所有项目通用**） | 落点（**跟项目**） |
|---|---|
| P1 声明与内容分离 | 声明写进 `placement.declarations` 指定的文件（或认出来的那一个） |
| P2 控制流与内容分离 | 控制流写进 `placement.control_flow`；**项目没有就建**，但名字听项目的 |
| P3 剧情时刻的 `$` 不搬 | 留在内容文件里、一拍一行（这条没有例外） |
| P4 可变的用 `default` 不用 `define` | 无例外（Ren'Py 存档泄漏警告） |
| P5 不猜、不认就报 | 认不出落点 → `unknown_statements` 式体检 + **问一次**写进清单 |

### 四种形状落点对照

| | 形状 A（sr_general） | 形状 B（官方模板） | 形状 C（散落） | 形状 D（00 前缀） |
|---|---|---|---|---|
| 声明写哪 | `definitions.rpy` | `script.rpy` 开头 / `options.rpy` | **认"最像声明文件"的**，或问 | `00_variables.rpy` |
| 控制流写哪 | `chapter_controller.rpy` | **新建** `game/story_control.rpy`（建议名，可改） | 同左 | 同左 |
| 剧情时刻 `$` | 章节里 | `script.rpy` label 里 | 各文件里 | 各文件里 |
| 工具要不要改项目结构 | 不改 | **不改**（只新增控制流文件） | 不改 | 不改 |

**关键：形状 B/C/D 不需要"迁移到 A"**——工具跟过去，不是把项目掰过来。

---

## 五、那"最小侵入 + 最能读懂 + 防范极端"怎么在通用模型下成立

| 判据 | 通用化后的表述 |
|---|---|
| **最小侵入** | 只写 `placement` 指定的文件 + 内容文件的拍边界；**绝不引入项目没有的新文件名**（除非项目声明同意） |
| **最能读懂** | 声明进声明文件、控制流进控制流文件、剧情时刻留在现场——**不管那三个文件叫什么** |
| **防范极端** | P4（default/define）+ 存档兼容 + `HANDWRITTEN_TARGET` + **认不出落点就问、不猜** |

### 极端清单里新增三条（通用化特有）

| 极端 | 后果 | 防范 |
|---|---|---|
| **认错落点**（把声明写进台词文件） | 剧本被污染 | 认不出就**问一次**并写进清单；绝不默认猜一个 |
| **项目没有控制流文件** | 工具凭空造个 `chapter_controller.rpy` 被当成垃圾 | 新建前**征得同意**（清单里写 `control_flow` 才建） |
| **两个项目约定不同** | 换个项目就坏 | `placement` 随项目走（在 `storygraph.rules.json` 里，不进工具代码） |

## 六、实施顺序（通用化专用）

| 步 | 做什么 | 判据 |
|---|---|---|
| **G1** | `Conventions` 加 `placement` 段 + 自动识别（声明密度/控制流形状/生成物命名） | 四种形状的样例项目，识别结果与人读一致 |
| **G2** | 清单 `storygraph.rules.json` 支持 `placement`，声明覆盖识别 | 手写清单后识别结果被覆盖；坏 JSON 不崩（已有容错） |
| **G3** | 变量声明写入走 `placement.declarations`；认不出 → 问一次写进清单 | 形状 B/C/D 的项目，声明不进内容文件 |
| **G4** | 控制流写入走 `placement.control_flow`；项目没有则征得同意再建 | 不经同意不新建文件 |
| **G5** | 体检报告加"落点识别"一节（认成了什么、依据是什么、要不要改清单） | 报告里分得清"声明的 vs 认的"（Conventions.source 已有这字段） |

**与 S 系列（图编辑器）的关系**：S1–S4 是"图上怎么接线"，G1–G5 是"接的线写到哪"。
G 是 S 的地基——落点没通用化，S 的写回就只对 sr_general 成立。

---

## 七、诚实边界

| 有依据 | 仍是判断 |
|---|---|
| `project_conventions` 三层机制已存在且被 `storygraph.rules.json` 使用 | `placement` 的键名/结构（上文是提案，要对着真实清单用法定稿） |
| 形状 A 在真机验证过 | 形状 B/C/D 的识别准确率**未验证**——需要 2–3 个不同形状的样例项目 |
| P4（default/define）是 Ren'Py 官方警告 | 新建控制流文件的命名建议是否给 2–3 个候选让用户选 |
| `files_look_like_control_flow` 已有 | 它对形状 B（内联 jump）会怎么判，未测 |

---

## 八、一句话总结

> **`sr_general` 是工具围着它做出来的形状，不是所有项目的答案。
> 通用化 = 原则通用（声明/控制流/剧情时刻三分），落点跟项目（`placement` 段认或声明）。
> 基础设施三层机制已在，只差"文件落点"这一维——G1 起手。**
