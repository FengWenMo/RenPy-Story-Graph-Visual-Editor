## 0. 一句话结论

**图编辑器不缺"编辑能力"，缺的是一条"图操作 → 拍级修改 → 受控补丁"的落地管道；
而这条管道的零件（line_id、flow 拍、patcher）已经造好了九成，缺的是接线与"锚点确认"这一道闸。
定位问题则要拆成两件事：产品定位（图是 label 级结构编辑器）今天已经清楚，
真正没定的是"节点坐标"这类布局数据的身份——它现在是手工保存的旁挂 JSON，没有绑定到项目。**

业界把这类问题叫 **round-trip engineering（往返工程）**，公认做法只有一条主干：

> **视觉编辑产出「增量」，不是「整份重写」；增量落到源文本时走带格式保留的受控补丁；
> 对不上锚点就停下来问人，绝不猜。**

这与本项目的铁律（不归己的行逐字节不动 / 不猜 / 先 diff 后写）完全同向——
缺的不是理念，是把图这一侧接进既有管道。

## 1. 先把"定位"拆开：这是两个问题

"图编辑器的定位与回写"里的**定位**，在讨论里混着两件事，必须拆开：

| # | 问题 | 今天的答案 | 还悬着的部分 |
|---|---|---|---|
| **A. 产品定位** | 图在整个工具里是干什么的 | ✅ 已收敛：**label 级结构编辑器**（一块 = 一章），卡片是拍级内容编辑器（调查文档 §四） | 文案还没被教会"改接线来图上"——入口文案仍写着"不写脚本" |
| **B. 节点定位（布局）** | 每个块在画布上的 x/y 是什么数据、存在哪、会不会丢 | ⚠ 半成品：手工「保存/加载布局 JSON」，字段是 `nodes/edges/next_ids` | **布局不随项目走**；重载章节后手工摆的位置会丢；节点 id 变了坐标就对不上 |

回写问题也有两层，分别对应图上的两类对象：

| # | 对象 | 今天 | 缺口 |
|---|---|---|---|
| **C. 边的回写** | 图上改 call/jump 接线 | `origin='source'` 的边有 `line_id`；`update_beat_flow` 改拍；patcher 落盘 | **图上的命令没接到这条路**——`AddEdgeCommand` 只改图模型 |
| **D. 布局的回写** | 坐标写到哪 | 手工存 JSON | 无自动落盘、无项目绑定、无合并策略 |

下面按业界做法逐个对。

## 2. 现状盘点：管道已经修到哪了（代码事实）

回写这件事，本项目其实已经建了三段，**只有第一段的"图侧入口"没接上**：

```
[图操作]  AddEdge / UpdateEdge / Retarget / RemoveEdge   ← 只改图模型，停在这
    │
    │  ✗ 缺这根线
    ▼
[拍级修改]  update_beat_flow(beat, type, target, …)      ← story/flow.py，已有
            insert_flow_beat(…, anchor_idx)              ← 卡片「↳ 插入控制流卡」，已有
            Edge.line_id ↔ Beat.line_id 一一对应          ← 2026-10-22 已建
    │
    ▼
[受控补丁]  patcher.patch_export / recover_source_ranges  ← 2962 行，相似度 0.994+
            只替换真改过的行，其余逐字节保留；return/label 白名单不删
    │
    ▼
[门禁]     generation_guard + 先 diff 后写（铁律 5）      ← 已接入 write_generation
```

**推论（判断）**：回写不是"从零建一条新路"，而是**把图的命令出口从"改图"扩成"改图 + 改拍"**，
后两段原样复用。这决定了工作量与风险量级——是接线，不是重写。

已有的关键零件（都有测试钉着）：

| 零件 | 位置 | 作用 |
|---|---|---|
| `Edge.origin`（`source`/`manual`） | `graph/models.py` | 区分"脚本里已有的边"与"用户画的草图"，重建时不会误删草图 |
| `Edge.line_id` | 同上 | 同一 label 里两次 `call side` 也能按拍对位 |
| `flow.update_beat_flow` | `story/flow.py:177` | 只改目标/类型，**保留参数与 from**；校验不过则 Beat 一字不动 |
| `flow.parse_flow_line` | 同上 | 不认识的写法返回 None，宁可走原样通道也不猜 |
| `insert_flow_beat` | 会话层 | 按锚点插入 flow 拍，已有卡片入口 |
| `patcher` | `story/patcher.py` | 增量导出；未改时逐字节相同；结构性行绝不删 |
| `save_layout` / `load_layout` | `app/session_graph.py:527/561` | 布局 JSON 向后兼容旧格式 |

## 3. 业界怎么做（工业化对照）

### 3.1 往返工程（Round-Trip Engineering）—— 图 ↔ 源码同步的总纲

UML/建模工具（Visual Paradigm、Enterprise Architect、MagicDraw）处理"图与代码不同步"已有二十年实践，
公开教程里反复出现的三条，正好是本项目缺的三段：

| 业界原则 | 原话/做法 | 对应本项目 |
|---|---|---|
| **双向 + 增量** | "Synchronize incrementally — merge changes in either direction without overwriting valuable work" | 图改边 = 增量，不是整章重写（patcher 已经是这个模型） |
| **合并时保留手写** | "Merge mode preserves handwritten logic during forward" | 不归己的行逐字节不动（铁律 1，patcher 已守） |
| **漂移检测** | 最大风险是 "model-code drift"；要周期性 reverse 核对 | 图边与 flow 拍的对账（`origin='source'` 边应能被 flow_edges 重建出来） |

学术侧（SciTePress 增量往返、arXiv 的 DDD 往返）补充一条关键工程细节：

> 变更要走 **delta（增量描述）** 而不是"重新生成整个产物"；
> 重命名会波及引用方，所以**改名与改内容要区分处理**。

本项目的 `RenamePatch`（plan→apply→rollback）正是这个区分，方向是对的。

### 3.2 图编辑器怎么保存"坐标"—— 布局持久化的行业惯例

翻了 Unity 节点编辑器、通用 node_editor、行为树等公开实现，**做法高度一致**：

```
{ "nodes": [ {"id": …, "x": …, "y": …, …} ],
  "edges": [ {"from": …, "to": …, …} ] }
```

| 惯例 | 说明 | 本项目现状 |
|---|---|---|
| **布局是 sidecar（旁挂），不进源码** | 源码/脚本里不写坐标；图数据独立成 JSON/资产 | ✅ 已符合（布局 JSON 与 .rpy 分离） |
| **坐标是"会话/工程状态"，不是"剧情内容"** | 改坐标不该触发脚本重写 | ✅ 已符合 |
| **稳定键用业务 id，不用数组下标** | 重载/重排后仍能对回原节点 | ⚠ 用的是 `node.id`（自增整数），**不是 label** |
| **导入时校验 + 保留未知字段** | 旧文件不至于崩 | ✅ `load_layout` 已做 |
| **相对画布坐标**，不是屏幕绝对坐标 | 窗口大小变了不乱飞 | 需核对（判断：`Node.x/y` 是画布坐标，符合） |

**两处与惯例的差距（这是布局问题的全部）**：

1. **存哪**：现在是"用户点保存→自己挑路径"。业界要么自动存到项目目录（`<项目>/.storygraph/layout.json`），
   要么存进工程资产。**手工保存 = 迟早忘存 = 摆好的版式白费**（用户 2026-10-04 抱怨"保存布局.json 哪去了"
   正是这类痛的前一次爆发）。
2. **用什么键**：`nodes` 的键是 `node.id`（每次构建图重新分配的整数）。**同一章重新导入后 id 会变，
   坐标就挂到别的块上**。业界用稳定业务键（label 名 / 文件路径）做主键，id 只当会话句柄。

### 3.3 叙事工具怎么处理"图上的线 = 脚本里的跳转"

对照 `叙事工具行业调研.md` 与各家官网，叙事工具分两派，**没有一派是"图画一半、脚本写一半"**：

| 派 | 代表 | 图与脚本的关系 | 对本项目的启示 |
|---|---|---|---|
| **图即真源** | articy:draft、Arcweave、Twine、Chat Mapper | 图/数据库是唯一真源，脚本是导出物 | 与铁律冲突（.rpy 是运行时真源），**不采纳** |
| **文本即真源** | ink、Yarn Spinner、Ren'Py | 文本是真源，图是只读视图或辅助 | **半采纳**：图可以编辑结构，但一切编辑最终必须落到文本语义（拍）上 |
| **中间形态** | Chat Mapper 2026 改版 | 图上改 → **先立 revision，接受才落地**；全图确定性校验（断链/死路/未定义变量） | **直接借鉴**：图上的改动走"提议 → 确认 → 落地" |

两派之外有一条**反面教训**（intfiction 社区，IF 老手 Dan Fabulich）：

> "可视化只在不需要它的简单样例里有效，在最需要它的复杂环境里失效"；
> 大项目里节点图会变成"大陆、半岛与群岛"，认知负担从讲故事变成找路。

→ 对应本项目调查文档 §六的"明确不做"（不做拍级画布、不在图里编辑 menu 体）**是正确取舍**。
图保持 **label 级（一块一章）**，正是躲开"群岛效应"的粒度选择。

### 3.4 文本保真：CST / trivia 与"特殊标记"

图编辑要把结果写回文本，业界两套做法：

| 做法 | 代表 | 思路 | 对本项目 |
|---|---|---|---|
| **CST 带 trivia** | Modelica 图形编辑器（Lund 研究）、Glisp、Roslyn | 解析时把空格/换行/注释存进旁路结构，打印时还回去 | patcher 的"原文行原样保留"已是**效果等价**的简化版；不必上完整 CST |
| **文本内嵌标记 + 文件尾元数据** | Luna/Enso | 文本里埋 marker，位置元数据存文件尾，图编辑对用户透明 | 不必——布局已走 sidecar JSON，更干净 |

**结论**：格式保真这层**不需要新造**，patcher 够用。真正要造的是"哪一处文本该被改"的定位能力
（= line_id / 锚点），而这正好是 `Edge.line_id` 与 `Beat.src_first/src_last` 已经提供的东西。

## 4. 根因：为什么"图上改了、游戏里没变"

把三条代码事实与业界原则对上，根因只有一句话：

> **图的命令层（`graph/commands.py`）被有意设计成"只改图模型"，
> 而"改拍 + 受控补丁"这条下游是在卡片侧另建的——两条路在会话层没有汇合。**

具体拆成四个缺口（按危险度排序）：

| # | 缺口 | 后果 | 危险度 |
|---|---|---|---|
| 1 | `origin='source'` 边改目标/类型时不落 `Beat.raw` | 图与脚本静默分叉 | **P0**（"图上看着改了"是信任问题） |
| 2 | `origin='manual'` 草图边无锚点、无"应用"动作 | 用户以为画了就生效 | **P0**（同上，且更常见） |
| 3 | 布局不自动落盘、键不稳定 | 摆好的版式会丢 / 挂错块 | **P1**（烦，但不毁数据） |
| 4 | 无"图 ↔ 拍"漂移对账 | 分叉后没人发现 | **P1**（体检能力） |

注意缺口 1/2 的表现是**信任损伤**，不是数据损坏——这正是调查文档说
"策划一旦发现我看到的和生成的不一样，这个工具对他就不存在了"的那一类。

## 5. 推荐方案

### 5.1 回写（缺口 1/2）：「命令 → 拍 → 补丁」三段接线

**总原则（与业界 round-trip 一致，与本项目铁律一致）**：

1. **图操作产出增量意图（delta），永不整章重写**；
2. **每条意图必须有锚点**（`line_id` 或用户选定的插入位置），没有就停下问；
3. **落地前给人看 diff**，确认才写（铁律 5）；
4. **两条边规则不同**，界面上一眼分得出（实线/点划线已具备，保留）。

#### a. `origin='source'` 边（脚本里已有 call/jump）—— 直接改拍

```
图上「改目标/类型」
  → 按 edge.line_id 找到 flow 拍
  → flow.update_beat_flow(beat, …)          # 校验不过则一字不动
  → 标记该拍 dirty
  → 导出时走 patcher（只改那一行）
```

- **为什么安全**：line_id 是拍的身份（同 label 两次 call 也分得开）；
  `update_beat_flow` 保留参数/from；patcher 只动真改过的行。
- **找不到拍怎么办**：line_id 失效（拍被删/表被改）→ **报"对不上锚点"，不猜、不改**（铁律 4）。

#### b. `origin='manual'` 草图边 —— 先问锚点，再插 flow 拍

```
图上画一条 A → B（call/jump）
  → 弹锚点确认：「插在哪一拍后面？」[默认：A 章末] [可选：当前选中的拍]
  → insert_flow_beat(after=锚点, type, target)
  → 该边 origin 升格为 'source'，补上 line_id
  → 走同一条 patcher 路径
```

- **为什么不默认"章末"直接写**：调查文档硬约束 1 写死了"不猜锚点"。
  默认值给章末是**给一个建议**，仍要人确认——这正是 Chat Mapper
  "revision before any accepted change lands" 的落地形态。
- **边界**：目标 label 不存在 → 问"要不要顺手建这个 label 的骨架？"（只建空 label，不生成内容——
  调查文档 §六已排除"手画一线自动生成一整章"）。

#### c. 落地统一出口：复用 `write_generation` + diff

图侧改动与卡片侧改动**必须走同一个落盘出口**（WRITERS 登记 + 门禁），
不许图侧再开一条写盘路径——否则守卫 `test_single_write_entry` 会红，这是故意的。

**预期工作量（判断）**：接线 + 对话框 + 测试 ≈ 2~3 天；
其中一天要花在"line_id 失效 / 表被外部改动"这类对抗用例上（用户方法论：先跑既有测试 → 白盒 → 对抗攻击）。

### 5.2 布局（缺口 3）：sidecar + 稳定键 + 自动落盘

| 改什么 | 做法 | 为什么 |
|---|---|---|
| **存哪** | 默认 `<项目>/.storygraph/graph_layout.json`，打开项目自动读、关闭/改动后自动写 | 消灭"忘保存"；`.storygraph/` 已是项目内工具目录约定 |
| **主键** | `nodes` 的键从 `node.id` 改为 **`file_path::label_name`**（稳定业务键）；`id` 只留在 `next_ids` | 重载/重排后坐标不挂错块（业界惯例） |
| **合并策略** | 图结构变了（新增块/删块）时：**留存块的坐标保留，新块自动布局补位，消失块的坐标丢弃并记一条日志** | 对应 round-trip 的"增量同步不覆盖有价值的工作" |
| **兼容** | 旧格式 JSON（键是整数 id）读入时自动迁移：按 `label` 字段匹配迁移坐标 | 用户手排的版式贵（`save_layout` 注释原话），不能作废 |
| **多人** | 布局文件不进协作同步的关键路径（坐标冲突无伤大雅）；`collab.db` 可选存一份 | 避免为坐标引入锁竞争 |

**预期工作量（判断）**：1 天（含旧格式迁移用例）。

### 5.3 漂移对账（缺口 4）：图 ↔ 拍的一致性体检

加一条体检（放 `tools/` 或会话诊断面板）：

```
for 每条 origin='source' 边:
    能用 line_id 找到 flow 拍，且拍的目标/类型与边一致？  否 → DRIFT
for 每张 flow 拍:
    图上存在对应边？                                    否 → ORPHAN_BEAT（可能是删边没同步）
for 每条 origin='manual' 边:
    标"草图未落地"                                     → 信息级，不算错
```

对应业界 "periodic consistency checks" 与 Chat Mapper 的确定性校验（断链/死路）。
**先只报不改**（M 不变量：工具只做发现、展示，不猜语义）。

### 5.4 产品定位的收尾（缺口 0）

方案层面已经定了（图 = label 级结构编辑器），剩下的是**话术与入口**：

- 三处文案（`add_edge` 状态栏、`AddEdgeDialog`、图例）从"不写脚本"改成
  **"写这条线会改本章第 N 拍"**（接通回写后）；落地前则写"草图，点「应用到脚本」才会写"。
- 右键菜单把「应用到脚本」做成显式动作（对应 git 的 stage/commit 语义），
  而不是隐藏在导出里。

## 6. 方案取舍：为什么是 A 不是 B/C

| 方案 | 描述 | 判定 |
|---|---|---|
| **A. 命令 → 拍 → 补丁（推荐）** | 图操作产 delta，落到拍，受控补丁写盘 | ✅ 复用九成管道；与铁律同向；风险可控 |
| B. 图只读，点击跳卡片 | ink/Yarn 纯文本派 | ❌ 用户已明确否掉（"只能在卡牌页面内决定 label 跳转是非常麻烦的"） |
| C. 图即真源，整章生成 | articy 派 | ❌ 违反铁律 1/5；整章重写已在此前造成过事故（`generated.rpy` 撞 label） |
| D. 投影式编辑（MPS） | 结构即真源，无文本 | ❌ 与 Ren'Py 生态、与"程序敲代码自动反映到表格"的需求都不兼容 |
| E. 上完整 CST/trivia | Roslyn 式格式树 | ⏸ 不必：patcher 的行级保留已达同等效果；等真要"注释跟着语句搬家"再议 |

## 7. 分阶段与判据

| 阶段 | 内容 | 判据（可测） | 优先级 |
|---|---|---|---|
| **W1** | 布局：自动落盘 + 稳定键 + 旧格式迁移 | 重载后坐标 100% 挂对块；旧 JSON 读入不丢坐标；改动后自动保存有落盘 | **P1** |
| **W2** | 回写 a：`source` 边改目标 → `update_beat_flow` → patcher | 图上改 call 目标，导出后**只 diff 出那一行**；line_id 失效时报锚点错误、零写 | **P0** |
| **W3** | 回写 b：草图边 → 锚点确认 → 插 flow 拍 → 升格为 source | 不确认零写；确认后 origin/line_id 正确；删边同步（控制流卡第三阶段已有删边，补"删图边→删拍"需再议） | **P0** |
| **W4** | 漂移对账 + 文案/入口收尾 | 体检报 DRIFT/ORPHAN 与构造的分叉样本一致；文案不再写"不写脚本" | **P1** |
| **W5** | （可选）目标 label 不存在时建骨架 | 只建空 label，生成物过 generation_guard | P2 |

每阶段的测试姿势（按你的方法论）：

1. **先跑既有**：`test_flow_target_brief` / `test_graph_statements` / `test_incremental_export` / `test_custom_statement_entry` 等相关面；
2. **白盒**：核对命令层是否真的调到了 `update_beat_flow`（不是又写了一套字符串替换）；
3. **对抗**：line_id 失效、外部改表、同 label 双 call、草图边未确认就关窗、布局 JSON 被手改成坏值——
   每一条都要"要么全对、要么完全不动"。

**明确不做（沿用调查文档 §六 + 本文 §6）**：拍级画布、图内编辑 menu/if 体、
画线自动生成整章、把布局写进 .rpy、整章重写回源文件。

## 8. 和"工业化"这个要求的对应关系

用户要的是"行业搜索 + 工业化解决方案"。工业化在这里的具体含义（逐条对应上文）：

| 工业化特征 | 业界出处 | 本方案落点 |
|---|---|---|
| 增量而非全量 | Round-trip / 增量往返论文 | W2/W3 全部走 delta → patcher |
| 身份稳定 | Yarn `#line:` / Godot `[ID:KEY]` / Ren'Py 翻译单元教训 | `Edge.line_id` + 布局稳定键（W1） |
| 保留手工改动 | "merge mode preserves handwritten logic" | patcher 已有；图侧不整章重写 |
| 变更可审阅 | Chat Mapper revision-before-accept | 锚点确认 + 先 diff 后写（铁律 5） |
| 一致性可检测 | periodic consistency checks / 确定性校验 | W4 漂移对账 |
| 失败显式化 | "import report"（ChatMapper）/ 门禁 | 对不上锚点就报，零写；不猜 |
| 布局与内容分离 | 节点编辑器普遍惯例 | 布局 sidecar（W1） |

## 9. 遗留的判断题（留给用户拍板）

> **2026-10-23 晚补充**：判断题 1/2 已展开成详细分析，
> 见 [`答复_图上删加调用的位置问题_2026-10-23.md`](答复_图上删加调用的位置问题_2026-10-23.md)。
> 核心修正：**工具判断不了"合适的位置"**（那是叙事判断），只能做到
> "看得见位置、选得定位置、找得回位置、绝不猜"。实施顺序改为 S1（边上显示位置徽标）
> → S2（加边锚点确认）→ S3（删边防弹回）→ S4（回到上次位置）。

1. **删图边要不要删拍？** 详答见上述答复文：**默认只删线**（删比藏危险），
   真删做成显式动作「连同脚本里的调用一起删」；只删线时进"用户隐藏列表"防刷新弹回。
2. **草图锚点要不要记住上次选择？** 详答见上述答复文：不是"记住并静默沿用"，
   而是**给一键「回到上次的位置」**——删后加回本质是还原，不该逼用户重新翻拍列表。
3. **布局文件进不进 git？** 建议进（手排版式贵），但协作同步不强制。
4. **W1（布局）与 W2（回写 a）谁先做？** 建议 S1（位置徽标，只读）最先——它回答
   "不知道 call 在哪"这个读的问题，且零写盘风险。其余按痛点排。

## 10. 一句话总结

> 图编辑器的"定位"问题，产品层面已经答完（label 级结构编辑器），
> 没答完的是**坐标数据的家**；"回写"问题则不是缺能力，是缺一根线——
> 把图的命令出口接到已有的 `line_id → update_beat_flow → patcher` 管道上，
> 并给草图边加一道"锚点确认"的闸。业界管这套叫 round-trip engineering，
> 而它最难的部分（保真补丁、稳定身份、门禁）本项目已经付过学费了。
