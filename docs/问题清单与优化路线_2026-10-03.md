**P1-1　分支内舞台指令失去分支保护**　→ **已修（2026-10-05）**

- 典型：`pomodorro/script_pomo.rpy` 的 `if pomoplace == "ocean" / elif "cafe" / elif "library"`
  三分支背景 → 产物里 `pomoplace` **3 次 → 0 次**，三个背景依次无条件 show

  **条件与当前拍不一致时先落拍**，各自带上自己的条件（复用 menu 那套
  "扁平拍 + 按结构归组"）。实测 13/13 条分支内舞台指令全部留在自己的分支里。

**P1-2　menu 结构的残余风险**

### 3. `transform` 链路（P2-4）——**查清：通的，但走的不是 `beat.transform`**

`beat.transform` 是**旧模型残留**：只在渲染时被读（`with <transform>`），
解析与 Excel 回导**都不写它**，所以真实项目 2013 拍里有值 0 次。
**自定义 transform 的能力是通的，载体是另外三个字段**：

| 场景 | 字段 | 单元格编码 |
|---|---|---|
| `show eileen happy at leftish` | `beat.at` | 立绘列 `eileen happy@leftish` |
| `scene bg room at bgfit` | `beat.scene_at` | `scene_at` |
| `with Dissolve(0.5)` | `beat.with_` | 转场列 |

新增 `TestCustomTransformRoundtrip`（4 条）把这条路钉住，并**顺手挖出一个
真实缺陷**：

```renpy
show image puzzle_path at Transform(xysize=(1920, 1080))
```

分词器把逗号一律当分隔符，`at` 收成
`['Transform(xysize=(1920', '1080))']`，拼回去（空格连接多目标）变成

```renpy
show image puzzle_path at Transform(xysize=(1920 1080))    # Python 语法错误
```

**产物直接跑不起来**，而语句多重集断言**看不出来**（它把 `at` 列表归一化了，
两边"一样"）。修法：分词器按**括号深度**决定逗号是不是分隔符；
`at` 多目标之间保留逗号（`_join_at_targets`）。
真实项目 `mini_game_puzzle.rpy` 第 262/284 行就是这个写法。

### P1-2　菜单分组在编辑下会不会错乱 —— **补上了，并且真的抓到一个**

新增 `tests/test_roundtrip_invariants.py::TestMenuGroupingUnderEdits`（6 条），
模拟策划真实的四种改法：选项之间插一拍、菜单后追加一拍、两个选项对调、
删掉一个选项。**第 2 条当场变红** —— 而且是最坏的那种坏法：

```
插入一拍之前                     插入一拍之后（修复前）
menu:                            menu:
    "选项A":                         "选项A":
        "A 的内容"                       pass
    "选项B":                     "插进来的旁白"        ← 掉出菜单
        "B 的内容"               if True:              ← 无条件执行了
"菜单之后"                           "A 的内容"
                                 "选项B"              ← 选项变成一句旁白
                                 if True:
                                     "B 的内容"
```

一次误判把**整个菜单拆散**：选项降级成旁白、分支体降级成无条件执行。

**根因**：分组是**重建**的（`_menu_member` 存不进 Excel），
`_in_menu_body` 在插进来的那一拍上判 False，`_take_menu_run` 就当场收尾。

**修法**：组**只能收在"下一个带选项/成员标记的拍之前"** ——
`_menu_looks_unfinished` 往后扫，后面还有 `menu_option` 或
`_menu_member=True` 的拍时，中间那张认不出归属的拍照收不误。

**但"收进来"本身也是改变语义**（那一拍变成"只有选中该选项才播"），
所以再补一层：`_is_menu_foreign` 把"认不出归属"的拍单独标出来，
渲染时**按原位置**放回去并加一句显式警告：

```renpy
menu:
    "选项A":
        # TODO: 这一拍不确定属于哪个选项
        "插进来的旁白"
        "A 的内容"
    "选项B":
        "B 的内容"
```

`.rpy → .rpy`（`_menu_member` 是 True）那条路**不加任何警告**，产出逐字不变。

### Bug 1：`if` 里包 `menu`，整块降级（解析层）

```renpy
输入                          产物（修复前）
if flag:                      label a:
    menu:                         "左边"        ← 裸旁白
        "左边": jump left         "右边"        ← 裸旁白

```

条件 / caption / 两个 `jump` **全部消失**，选项 `kind` 连 `menu_option`
都不是。**两处根因**：

1. **解析器把两种"条件来源"混成了一个**。`accum_cond` 同时含

2. **渲染层从来没写过"菜单整块的条件"**。`_render_menu_segments` 只管

### Bug 4：拍的 label 顺序回头 → 产物出现重复 `label`

### Bug 5：条件拍的块体没有缩进 → `if` 与块体齐平（语法错误）

```renpy
            if deepest:
            e "深层"        ← 与 if 齐平 = Ren'Py 报错
            if not ((deepest)):
            e "深层的 else"
```

两处独立缺陷，都会让**产物跑不起来**：

### Bug 6：菜单选项体里的嵌套 `if` 被当成"认不出归属"（静默改剧情）

```renpy
menu:
    "选项":
        show bg_deep
        if deepest:        ← 条件变成 ((外层) and (选项)) and (deepest)
            e "深层"
        else:
            e "深层的 else"
```

`.rpy → .rpy` 这条路上 `_menu_member=True` 认得出来；但 **`_menu_member`
是运行时元数据、存不进 Excel**，所以**表格往返之后**这两拍只能靠条件认。
认不出的后果不是"少一句警告"，而是渲染层**不再写 `if deepest:`** ——
两个分支都被无条件执行（静默改剧情），外加一句 TODO。

**修法**：新增 `_condition_is_refinement(cond, base)` —— 条件是块体基准的
**加强版**（按 `and` 递归拆原子，看集合包含）就说明它是嵌套 `if`，不是外来拍。

**坑**：第一版忘了递归剥括号。`((outer) and (middle)) and (deepest)` 只拆
外面那层得到 `{'(outer) and (middle)', 'deepest'}`，与 `base` 的
`{'outer','middle'}` 对不上 → 判定失败。递归之后才是
`{'outer','middle','deepest'}` ⊇ `{'outer','middle'}`。

**保留的守卫**：条件**为空**仍然算"认不出归属"。解析器给选项体里的拍
（含嵌套 if）都会带累积条件，所以"条件为空"只可能是策划手工插进来的拍
（`Beat(kind=…, text=…)` 不带条件）—— 那正是它唯一的特征，删掉这个守卫

### Bug 7：`=` 开头的用户文本在 Excel 往返后**静默消失**

### 11.1 另一个 P0：产物里的 Python 语法错误

`audit_roundtrip.py` 一直报着一处：

```
script.rpy: 第 80 行 'l oh "3"' —— invalid syntax
```

原文第 93 行是作者手写的 `l oh "3"`（`l` 后面多打了个 `oh`）。
Ren'Py 把**裸的 `词 词 "串"`** 当台词读（角色 `l oh` 说 `"3"`）——
Ren'Py 要到**运行时**才抱怨角色未定义，那是"脚本能跑"的范畴。

而工具把它归成 `raw`，导出时按"裸 python 表达式"补了 `$`：

```
原文：  l oh "3"        ← 脚本能跑
产物：  $ l oh "3"      ← Python 语法错误，Ren'Py 加载就报错
```

**工具的产物比作者原文更糟** —— 所以是 P0。

**修法（`_looks_like_dialogue` + `_RENPY_STATEMENT_HEADS`，两者并集）**：
只在"这行只可能是台词/已知语句"时才原样透传。

| 形态 | 判据 | 为什么需要 |
|---|---|---|
| 台词 | `标识符链 + 引号串 + 行尾` | `l oh "3"` 的第一步是**角色名**，动词白名单不可能覆盖 |
| 已知动词 | `show` / `jump` / `pause` … 白名单 | `show screen my_hud` **没有引号串**，形态判据认不出 |

**两版都踩过坑，都记在这里**：

1. 只做动词白名单（第一版的历史实现 `_RENPY_STATEMENT_HEADS`）→
   漏 `l oh "3"`（它不是动词开头）。
2. 只做台词形态（我这次的第一版）→ `show screen my_hud` 被补成
   `$ show screen my_hud`（**语法错误**），`TestOpaquePreserved`
   当场红了两条。

`if` / `elif` / `else` / `while` / `for` **故意不在**白名单里：
它们在 `raw` 里出现时是**代码块内部的条件行**，当语句透传会把块结构弄坏。

为什么不做"整体像 Ren'Py 就透传"的猜测：第一版的历史实现那么做过，
实测红了 **13 个**测试。要放宽必须**先有证据**。

### 11.2 让工具**再也写不出**跑不起来的脚本

只修 `l oh "3"` 是治标 —— 下次换个形态又会漏。
所以 `generation_guard` 新增第 0 条门禁 **`PYTHON_SYNTAX_ERROR`**：

把产物里所有 `$ …` 行与 `python:` 块体逐条过一遍 Python 编译器
（`compile(…, 'exec')`；跳过注释与空行）。编译不过就是 **block**，

比图像名/标签重名更致命（那两类至少能进到解析阶段）。

这与 P0 静默覆盖是同一个性质：工具**算出了"要出事"却没拦住**。
以前的状况是只有 `audit_roundtrip.py` 事后能看见，而文件照写不误。

## 十七、剩下三条"排版漂移"：查清了，其中一条是真 bug（2026-10-05 续十二）

### 17.1 结论先说

| # | 现象 | 定性 |
|---|---|---|
| 1-3 | `python:` 块内**续行（括号内换行）的缩进**比原文大一档（12 → 20） | **假阳性**。括号内换行的缩进在 Python 里完全自由，语义一模一样（`_unparsable_python` 全程 0 处错误）。审计按**逐行文本**比对才把它算成丢失 |
| （已修） | `python:` 块**内部**的**空行**会丢 | **真 bug**，已修（见 17.3） |

### 17.2 为什么"修不动"要写进代码里

对那 3 条试了**三种**改法，每一种都实测让情况变糟：

| 改法 | 结果 |
|---|---|
| `_indent_beat_lines` 的 `base` 改成"从非续行里取" | 解析异常 **0 → 5** |
| 只给续行额外减一档（`base + 4`） | 解析异常 **0 → 5** |
| `_indent_block_body` 首行加基准、其余不加 | 丢失 **3 → 7** |
| 把续行也按块体基准平移（`_collect_python_block`） | 丢失 **3 → 7**、新增 28 → 82 |

前几种的问题都是**作用面太宽**：`_indent_beat_lines` 与
`_collect_python_block` 是**每一拍 / 每一个 Python 块**都要走的路，
改它们等于改全项目；而这几条续行只是两个小游戏文件里的排版。

所以最后**明确不动**，并把结论写进两个函数的 docstring ——
下一个想动手的人会先看到"试过哪几种、为什么失败"，
而不是从零再试一遍（这一轮我自己就试了四轮）。

留了两个**暂时没有调用方**的辅助函数（`_has_open_bracket` /
`_shift_embedded_indent`）：它们是"续行 vs 下一层块体"的**唯一正确判据**，
下次真要修时能直接用，docstring 里也写明了为什么留着。

   `window_nodes`(12) / `window_export`(10) / `window_assets`(3) /
   `window_keyboard`(5)。
3. `tests/test_main_window_mixins.py` 结构守卫：基类顺序、同名静默覆盖、
   `REQUIRES` 双向、覆盖面、Qt 成员清单**真的去问 Qt**。

**踩到的坑（已写进守卫）**：六个 mixin 必须排在 `QMainWindow` **前面** ——
`eventFilter` / `closeEvent` 是 Qt 虚函数（`QObject` 自己就定义了），
排在后面会被它抢先、mixin 那份成死代码。表现为 **13 条键盘用例全红，
而 `hasattr(MainWindowQt, 'eventFilter')` 照样是 True**。
这类事故是"搬家不是改契约"里最容易漏的一种：方法**在**，**谁先被找到**变了。

**另一个坑（我自己的脚本 bug）**：批量搬迁脚本只认 `ast.Name` 目标，
于是 `PREFETCH_AHEAD, PREFETCH_BEHIND = 2, 1`（元组解包）**既没被搬走、
也没被算进覆盖面** —— 脚本报"一个都不漏"，实际把它们**从主类里删掉了**，
搬到别处的 `self.PREFETCH_AHEAD` 会在运行时 `AttributeError`。
修法是取值和核对**两个方向都认元组**，并加一条"反向核对：主类原有成员
一个都不许凭空消失"。同一疏漏在守卫里也咬了一次。

### 18.2 P3-13：静默 except（**不照做审计报告的建议**）

审计报告说"321 个 except 里 99 个 body 只有 pass，196 处 `noqa: BLE001`"，
建议**把 `except` 收窄成具体异常**。数字属实，但结论**没照做**：

> 那些位置确实需要兜住一切（清理、Qt 控件已销毁、可选缓存写不进去、
> 第三方表格式千奇百怪）—— 收窄成 `except ValueError` 只会让真正的
> 异常逃到上层，变成"整个界面崩一下"，比现在更糟。
> 真正的毛病不是"宽"，而是**一出事什么都没有**。

所以**保留宽捕获、补上痕迹**：`except Exception as e:` +
`swallow('<模块>.<函数>', e)`。88 处（258 个宽捕获里"既没用异常对象、
也没有任何调用"的那些）全部补上，**静默数 88 → 0**。

判据刻意**不是**"必须调 `swallow`"：`self._status(f'…{e}')` /
`logging.warning(...)` / `_emit(ENGINE_ERROR, …)` 都算"说了"。
只认 `swallow` 会把它们全红掉，那这个守卫没人愿意留。

批量改写工具踩了**三次**（都写进 `tools/_add_swallow.py` 的注释了）：
1. `ExceptHandler.lineno` **不是** `except` 那一行 —— 实测它指向
   `try` 体里的语句，甚至指向 `except` 自己（差一行）。用它去"给 except
   行补 `as e`"改到了 `try` 体里，产物成 `try: … as e`（语法错误）。
   → **批量改写只认文本，`ast` 只用来说明"哪些该改"。**
2. 多行 import 的括号里不能插 import（4 个文件语法错误）。
3. 不能给 `core/safeguard.py` 自己插 `swallow`（**无限递归**）
   或自 import（`ImportError`）。

### 18.3 P3-15：`content_hash` 加宽（顺带发现第二处写死的位数）

八位 hex = **32 bit**，生日碰撞门槛只有 65536 个内容。
撞了的后果**不是丢内容，是"身份"错**：`make_translation_uid` 把
`{label}_{hash}` 当翻译单元身份，两条不同台词撞上同一 hash 时第二条被
改名，**已有译文对不上号**；`collab_store` 拿它当"内容变没变"的判据，
撞了就当没变、**改动静默不同步**。

改成 **16 位（64 bit）**，门槛抬到 43 亿。可以改的理由：它是
**本项目自己算的**，不是 Ren'Py 外部格式 —— 文档里那句"与 TU 的 hash
部分逐字节一致"指的是**两边算法要一致**（唯一真源 `core/uid.py`）。

**顺带发现的真问题**：`renpy_parser.py::_unique_id` 里**也写死了一个
`[:8]`**，而文档明令"禁止各自拼接 `f'{label}_{hash}'`"。
把一边改成 16 之后两边不再一致，而**所有测试都是绿的**（各自内部都自洽）。
所以新守卫 `tests/test_content_hash_contract.py` 比的是**产物**
（两处拼出的 uid 必须相同），不是"有没有 import 常量"。

唯一豁免：`renpy_parser` 里**翻译文件数据库的键**也截了 8 位 ——
但它输入是 tl 文件里的原文、不参与 `content_hash` 契约，**加宽它只会
让用户的既有译文查不到**。有测试钉住"豁免恰好对应 1 处"。

### 18.4 P3-12：拆 `layout_graph`（147 → 消失），并修它藏着的两个真 bug

`graph/layout.py::layout_graph` 原本 358 行 / 复杂度 **147**（全项目第一），
里面塞着 7 个闭包加一整段主流程。把那几段提成模块级私有函数后，
**不带闸时与 HEAD 逐字节等价**（`tools/_verify_layout.py`：11 个形状全一致）。

顺带发现两个**既有**真 bug（HEAD 同样有，不是拆分引入的）：

**① `_ensure_dag` 会死循环 → 窗口卡死。**
原实现是 `while True:` —— 反一条边有可能**造出新的环**，如此往复。
实测 25 节点 / 50 边的随机图**几分钟不返回**（连分层都没走到），
而它在 UI 线程上被调用。

**② 布局不确定：同一张图每次打开排得不一样。**
`tools/_hashseed_demo.py`：20 节点 / 24 边，6 个 `PYTHONHASHSEED`
给出 **4 种坐标和**。`tools/_trace_layout.py` 逐步摘要定位到根因：
前 8 个阶段在所有 seed 下完全一致，**从 `bary_1` 起分叉** ——
`_barycenter_once` 里 `ext_neighbors` 是 `defaultdict(set)`，
而 `sorted(zip(weighted_vals, neighbors, weights))` 在第一个元素相等时
退化成比较 `neighbors` 的**随机顺序**。`_ensure_dag` 取"第一条环内边"
也有同样毛病。两处都改成按 `str(nid)` 排序。

用户侧表现是"剧情图每次打开形状都不一样" —— 比"排得不够好"更让人不安。

**降交叉也封了顶**：`_reduce_crossings` 必然终止但**很慢**
（每接受一次交换就从该层最左重扫）。病态图上几秒滑到几分钟。
加了**纯计数**预算 20000：正常图实测 ≤2600 次（51 块 0.03~0.06s、
100/200 最多 1.88s）。

> ⚠ **第一版用的是"时间"预算，那是个错误**：功能上确实挡住了卡死，
> 但它让布局**又变回不确定的** —— 同一张图，机器忙一点就多截断几次、
> 层内排法就换一个。改成纯计数后才与 HEAD 对齐。
> **凡是"结果要稳定"的东西，都不要用墙钟时间当预算。**

### 18.5 这一轮的方法学沉淀

四条，都来自踩过的坑：

1. **先补网，再拆**，而且网要铺在**外部可观察行为**上
   （内部快照在拆分中会全量变化，人眼审不动）。
2. **批量改写脚本只认文本，`ast` 只用来说明"哪些该改"** ——
   `ExceptHandler.lineno` / `Import.end_lineno` 这些"看起来能用"的行号，
   实测会把改动落到错误的位置，而且 `ast.parse` 之后完全合法。
3. **批量脚本自己要有"反向核对"** ——
   只查"清单里的都处理了"挡不住"清单本身漏项"
   （`PREFETCH_AHEAD` 那次就是这么被删掉的）。
4. **改公共契约之前先确认它到底约束什么** ——
   "必须与 TU 逐字节一致"听起来像"要迁就外部格式"，实际是"两边算法一致"。
   前者不敢动，后者可以两边一起改。

### 19.4 拆分的安全网：**逐字段比对 HEAD**

这一步很关键，值得单独说。前面拆 `layout_graph` 能用"坐标逐字节比对"，
是因为结果是一堆数字；而这几个函数的结果是**结构化对象 / 一整份脚本文本**。

所以每个都配了一个 `tools/_verify_*.py`：从 git 取 HEAD 版本，
与工作区版本对**同一批真实输入**各跑一遍，**深度比对结果**。

| 脚本 | 比对对象 | 规模 |
|---|---|---|
| `_verify_layout.py` | 每个节点的 `(x, y)` | 11 个图 |
| `_verify_snapshot.py` | `stage_snapshots` 的全部字段 | 真实项目 2033 拍 / 57 批 |
| `_verify_patch.py` | `PatchResult` 全部字段（含 `text` 全文） | 14 脚本 × 4 种改造 / 45 例 |

**为什么比 `text` 全文而不只比 `ok`**：增量补丁的价值就在"写出来的
那几行"，`ok` 相同而正文不同等于悄悄改了产物。

这三条**都跑出了 0 差异**，所以"纯搬家"这个说法是有证据的，
不是"测试还是绿的所以应该没事"。

### 19.5 还没动的两个，以及为什么先不动

`beats_from_statements`（101 / 538 行）与 `_parse_statement`（60 / 375 行）
**这一轮没动**，原因是它们和前面三个不是一类：

- `layout_graph` / `stage_snapshots` / `patch_export` 的"接缝"是
  **有名字、有明确输入输出的块**（原作者本来就写成了内层 `def`）；
- `beats_from_statements` 是一个 **538 行的分派循环**，里面 6 个闭包
  **共享可变状态**（`pending` / `seq` / `current_label` /
  `pending_has_stage`），搬家必须把状态打包成对象或显式传参 ——
  那是**改结构**，不是搬家，风险等级完全不同；
- `_parse_statement` 是**扁平的 if 链**（59 条 `if kind == …`），
  拆它只能按 kind 分组，而分组边界靠的是"哪种语句属于哪类"这种
  **语义判断**，不是结构信号。

`beats_from_statements` 是**解析心脏**：它的安全网只有
"往返不变式"（parse → beat → xlsx → beat → compile → 再解析，
逐行文本多重集相等），而那个网**已经带着 3 条已知丢失**（见 §十七）。
也就是说"拆坏了"和"本来就有 3 条"在这张网上**分不开** ——
这是先补一层更细的网（比如"逐拍字段快照 + 真实项目全量"）才能动它的理由。
