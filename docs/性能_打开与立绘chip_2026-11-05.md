# 打开变慢 + 切换属性卡顿：先把"每次都在做同一件重活"找出来（2026-11-05）

用户报的两条：

> 「打开时有点卡了……等待时间较长」
> 「切换不同属性时，会有明显的卡顿？比如卡片编辑器中，属性1和属性2交替切换，
>   加载的时间明显比连续切换属性1强」

两条都不是"哪里写得慢"，而是**同一件重活被反复做**，而且做在 GUI 线程上。
下面所有数字都是真机 `sr_general`（影子副本 + junction 到真素材，真机不写）

## 一、切 chip：一次点击 5.2 秒，其中 4 秒是存一张 3300 万像素的 PNG

探针（`.pip-tmp/perf_probe.py`）在卡片上交替点「属性 1 / 属性 2」：

| 点击序列 | 修复前 | 修复后 |
|---|---|---|
| 纯属性 1 × 4 | 255 / 297 / 968 / 1050 ms | 80 / 58 / 55 / 67 ms |
| 交替 属性1 → 属性2 | 417 / **5175** ms | 102 / 73 ms |
| 交替 ×4 | 271 / 4615 / 4687 / 260 ms | 124 / 88 / 75 / 80 ms |
| 4 次点击合计（cProfile） | **10.85 s** | **0.58 s** |

cProfile 里的钱花在哪（修复前）：

```
_thumb_path → resolve_sprite_thumb_path → session.path_of_image
  → asset_catalog.image_path → composed_sprite_path
    → compose_sprite 9.45s/4 次（每次 2.4s）
        · canvas.save()  4.08s   ← PNG 编码 4320×7680（每张 ~1.0s）
        · 解码两张源图   2.26s
        · PIL 合成 ops   0.8s
```

也就是说：卡片上那张 **88×118** 的缩略图，是先按**原图 4320×7680** 合成、
存成一张 100 MB 级别的中间 PNG、再让缩略图那条路把它缩到 1/40 —— 每次都这样。

### 修法：合成**按尺寸**做，且缩略图那条路走缩略图缓存

`storygraph/app/layer_compose.py`

* `compose_sprite(plan, cache_dir=None, max_size=None)`：
  * 给了 `max_size`（卡片：`2×格子`，`ui_qt/sprite_grid.py: sprite_compose_size()`）
    → 每一层**按目标尺寸解码**（`app.thumbs.decode_sync`，命中缩略图缓存时 ~1ms），
    裁切/蒙版/位移按同一下采样比例缩放，产物就是格子那么大；
  * 没给 → 仍按原图分辨率合成，但**最长边封顶 `MAX_SIDE = 1400`**
    （舞台预览也画不了更大）；
  * 缓存键里带上目标尺寸（`_sig(plan, box)`），"卡片要小的、预览要大的"各存一份，
    不会互相盖掉。
* `ui_qt/sprite_thumbs.resolve_sprite_thumb_path(..., max_size=None)`：
  给了 `max_size` 时**先**走"按这个尺寸合成"，再退回资源表注入的解析器；
  `ui_qt/sprite_grid.py` 的 `_thumb_path` / `prefetch` 都传 `sprite_compose_size()`。

真机产物对比：`composed/90aae…png` = **230×408 / 60 KB**（修复前是
4320×7680 的原尺寸 PNG）。人眼核对过：脸和外套的裁切/蒙版在缩放后仍然对齐
（`.pip-tmp/composed_check.png`，`lan close_happy base_hand_up`）。

## 二、还有一半卡顿：`discover_scripts` 每次 0.9 秒，一次点击要调十几次

`storygraph/parsing/discover.py` 原来用 `Path.rglob('*.rpy')` —— 它会**走遍
整个 `game/`**，包括 `gui/`（1154 个文件）、`pomodorro/`、`minigamepieces/`
这些素材目录，扫完才按 `SKIP_DIR_PARTS` 过滤。

| | 修复前 | 修复后 |
|---|---|---|
| `discover_scripts`（95 个 .rpy） | ~900 ms | **11.3 ms** |

`os.scandir` + **遍历时就剪枝**（`tl` / `common` / `renpy` / `cache` / `saves`
不进），结果与原来完全一致（原来也是事后滤掉这些目录），只是不再白走。
这个函数在一条点击链上被调 16 次（`layer_model_stamp` / 章节导航 / 导入 /
卡片刷新），在"打开项目"里也会被调多次。

## 三、打开项目：从 17 s 到 4 s（同一台机器、同一份项目）

`open_project_path` 的 cProfile（修复后，冷文件缓存那一档）：

| 项 | 耗时 |
|---|---|
| 读 6 张资源表（7 次 `load_workbook`） | 0.47 s |
| 符号表 / 章节索引（95 个 .rpy 解析一次） | ~1.5 s |
| `sync_asset_tables`（扫盘 + 对齐） | 0.87 s |
| 其余（导航、连续性、恢复剧情图） | ~1 s |
| **合计** | **3.9 s**（第二次打开同进程 **0.67 s**） |

修复前的同一处是 **17 s**（当时 `discover_scripts` 0.9 s/次 × 多次 +
资源表冷读）。这一档有磁盘缓存的影响，所以别把 17 → 4 当成严格 A/B；
能复现的严格对比是上表里那两条单函数数字。

**还没动的**（知道它在、但这一轮不碰）：`_refresh_asset_choices` 里
`Symbols` 第一次索引要解析全项目（~1.3 s）。它和"卡片提示"共用同一份，
挪到后台线程要动 `entry_warm` 那一套；先记在这里。

**还能感到的**：某一组"从没合成过"的属性组合，第一次点仍要 ~0.3 s
（两张原图各解码一次；之后这一对源图进缩略图缓存，再换别的组合就是几十毫秒）。
把它挪到加载器线程是下一步，这一轮先不动 —— 那要改 `_load_thumb` 的回调时序。
