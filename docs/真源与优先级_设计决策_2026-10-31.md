## 一、为什么现在必须定

`.rpy` 是唯一真源，这条没有争议。有争议的是**它之后进来的东西**：剧本表（`xlsx`）、资源映射（`storygraph.mapping.xlsx/json`）、自定义模块（`storygraph.rules.json`）、引擎事实（`storygraph.engine_facts.json`）、资源表（`asset_tables/*.xlsx`）、CDS 扫描、词汇表。

它们都可以"说点什么"。于是同一个问题会有多个答案：

- 这张图是谁？—— 项目里 `layeredimage` 说了、映射表说了、资源表的 Tag 列也说了。
- 这句话是什么音乐？—— `play music bgm_01` 说了、映射表说它叫「日常」、`calls.label` 说它叫「日常 BGM」。
- 这一行合法的吗？—— 引擎 lint 说非法、`rules.json` 的 pattern 说合法、工具内置规则说不认识。

**不定优先级的代价不是"偶尔选错"，是"每次都重新猜一次"**：换个人来读代码、换个月份回来改，同一个冲突会有不同结论。而且它是**静默的** —— 没有任何地方会报"这两处说法不一致"。

这正是 `outfit` 那次争议的实质：真正的问题不是"工具针对了我的项目"，而是**工具在多个来源之间没有可解释的选择规则**，于是任何结论看起来都像"特意为我写的"。

**矛盾 1（代码与你的意图相反）**

**矛盾 2（优先级藏在写法里）**
`Vocabulary.plus()` 是"后来者优先"。于是"映射 > `calls.label`"这条规则**不在任何常量里**，只在 `session_assets:527` 那一行的写法里。写反了行为就反，两边都自洽、都不报错。

**矛盾 3（目录远近 vs 格式）**
`mapping_sources` 是"先项目根整组、再 `game/` 整组"，组内 xlsx > json。所以**项目根的一份 JSON 会赢过 `game/` 里人做的 Excel**。代码是清醒的（注释写了理由），但这条和"Excel 优先"的直觉冲突，而界面没说出来。

## 二·五、已经发生的实例：`outfit` 在两个近乎克隆的项目里不统一

这不是假想。用户 2026-10-31 实测（两个项目只差几个文件：

`D:\千连万理\sr_general` 与 `D:\千连万理\RenPyTest\sr_general`）：

| | 原件 | 副本 |
|---|---|---|
| `definitions.rpy`（4 个 `layeredimage`、7 个 outfit 属性） | 只差一行（`define DY` / `dy` 大小写） | 同上 |
| `game/chapter1_4.generated.rpy`（工具早先的导出产物） | 无 | **有** |
| `game/chapter3_1.rpy` / `tmp_shot_probe.rpy` | 无 | **有** |
| `images/characters/<角色>/中英对应.txt` | 无 | **有** |

**同一个 `xing`，代号表不同**：

- 原件：`xing` 的「B」号服装 → **留空**，notes 说"只对上一次（base_hands_down），证据太弱"；
- 副本：`xing` 的「B」号服装 → **`B`**，notes 说"出现 2 处"。

原因只有一句话：`show xing base_hands_down hengaolen` 在
`chapter1_4.rpy` 里**一句**，而副本多出来的 `chapter1_4.generated.rpy` 里
**又有一句**（同一拍的另一份投影）—— 工具把同一个事实数了两遍，票数 1 → 2，
正好越过"证据太弱"的门槛。**项目的声明一个字都没改，结论却变了。**

### 根因：两套"什么算剧本"

- `parsing/discover.py` 早就有 `DERIVED_SUFFIXES`（`*.generated.rpy` /
  `*.blocked.rpy` / `*.bak.rpy`）和 `SKIP_DIR_PARTS`，`discover_scripts()` 用它
  回答"项目里有哪些章节"；
- `assets/sprite_codes._script_texts()` 自己写了一遍 `game.rglob('*.rpy')`，
  **不知道**那条判据 —— 于是 `generated` 副本、翻译目录、探针脚本全进了
  "证据库"。

一条判据存在过、却只被一半的调用者使用，等于没存在。这与 §一 说的"混合策略"
是同一个病：**同一个问题（哪些文件算项目的脚本）有两个实现**。

### 修法与判据

`_script_texts()` 改用 `DERIVED_SUFFIXES` / `SKIP_DIR_PARTS`（唯一真源，
不再另写一套）。实测（`tools/_probe*` 那一轮同一份代码）：

- 修前：两个项目的 `outfit_codes` **5 行不同**（`xing` 的 B、以及 4 处票数说明）；
- 修后：**11 行逐字段相同**，`xing` 两边都留空、都带同一句"证据太弱"。

判据（`tests/test_sprite_codes.py`）：同一章 + 一份 `.generated.rpy` 副本
→ 代号必须与**没有副本时完全一样**；`_script_texts` 里不许出现任何派生后缀。

### 由它引出的两条规矩（已写进 §4.4 / §4.5）

1. **投影不投票**：工具自己的产物（`.generated` / `.blocked` / `.bak`）是
   事实的投影，不是事实。任何"统计/计数/推断"的输入都必须是**作者写的源**。
   这条比"映射优先还是声明优先"更靠前 —— 它连"谁和谁比"都还没到。
2. **一个判据只能有一个实现**：`DERIVED_SUFFIXES` 这种"什么算脚本"的判据，
   第二个调用点必须 **import**，不许复制。复制出来的那一天不会红，等它和原件
   分叉的那一天才会 —— 而那时症状是"两个项目答案不一样"。

> 副本里还有一处**不是** bug：它多带了两份编号表（`对应.txt` +
> `中英对应.txt`），两份编号对不上时工具按"和剧本注释对得更多"挑一份，
> 于是 `lan` 的 8/9/10 号与原件不同。这是**项目数据不同**，不是污染；
> 但它暴露了下一个问题：**两份声明打架时，工具在"投票"而不是"报冲突"**。
> 按 §4.1 的顺序，这属于第 ④ 步（合并不了 → 允许覆盖，但必须写进层序
> 常量 + 冲突报告）—— 现在只做到"notes 里说一句"，还没做到"让选"。

## 三、外部参照：优先级架构的两个经典教训

### 教训 1：优先级战争的结局是 `!important` 军备竞赛

CSS 的 specificity 是"给每条规则算权重，权重高的赢"。它的实际结局是有名的：

> *"Each fix requires a more specific selector. It's an arms race that only ends with `!important` — the nuclear bomb of CSS."*
> *"Reaching for `!important` is usually a sign the underlying selectors need rethinking, not that you need a bigger hammer."*
> *"The practical goal is not to win specificity battles but to avoid them."*

CSS 后来推的解法是 **`@layer`**：

> *"A rule in a later layer beats a rule in an earlier layer **regardless of specificity**, so you can put resets, frameworks, and your own components in a deliberate order and stop fighting the score."*

**对我们的含义**：优先级应该是**一份显式声明的层序常量**，不是"每条数据自己算一个权重"。而且层序要少、要固定、要写在人能读到的地方。

同一批资料里还有一句更要命的：

> *"Specificity bugs overwhelmingly arise from **mixing strategies within a single codebase without a clear priority model**."*

我们的现状正是"混合策略"：有的靠目录、有的靠格式、有的靠调用顺序、有的靠字典覆盖。

### 教训 2：最好的优先级是"不需要优先级"

"make illegal states unrepresentable" 那一路的思路是：

> *"If the type or data shape permits a state the domain forbids, a future caller will construct it."*
> *"The gap that forces **every writer to defend a rule the structure itself does not hold**."*

它给了三层递进（从强到弱）：

| 层 | 做法 | 效果 |
|---|---|---|
| **Unrepresentable** | 结构上不可能出现冲突 | 冲突不存在，无需规则 |
| **Impossible** | 只有一个变更权威（single writer） | 冲突只能来自一处，可审计 |
| **Detectable** | 做不到就**大声报**，绝不当静默 no-op | 冲突可见，可裁决 |

这比"排一张优先级表"强得多。**优先级表是第三层，不是第一层。**

我们其实已经做对了一部分（只是没被写下来）：

- `vocabulary.from_mapping` 的注释明确写着"那几段是**投影、不是副本**" —— 这是第一层：同一事实只有一处，其余是视图。
- `WRITERS` 单写入口 + `HANDWRITTEN_TARGET` 拒写 —— 这是第二层。
- `engine_facts` 的 `conflicts` 字段 —— 这是第三层的雏形（两源不一致时记下来，不静默挑一个）。

缺的是：**这三层没有被统一成一条规矩**，于是新加的资产（映射、rules、词汇表）各自发明了一套。

### 配置分层的三条通用律（补充）

- **律 1**：越具体、越晚近的层越赢（CLI > env > project > user > defaults）。
- **律 2**：优先级是 **per-key**，不是 per-file —— *"if local is silent on a key, project's value takes effect"*。**静默不等于覆盖**。
- **律 3**：有一层是**天花板**，不是地板 —— `distro_policy` 的定义是 *"immutable ceiling, cannot be widened at runtime"*。对我们就是：**引擎说这行非法，任何映射都不能把它变成合法**。

## 四、决策

### 4.1 第一原则：先消除冲突，再排优先级

任何"两个地方都能回答同一个问题"的情况，先问能不能**合并成一处**。只有在合并不了的时候，才允许出现一层覆盖，并且必须显式声明层号。

判断顺序（**照这个顺序走，不要跳步**）：

```
① 这个事实的所有者是谁？        → 只能有一个
② 第二处能不能改成"投影"？      → 能就改（不引入优先级）
③ 改不了，能不能只留一个写入口？ → 能就做（不引入优先级）
④ 还是不行 → 才允许"覆盖"，并写进层序常量 + 冲突报告
```

### 4.2 第二原则：真源按"域"分，不按"层"分

`.rpy` 是**内容域**的真源，不是所有域的真源。四个域，每个域一个所有者：

| 域 | 拥有的事实 | 所有者 | 其余角色 |
|---|---|---|---|
| **A 内容** | 说什么话、谁出场、怎么演 | `.rpy` | 剧本表 = **编辑面**（不是真源） |
| **B 身份** | 这张图是谁、这首歌叫什么 | 引擎事实 / 项目声明 | 映射 = **纠正层** |
| **C 形状** | 这一行怎么写才合法 | 引擎 lint / CDS | `rules.json` = **声明层** |
| **D 命名** | 屏幕上显示成什么 | 映射 | 词汇表 = **投影** |

"剧本表是不是真源"这个问题的答案是：**它不是真源，它是编辑面**。
真源 = 冲突时说了算的那个；编辑面 = 你打字的地方。这两件事分开，问题就消了 —— 就像 git 工作区不是真源，但你确实在那里改代码。

### 4.3 第三原则：层序是常量，不是算法

仿 `@layer`：写一张**固定的、短的、人能读的**层序表，放在一个文件里，任何模块不许自己发明顺序。

**这份表格已经从文档搬进代码**：`storygraph/core/authority.py`（`AUTHORITY` /
`IDENTITY_ORDER` / `SOURCE_LAYER` / `DOMAINS`）。下面这一块与它**逐字对应**，
`tests/test_authority_layers.py` 会读本文件比对 —— 两边不一致当场红。

```python
# 权威从高到低（数字小的赢）。任何"谁覆盖谁"都必须查这张表。
AUTHORITY = {
    'engine':    0,   # renpy lint / json-dump / engine_facts —— 天花板，不可覆盖
    'mapping-exact': 1,  # 映射里**点名某个资产 ID**的精确覆盖（人明确纠正）
    'declared':  2,   # .rpy 里的字面量声明（layeredimage / define / image）
    'mapping-rule':  3,  # 映射的 glob 规则（人写的通配，可能猜错）
    'registry':  4,   # 资源表的 Tag/Attributes 列
    'inferred':  5,   # 路径目录段 / 文件名
    'unknown':   6,   # 认不出（不猜）
}
```

**为什么"精确覆盖"在"项目声明"之上、"glob 规则"之下**：精确覆盖是人**指着
某一张图说"它叫这个"**，这是最高级别的人为意图 —— 它可以纠正声明，但只对
**点名的这一张**生效，且必须留痕（§七.1）；而 glob 规则是"这一类大概都这样"，
它可能猜错，**不该盖掉项目里写死的东西**（§六 6.2：个体显式 > 批量规则）。

> **2026-10-31 订正**：这一节原先写的是 `declared: 1 / mapping-exact: 2`
> —— 数字与本节自己的那句"精确覆盖排在项目声明**之上**"相反，也和 §五 P0-1、
> §七.1 相反。三处各说各的、谁都不报，正是本文件 §一 说的那种病。
> 现在以**代码常量**为准，文档跟着它走，并有测试盯着。

### 4.4 五条通用律（挂在所有域上）

1. **静默不覆盖**：没写 = 不参与这一题。空单元格不是空字符串，空 `label` 不是"要清空名字"。
2. **覆盖要留痕**：赢家赢，但报告里要写"这条被谁覆盖了、原来是什么"。
3. **引擎是天花板**：映射可以让名字更好读，不能让一行非法代码变合法。
4. **单写者**：同一时刻只有一个东西在写 `.rpy`。Excel 是输入法 + 显示面，不是第二个存储。
5. **投影不投票**（2026-10-31 从 `outfit` 那个 bug 里长出来的）：工具自己生成的
   产物（`*.generated.rpy` / `*.blocked.rpy` / `*.bak.rpy`）**是事实的投影，不是事实**。
   任何"统计 / 计数 / 推断"的输入只能是**作者写的源** —— 否则同一句话会被数两遍，
   两个只差一个副本的项目就会给出不同答案（§二·五）。
   这条比"谁优先"更靠前：它连"谁和谁比"都还没到。

### 4.5 新资产准入五问（以后加任何"注册资产"都要先答）

1. **它拥有哪个域的事实？** —— 必须唯一。有重叠就不是新资产，是那个域的新一层。
2. **它在 `AUTHORITY` 的哪一位？** —— 写进常量，**不许靠调用顺序**。
3. **它静默时意味着什么？** —— 只能是"不覆盖"。要"覆盖成空"必须显式写 `null` 并报出来。
4. **它和邻居冲突时，报告里长什么样？** —— 说不出这句话，就不许合入。
5. **它的输入里有没有工具自己的产物？**（2026-10-31 加）—— 有，就说明"什么算项目
   原文"这条判据被复制了一份；先把它**合并成一个谓词**（`DERIVED_SUFFIXES` 那种），
   再谈统计。判据复制出来的那一天不会红，分叉的那天才红 —— 而那时症状是
   "两个项目答案不一样"。

## 五、按本项目的具体改法

### P0-1 修 `resolve_image` 的顺序（真 bug，改动最小）—— ✅ 2026-10-31 已落地

现状（改前）：映射（精确覆盖 + 规则）整体在项目声明之前。


`resolve_image` 在两层之间插入"项目声明"；层序常量落在 `core/authority.py`，
`tests/test_authority_layers.py` 同时盯代码与本文档。
**判据已钉**：`test_asset_identity.TestDeclaredBeatsGlobRules`（3 条）。
**顺带**：声明过的行走 `source='declared'`（以前误报成 `tag-column`），
资产选择器的"凭什么这么判"因此能说出"项目自己的声明"。

### P0-4 证据只数真源，不数投影 —— ✅ 2026-10-31 已落地

## 六、三个未决问题：行业是怎么做的

### 6.1 「显式覆盖能不能改掉声明」→ systemd drop-in 模型

systemd 面对的是同一个问题：发行版给了单元文件（vendor），管理员要改，但**不能直接改**（包升级会覆盖）。它的答案是 **drop-in**：

- vendor 文件在 `/usr/lib`，**永不直接编辑**；
- 覆盖写在 `/etc/<unit>.d/*.conf`，**只写你要改的那几行** —— *"A drop-in contains only the sections and keys you are changing; everything else inherits from the base unit untouched."*
- 合并规则**按值类型分**：*"scalar keys replace, list-based keys append."*
- **可查看合并结果**：`systemctl cat` 打印「vendor 文件 + 每个 drop-in，按应用顺序，每个带路径注释」；
- **可一键撤销**：`systemctl revert` 删掉所有 drop-in，回到纯净 vendor 状态；
- **它自己承认的风险**：*"if the vendor changed something for a reason... your override of that setting now pins the old behaviour."* —— 覆盖层会**悄悄钉死旧行为**，vendor 后来改了你也不知道。

**结论：能覆盖，但覆盖必须满足四条**（缺一条就会变成"不可审计的补丁"）：

1. **只写差异**（映射表里只填要改的那个字段，不是整条复制）
2. **能看合并结果**（谁覆盖了谁、按什么顺序）
3. **能一键撤销**（删掉那条覆盖就回到声明值）
4. **被覆盖的原始值变了，要提醒复核**（防"钉死旧行为"）

对应到本项目：`images` 表的精确覆盖就是 drop-in。现在缺的是 2/3/4。

### 6.2 「glob 规则能不能改身份」→ 个体显式 > 批量规则

行业里凡是"批量规则 + 个体动作"并存的地方，**个体一律优先**：

| 场景 | 批量规则 | 个体动作 | 谁赢 |
|---|---|---|---|
| `.gitignore` | 通配忽略 | `git add -f` | **个体**（强制添加） |
| ESLint | config 里的 glob 规则 | `/* eslint-disable */` | **个体**（行内注释） |
| CSS | class 选择器 | inline style | **个体** |
| systemd | vendor 默认 | drop-in（具体文件名） | **个体**（且 drop-in 不支持通配） |

注意 `.gitignore` 那条特别说明问题：批量规则**可以被推翻，但必须逐个显式**（`-f`），没有"这一类全部强制"。

**结论：glob 规则不改已声明的事实。** 人要改就写一条**精确覆盖** —— 这正好和 6.1 合成一条规矩：
> **规则只补空缺；覆盖必须精确。**

### 6.3 「离线冲突用指纹拒绝写」→ HTTP `If-Match` / 412

这是标准的**乐观并发控制（optimistic concurrency control）**：

- 读取时服务器给一个 `ETag`（内容哈希）；
- 写入时带上 `If-Match: <etag>`；
- 不匹配 → **412 Precondition Failed，拒绝写**，而不是覆盖。

关键的三条细节，恰好是"用错就白费"的地方：

1. **强 ETag vs 弱 ETag**：强 = 字节完全相同，弱 = 语义等价。我们要的是**强**（字节哈希），因为"逐字节相等"是铁律 1。
2. **拒绝后必须 reconcile，不能拿新指纹重发旧内容**：
   *"If you just swap in the new tag and resend the old edit, you overwrite the other person's change and the check bought you nothing."*
3. **检查与写入必须原子**：
   *"On the server, check the tag and write in one atomic step, or two writers can race past it."*

冲突后的处理策略，行业共识是**交给人裁决**，不是自动合并也不是盲目重试：

> 并发编辑 → *"提示用户，让用户选择合并或覆盖"*

**结论：用，但要做对三件事** —— 只在真变时拒（不是每次保存都问）、拒绝时给「合并 / 覆盖 / 放弃」三选、检查与写入在同一把锁里。

我们已经有 `diff3` 这个 reconcile 工具，所以不是替换它：**指纹做准入，`diff3` 做 reconcile**。

### 6.3b 补充：冲突判定要做「三态」，不是「二选一」

只做"指纹不符就拒绝"会有一个副作用：**文件被人摸了一下（touch、git checkout、备份工具重写），指纹就变了，但内容没变** —— 每次都弹冲突，用户很快就学会无视它。

成熟实现（Cherry Studio 的 `write_if_unchanged` → `STALE_VERSION` 处理）把"校验失败"拆成三种情况分别处理：

| 磁盘当前内容 | 判定 | 处理 |
|---|---|---|
| **等于本次要写的草稿** | 不算冲突 | **直接采纳**（盘上已经是这个内容了） |
| **等于基线**（只是被 touch） | 不算冲突 | **rebase 重试**（推进基线后重写，限制重试次数防病态循环） |
| 与基线、草稿**都不同** | **真分叉** | 才算冲突，暂停自动保存，弹框让人选 |

还有一条同样重要的：**冲突只在写入时判定**。
*"watcher 事件永远不会重载一个脏模型（VS Code 语义）"* —— 编辑器空闲时外部变更静默重载；模型脏时不打断输入，等下一次保存时再暴露。这避免了"我正在写，磁盘一变就被打断"。

### 6.3c 补充：三路合并的前提是「有 base」

三路合并**必须有共同祖先**：

> *"Without finding the common ancestor, [the tool] would only know that both files are different in the tips, but not which version to pick."*
> *"Only a 3-way merge gives you the ability to know whether or not a chunk is a change from the origin and whether or not changes conflict."*

没有 base 的"两路"其实不是合并，是**逐段二选一**，每个差异都会变成冲突。

**对本项目的直接含义**：能不能自动合并，取决于**表里存不存 `.rpy` 的原文快照**（base）。
- 只存哈希 → 只能三态判定 + 人二选一；
- 存了原文 → 才有资格谈三路合并。

存储成本可估：每章一份原文快照（真机 96 章、平均千行量级，压缩后 MB 级）。这是"要不要"的问题，不是"能不能"。

### 6.4 三条结论汇总

| 问题 | 行业答案 | 对本项目的落法 |
|---|---|---|
| 精确覆盖能否改声明 | **能**。但 provenance（来源记录）是 precedence 的另一半：*"Precedence answers which value wins. Governance also needs to answer where that value came from."* 覆盖记录要 append-only，记 who/when/原值/新值/理由，理由不许是 "n/a" | `images` 精确覆盖可以改；**不改 `.rpy`**，在工具侧留一条 append-only 记录，且原值变了要提醒复核 |
| glob 规则能否改身份 | **不能**。默认用逐条例外：*"Default to per-finding exceptions"*；批量覆盖会连带盖住*"every advisory published against it tomorrow, including ones nobody has read"*。scope 要与意图匹配，**不确定时选更窄的** | 规则只给没人声明过的图补身份；要改就写精确覆盖（一条一个资产） |
| 冲突用指纹拒绝写 | **用，但做三态**：采纳 / rebase / 真冲突；冲突只在写入时判定；`--force` 式"全都覆盖"是**错的形状**（*"bypasses every blocker, leaves no audit trail"*） | `.rpy` 字节哈希做 `If-Match`；哈希相同 → 静默采纳，仅元数据变 → rebase，真分叉 → 弹 `diff3` 让人选 |

## 七、三个问题定下来的结论

1. **覆盖改掉声明后，留痕吗？→ 留，但不写进 `.rpy`。**
   理由：`.rpy` 是用户的文件，往里面写工具注释就是往唯一真源里掺沙子；而"谁覆盖了谁"是**运行期可重建的信息**，不是事实本身。
   做法：工具侧一条 append-only 记录（原值、新值、来源文件与行号、时间），并在映射对话框显示"这一条覆盖了 `layeredimage` 的声明"。
   **必须做的一半**：原声明值变化时提醒复核 —— 否则就是 systemd drop-in 那个"钉死旧行为"的老坑。

2. **一条覆盖只能覆盖一个资产吗？→ 是。**
   理由：批量覆盖会连带盖住"明天才出现的东西"（*"every advisory published against it tomorrow, including ones nobody has read"*）；而且 `--force` 式的一揽子覆盖**没有审计价值**。
   代价是麻烦（覆盖十个要写十条），**这正是"显式"的价格**，也是它不会被误当规则用的原因。

3. **冲突处理做成什么形状？→ 先做"三态 + 人在场裁决"，不做自动合并。**
   - 哈希与草稿相同 → **静默采纳**（盘上已经是这个内容）
   - 哈希与基线相同（只是被 touch）→ **rebase 重试**，不算冲突
   - 真分叉 → 拒绝写入 + 弹 `diff3`，让人在「合并 / 保留我的 / 用盘上的」里选
   - **冲突只在写入时判定**，不打断正在进行的编辑
   - **存什么**（2026-10-31 拍板）：只存**哈希**，不存原文快照 —— 见 §八（含
     base 以后的加法路径与触发条件）。

   **✅ 2026-10-31 已落地（判定这一半）**：`story/write_gate.py::classify(
   disk_bytes, base_sha1, draft_text, base_text=None)`（签名照 §8.4 定死）+
   `Verdict`（`ADOPT` / `REBASE` / `CONFLICT`，`ok` = 前两态）。
   `EditorSession.source_unchanged()` 改成**只比内容**：`touch` / `git checkout`
   只改 mtime 时不再退回保守对位（那正是 rebase 那一态的收益）。
   `base_text` 给了才做**行级三路合并**（`merge_text`，改动不重叠才合并；
   有候选也仍是 `CONFLICT` —— 合不合并由人定）。
   判据 `tests/test_write_gate.py`（17 条：三态 / touch 不算冲突 / 合并候选 /
   同一行冲突 / 同一插入点冲突 / 删文件算冲突）。

## 八、待定项已定：先做哈希，不做 base（**选项保留**）

### 8.1 决定（2026-10-31，用户拍板）

> 我倾向于先做哈希，先不做 base！但这个 base 可以以后再做……必须保存好这个选项！

**决定**：表里只存**内容哈希**（已经在存），**不存** `.rpy` 原文快照。
base 作为**以后可以加的选项**保留；它什么时候被重新提上日程、接缝在哪、
怎么加才不用迁移，全部写死在 8.4 / 8.5 —— **这一节就是"保存好这个选项"的地方**。

为什么这是对的（三条，按分量排）：

1. **观察频率**：单写者纪律下真分叉本来就罕见；§6.3b 的三态里只有第三态
   （真分叉）需要 base，前两态（盘上已是草稿 / 只是被 touch）用哈希就够；
2. **成本**：96 章原文副本（压缩后 MB 级），外加"快照本身过期"这一层新问题；
3. **可逆性**：哈希 → base 是**加法**（多存一份原文，读的时候有就用、没有就退三态），
   base → 哈希才是**减法**。先做可逆的那一半。

> 换句话说：先存 base 等于为一种**还没被观察到**的频率付设计成本；
> 而"先哈希"不堵死任何路 —— 8.4 的三处接缝就是留给它的门。

### 8.2 现在存了什么（已有，不是新做）

| 位置 | 存什么 | 谁在用 |
|---|---|---|
| `story/table_meta.py` 的 `来源指纹`（`sha1(原始字节)[:16]`） | 摊表那一刻的源文件指纹 | `staleness_note`（"表比源码旧"的**直接证据**） |
| `app/session_table.py::_fingerprint_of`（size + mtime_ns + sha1[:16]） | 载入那一刻的源文件指纹 | `source_unchanged()`（"行号还新不新鲜"） |

也就是说：**"变没变"已经能回答，"变成什么"还不能** —— 那正是 base 才有的能力，
也正是这次决定先不要的东西。

### 8.3 明确不做什么（免得以后有人"顺手"加上）

- 不往 `.rpy` 里写工具注释/元数据（铁律 1：真源不掺沙子）；
- 不存原文快照（§8.1）；
- 不做"指纹不符就一律拒绝"—— 那是**二态**，会把 `touch` / `git checkout`
  当成冲突，用户很快就学会无视它（§6.3b）。三态里只有第三态才需要人。

### 8.4 保留的那扇门：base 以后怎么加（不迁移）

三处接缝，加 base 时**不用改调用方**：

1. **存**：`table_meta.write_meta` 多写一个隐藏键（例如 `来源原文`，
   gzip + base64），或落 `<项目>/.storygraph/bases/<sha>.rpy`。
   二选一，**别两处都存**（同一个事实两个家，就是本文件 §一 的病）。
   `read_meta` 已经把那张表当成 `{键: 值}` 读 → 老表没有这个键，自然退化成
   "没有 base"，**不需要 schema 版本号**。
2. **判**：三态判定函数的签名现在就定死为
   `classify(disk_bytes, base_sha1, draft_text, base_text=None)`。
   `base_text` 缺省 → 第三态只能"人二选一"；给了 → 多一条"自动三路合并"。
   签名先定，是因为**加参数不用改调用方**，改签名要。
3. **合**：`story/beat_merge.py::three_way`（`fingerprint` / `Delta`）已经在了，
   缺的只是"喂给它 base 拍"这一步 —— 那是**读表**的活，不是写盘的活。

### 8.5 什么时候重新打开（触发条件，写死在这里）

满足任意一条，就把 base 提上日程（并回来改本节 + 加一条测试）：

- 同一个月内**真分叉 ≥ 3 次**（不是 touch、不是哈希相同的那种）；
- 同一章在 24h 内被**两个不同的写者**改过（用户 + 程序员 / 两台机器）；
- 用户明确提出"能不能自动合并，不要每次让我二选一"。

三条都是**可观察的**（导出回执与日志里数得出来），不是"感觉需要"。

## 九、一句话总结

**优先级表是最后手段，不是第一手段。**

顺序永远是：**能合并就合并 → 不能合并就单写者 → 再不行才分层，而且层序要写成常量、冲突要报出来。**

`.rpy` 是**内容**的真源；映射是**命名**的真源；引擎是**合法性**的天花板。三者不冲突，因为它们回答的不是同一个问题 —— 真正需要裁决的，只有"身份"这一域，而那一域的顺序应当是**人明确纠正 > 项目声明 > 批量规则**。

还有一条比"谁优先"更靠前：**投影不投票**。工具自己的产物（`*.generated.rpy`）
是事实的影子，不是事实 —— 影子一旦能投票，两个只差一个副本的项目就会
给出不同答案（这正是用户 2026-10-31 挖出来的那个 `outfit` 不一致）。
