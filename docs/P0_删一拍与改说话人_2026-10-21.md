# P0：删一拍 + 改另一拍的说话人 → 删不掉，还报"成功"（2026-10-21）

> 用户要求"绝对要找出所有的 P0"。
> 做法：先按"手工会想到的场景"逐条打（9 个顺序操作 / 11 个结构+引擎场景 /
> 4 个 IO 场景），**全军覆没**——都干净。于是换成**随机变异 + 不变量**：
> 100~300 轮随机叠 1~3 个操作，只查"绝对不该发生的事"。
> 第 4 轮就炸出一个。

---

## 一、P0 长什么样

### 复现（`tools/probe_fuzz_invariants.py`，种子 20261021 第 4 轮）

源文件（一拍 = 舞台/代码 + 台词）：

```renpy
label ch01:
    scene bg room
    show ling happy at left
    $ gold = 10
    ling "第一句台词"
    ling "第二句台词"      ← 表里删掉这一行
    $ gold += 1
    ling "第三句台词"
    hide ling
    ling "第四句台词"
    return
```

表里做三件事：

1. 删掉「第二句台词」那一行；
2. 把「第一句台词」的说话人 `ling` 改成 `e`；
3. 把「第四句台词」改成「第四句台词（改8）」。

导出回原文件 → 回执：

```
增量补丁：对位 3/3 拍，实际改动 2 行，原文其余部分逐字节保留
```

退出码 0。而产物：

```renpy
    e "第一句台词"
    ling "第二句台词"      ← 表里已经删了，文件里还在
    ling "第三句台词"
    ling "第四句台词（改8）"
```

**用户在表里删掉的一句台词，导出后还在。** 而且这正是最糟的形态：
程序跑起来会多播一句，而工具说"只改了 2 行"。

### 对照：只删一拍（不改说话人）是好的

同样的表，只删「第二句台词」、别的都不动 → 产物正确（那句和它的 `$ gold += 1` 一起走）。
所以缺陷只在**组合**里出现——这也是手工挑场景挑不到它的原因。

---

## 二、根因：`replace` 分支只处理了一半

`recover_source_ranges` 用 `SequenceMatcher` 对齐"源拍"与"表拍"，四个分支：
`equal` / `replace` / `insert` / `delete`。

- `delete` = 源里有、表里没有 → **进 `dropped_out`**（用户删的拍）→ `_plan_deletions` 去删行；
- `insert` = 表里多出来的新拍 → 给插入点；
- `replace` = 两边都有但身份变了（说话人/舞台改了）。

问题在 `replace`：拍数不等时，它只处理了**表多出来**的那一半（`j1+pair..j2` → 插入点），
**源多出来**的那一半（`i1+pair..i2`）没人管——既没拿到行号，也没进 `dropped_out`。

本例的对齐键（`label/kind/speaker/condition/舞台指纹`）：

```
源：  [ling, ling, ling, ling]     ← 4 拍
表：  [e,    ling, ling]           ← 3 拍（说话人改了一个）
```

`SequenceMatcher` 给出 `replace(源0:2, 表0:1)` + `equal(源2:4, 表1:3)`：

| 表的拍 | 配到的源拍 | 结果 |
|---|---|---|
| 第一句（说话人 e） | 第一句（含 scene/show/$） | 说话人改写 ✔ |
| 第三句 | **第三句** | 改词？不，正文相同 → equal |
| 第四句（改8） | 第四句 | 改词 ✔ |

而**源第 2 拍（第二句台词）落在 `replace(源0:2, 表0:1)` 的尾巴上，`pair=1` 只吃掉了
源第 1 拍**——第 2 拍被跳过。于是：

- `dropped = 0`（没人知道它该被删）；
- `_plan_deletions` 无事可做；
- `_verify_patch` 只查"**生成的内容**都在产物里"，不查"**源的内容**有没有凭空多出来"
  → 校验通过 → `ok=True` → 写盘。

## 三、修法

`replace` 里"源多出来的拍"按 `delete` 同一语义处理：

```python
for k in range(i1 + pair, i2):
    dropped.append(name)
    if dropped_out is not None:
        dropped_out.append(pool[k])
```

### 修完之后的行为不是"能删了"，是"不再静默"

修完之后这个组合会走到**上一轮那道表过期守卫**（`dropped` 里有台词 + 表里有拍正文
在源里找不到），于是判"两种可能分不开"，**拒绝增量**：

```
表与源码不同步：源里有 1 拍台词不在表里（例如「第二句台词」），
表里有 1 句在源里找不到（例如「第四句台词（改8）」）——
这有两种可能：① 导表之后源文件被改过（程序员加了内容）；
② 你在表里删了一拍、同时又改了另一拍的说话人/舞台。
两种目前分不开，按"不猜"拒绝增量
```

**为什么不去"把这一刀做对"**：`replace` 的配对本身是"按顺序硬配"，
表过期时它会把"改过的那拍"配到"程序员新加的那拍"上（上一轮 P0 的根因）。
两种局面在数据上**不可区分**——放行就等于把上一轮的 P0 放回来。
所以这里选"拒绝 + 说清两种可能"，而不是猜。

### 判据（`tests/test_p0_stale_source_guard.py::TestDeletePlusSpeakerChange`，3 条）

1. **不许静默**：写成功了被删的那句就必须不在产物里；写不成功源文件必须逐字节不变；
2. 另外两处改动要么都落地、要么整份不动（不许只落一半）；
3. 拒写时理由要把两种可能都说出来（不然用户以为工具坏了）。

## 六、顺带修的一个"说假话"

批量删 30 拍（100 拍的章节）本来是对的（70/70、顺序全对），但回执写：

```
其中删掉了源文件里 5 行（ling "第099句"）
```

实际删了 **30** 行 —— 因为上一轮引入 `removed_preview` 时，**拿预览的长度当总数**
（预览截断在 5 条）。数字说少，比不报更糟：用户会以为只删了 5 行。

修法：`PatchResult` / `CompileResult` / `export_table` 都多带一个
`removed_count`（真实行数），预览仍然只留 5 条做样例；回执写成
「删掉了源文件里 30 行（`ling "第099句"`）」。

判据：`tests/test_table_export_inplace_guard.py` 里那条"删行点名"用例
同时钉住"数量不是预览长度"。
