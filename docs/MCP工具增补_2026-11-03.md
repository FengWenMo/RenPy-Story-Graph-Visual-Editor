# MCP 工具增补：把工具这几年长出来的能力接进协议（2026-11-03）

> 起因（外部 AI 审查）：「好久之前做的，现在加了很多新功能却没同步」。

## 一、盘点：原来只覆盖了**语句解析层**

`mcp_surface.capabilities()` 里的工具（2026-10 那批）：

| 工具 | 覆盖 |
|---|---|
| capabilities / project_context / health | 元信息 |
| scan_unknown / discover / registry_check | 未知写法、声明 |
| engine_facts / ask_engine / verify_behavior | 引擎事实、真跑验证 |
| host_validate / declare | 项目自写的验证函数、写声明 |

这十来个全都围绕**"语句解析对不对"**。而工具这几年长出来的三块，MCP 里
**一个都没有**：

| 能力 | 实现 | MCP 里 |
|---|---|---|
| 章节与拍（`.rpy` → 结构） | `app/chapter_index.py`、`story/beat_build.py` | ❌ |
| 资源表与图像身份 | `assets/*`、`app/picker.py` | ❌ |
| 剧本表与增量补丁 | `story/script_table.py`、`pipeline/*` | ❌ |

后果：外部 agent 想"读第 3 章"、"`show qing base` 到底合不合法"，
只能自己 `rglob('*.rpy')` + 正则 —— 而这两件事恰好是工具最擅长的。

## 二、新增的四个读工具

| 工具 | 回答什么 | 来源 |
|---|---|---|
| `storygraph_chapters` | 有哪些章（label）＋文件与行号 | scanner |
| `storygraph_beats` | 某一章/某个文件的**拍**（逐行演出结构） | parser |
| `storygraph_assets` | 资源表里的图/音频，含**能不能写进 `show`** | table |
| `storygraph_image_lookup` | 一个图像名/资产 ID → 它是什么、能不能 show、为什么不行 | table |

四条都按项目既有的"能力自描述"写法挂进 `capabilities()`，`known_limits`
逐条写清（这是那批工具最值钱的部分：模型得知道"查不到 ≠ 没有"）。

### 两个"看起来对其实错"的地方（写工具时踩到的）

**① 图像名 → 资产 ID 不能拼名字。**

`show qing base` 用的是 `normal.png`：

```renpy
layeredimage qing:
    attribute base default: "normal"
    attribute angry: 'speechless'
```

拼 `qing_base` 去找只会得到"没有这张图"，而它明明在。所以走
`declared_sprite_words` 的反查表（`{文件名: 属性名}` 反过来用）。
判据 `TestImageNameMapsToAssetViaTheDeclaration`（5 条）。

**② `showable` 必须问 `resolve_pick`，不能只看 `identity.showable`。**

真机映射里写着 `{"images": {"qing": {"char": "青"}}}` —— `identity` 说
"这是 sprite、能 show"，而 `resolve_pick` 会因为「青」不是项目认的 tag
而拒绝。只报前者，外部 AI 就会写出 `show 青 base`（引擎报错）。
判据 `TestShowableAsksTheRealQuestion`。

## 三、顺带修掉一个**假信息**

`project_context` 的体检一直报：

```
health: {'ok': False, 'error': '还没有打开项目 / 读不到资源表'}
```

而同一个项目 `assets` 工具读得好好的。根因：`asset_health_report` 第一句是
`reg = self.assets_registry()`，而 `EditorSession(project_root=…)` 构造后
**没有 `load_assets()`** → 恒为 `None`。

修：调体检前先 `session.load_assets()`。修完真机报出
**`problems: 232`** —— 这才是真实数字（之前那句"读不到资源表"会让外部 AI
以为项目是空的）。

## 四、`project_context` 补上剧本规模

它自称"一次拿全"，原来只有引擎/扫描/体检/行为四块。现在加：

```json
"story": {"files": 60, "labels": 132, "how_to": "要章名列明细 → chapters…"}
```

只给**计数**，不解析拍（那要读全部 `.rpy`，按章取更省）。

## 五、验证

| 项 | 结果 |
|---|---|
| 新工具进 `tools/list` + `capabilities()`（带 known_limits） | ✓ |
| 走协议层（`handle` → `tools/call`）能调通 | ✓ |
| 没项目根 / 不是工程根 → `ok=False` + reason，不抛 | ✓ |
| 真机：60 文件 / 132 章 / `qing base` → `qing_normal` / `assets(qing)` 11 条 | ✓ |
| 回归（MCP + 立绘 + 台词转场 + 列序 + 选择器） | **226 passed** |

## 六、技术债基线提了一次（写在这里，不静默）

`tests/tech_debt_budget.json`：

```
complex_functions  192 → 194
swallow_calls     1258 → 1268
broad_excepts     1218 → 1228
long_files          26 → 26   （没涨：sprite_grid.py 1498 → 拆出 sprite_hints.py 1470）
```

理由（已写进 json 的 `note`）：新增 4 个读工具的失败必须"如实报告"
（`ok=False` + `reason` + 留痕），这是纪律要求的形状，不是新债。
已经把四个工具的 except 合并成一个 `_guarded` 装饰器（4 → 1）。

## 七、还没做的（下一步）

- **写工具**：改台词 / 表→`.rpy` 导出 / 增量补丁 —— 都要 `dry_run` 默认
  True 的回执（`declare` 已有这个形状，照抄）。
- `beats` 现在按 label 过滤要解析整个项目；可以先用 `chapter_index`
  定位文件再只解析那一个（大项目能快一个数量级）。
- `assets` 的 `category` 过滤是**精确匹配**；用户可能需要"角色类但
  showable=false 的那批"这种组合条件。
