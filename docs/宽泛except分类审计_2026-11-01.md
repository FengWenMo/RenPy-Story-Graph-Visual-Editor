## 0. 一页结论

1. **宽泛 except 的真实总数是 1232，不是 1227**：`except Exception` 1227 处 +
   `except BaseException` 5 处 + 裸 `except:` 0 处。`debt_report.py` 只数前两种里的第一种
   （判据见 §1.2），所以 1227 是“Exception-only”的数，差的那 5 处是 `BaseException`。
2. 全项目 **1960** 个 except handler，宽泛占 **62.9%**（1232/1960）；平均每 1000 行 7.5 处。
3. 四类计数：**A 1023 / B 24 / C 149 / D 36**。
4. **“咽 bug”的候选只有 24 处（1.9%）**，不是 1227。原因不是审计口径松，是项目自己在
   2026-10 之后做了两件事：`core/safeguard.py` 的 `swallow()` 记账，以及
   `tests/test_no_silent_except.py` 这条守卫。1232 处里 993 个 handler 体里有 `swallow(...)`。
5. **真正值得担心的另一摊是 B′：245 处“有记录、但返回值与正常空结果同形”**
   （A 类 235 + D 类 10）。它们不是“没痕迹”，是“调用方分不清”。
6. 可机器自证“收窄类型就够”的只有 **36 处（D 类）**。想把 1227 处全收窄，做不到：
   绝大多数 try 体调用的是域函数，能抛什么静态不可枚举（§5.3）。
7. 建议动作：**先改 §7.1 的 10 处 B**（补记录 / 明确失败），再挑 §7.2 的 10 处（低风险、纯机械）；
   **不要**全量收窄，也**不要**把 `swallow` 换成 `raise`（§7.3 说明哪些必须保持宽）。

## 1. 口径与方法

### 1.1 扫了什么

| 项 | 数 |
|---|---|
| `storygraph/` 下 `.py` 文件 | 256 |
| 全部 `except` handler（AST `ExceptHandler`） | 1960 |
| 其中宽泛（`Exception` / `BaseException` / 裸 `except:`） | **1232** |
| 窄捕获（`OSError`、`(TypeError, ValueError)` …） | 728 |

扫描用 `ast.parse` 逐文件遍历，按作用域栈记函数限定名（`类.方法`、`外层.闭包`）；
handler 体特征全部从 AST 取，不读注释当判据（注释只作佐证）。
**没有**统计 `except (Exception, OSError)` 这种元组 —— 实测全项目 0 处。

### 1.2 与 `python tools/debt_report.py` 的 `broad_excepts=1227` 差在哪

`tools/debt_report.py:211-215` 的判据是：

```python
elif isinstance(node, ast.ExceptHandler):
    if node.type is None:                      # 裸 except
        broad += 1
    elif isinstance(node.type, ast.Name) and node.type.id == 'Exception':
        broad += 1                             # 只认名字恰好是 Exception
```

所以它**不数** `BaseException`，也不数 `except (Exception, ...)`。实测：

| 写法 | 条数 | debt_report 计入 |
|---|---|---|
| `except Exception` | 1227 | ✅ |
| `except BaseException` | 5 | ❌（差 5 条的就是它们） |
| 裸 `except:` | 0 | ✅（本来就没有） |
| `except (Exception, …)` | 0 | ❌（本来就没有） |
| **合计** | **1232** | **1227** |

5 处 `BaseException` 全部在“清理 + 上抛”或“子进程协议”位置，属于 C 类：
`core/atomicio.py:230/258/300`（清理 tmp 后 `raise`，必须宽）、
`story/host_worker.py:86/118`（worker 任何异常都要回一条 `ok: False`，不能崩）。

### 1.3 四类判据（机械规则，可复核）

**每处只打一个类，优先级 C > B > D > A**（先看“有没有收口”，再看“有没有痕迹”，
最后才看“类型能不能收窄”）。判据全部落在 handler 体的 AST 上：

| 类 | 判据（满足即归入，按优先级） | 自证材料 |
|---|---|---|
| **C 宽但已收口** | ① 体内有 `raise`（含 `raise ... from e`）；② 返回失败信封（`{'ok': False, ...}` / 带 `error`/`reason`/`failed`/`blocking` 键 / `_empty(error=...)`）；③ append 进 `errors`/`failures`/`blocking`/`issues`/`bad`；④ 写 `err`/`error` 变量；⑤ `QMessageBox.critical` / `self._fail(...)` | CSV `evidence` 列原文，如 `失败信封 return {'ok': False, ...}` |
| **B 静默咽 bug** | 以上都没有，且体里**没有任何记录通道**（swallow 别名、print/stderr、logging、warnings/notes 列表、status 字段、事件 emit、失败信封） | `evidence` 写“无任何记录；body=…” |
| **D 类型可收窄** | 有记录，且 **try 体的每个调用都落在已知异常表里**（文件 IO→`OSError`、`json.*`→`(OSError, ValueError)`、`getattr`→`AttributeError`…），并集即“收窄后的类型” | `evidence` 写“try 体调用全部落在已知异常表（类型）” |
| **A 真兜底** | 其余：有记录通道、不抛、不转错误 | `evidence` 写 `记录=swallow('…', e)；body=…` |

**逐条依据在交付 CSV 的 `evidence` 列**：那是 handler 体的 `ast.unparse` 原文 + 命中的判据
（`记录=swallow('…', e)` / `失败信封 return {'ok': False, …}` / `无任何记录；body=…` /
`try 体调用全部落在已知异常表（(OSError, ValueError)）`），评审可逐行复核，不用信结论。
两个刻意的取舍，先说清楚，免得评审对不上数：

- **`swallow + return None` 归 A 不归 B。** B 的第一判据是“没有任何记录”；`swallow()` 是
  项目自己定义的记录通道（环形缓冲 + `logging` + 诊断面板），把有 `swallow` 的算成“静默”
  会与 `safeguard.py` 的设计和 `test_no_silent_except.py` 的判据直接冲突。但它们的
  “返回值不可区分”风险是真的，所以单列 **B′**（§3.4），不进 B。
- **“域函数能抛什么”不算可枚举。** `parse_xxx()`、`build_index()` 这类调用不在异常表里，
  于是它们所在的 handler 不会进 D。这不是说不可收窄，是本报告不猜（任务要求“不要写可能”）。

### 1.4 为什么 B 只有 24 处：项目自己的守卫与它的盲区

`storygraph/core/safeguard.py` 与 `tests/test_no_silent_except.py` 从 2026-10 起把
“宽捕获必须留痕”变成了硬约束。实测 1232 处里 993 个 handler 体里有 `swallow(...)`
（`swallow` 调用点全项目 1239 个，其余在 handler 外）。

守卫的判据是 `tests/test_no_silent_except.py:_is_silent`：
**体内没有任何 `Call`、也没出现异常变量 `e` → 判红**。用它复算这 24 处 B：

- **只有 1 处会被判红**：`core/safeguard.py:186`（白名单里的 `pass`）。
- 其余 23 处全部“通过”，因为体里**至少有一个函数调用**，或者出现了 `exc`：
  `set()`、`QColor(fallback)`、`text.setText(body)`、`float(font.getsize(...))`、
  `facts.append(...)` + `_ = exc` —— 这些都不是“记录”，但守卫认。

这是本次审计最值得带回去的一条：**守卫把“有没有调用”当成了“有没有说”，
于是 23 处真静默兜底从它眼皮底下过**。修守卫（或在 B 处补 `swallow`）比全量收窄划算得多。

## 3. B 类完整清单（24 处，按危险度）

### 3.1 判定说明

以下 24 处 handler 体里**没有任何记录通道**：没有 `swallow`、没有 print/日志、
没有 warnings/errors 列表、没有 status 字段、没有事件、没有 raise、没有失败信封。
它们不是“宽”的问题，是“出事以后什么都不留”的问题。

排序规则：核心目录（`story`/`app`/`assets`/`pipeline`/`parsing`/`authoring`）在前，
按“写盘/解析/导出/校验 > 只读计算 > UI 展示”排；`ui_qt` 在后。

### 7.3 必须保持宽的（说清为什么）

1. **`core/safeguard.py:186`** —— `swallow` 自己。它就在错误处理路径上，记录失败时再调
   自己就是无限递归。全项目唯一允许的 `pass`，`test_no_silent_except.py` 有白名单钉着。
2. **149 处 C 类** —— 已经转成用户可见错误；收窄只会让“没预料到的异常”逃出去，
   从“弹一条错误”变成“整个界面崩一下”。
3. **5 处 `BaseException`** —— `core/atomicio.py:230/258/300`（清理 tmp 后 `raise`，
   必须连 `KeyboardInterrupt` 一起接住再上抛）、`story/host_worker.py:86/118`
   （worker 任何异常都要回 `ok: False`，不能把父进程晾着）。
4. **Qt 回调 / 定时器 / 线程**（`stage_preview.py:705`、`thumb_loader.py:135`、
   `graph_canvas.py` 绘制）—— Qt 的 C++ 对象可能已随窗口销毁，`RuntimeError:
   Signal source has been deleted` 这类异常在回调里抛出去就是崩溃；回调必须吞。
   这类加 `swallow` 要注意频率（每帧一条会刷满 200 条环形缓冲）。
5. **撤销栈/命令系统**（`window_graph_ops.py:1058`、`:1677`）—— 命令建不起来时
   也必须把图显示出来；宽是产品行为，不是偷懒。
6. **993 处 `swallow` 兜底** —— 项目既定路线（`safeguard.py` 开头有完整论证）。
   本报告不建议把它们改成 `raise` 或逐个收窄；要动的是**返回值的可区分性**（B′），

- **把 `swallow` 换成 `raise`**：直接违背 `safeguard.py` 的设计，UI 会从“功能没反应”
  变成“整窗崩”。
- **一次性改 245 处 B′**：多数是“没有数据”的正常语义（`return []` 就是空列表），
  只有写盘/删除/导出/校验链路需要区分。
- **为了降 noqa 数而删 noqa**：`BLE001` 是项目的显式约定（1197 处），删了只会让
  `ruff`/审计看不见，不会让代码更安全。

### 8.2 判据边界（哪些情况本报告不判）

1. **动态调用**：`getattr(self, name)()`、`eval`、插件式 hook —— 异常类型不可静态枚举，
   一律按 A/B/C 归，不进 D。
2. **域函数**：`parse_*` / `build_*` / `export_*` 的异常族没有清单，不进 D（§5.3）。
3. **多语句 handler**：只按“有没有记录通道 / 有没有 raise”判，不判“记录得够不够详细”。
   例如 `swallow('x', e)` 一律算有记录，哪怕 context 起得很差。
4. **`# noqa` 注释**只用来统计约定覆盖率，不参与分类（注释不是行为）。
5. 行号取自 AST（`ExceptHandler.lineno`），与编辑器一致；`parsing/renpy_parser.py`
   含一个 form feed，本报告按 `\n` 切行以保证与 AST 对齐。

### 8.3 与既有文档/守卫的关系

- `storygraph/core/safeguard.py` 开头记录了 2026-10-05 那次审计：321 个 except、99 个 body
  只有 pass、全项目 196 处 noqa。本次在同一范围（`storygraph/`）量到：1960 个 except、
  **1 个 `pass`**（`safeguard.py` 自己的白名单）、1197 处 noqa。
  `pass` 基本清零是那次改造的直接成果；但**“有记录”不等于“处理得对”**，
  B′ 那 245 处就是证据。
- `tests/test_no_silent_except.py` 的判据偏松（§1.4）。若要继续用这条守卫，
  建议把判据从“有没有调用”改成“有没有**记录通道**”，白名单仍然只留 `safeguard`
  那一处 —— 这样 24 处 B 会当场变红，正好当施工清单。
