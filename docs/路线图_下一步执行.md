## 步骤 0 · 行身份契约（**先写文档，暂不动代码**）

### 做什么
写 `docs/契约_行身份.md`，把"每种编辑操作之后，这一句的身份 ID 会怎样"写成**可执行的规则表**。
再写 `tests/test_line_identity_contract.py`，**每条规则至少一个用例**。

### 为什么需要做
- **四件事共用同一个 ID**：XLIFF 的 `<trans-unit id>`、TTS 的语音文件 key、Unity 导出的行映射、协作库的主键。
- **而且这是行业标准要求的，不是我们自己造的**：Godot Dialogue Manager 的 `[ID:KEY]`、
  Yarn Spinner 的 `#line:`、XLIFF 的 `trans-unit/@id` —— **三个标准都要求稳定 ID**。
- 反过来说：**ID 不稳 = 进不了专业本地化流程**，也做不了语音缓存，也没法做 QA 反馈定位。
- 现在 `LineId` 的实际行为**没写下来过**，所以每个人（包括我）都在猜——上一轮我就猜错过一次（见下）。

### 应当如何实现

**规则表（草案，评审后定稿）**：

| 编辑操作 | ID 行为 | 备注 |
|---|---|---|
| 改台词正文 | **不变** | 最常见，必须成立 |
| 改说话人 | **不变** | ⚠ `LineId` 里有 speaker 的话就会变 —— 要检查 |
| 改条件（condition） | **不变** | `_align_key` 含条件，但条件**不该**进 ID |
| 改舞台（show/hide/scene/bgm/sfx） | **不变** | 演出变了，身份没变 |
| 改代码块内容 | **不变** | |
| 删一行 | 该行 ID **作废**（永不回收） | |
| 合并两行 | 两个 ID 都**作废**，发新 ID | |
| 插入 / 复制一行 | 发**新 ID**，不得与既存重复 | |
| **移动一行**（改顺序 / 跨章节搬） | **不变** | ⭐ **位置不是身份的一部分** —— 这是全表最关键的一条 |
| 从 `.rpy` 重新摊表覆盖 | **必须保持原 ID** | ⚠ 见"当前的真失稳源" |

**⚠ 当前的真失稳源（上一轮我说错了，这里更正）**：

我上一轮写"插删会让后面所有 ID 位移"—— **不准确**。实测代码路径是：

- `beat_model.py:3405`：`if not b.line_id: b.line_id = f"{label}.{b.seq:04d}"` —— **只在空时生成**；
- Excel 侧 `行号`/`序号` 是**存量列**（`beat_model.py:1311,1336` 从行里读），
  所以**在 Excel 里插删行，已存量的 ID 不会位移**。

**真正的失稳源有两条**：
1. **"从 `.rpy` 重新摊表覆盖表格"这条重建路径** —— `beat_build` 的 `seq` 是
   **按解析位置递增**的（`beat_build.py:196` 等 9 处 `self.seq += 1`），
   重建时 `line_id` 会按位置重算 → **全部 ID 变**。
   ⇒ 所以规则表必须专门写这条：**重建路径必须保住存量 ID**。
2. **新插入的行**拿到 `label.seq`，而 `seq` 按位置算 → **可能与既存 ID 重复**。
   （协作库侧已有 `collab_store._unique_line_id` 去重，Excel 侧要在契约里明确同样要求。）

### 做到什么程度
- `docs/契约_行身份.md`：规则表 + 每条规则的**反例**（什么样的编辑会踩）+ 与 `Beat` 字段的映射。
- `tests/test_line_identity_contract.py`：规则逐条有用例。
- **先写用例证明当前行为不符（红），再改代码（绿）** —— 尤其"删行 ID 作废"和"移动 ID 不变"这两条，
  当前**大概率不满足**。

### 验证标准
- 规则表每一条都有对应测试，且**测试名直接写规则**（例：`test_改台词正文_ID不变`）。
- 改一行台词 → `行号` 列**逐字不变**（用 Excel 读回落后的值断言，不是肉眼看）。
- 把第 3 行移到第 10 行 → **ID 不变**。
- 在第 3 行插入一行 → 新行拿到**全新且不重复**的 ID，原第 4~N 行 ID **不变**。
- 从 `.rpy` 重新摊表覆盖 → **已有行的 ID 全部不变**。

### 边界（明确不做）
- **不做 ID 回收池**：ID 一旦作废永不复用（避免旧翻译/旧语音被错误挂到新句子上）。
- **不做跨项目 ID 稳定**：每个项目独立命名空间。
- **不把"内容哈希"当 ID**：内容哈希改一个字就变（Ren'Py 官方 translation 就是这么翻的车）。

### 后续可拓展性
契约是**唯一真源**：未来的 TTS key、XLIFF `trans-unit/@id`、Unity 导出映射、协作库主键，
**都从这份文档的规则派生，不各写一份**。加一个出口 = 加一个适配器，不是加一套规则。

## 步骤 1 · 金标审计（**重录之前必须做**）

### 做什么
**人工审一遍当前 10 个 golden 对应的当前输出**，逐个文件确认"零丢失零多出"**是真成立**，
而不是"当前行为"被当成"正确行为"。

### 为什么需要做
- **金标 = "当前工具的输出"当基准。** 如果当前工具在某处有 bug，
  重录金标 = **把 bug 固化成基准**，以后谁修了这个 bug 都会被金标挡回去。
- 这是最容易漏的陷阱：**自动化程度越高，越容易不自觉地拿"当前行为"当"正确行为"**。

### 应当如何实现

**难点一：sha256 不可人审。** 现在 10 个 golden 大多是指纹文件
（`golden_scan_fingerprint.txt` 有 1MB），人没法审 sha256。
⇒ **金标要成对存在**：`指纹`（给机器比）+ **`describe` 可读快照**（给人看）。
  ✅ 现成模式：`golden_describe_fingerprint.txt`（27KB）已经是可读的。

**难点二：字节相等 ≠ 正确。** `tools/audit_byte_exact.py` 的判据是
"剥掉生成标记后字节完全相同"，它证明的是 **输出 == 上次的输出**，
**不能证明输出是对的**（两边一起错，指纹照样相等）。
⇒ 审计要加**独立于输出的第二判据**：**行级集合判据**——
  ① 输入的每一行都能在输出里找到；② 输出没有多余的行。
  这个判据能**定位**丢在哪一行，而不只是"不一样了"。

**做法**：
1. 对现有 golden 覆盖的真机 53 个 `.rpy`，逐个跑：
   `.rpy → 表格 → 带 --source 写回`，产出**可读 diff**（不是第一处差异，是**全部差异**）；
2. 人工判读每个差异：✅ 当前行为正确 / ⚠ 可疑 / ❌ 已知 bug；
3. 出《金标审计报告》——按类归因（`python:` 块 / 行尾注释 / menu 嵌套 / 条件分支 / ATL / 文件头）；
4. **报告里 0 个未处理的 ⚠/❌ 之后**，才允许重录金标。

### 做到什么程度
- 一份《金标审计报告》：按类给统计 + 逐条问题清单 + 每条的处置（修 / 接受 / 记为已知限制）。
- **可读 diff 工具**：把 `audit_byte_exact` 的"第一处差异"升级成"完整差异清单"。

### 验证标准
- 报告覆盖**全部**现有 golden 对应的文件，不是抽样。
- 每个 ⚠/❌ 都有处置记录；**处置完再重录**。
- 重录后的新 golden **与旧 golden 的差异清单**，能逐条对应到审计报告里的结论
  （即"金标变化 = 已知的、被批准的变化"）。

### 边界
- **审计只看"工具产物 vs 原文"，不判断剧情对不对**（铁律 9：语义永远由人标注）。
- 审计**不阻塞**已经开始的功能开发，只阻塞"重录金标"这一步。

### 后续可拓展性
- **行级集合判据**不只在审计期用一次 → 它成为**长期 CI 判据**（步骤 5 的 job A）。
- 审计报告的**分类统计**变成"哪些结构最容易出问题"的地图 → 指导 fixture 选取（步骤 2）。

## 步骤 2 · 脱敏 fixture 集（6–8 个正例 + 反例）

### 做什么
从真机里挑**边界样本**，脱敏后放进 `tests/fixtures/real_redacted/`，
每个 fixture 顶部写一行"**它测什么**"。

### 为什么需要做
- 现有可移植输入太弱：`demo/game/script/ch01.rpy` **39 行**，
  `menu` / `python:` / `#` 计数**全为 0** —— **覆盖不到任何保真边界**。
- 两次历史事故（**丢 18 行**、**`fadeout 1.0` 参数被吃**）都发生在
  `python:` 块与行尾内联注释这两类结构上 —— **而 fixture 现在一个都不覆盖**。

### 应当如何实现

**按历史事故定优先级**（不是按"结构复杂度"定）：

| 优先 | 类别 | 对应的事故 / 判据 | 大概几个 |
|---|---|---|---|
| **1** | `python:` 块 + **行尾内联注释** | 丢 18 行 / `fadeout 1.0` 参数被吃 / `_content_of` 去注释后算身份 / `_split_code_cell` 代码块归属 | 2–3 |
| **2** | **menu 嵌套** + **CDS**（`register_statement`） | 菜单选项体归属（选项挂错分支）/ 自定义语句三来源 | 2 |
| **3** | **ATL transform** + **文件头注释** | `atl.py` 解析求值 / 顶层保真块 | 1–2 |

**脱敏规则**（要能进 git、不能泄露项目内容）：
- 台词替换成无意义占位（`"第一句。"` → `"台词A。"`），**保留长度差异**（短句/长句/含引号/含换行/含转义各留几个）；
- 资源名替换成 `img_01` 这类假名，**但保留 tag 数量与命名风格**（要覆盖"看起来像说话人的行"那个坑）；
- 变量名替换，**保留条件表达式的形状**（`love >= 5` 这类分支区分特征必须留着）；
- **保留缩进、保留结构、保留行尾注释的位置**；
- 文件头写一行 `# 它测什么：……` + 一行 `# 来源：真机 <脱敏后的路径>（结构保留，内容已替换）`。

**反例 fixture（至少 2 个）**——**专门验证契约本身**：
- 表格里有一行在 `.rpy` 里**根本找不到** → 期望：**整份放弃 + 原文件逐字节不变 + 报错**；
- 两行身份冲突（同一说话人同位置的重复台词）→ 期望：**配不上就放弃**，不产出"半对"产物。

> ⚠ 这两个反例测的是**"要么全对、要么完全不动"里"完全不动"那半**——
> 这条分支现在**没有任何测试**。

### 做到什么程度
- `tests/fixtures/real_redacted/<case-id>/*.rpy` + 每 case 一个 `case.md`（一行"它测什么"）。
- 每个 case 至少 1 条 pytest（正例：往返字节相同；反例：整份放弃 + 逐字节不变）。

### 验证标准
- **每个 fixture 都至少有一条"当前会红"的用例** —— 否则它没测到东西（这是筛 fixture 的判据）。
- 反例必须证明：产物**等于**原文件（逐字节），且**有明确报错**（不是静默跳过）。
- fixture 全部进 git，且 `git grep` 不到任何真实台词 / 真实资源名 / 真实项目名。

### 边界
- **不塞 88 个 `.rpy`**（体积 + 脱敏风险 + 没人维护）；挑 6–8 个**边界**样本。
- 不做"整个真机项目"的 fixture。
- 脱敏**不改变结构** —— 改了结构，测的就不是原来那个坑了。

### 后续可拓展性
- **fixture 目录成为新功能的第一道回归网**：加一个渲染特性 → 必须同时加一个 fixture，
  否则它在 CI 上是无保护的。
- 反例 fixture 数量增长 = 契约的"拒绝分支"覆盖度提升。

## 步骤 3 · 事实文件采集状态 schema（**静默降级 → 显式降级**）

### 做什么
让"没采到"变成**看得见的一等公民**：缺项写成 `null` + `reason`，而不是**缺席**。

### 为什么需要做
这是 G2 里**最阴**的一条，而且比"写 null"更麻烦：

- 探针 `put(key, fn)` 逐项 `try/except` → **引擎 API 改名时探针不崩，只是"少一个键"**，
  事实文件照常生成（`probe_complete` 仍可能是 true）。
- 更阴的是：**缺席 ≠ 空值**。`core/engine_facts.py:807`：
  `kept = [... for s, v in contributions if v not in (None, '', [], {})]`
  —— **空值贡献会被直接丢掉**。
  ⇒ 于是新旧两份事实**都没有这个键** → `diff_facts` 的 diff **是空的** → **发现不了漂移**。

### 应当如何实现
1. **引入"显式缺席"贡献**：不是空值，是一条带原因的记录
   `{'value': None, 'reason': 'api_missing', 'source': 'probe'}`；
2. **改 `merge_fact` 的语义**（真技术落点，**光改采集侧不够**）：
   区分"**这个来源没说**"与"**这个来源明确说没有**"——
   前者不贡献，后者贡献一条 `value=None + reason`；
3. `FACT_KEYS` 里的每个键在 `facts` 里**必须存在**，值可以是 `null`；
4. `diff_facts` 增加一类漂移：**"新增缺席"**（旧有新无 → 报出来）。

### 做到什么程度
- `SCHEMA_VERSION` 升版；每个 `FACT_KEY` 的条目形如
  `{'value': …|None, 'source': …, 'reason': …|None}`；
- `reason` 至少能区分：`api_missing` / `parse_blocked` / `sdk_missing` / `timeout`。

### 验证标准
- **构造一个"某键采不到"的场景**（改探针或喂旧 dump），`diff_facts` **必须报出**，
  而不是 diff 为空 —— 这是本步的唯一硬判据。
- 现有 15/15 的真机采集用例**仍然通过**（不能因为语义变了而误报冲突）。

### 边界
- **降级只报告，不猜**：不因为某个键缺席就"推测"它的值。
- 不改探针的**只读**原则（不注册语句、不改配置）。
- 不把 `reason` 做成插件式可扩展（先定死 4 个，留扩展位即可）。

### 后续可拓展性
- `reason` 是**步骤 4 版本矩阵的落点**：不同版本缺不同的键 → reason 直接指向"哪个版本不支持什么"。
- 未来接"引擎事实漂移"告警时，`reason` 就是告警文案的原料。

## 步骤 4 · 引擎版本适配层（薄封装，**不做插件系统**）

### 做什么
7 处耦合点各做一层**薄封装**（策略 A 失败降级到 B），并声明版本支持范围。

### 为什么需要做
护城河（引擎事实驱动）**建在别人家的接口上**。接口一变，护城河静默变浅。

### 应当如何实现

**7 处耦合点（实测清单）**：

| # | 耦合点 | 位置 | 失败表现 |
|---|---|---|---|
| 1 | `renpy.list_images()` / `get_available_image_tags()` / `get_all_labels()` / `renpy.statements.registry` / `get_registered_image()` | `engine_collect.py:95-150` | 事实缺项 |
| 2 | `init 999 python:` 注入机制 | `engine_collect.py:82` | 探针不执行 |
| 3 | `--json-dump` 输出格式 | `core/engine_facts.py:43` | 静态清单塌 |
| 4 | `lint --error-code` 退出码语义 | `engine_collect.py:559` | 有错判错 |
| 5 | 引擎报错**英文文案**（`expected statement.` / `_PARSE_MARKS`） | `statement_probe.py:122` | parse error 判错 |
| 6 | `test` 输出格式（`[rpytest] Status:`） | `statement_probe.py:126` | 行为验证失效 |
| 7 | SDK 路径探测（环境变量 + 硬编码候选 `renpy-8.4.1-sdk`） | `engine_collect.py:56,186` | 换机找不到 SDK |

**版本矩阵按"主.次"声明，不过度设计**：
- ✅ 理由：Ren'Py **major** 才是引擎语义变更（7→8 改了 screen language），minor 通常是增量。
- ⚠ **诚实前提**：**我们实际只验过 8.4.1**（本机 `D:/software/renpy-8.4.1-sdk`）。
  ⇒ **第一版只声明 `8.4.x` 为"已验证"**，`8.3.x` / `8.5.x` 标 **"未验证"**——
  **不宣称**没验过的范围（宣称了就是拿没证据的话当护城河）。
- 每个已验证范围**固化一份 dump 当 fixture**，CI 跑解析回归。

**薄封装的样子**（示意，不是最终签名）：
```
读事实 → 策略 A（当前格式）→ 失败 → 策略 B（旧格式）→ 失败 → 显式降级（步骤 3 的 reason）
```
**不做**：插件系统、注册表、动态加载 —— 那是过度工程。

### 做到什么程度
- `docs/引擎支持矩阵.md`：版本范围 × 期望的事实键集合 × 验证方式；
- 7 处各有一个 `*_adapter`（带 fallback 链 + 明确的"都不行"出口）；
- 每个已验证范围一份 dump fixture。

### 验证标准
- 喂**未验证版本的 dump** → 要么解析成功，**要么响亮报"该版本未验证"**，
  **不许静默少字段**（这条直接依赖步骤 3）。
- 7 处耦合点各有一个"降级路径"用例（模拟策略 A 失败）。

### 边界
- **不追** Ren'Py 全部版本；只声明验证过的。
- 不自己实现 ATL 语义（那是 §3 的 C3，**做不到**）。
- 不把"适配层"做成对所有引擎的通用框架 —— **只服务 Ren'Py 一家**。

### 后续可拓展性
- 适配层是**唯一**碰引擎格式的地方 ⇒ 将来支持新引擎**只改这里**，
  采集/事实/校验/UI 全不动。
- 版本矩阵的 fixture 天然是**引擎升级的回归网**：引擎发新版 → 加一份 dump → 跑回归 → 决定要不要加一档。

## 步骤 5 · CI 接线（让护栏真的存在）

### 做什么
CI 增加两个 job，并把"字节保真"从"需要真机项目"改成"**仓库里就有 fixture**"。

### 为什么需要做
现在：**8 个 golden 守卫全在 `skipif(not REAL)` 名单里** ⇒
"逐字节零丢失"这句话在 CI 里**没有任何护栏**。
fork 的人改 `patcher.py`，CI 不会红。

### 应当如何实现
- **job A · 字节保真**：跑 fixture 集（步骤 2），
  判据 = **字节相等**（`audit_byte_exact` 同款）**+ 行级集合判据**（步骤 1 的产物）；
  **不许 skip**；
- **job B · 引擎解析回归**：跑版本矩阵的 dump fixture（步骤 4）；
- **解除 `skipif(not REAL)` 依赖**：fixture 在仓库里 → 判据不再需要真机项目；
  真机专属的那部分（如 `test` 行为级验证）**保留在本机**，但**不再承担"保真"职责**。

### 做到什么程度
- CI 页面能看到两个独立 job；
- `patcher` / `beat_render` / `beat_build` 任一处改动 → **job A 红**。

### 验证标准（关键：要真的验一次）
**故意改一行 `beat_render`，确认 CI 红**，再改回来。
⚠ 只看配置不算数 —— 必须**实际制造一次失败**并看到它红。
（这正是"回读校验 → 提交 → 提交后回验"那条纪律的同源要求。）

### 边界
- 不把 8GB 真机项目搬进 CI。
- CI **不跑** headless 不可用的行为级测试（`test` 需要显示设备）——
  那部分靠 job A 的 fixture 覆盖等价问题。
- CI **不跑**真机金标（体积 + 路径依赖），真机金标留在本机全量里。

### 后续可拓展性
- fixture 数**只增不减** ⇒ 护栏越用越厚。
- 行级集合判据一旦在 CI 里跑，就能直接支撑"**这个 PR 改了哪些拍**"的自动 diff（未来接 PR 机器人）。

## 步骤 6 · License 三件套 + 依赖 license 清单

### 做什么
`LICENSE` 文件（MIT）+ `pyproject.toml` 的 license 字段 + README 的 License 段 —— **三件一起**。

### 为什么需要做
现在 `pyproject.toml:11` 是 `license = { text = "Proprietary" }`，
且**仓库里没有 LICENSE 文件** ⇒ **名义开源、法务上不成立**：
别人看不到授权条款，法律上也没有授权。

### 应当如何实现
- `LICENSE`：MIT 全文（年份 + 版权人）；
- `pyproject.toml`：`license = "MIT"`（PEP 639 风格）+ `license-files = ["LICENSE"]`；
- `README.md`：加 License 段。

**依赖 license 扫描（已实测，2026-10-23）**：

| 依赖 | 用途 | 许可证 | 与 MIT 兼容？ |
|---|---|---|---|
| `openpyxl>=3.1` | Excel 读写（**必需**） | MIT | ✅ |
| `Pillow>=10` | 缩略图（**可选**） | HPND | ✅ |
| `PySide6>=6.5` | 界面（**可选**，无头 CLI 不需要） | **LGPLv3** | ✅（**动态链接** Qt for Python） |
| `pytest>=8` | 开发依赖 | MIT | ✅ |

⇒ **没有 GPL 依赖，没有冲突**。唯一要说明的是 **PySide6 为 LGPLv3（动态链接，可替换）**，
README 里写清楚即可。

### 做到什么程度
- 三个文件都改完；`python -m build` 产出的 wheel 元数据里 License 显示 MIT。

### 验证标准
- 读 wheel 的 `METADATA`，`License-Expression: MIT`；
- `pip install .` 后 `importlib.metadata.metadata('storygraph')['License']` 可读。

### 边界
- **LGPL 部分要说明**：PySide6 是动态链接，用户可替换 Qt —— README 注明。
- 若将来引入 GPL 依赖，需**重新评估**（不能只看"能不能装"）。

### 后续可拓展性
- 有了 LICENSE，**步骤 2 的脱敏 fixture 才有法务基础**（版权清晰的代码才能进仓库）。
- MIT 让"别人 fork 下来改补丁逻辑"成为**合法且被邀请**的行为 —— 这是步骤 5 的护栏能起作用的前提。

## 步骤 7 · XLIFF 通道（导出 + 导入，**一起做**）

### 做什么
导出 `.xlsx → .xliff`，再 `.xliff → .xlsx → .rpy` 导回来。

### 为什么需要做
- XLIFF/PO 是**行业标准**（Unity Localization、Godot Dialogue Manager、Trados、memoQ、Crowdin 都用）。
  我们现在走 Excel = **落后**。
- 但**只导出不导入是半通道** —— 译完回不来，只会制造失望。

### 应当如何实现
- **`<trans-unit id>` = 行身份**（**步骤 0 的产出**，不是另造一套）；
- **`<source>` 必须是用户能看见的原文**，**不能是 IR 归一化后的文本**：
  Trados / memoQ / Crowdin 会用 source 做**模糊匹配 + 翻译记忆（TM）**；
  归一化文本 → 源文微调就 miss → **TM 命中率归零，进不了专业本地化流程**。
  ⇒ **跨模块约束：IR 归一化不得污染面向人的原文。**
  （我们有人话层 `story/dsl.py`，XLIFF 的 source 要取自**人话层/原始台词**。）
- 导入侧：XLIFF → 待写回表 → **先出 diff 人确认**（铁律 5：未确认零写）→ 受控补丁 → 写回报告。

### 做到什么程度
一个 chapter 能导出、能导回来；译文逐字进 `.rpy`，且**除译文行外其他行逐字节不变**。

### 验证标准
真机一章做往返：导出 → 手改译文 → 导入 →
① **只有被译的那一行变了**；② 其余行**逐字节相同**；③ 写回报告列出改了哪几行。

### 边界
- **不做 CAT 工具**：不做 fuzzy match UI、不做 TM、不做术语库管理（只导出不管理）。
- 不做 XLIFF 2.0 以外的方言（先 1.2 + 2.0 最小集）。

### 后续可拓展性
- 同一套行身份未来直接接 Crowdin / memoQ 的 API —— **不用改格式层**。
- `<source>` 用人话层 → 天然支持**多语言复用**（同一份原文，多份 target）。

## 步骤 8 · fork 项目治理话术与登记入口

### 做什么
把"教它升级"从一个 UI 小功能，提升为 **fork 项目的治理入口**；并把边界写进对外口径。

### 为什么需要做
**fork 自定义语句是工具最危险的盲区，而 fork 项目恰恰最需要治理**——
"否则为什么要 fork"。标准语句我们能管，fork 语句**四路无信号、完全隐形**。
⇒ **我们价值最大的场景，正好是我们的盲区**。这个矛盾必须**诚实地处理**，不能装作没有。

### 应当如何实现
1. **对外口径写清楚**：
   > 标准语句能管；**fork 自定义语句需要人工登记进"教它升级"清单**。
   不要让人以为"引擎事实"是全知的（见 C7 边界声明）。
2. **登记要可审计**：登记项进 `rules.json` **和**事实文件
   ⇒ 把"我们不知道这些语句"变成"**我们知道、但引擎没告诉我们**"（这两件事在产品上完全不同）；
3. **措辞诚实**：登记后**引擎级保证仍然不可得**（探针在 parse error 时整个失效），
   所以登记项的标注是"**已登记，引擎级验证仍不可得**"，不是"已验证"。

### 做到什么程度
- 一份 fork 项目的登记模板（清单式：`语句名` / `参数形状` / `登记人` / `登记时间` / `证据`）；
- 对外话术一段（写进 README 与产品页）。

### 验证标准
拿**一个真的 fork 项目**试登记 → 能列出三档：
「标准语句（引擎已确认）」/「已登记语句（人工声明）」/「仍未知（引擎不可知）」——
**三档都要有样本**，且用户能一眼看懂自己项目落在哪一档。

### 边界
- **不承诺**覆盖 fork 语句；**不做"自动发现 fork 语句"**（四路无信号，做不了 —— 这是引擎编译器的性质）。
- 不做"让引擎认识我们的登记项"（引擎侧要项目自己改，工具不越界）。

### 后续可拓展性
- 登记项可导出成「**给引擎作者的 `register_statement` 建议清单**」——
  工具反过来帮项目把 fork 语句**标准化**，这是长线最有想象力的位置。
