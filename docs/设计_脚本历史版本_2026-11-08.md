## 一、先验：四个问题，四个跑出来的答案

探针 `.pip-tmp/probe_r11_rpy_backup.py`（每条都跑真函数，不读代码猜）：

| 问的 | 量到的 |
|---|---|
| "改一句 → 导出"（`write_generation` + `merged_from_source`）覆盖已有章节 | **有** `.rpy.bak`，逐字节是覆盖前那份；连推 8 次 → 正好 5 代（`KEEP_BACKUPS` 生效） |
| 手写文件（无生成标记）走同一条路 | 照样写、照样留 `.bak`（"目标就是源文件"的合并是正常用法） |
| **原地小改家族**（`story.paths.write_text_atomic`，不带 `backup=`） | **一个备份都不多** —— 目录里什么也不长 |
| 真项目 `D:\千连万理\sr_general`（95 个 `.rpy`） | `*.rpy.bak*` 共 **0 个**，`game/` 里只有 7 个 Excel 备份 |

结论一句话：**保护是不对称的**。整份覆盖（最危险的那一刀）有退路；而
"改一条 `show` 的 `@at` / 改一条源边 / 删一行源 / 换编排层"这种**频率高得多、
专门切手写剧本**的小改，磁盘上一点退路都没有 —— 只有内存里那套撤销，
**关窗即失效**。这正是第十轮刚给 `.ext.json` 补上的那个缺口，长在剧本上。

`components` 全景（谁写 `.rpy`）：

```
写 .rpy 的两条路
├── generation_guard.write_generation(..., backup=True)   ← 整份导出 / 导入 / 编译
│     └── 文件旁边留 <名>.rpy.bak（最多 5 代）
└── story.paths.write_text_atomic(...)  （不带 backup）    ← 原地小改家族
      ├── graph/commands.py（改 @at / 换表情 / 改源边 …）
      ├── story/control_{branch,route,takeover}.py（编排层）
      ├── story/choice_point.py（选择点）
      ├── app/source_line_delete.py（删一行源）
      └── story/sg_transforms.py（生成的 sg_* 变换）
      └── **从前：什么都不留**
```

## 二、为什么不干脆给原地小改也加 `backup=True`

因为原地小改**频率高一个数量级**：一张卡改五次就是三代。堆在 `game/` 里
就是几十上百个 `*.rpy.bak` —— `authoring/import_cleanup.py` 那个
「🧹 清理导入残留」和 `dialog_cleanup` 里"`.rpy.bak` 默认不勾（可能是手写
文件唯一的旧版本）"就是为这种堆积写的。用户的 `game/` 不该越来越脏。

于是**换个落点，不换规矩**：

```
<项目>/.storygraph/versions/<脚本相对 game/ 的目录>/<脚本名>.rpy.bak[-<时间戳>-<序号>]
```

- 在 `game/` **外面**：Ren'Py 只扫 `game/` 下的 `.rpy`，这里它一个字节都不读；
  「清理导入残留」也不会列它（那个扫描只认 `game/**` 下的四类后缀）。
- 在项目**里面**（不是用户缓存）：备份属于这个项目，换机器 / 打包带走都还在，
  `%LOCALAPPDATA%` 被清掉也不丢。
- 目录里放一个 `.gitignore`（内容 `*`）：用户 `git status` 不会看见几千个备份。
  **不动**用户自己的 `.gitignore`（有判据钉着）。

## 三、三处真源，一条闸

| 事 | 真源 |
|---|---|
| 世代放哪儿 | `version_store.history_dir()`：判据是**路径关系**（必须能 `relative_to(<根>/game)`），不是文件名猜测 → `build/` 产物、临时目录、Excel/JSON 都不留历史 |
| 有哪几代 | `version_store.versions_of()` = 历史目录 **+** 文件旁边老机制留下的 `.rpy.bak`，按 mtime 新的在前（少列一个来源，"我那份 `.bak` 呢"就变成一次实地翻目录） |
| 怎么存 | `atomicio.backup_file(..., where=…)`：与老机制**同一套命名与裁剪**（固定名 → 带时间戳 + 序；最多 `KEEP_BACKUPS` 代；固定名那份永不裁 = 工具第一次动刀之前的原稿） |
| 怎么放回 | `core.versions.restore(..., where=…)`：锁里读现在 → 比对 `expect_current` → 写回（写前先把现在这份备份掉） |

**一条闸没变**：`expect_current` 不符就一个字不写。防止"拿一份旧文本盖掉别人的改动"。

### 三个细节，都是踩出来的

1. **去重比"全部世代"，不是只比最新一代**
   `O → X → O → X`：第三次要把 `O` 换掉，可 `O` 早在固定名那份里存着了 ——
   不该再存一遍。只比最新一代会漏掉"更早的世代里就有它"（判据
   `test_reverting_to_an_old_state_does_not_store_it_twice`，变异 4 抓到）。
2. **空转写盘不烧一代**
   `story.paths.write_text_atomic` 把"马上要写进去的文本"传给
   `snapshot(incoming=…)`：逐字节一样时这次写盘本来就是空转。
   （第十轮给 `ext.registry.save` 立过同一条规矩。）
3. **备份失败 = 这次写盘不做**
   `snapshot` 读不出来 / 目录建不出来就抛 `OSError`，`write_text_atomic`
   在写之前就中止。判据里把 `.storygraph` 变成一个**文件**来逼出这条
   （`test_failed_backup_refuses_the_write`）：文件一个字节都没动。
   —— "用户以为有退路、其实没有"比"没有退路"更坏，这是 `atomicio` 的老规矩。

## 四、`backup=True` 那条路照旧

`write_generation(..., backup=True)` 仍然在**文件旁边**留 `.rpy.bak`，
**不进**历史目录（同一份内容不存两处）。为什么不动它：

- `dialog_cleanup` / `import_cleanup` / 用户手册 / 好几条判据都按
  "`.rpy.bak` 在文件旁边"写的；
- 它是"整份覆盖"那条路，频率低，堆得起。

于是列表要**合并两个来源**（判据 `test_listing_merges_both_homes_newest_first`）。
"放回"时新一代**一律进历史目录**：`game/` 一个文件都不许多
（`test_restore_from_legacy_bak_also_writes_into_the_history_folder`）。

## 五、界面：一条入口，两个注入口

菜单「更多工具 → 🕘 这个脚本的旧版本…」（`window_graph_ops._more_tools_menu`，
处理在 `window_recover.show_script_versions`）。

窗口还是第十轮那个 `VersionsDialog`，只是脚本这条路多注入两样：

| 注入 | 为什么 |
|---|---|
| `store=SCRIPT_STORE` | 一个"版本库"壳（`core.versions.Store`：怎么列 + 怎么放回）。**一个**参数而不是两个：`list_fn` / `restore_fn` 拆开时，调用方只传一个就静默半残（列的是旧目录、写的是新目录） |
| `before_restore=_script_restore_guard` | 放回**之前**问一句：内存里还有没导出的改动 → **不放回**。否则 `load_script` 重建拍列表时把它们凭空抹掉（撤销栈也重置了，救不回来） |

放回成功后：`load_script(path)` 按磁盘重读（拍号 / 行号 / 脏标记跟着换），
状态栏如实说"已放回 X，并按磁盘重读了这一章：N 拍"。
⚠ 顺序不能反 —— `load_script` 末尾会把状态栏写成「已载入 …」，先写就被盖掉
（第十轮在对话框里踩过同一个坑）。

顺带修掉一个**真**的"点了没反应"：`UnicodeDecodeError` 不是 `OSError`。
一份 GBK / 二进制的旧 `.rpy.bak` 会让槽函数抛异常，而 PySide6 的槽抛异常
**只打 stderr** —— 界面上什么都不发生。现在：那一行照样列出（内容格写
"不是 UTF-8 —— 只列出来，不放回"），预览给同一句话，点「放回」被拒且说明原因。

# 第十二轮（同日）：**留多久**、**占多少**、**清掉**

第十一轮把旧版本存下来了，但"留多久"直接沿用了 `KEEP_BACKUPS=5`（那是给
"一天存两三次"的配置清单算的）。这一轮先量这件事，再补三个口子。

## 九、先验：5 代对剧本不够用

探针 `.pip-tmp/probe_r12_window.py`：

| 问的 | 量到的（第十一轮刚上线时） |
|---|---|
| 同一小时连改 30 次 | 只剩 **5 代**，时间跨度 **1.1 秒** |
| 跨三天各改 10 次（伪造时钟） | 只剩 5 代，**"昨天那一版"一个都没了** |
| 界面上说得出"占多大"吗 | 说不出（状态栏只报"几代"） |

结论：按"次数"裁剪对配置清单够用，对**高频改的剧本**不够 —— 用户真正的诉求
常常是"回到昨天"，而不是"回到十分钟前"。

## 十、时间台阶：每个"多久以前"各留一版

`atomicio` 的裁剪多了第二个规矩（**只给脚本用**，`.json` / `.xlsx` 那条老路
一个字节都没变）：

```
留：固定名那份（原件，永远留）
  + 最近 KEEP_BACKUPS 份
  + 时间台阶 (1h, 6h, 1d, 3d, 7d, 14d) 各一份"最新的、已经比它更旧"的
```

于是每份脚本最多 1 + 5 + 6 = 12 个备份文件（每个几十 KB，95 个脚本约 25 MB）。

**⚠ 为什么按"年龄"而不是"日历上的哪一天"**：昨天关工具之前那一版，是在
**今天第一次保存时**才被写进备份的（那时它才被换掉），mtime 是今天。按日历
分组会把"昨天那一版"算成今天的，一裁就没 —— 第一版就是这么写错的（探针里
"跨天留档"一个都没留住）。

**⚠ 台阶不能让固定名参与挑**：固定名那份永远留着、而且通常最老，让它参与
"最新的、够老的那一份"，每个台阶都会命中它自己，等于台阶全废 —— 第二版
就是这么写错的（探针照样一条跨天版本都没留下）。判据
`test_the_original_does_not_eat_every_step` 专门钉这一条。

## 十一、说清"占多少"，也给一个"清掉"

这套东西被**故意**放在隐藏目录里（`game/` 外、`git status` 看不见），代价是
"它占了多少"在界面上完全不可见 —— 看不见的东西，人要么忘了它，要么突然发现
硬盘少了几十兆。所以：

- **历史版本窗口**的状态栏多了合计：`磁盘上有 3 代备份（共 585 B）`；
- 顶部说明多一行"留多少"（`最近 5 次改动，外加 1 小时前、6 小时前、1 天前、
  3 天前、7 天前、14 天前 各留一版`）；
- 菜单多一条「🧹 历史版本（占多少 / 清掉）…」：先摊账（多少文件、多大、
  几个脚本、最早到哪天、跨几天），再问一句，**点「全部删掉」才删**。

清理的三条规矩：只删 `history_root()` 里认得的版本文件（**符号链接不跟**、
目录不动、`.gitignore` 不动）；删完收空目录，但 `.storygraph/` 留着
（`layout.json` 在里面）；单个文件删不掉（被占用 / 只读）→ 记进 `failed`，
不当中断。删完工具照样会继续留新的 —— 这不是"关掉历史版本"的开关。
