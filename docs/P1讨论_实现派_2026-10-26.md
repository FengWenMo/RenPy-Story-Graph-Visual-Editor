## ① 给无标题 menu 加标题（从无到有）→ 补丁拒

### 判词：**修**（收尾两形态）。高频编辑面，修法已用 monkeypatch 验证，小改今天能完。

### 现状（探针 `_p1debate_impl_menu_caption.py`，两条出口 × 六形态）

| 形态 | 卡片路 | 表格路 |
|---|---|---|
| 裸 `menu:` | ✅ | ✅ |
| 带名字 `menu my_menu:` | ✅ | ✅ |
| 带参数 `menu (nvl=True):` | ✅ | ✅ |
| CRLF 载体 | ✅ | ✅ |
| **嵌在 if 里** | ❌ `1 处新增内容没能落进产物` | ❌（note 里同款） |
| **带 extras（`set seen`）** | ❌ 同上 | ❌ 同上 |

两条出口同口径（铁律 6 过）；拒绝时文件字节零变化、拒因完整（铁律 2 过）。问题是两个形态的补丁落不了地。

### 根因（探针 `_p1debate_impl_menu_caption_bisect.py` + `_p1debate_impl_extras_shape.py` 钉死）

**形态 A · 嵌在 if 里**：单拍渲染（`beat_render.render_beat_to_rpy`，条件拍）输出

```
['if flag:', '    menu:', '        "新标题"']
```

而 `_replace_matched` 的菜单标题通道（`patcher.py:1577-1605`）拿 `gen_bodies[0]` 去比菜单头：

```python
_mh = _norm(old_lines[0])                      # 'menu:'
if (_MENU_HEAD_RE.match(_mh) and _mh.endswith(':')
        and _norm(gen_bodies[0]) == _mh        # ← 'if flag:' ≠ 'menu:' → 通道整条不触发
```

`if flag:` 是**结构行、不是拍的内容**——同文件 `_body_lines()`（`patcher.py:993`）就是干这个的
（"条件拍的生成结果是 `if 条件:` + 块体，而块头不是拍"），通道没用它。

**形态 B · 带 extras**：菜单块里的 `set seen`（解析器归进 `MenuNode.extras`，`renpy_nodes.py:246`，
拍的 `raw` 字段）在**两条渲染出口里长成两种样子**（探针 `_p1debate_impl_extras_fate.py` §3 实测）：

| 出口 | 输出 |
|---|---|
| 单拍渲染（补丁用） | `['$ set seen', 'menu:', '    "新标题"']` |
| 整份渲染（全量用） | `['menu:', '    "新标题"', '    set seen']` |

两个差异：① 单拍给 `set seen` **补了 `$`**（走了代码通道——`set` 是 Ren'Py 语句不是 Python，
`$ set seen` 是把能跑的脚本改坏，铁律 5）；② 位置在 menu 头**前**而不是标题**后**。
零改动往返侥幸逐字节相同（那行没进任何拍的区间、原样留着），但"加标题"一来，
`all(_is_caption_line(x) for x in gen_bodies[1:])` 被它卡住 → 通道不触发 → `lost_new` → 整份拒。

### 修法（复用已有口径，两步）

1. **`beat_render`：菜单 extras 与整份渲染同口径**（这是独立缺陷，不只是绕过 ①）。
   `render_menu_block`（`beat_render.py:1696`）已经是"逐字吐、不补 `$`、在标题后"；
   单拍路径把 `raw` 交给代码通道补 `$` 是错的。改法：KIND_MENU 的单拍渲染把 `raw` 按
   `render_menu_block` 同一写法输出——**同一个函数出**（M1 的教训："两处各写一份正是 P0-2 的来源"）。
2. **`patcher._replace_matched` 标题通道两处判据**：
   · 头比较改用 `_body_lines(gen_bodies)[0]`（剥掉开头 `if/elif/else`）；
   · `gen_bodies[1:]` 允许 "caption 前缀 + extras 尾巴"，extras 尾巴必须与 `old_lines` 里的
     extras **逐字相同**（认不出就原样抄，铁律 3）；extras 不同 → 维持拒绝。

修法可行性已用 monkeypatch 证明（`tools/_p1debate_impl_menu_fix_sim.py`）：
嵌套形态落地且全文逐行正确、裸/带名字/清空标题回归面全过。

### 风险点（最可能毁字节的一步 + 判据怎么兜）

- **最危险**：标题通道是把 old/gen **就地改写后继续走配对**（不是递归）。
  模拟第一版把改写结果递归调回原函数 → 通道**二次触发**把注入的标题又剥掉，
  连"裸 menu 加标题"这个本来就过的形态都被打坏（探针 §3 当场红）。
  修真实代码时同样要防：通道处理完必须直接进配对段，不许绕回通道入口。
- **空白标题护栏不许回归**：`_caption_is_substantive`（`patcher.py:750`）——作者写 `" "`（全空白）
  渲染出来是"没有标题"，照删就是静默删行（真机 `script_pomo.rpy:205` 被抓过）。
  模拟第一版就把它误删了（§3 红）。判据必须含这条。
- **判据（构造期望全文）**：六形态 × 两条出口各断言**完整期望文本**（探针已示范，直接搬进
  `tests/test_p0_round4.py::TestMenuCaptionFromScratch` 扩容）：

```python
# 嵌套：期望全文（逐行）
['label start:', '    if flag:', '        menu:', '            "新标题"',
 '            "开始":', '                e "a"', '    return']
# extras：期望全文（逐行，extras 不许动、不许补 $）
['label start:', '    menu:', '        "新标题"', '        set seen',
 '        "开始":', '            e "a"', '    return']
```

外加后果链判据（`test_menu_head_modeling` 风格）："产物里不许出现 `$ set seen`"。

### 代价：小改（渲染口径 ~15 行 + 通道判据 ~20 行 + 判据 6 条）。**今天能完。**

## ② 真机复杂文件上移动拍被拒（"重排段里有认不出的行"）

### 判词：**修（窄口）**——只放行"init 期声明行"进空隙；跨块头/跨 label/带条件的拒绝**保持**。
同时校准期望："移动等于不可用"不成立（62% 相邻移动已可做）。

### 现状（探针 `_p1debate_impl_move_real.py`，真机 `script_pomo.rpy` 74 对相邻移动）

可增量移动 **46/74**。拒因分布：

| 对数 | 拒因 | 该不该拒 |
|---|---|---|
| 11 | 挪过结构块头（`elif pomoplace == "cafe":` 等） | **该拒**——挪出分支=改剧情/换判定顺序 |
| 11 | "要挪请先清掉这一拍的条件"（带条件拍移动） | **该拒**——位置=条件语义 |
| 3 | 跨 label | **该拒**——增量补丁不猜结构改动 |
| 3 | 重排段里有认不出的行 | **可修**（本条的窄口） |
| 2 | 条件对不上 / 台词找不到 | **该拒**（连带效应，拒因已点名） |
| 2 | `move_beat` 自身拒（菜单/选项体块头不许单独挪） | **该拒**（拆块=坏结构） |

"认不出的行"逐对点名（`_p1debate_impl_move_gaps_and_broken.py` §1）：

```
L97:  define persistent.pomoscript = True   ← 顶层声明，init 期
L135: image overworld = "…/overworld.jpg"   ← 顶层声明，init 期
L217: image bgbed = "…/bgbed.jpg"           ← 顶层声明，init 期
```

全是**文件级声明行**（`define`/`image`），夹在 `label` 之间（真机 `script_pomo.rpy:97/135/217`）。
`_plan_reorders`（`patcher.py:3093-3099`）的空隙判据是"只许空行/注释"，撞上它们就整段放弃。

### 修法（窄口，只动 `_plan_reorders` 的空隙准入）

空隙行判据从"空行/注释"放宽为"空行/注释 **+ init 期声明行**"：

```
允许留在空隙原地不动的（收紧到枚举，不猜）：
  define … / default … / image … / transform …（无冒号结尾的单行声明）
不允许的（维持拒绝）：
  $ …（运行期代码）、任何以冒号结尾的块头、play/stop/jump/call、认不出的一切
```

依据：`define`/`image`/`default`/`transform` 是 Ren'Py 的 **init 期语句**，运行序不敏感
（声明在哪个 label 之间都一样生效）；`$ …` / `play` / 控制流是运行期语句，位置即语义——那要继续拒。
`_BLOCK_HEAD_RE`（`patcher.py:1114`）已认得这组词，判据直接复用它 + "不以冒号结尾"。
拒因文案顺带升级：点名行文 + "这行是顶层声明，可以随空隙原地不动；若是运行期语句请全量重写"。

**不修的部分直说**：跨 `if/elif` 块头的移动、跨 label 的移动、带条件拍的移动——修它们必然
"猜这一挪是不是用户想改剧情"（铁律 3），而且审计第三轮 P0-11 的教训就是移动语义猜错过一次。
拒因现在已说人话（`patcher.py:3106-3125`，10-25 已修文案），保持。

### 风险点

- **最危险**：把"运行期语句"误放行进空隙（`$ persistent.x = True` 长得也很像声明）。
  判据必须是**白名单枚举**（define/default/image/transform 且无冒号），不是"看起来像声明"。
- **判据（构造期望全文）**：合成样本——两个普通拍之间夹 `define persistent.x = True`，
  移动后期望全文逐行断言：两个拍换位、define 行**逐字节原地不动**；
  反例判据：夹 `$ renpy.block_rollback()` 的同款移动**必须拒** + 字节零变化。
- 另一个隐患（顺带记录，不在本条修）：非相邻移动实测出现"认不出的行（例：`jump pomo_script2`）"
  ——`jump` 明明是拍（flow 拍），却落进了空隙，是 `_plan_reorders` 成员判定与行区间错位的连带。
  真机 8 对非相邻采样里 1 对，先记账不动。

### 代价：小改（空隙准入 ~15 行 + 拒因 ~10 行 + 判据 4 条）。**今天能完。**

## ③ 改 if 条件被拒（"条件改动走全量"）

### 判词：**链头/独立 if 已修，不需再动；elif/嵌套/清空不修**——修它必然引入猜语义。

### 现状（探针 `_p1debate_impl_if_condition.py`，6/6）

| 形态 | 现状 | 字节 |
|---|---|---|
| 独立 if 改条件（`if flag:` → `if not flag:`） | ✅ 增量，只动那一行 | 1 行 |
| 链头改条件（`if a == 1:` → `if a == 9:`） | ✅ 增量，`elif` 行逐字节不动 | 1 行 |
| **elif 改条件** | ❌ 拒 + 具体理由（"表里存的是展平后的累积条件…"） | 0 |
| **嵌套 if 改条件** | ❌ 拒 + 具体理由（"累积条件含外层"） | 0 |
| **清空条件** | ❌ 拒（"那是拆掉这一层 if，结构改动"） | 0 |
| 条件没改 | ✅ 零 diff | 0 |

`_plan_condition_rewrites`（`patcher.py:2859`）就是 10-25 的修法：链头/独立 if 换那一行的条件正文，
别的字节不动。审计说的"条件改动走全量"是**修前**状态。

### 为什么不修 elif/嵌套（直说）

表里存的条件是**累积形式**（`renpy_parser._w_if:2939-2970`：第 2 支是 `(b2) and not ((b1))`）。
用户在卡片上改的也是这个累积值。要把它写回文件，只能：

- (a) 反解出这一支的"自己的条件"再写 `elif` 行 —— 反解 = **猜**（累积到 own 的分解不唯一，
  用户填 `(b) and not (a)` 时无法判断他是想改 `elif` 的 own 还是想改链头再重排）；
- (b) 把整条链头重写成展平 `if` —— 那是改用户没碰过的结构行（`_chain_renumber` docstring 记着
  这个教训：diff 一大片，评审看不出是工具干的）；
- (c) 清空条件 = 拆掉 `if` 层 —— 结构改动，已有明确拒因。

三条都违反铁律 3/5。**拒因已经说人话**（`_condition_hint`，`patcher.py:2124`，逐类点名
elif/嵌套/清空各为什么不行），出路也有（全量重写这一章 / 导出到 `build/renpy/`）。
产品上如果嫌重，正确的方向是**改表的语义**（表里存 own 条件而不是累积条件），
那是模型层的大改且牵动 Excel 列语义与所有旧表——不属于 P1 收尾的范围。

### 代价：0（现状即设计内）。硬修 elif = 大改 + 必毁数据，**不修**。

## ④ `write_asset_excel` 表坏了才整份重建（有隔离备份）

### 判词：**修**——这是四条里**唯一还在丢用户工作**的（其余三条都是"拒但安全"）。
用户对同类问题（P0-F）已明确表过态："不要做隔离备份，这解决不了根本问题"，要求**直接保住**。

### 现状（探针 `_p1debate_impl_move_gaps_and_broken.py` §2/§4）

策划维护的 `images.xlsx`（加了「配音演员」列、`future` 手写占位行、「分类说明」页、标黄+批注），
表损坏（zip 截断）后点「扫描资源」：

```
repaired=['images.broken-20261026-….xlsx']     ← 隔离副本在
新表：配音演员列=False  future行=False  页=['Sheet']  批注=None   ← 全没
```

更糟的一处（§4）：**表被 Excel 占用（PermissionError）也被当成"坏了"**——隔离 + 重建。
表根本没坏，用户回来发现自己的表被重建了。这是最毁数据的一步。

### 修法（复用 `xlsx_preserve` 的"按编号对行、认不出按真实文件"，三层）

1. **分流：被占用 ≠ 坏表**。`PermissionError`/`OSError`（锁定、权限）→ **一个字节都不动**，
   直接报"资源表被占用（可能 Excel 开着），请先关闭再扫描"。这层最便宜也最救命。
2. **坏表先抢救，再合并**（复用 P0-F 口径）：
   - 正常读失败 → **zip 级抢救**（新函数 `xlsx_preserve.salvage_rows`）：xlsx 就是 zip，
     直读 `xl/sharedStrings.xml` + `xl/worksheets/sheet*.xml`（含 `inlineStr` 分支——
     openpyxl 写的就是 `t="inlineStr"`，探针 §3 一开始漏了这个分支读出空值，补上后完整读回）。
     实测：`workbook.xml` 损坏 / 缺 `styles.xml` 这两种 openpyxl 拒载的形态，都能完整读回用户行。
   - 抢救出的行 → 喂给 `plan_kept_rows`（`xlsx_preserve.py:598`）同一条管线：
     **按编号对行、认不出按真实文件**；抢救行一律按"人的行"处理（没 ID 有内容 → 留），
     不覆盖扫描行。人的列/页/批注走既有 `restore_asset_marks`/`restore_extra_sheets`。
3. **zip 都打不开**（探针 §3"截断 zip"形态，0 行可救）→ 才退到现在的行为（隔离 + 重建），
   但回执必须点名"这 N 行没能保住、隔离副本在哪"——**隔离是兜底不是方案**。

### 风险点

- **最危险**：抢救读出的值与 openpyxl 读出的**类型不一致**（数字被读成字符串、None vs ''），
  合并时把扫描行冲掉。判据：抢救行**只进 keep 通道**（人的行），扫描行永远来自 `scan_assets`；
  构造期望全文断言新表 = 扫描行 + 抢救行并集，且扫描行的自动字段不许被抢救行覆盖。
- **第二危险**：把"锁定"误判成"损坏"（现状就是）→ 重建。判据：模拟 `load_workbook` 抛
  `PermissionError` 时，**文件字节零变化 + ok=False + 拒因含"占用"**。
- **判据（构造期望全文）**：照 `tools/_p0_audit_round6_asset_tables.py` 的 8 条矩阵重录一份
  "坏表版"：配音演员列+值 / future 手写行 / 无 ID 备注行 / 颜色+批注 / 分类说明页 /
  被占用不动 / zip 截断才隔离+点名 / 回执说清保住几行。

### 代价：中改（`salvage_rows` ~80 行 + 分流 ~20 行 + 判据 8 条）。**今天能完**
（`xlsx_preserve` 的 P0-E/P0-F 管线现成，是"接着写"不是"重新发明"）。
