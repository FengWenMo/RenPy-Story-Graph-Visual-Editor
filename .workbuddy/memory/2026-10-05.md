（上一轮 2086 → 这一轮 +51）；`tools/journey_check.py` 真实项目**全部步骤通过**。

## 边界①：`build` 的"必然失败"是门禁**假阳性**，不是产物坏了

这是这一轮最重要的发现 —— **昨天那个根因判断是错的**。

昨天的说法：「根因是全项目合并时 minigame 的多行 `python:` 块缩进被压平」。
实测（先把产物整块编译一遍）：

    产物里 7 个 `python:` 块，整块 dedent 后编译 → **一个都不错**

真正的原因在 `generation_guard._python_syntax_issues`：它把块体
**一行一行**丢给 `compile()`，于是

    positions = [                     → '[' was never closed
    ]                                 → unmatched ']'
    for i, digit in enumerate(x):     → expected an indented block

`cli.py build` 报的那 **10 条 PYTHON_SYNTAX_ERROR 逐条都是这一类**。

**教训（这一轮最值钱的一条）**：假阳性比漏报更贵。漏报只是"没拦住"，
而假阳性让一条命令对真实项目**永远失败**，并且理由指向一个**不存在**的问题 ——
人会照着假线索去改本来正确的代码。所以判据的**粒度**和判据本身一样重要。

修法：块体**整块**编译、`$` 语句**整条**编译（续行按括号/引号平衡分组，
复用 `beat_render._group_code_statements` —— 同一条判据只该有一处）。
块头形态同时扩到 `init python:` / `init N python:` / `python early:`。

变异验证：`tools/mut_python_syntax_guard.py` 把它打回逐行编译 →
`TestNoFalsePositives` **4 条红**，真错那几条仍绿。

## 边界②：命令行也能走增量（`--source`）

`table xlsx2rpy` / `compile` 加 `--source <这一章原来的 .rpy>`：
有源就走 patcher 增量合并，原文逐字节保留、只换改过的那几行。

**但"能增量"只做了一半。** 另一半是补丁对不上时**不许静默退回全量**：

    `--source X --out 新路径` → 目标是新的 → P0 那条手写护栏不适用
    → 静默全量 → 源里的 define / image 没了，而退出码是 0

真实项目 `pomodorro.rpy` 实测丢 **37 处顶层语句**。所以新增门禁
**`OPAQUE_LOST`**（`write_generation(source_text=…)`）：顶层语句没进产物就
**拒写**并列出丢了哪几行；`--force` 可越过（降级 warn，**仍然报出来**）。

`CompileResult.guard_warnings` 就是为这个加的：**"写成功了"与"有没有话要说"
必须分开承载** —— 只读 `guard_issues` 的话，`--force` 那一刀就成了静默覆盖
（又是 P0 的形态）。

实测（真实项目）：`ball_moving_game.rpy` 改 1 行、顶层语句全保住；
`whackamole.rpy` 改 2 行、13 处顶层语句全保住；`pomodorro.rpy` 拒写。

## 边界③：顶层 `init python:` 随表走，回到文件级

昨天只做到"知道它会丢"。这一轮做的是**保真**（用户给的二选一里更彻底的那个）：

    解析器：顶层 `python:` 块 → `PythonNode`（带块头原文）→
            `ParseResult.file_blocks`（`FileBlock`）—— 不再当"未建模块"跳过
    表    ：挂到**第一张拍**上，走隐藏列 `FileBlocks`
            （表只有"拍"一个单位，信息只能搭在拍上）；
            纯定义文件会**造一张空拍**来携带它
    渲染  ：`render_beats_to_rpy` 在**所有 label 之前**原样写回

实测 `whackamole.rpy`：原文 2 个块 / 56 行块体 → 产物 **2 个块 / 56 行，真丢 0**。

## P0-1：`_quote` 不转义控制字符 → 产物语法坏

## 续十二：交付前最后一扫 → 抓到「导出控制流」串位（真 bug）

### 怎么发现的

不是测出来的，是**看根目录**看出来的：一个叫 `False` 的 178 字节文件，
内容是控制流产物（`label a_control` / `b_control`）。
文件名是 `False` = 有个路径变量被 `str()` 了。顺藤摸到：

```
window_graph_ops.py:462   lambda: self.export_control_flow(wrapper=True)
window_graph_ops.py:464   lambda: self.export_control_flow(wrapper=False)
```

而签名是 `(self, target=None, wrapper=None)` —— `wrapper` 是**第二个位置
参数**，所以 `False` 落进了 `target` → `str(False)` 当路径写盘 →
紧接着 `Path(False).is_file()` 抛 TypeError（在 Qt 槽里直接炸）。
两个菜单项**全部**失效，其中一个还会先吐一个垃圾文件。

### 三层修法（每层理由不同）

1. **签名层**：`wrapper` 改 **只许关键字传**（`*`）。妙处是那两个 lambda
   **本来就是按关键字写的**，改完签名它们自动变对，一行都不用动；
   而且"串位"从此**写不出来**（位置传 → 解释器当场报错）。
2. **判据层**（`session_graph.export_control_flow`）：不是 `str`/`Path`
   直接 `ok=False`，**不碰磁盘**。这层与调用方怎么写无关。
   只做第 1 层的话，别的调用方照样能把 `None` 塞进来。
3. **测试层**：`tests/test_control_flow_target.py`（12 条）。
   `monkeypatch.chdir(tmp_path)` + 断言"目录里一个文件都不许多出来"——
   判据用"有没有副产物"，比"`ok` 是不是 False"更贴事故形态。

### 变异验证（两条都做了）

- 关掉判据层（`if False and ...`）→ **8 红**，且失败原因正是 `pathlib`
  的 TypeError = 原始事故形态；
- 把 `wrapper` 改回位置参数 → **1 红**（签名那条）。
  两层各自独立回归，没有"一条测试挡两层"的假象。

### 教训

- **垃圾文件是 bug 的指纹**：根目录多出莫名其妙的文件，先问"哪个路径变量
  被字符串化了"，比 anywhere 都快。这次从"看见文件"到"定位调用点"不到 5 分钟。
- **`wrapper` 这类"开关型参数"默认就该 keyword-only**：它和 `target`
  语义差太远，位置传错还**不报错**（bool 能 `str()`），是典型的静默通道。

"结构变了"有两种可能 —— 被压平（缺陷）或**人有意**给某个选项加了内容
（正常操作，在表里加一行 / 在卡片编辑器里插一张卡都会这样）。只比"源 vs 产物"
分不出这两者；而"假阳性比漏报更贵"，拦错一次人就会学会忽略这条警告。
等结构位进表（方案 B）判据变成"产物 vs 表里说的结构"，那时才能升 block。

**实测生效范围**（`tools/probe_structure_gate_cli.py`，真 CLI）：

## 实施 B 阶段一：结构位进表（`Nest` 列）+ 对拍

用户："继续做B阶段一"。目标只有一句：**把"这条拍属于哪个选项"写进表，
并证明它和老推断处处一致**；这一步**不改行为**。

### 做了什么

- `core/nest_path.py`（新）：DSL 唯一定义处（解析器写、渲染读；跨包不许
  import 私有名）。`join_nest` / `option_key` / `split_nest` / `body_chain`。
  路径形如 `if:1>menu:2>A>if:3`，选项体用**位置键** A/B（改文案不该算结构变）。
- 解析器 `_walk`：加 `nest_path` 参数 + **同 kind 文档序计数器**（整个 label
  共用），`menu:n` 段后跟选项位置键；菜单头在父块、选项行在菜单层。
  写进 `stmt.nest_path` —— **动态属性**，不是 dataclass 字段
  （Statement 的相等/哈希是内容指纹契约，结构位进去会改指纹）。
- `Beat.nest_path` + 隐藏列 `Nest`（`BEAT_FIELDS` 24 → 25）：
  `''` = 顶层（写 `-`），`None` = **不知道**（老表/手工行，写空）——
  两者必须分得开，否则对拍把"不知道"当"顶层"，老表天天假报。
  脏值（被清洗过）→ 按"不知道"处理（拿残缺路径指认结构 = 假阳性）。
- `beat_render.nest_placement_conflicts`：对拍器。与渲染**同源**
  （`split_beat_units` + `_menu_segments`，嵌套菜单递归、计数器继续数），
  逐拍比 `body_chain(nest_path)` vs 老推断实际摆的链；只对结构位齐全的
  label 判。
- 通道：`NEST_CONFLICT`（warn）→ `CompileResult.guard_warnings` → CLI summary；
  编辑器接进 `export` 的 `note` + `structure_conflicts` 计数。
- `tools/render_hash.py`：把两条路的产物逐字节哈希 —— 用来证明"零行为变化"。
