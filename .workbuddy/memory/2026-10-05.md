## 边界①：`build` 的"必然失败"是门禁**假阳性**，不是产物坏了

这是这一轮最重要的发现 —— **昨天那个根因判断是错的**。

昨天的说法：「根因是全项目合并时 minigame 的多行 `python:` 块缩进被压平」。
实测（先把产物整块编译一遍）：

    产物里 7 个 `python:` 块，整块 dedent 后编译 → **一个都不错**

真正的原因在 `generation_guard._python_syntax_issues`：它把块体
**一行一行**丢给 `compile()`，于是

    positions = [                     → '[' was never closed
    ]                                 → unmatched ']'
    for i, digit in enumerate(x):     → expected an indented block

`cli.py build` 报的那 **10 条 PYTHON_SYNTAX_ERROR 逐条都是这一类**。

**教训（这一轮最值钱的一条）**：假阳性比漏报更贵。漏报只是"没拦住"，
而假阳性让一条命令对真实项目**永远失败**，并且理由指向一个**不存在**的问题 ——
人会照着假线索去改本来正确的代码。所以判据的**粒度**和判据本身一样重要。

修法：块体**整块**编译、`$` 语句**整条**编译（续行按括号/引号平衡分组，
复用 `beat_render._group_code_statements` —— 同一条判据只该有一处）。
块头形态同时扩到 `init python:` / `init N python:` / `python early:`。

变异验证：`tools/mut_python_syntax_guard.py` 把它打回逐行编译 →
`TestNoFalsePositives` **4 条红**，真错那几条仍绿。

## 边界②：命令行也能走增量（`--source`）

`table xlsx2rpy` / `compile` 加 `--source <这一章原来的 .rpy>`：
有源就走 patcher 增量合并，原文逐字节保留、只换改过的那几行。

**但"能增量"只做了一半。** 另一半是补丁对不上时**不许静默退回全量**：

    `--source X --out 新路径` → 目标是新的 → P0 那条手写护栏不适用
    → 静默全量 → 源里的 define / image 没了，而退出码是 0

真实项目 `pomodorro.rpy` 实测丢 **37 处顶层语句**。所以新增门禁
**`OPAQUE_LOST`**（`write_generation(source_text=…)`）：顶层语句没进产物就
**拒写**并列出丢了哪几行；`--force` 可越过（降级 warn，**仍然报出来**）。

`CompileResult.guard_warnings` 就是为这个加的：**"写成功了"与"有没有话要说"
必须分开承载** —— 只读 `guard_issues` 的话，`--force` 那一刀就成了静默覆盖
（又是 P0 的形态）。

实测（真实项目）：`ball_moving_game.rpy` 改 1 行、顶层语句全保住；
`whackamole.rpy` 改 2 行、13 处顶层语句全保住；`pomodorro.rpy` 拒写。

## 边界③：顶层 `init python:` 随表走，回到文件级

昨天只做到"知道它会丢"。这一轮做的是**保真**（用户给的二选一里更彻底的那个）：

    解析器：顶层 `python:` 块 → `PythonNode`（带块头原文）→
            `ParseResult.file_blocks`（`FileBlock`）—— 不再当"未建模块"跳过
    表    ：挂到**第一张拍**上，走隐藏列 `FileBlocks`
            （表只有"拍"一个单位，信息只能搭在拍上）；
            纯定义文件会**造一张空拍**来携带它
    渲染  ：`render_beats_to_rpy` 在**所有 label 之前**原样写回

实测 `whackamole.rpy`：原文 2 个块 / 56 行块体 → 产物 **2 个块 / 56 行，真丢 0**。

## 续十二：交付前最后一扫 → 抓到「导出控制流」串位（真 bug）

### 怎么发现的

不是测出来的，是**看根目录**看出来的：一个叫 `False` 的 178 字节文件，
内容是控制流产物（`label a_control` / `b_control`）。
文件名是 `False` = 有个路径变量被 `str()` 了。顺藤摸到：

```
window_graph_ops.py:462   lambda: self.export_control_flow(wrapper=True)
window_graph_ops.py:464   lambda: self.export_control_flow(wrapper=False)
```

而签名是 `(self, target=None, wrapper=None)` —— `wrapper` 是**第二个位置
参数**，所以 `False` 落进了 `target` → `str(False)` 当路径写盘 →
紧接着 `Path(False).is_file()` 抛 TypeError（在 Qt 槽里直接炸）。
两个菜单项**全部**失效，其中一个还会先吐一个垃圾文件。

### 三层修法（每层理由不同）

1. **签名层**：`wrapper` 改 **只许关键字传**（`*`）。妙处是那两个 lambda
   **本来就是按关键字写的**，改完签名它们自动变对，一行都不用动；
   而且"串位"从此**写不出来**（位置传 → 解释器当场报错）。
2. **判据层**（`session_graph.export_control_flow`）：不是 `str`/`Path`
   直接 `ok=False`，**不碰磁盘**。这层与调用方怎么写无关。
   只做第 1 层的话，别的调用方照样能把 `None` 塞进来。
3. **测试层**：`tests/test_control_flow_target.py`（12 条）。
   `monkeypatch.chdir(tmp_path)` + 断言"目录里一个文件都不许多出来"——
   判据用"有没有副产物"，比"`ok` 是不是 False"更贴事故形态。

### 变异验证（两条都做了）

- 关掉判据层（`if False and ...`）→ **8 红**，且失败原因正是 `pathlib`
  的 TypeError = 原始事故形态；
- 把 `wrapper` 改回位置参数 → **1 红**（签名那条）。
  两层各自独立回归，没有"一条测试挡两层"的假象。

### 教训

- **垃圾文件是 bug 的指纹**：根目录多出莫名其妙的文件，先问"哪个路径变量
  被字符串化了"，比 anywhere 都快。这次从"看见文件"到"定位调用点"不到 5 分钟。
- **`wrapper` 这类"开关型参数"默认就该 keyword-only**：它和 `target`
  语义差太远，位置传错还**不报错**（bool 能 `str()`），是典型的静默通道。

1. **`_inline_note` 里加 `src_first == src_last`** —— 行号是运行期元数据、

   采集时定死）。
2. **选项行的注释不是独立 AST 节点**：`menu:` 里的选项行是 `MenuNode` 的一部分，
   `cur_inline` 拿到的是 `menu:` 那一行的。要在 `_parse_menu` 里把注释挂到

3. **`render_beat_to_rpy` 有两个 return**：条件拍那条（`if cond:` + 本体）

    show lan agreeable …        show lan agreeable …       show lan_agreeable

根因：`beat_render._emit_image_name(name, resolver)` —— **没给 resolver
时按旧行为"空格换下划线"**（代码注释自己写着"没给 resolver 时保持旧行为，
兼容单测与无资源表场景"）。真实工程 `definitions.rpy:111` 定义的是
`image bg bg1_1`（tag `bg` + 属性），`grep bg_bg1_1` 全工程 **0 命中**。
真实项目 **7 个文件**命中这一条。
它不算"未知 bug"（是今天有意写的降级），但后果是产物里出现不存在的图像名
—— 需要用户拍：无 resolver 时该"原样保留"还是"改写"。

### 两处"待定性"（可能是我判据太严）

1. `if:<n>` **文档序会漂移**（`mini_game1.rpy` 少 `if:3` 多 `if:3/4`、
   `mini_game_dfinder.rpy` 多 `if:3`）：`if` 编号是"label 内文档序"，
   `elif/else` 展开成兄弟后编号跟着变 —— 路径因此不是稳定标识。
   要不要把"分支序"也编进路径（`if:1#1`）值得想一下。
2. `empty_option_body` / `credits_screen.rpy`：空选项体往返后**多一张拍**
   （`pass` 占位拍进了表）。无害但不对称。

### 我自己的判据错了三次（照例记下来）

1. 正则判"未闭合字符串"把**已闭合**的 `"选项":  # 注释` 也报了 →
   13 个用例 10 个假红，差点当成"嵌套全坏"。改用第一轮已验证的
   "去转义后数引号奇偶"口径。
2. 注释标签**跨 label 重复**（同一份 body 在 5 个 label 里复用）→
   "翻倍"判据自己骗自己。
3. `\x00menu` 占位符让"逐字节相等"报错，但那是**两条路对占位符的处理不同**
   导致的（Excel 会洗控制字符）—— 现象真、归因要更小心。

## 用户实测报到：图像名被"降级"改坏（hell_nest_inline 打出三个大 bug）

用户给了 `tools/hell_nest_inline.py`（第一轮 hell 的续作，专打 `Nest` × `Inline`

### 先分清楚是谁的锅

把 `hell_nest_inline.py` 拷进 `876bcc2`（B 阶段一）的 worktree 跑，
**失败用例集与今天几乎一样**（只有 `elif_chain_in_option_body` 现在修好了）——
所以嵌套菜单压平、条件翻倍、对拍器冲突这些都是**老 bug**，不是这一轮引入的。
（`c4da5f5` 之前跑不了这个脚本：`nest_placement_conflicts` 是 B 阶段一才有的。）

### 修掉的三条（都属于"降级其实是破坏"）

1. **图像名**：`resolver is None` 时改成**原样返回**（从前 `replace(' ','_')`）。
   真实项目 `image bg bg1_1`（tag + attribute）全工程没有 `bg_bg1_1` →
   `scene bg bg1_1` 过表变 `scene bg_bg1_1`，运行时找不到图（7 文件 17 处）；

3. **原生尾段重复挂转场**：作者写在 `Stage` 列的那一行会逐字输出一次，
   `beat.with_` 又按"有背景就挂背景"挂一次 → 同拍两条转场。判据用原文 `beat.stage`。

结果：`scene_show_tag_attr` 与**真实项目 40 个文件**由 FAIL 转 ok
（那 17 处就是这三条）；5 条钉着旧"下划线"契约的测试同步改成正向

### 还没修的（诚实记着）

## 下一轮：嵌套菜单**真的**能渲染了（用户："我要的不只是对拍，而是实际生成的无限嵌套可行"）

### 三个缺陷（都在同一条路上，`tests/` 里一条嵌套用例都没有 → 一直没暴露）

1. `_menu_segments_by_path` 第二趟"凡 `menu_option` 一律跳过" → 嵌套菜单的
   **选项行被静默丢掉**（我 B 阶段二引入的）；
2. 选项体把"非记账条件"的拍一律**扁平渲染**（`_indent_beat_lines`）→ 嵌套菜单
   的头/选项行永远走不到递归的 `render_menu_block` → 渲染成一句台词；
3. `_nest_plan` 用"数第几张 `KIND_MENU`"编号，而它会被递归调用在**子列表**上
   （选项体那一段）→ 局部次序与 label 文档序不一致 → 切组只切到菜单头一拍
   （`probe_nested_render.py` 的调用轨迹：`render_menu_block(indent=8 拍数=1)`）。

### 修法

- 菜单编号改成**从块路径推**（`_menu_number_from_path`）；
- 选项体只有一条渲染路：剥掉记账条件 → **整段**交给递归渲染器；
- 缩进口径统一：选项体自己按 `inner` 补前缀，菜单块按相对形式渲染 →
  菜单头/选项/选项体 = `inner`/`inner+4`/`inner+8`，**嵌套任意深**；
- 对拍器**按 label 作用域**跳过有嵌套的那一份（老推断只有 1 bit，遇到嵌套
  **整份**摆错，连嵌套之后的拍都算进假选项）—— 假阳性比漏报更贵。

### 验收

- `tests/test_nested_menu_render.py` **16 条**：两层逐字比产物、两条路逐字节一致、
  **深 2~6 层**参数化（每层深 8 格）、深 3/5 是不动点、与 `if` 交错、
  菜单整块挂 `if` 时在菜单外面；
- `tools/hell_nest_inline.py`：`minimal_nested_menu` / `menu_in_menu_in_menu`
  转 ok（14 → 11 失败）；
- 全量 **2406 passed / 2 skipped**；
- **真实项目产物逐字节不变**（`212a48c5b565` / `f8f75139b8e4`）—— 没有附带影响。

### 还没修（诚实记着）

- **条件翻倍**：产物里已展平的条件再解析会被再累加一次外层条件
  （`if (a) and (c):` → `if (a) and ((a) and (c)):`），每轮更长。
  N2 不动点抓到；语义等价但违反不动点。
- `empty_option_body`：空体补 `pass` 后多一条 `menu:1>A` 路径。
- hell 真实项目 6 处：5 处像 harness 过严（`if:n` 计数没算 elif 展平、补 pass），
  1 处 `chapter1_2.rpy` 的 N3 像真差异，待查。

新探针：`tools/probe_nested_render.py`（记录每次 `render_menu_block` 的
缩进/拍数/分段 —— 三个缺陷全靠它的调用轨迹定位）。
