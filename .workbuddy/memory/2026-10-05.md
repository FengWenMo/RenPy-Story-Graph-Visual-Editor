## 边界①：`build` 的"必然失败"是门禁**假阳性**，不是产物坏了

这是这一轮最重要的发现 —— **昨天那个根因判断是错的**。

昨天的说法：「根因是全项目合并时 minigame 的多行 `python:` 块缩进被压平」。
实测（先把产物整块编译一遍）：

    产物里 7 个 `python:` 块，整块 dedent 后编译 → **一个都不错**

真正的原因在 `generation_guard._python_syntax_issues`：它把块体
**一行一行**丢给 `compile()`，于是

    positions = [                     → '[' was never closed
    ]                                 → unmatched ']'
    for i, digit in enumerate(x):     → expected an indented block

`cli.py build` 报的那 **10 条 PYTHON_SYNTAX_ERROR 逐条都是这一类**。

**教训（这一轮最值钱的一条）**：假阳性比漏报更贵。漏报只是"没拦住"，
而假阳性让一条命令对真实项目**永远失败**，并且理由指向一个**不存在**的问题 ——
人会照着假线索去改本来正确的代码。所以判据的**粒度**和判据本身一样重要。

修法：块体**整块**编译、`$` 语句**整条**编译（续行按括号/引号平衡分组，
复用 `beat_render._group_code_statements` —— 同一条判据只该有一处）。
块头形态同时扩到 `init python:` / `init N python:` / `python early:`。

变异验证：`tools/mut_python_syntax_guard.py` 把它打回逐行编译 →
`TestNoFalsePositives` **4 条红**，真错那几条仍绿。

## 边界②：命令行也能走增量（`--source`）

`table xlsx2rpy` / `compile` 加 `--source <这一章原来的 .rpy>`：
有源就走 patcher 增量合并，原文逐字节保留、只换改过的那几行。

**但"能增量"只做了一半。** 另一半是补丁对不上时**不许静默退回全量**：

    `--source X --out 新路径` → 目标是新的 → P0 那条手写护栏不适用
    → 静默全量 → 源里的 define / image 没了，而退出码是 0

真实项目 `pomodorro.rpy` 实测丢 **37 处顶层语句**。所以新增门禁
**`OPAQUE_LOST`**（`write_generation(source_text=…)`）：顶层语句没进产物就
**拒写**并列出丢了哪几行；`--force` 可越过（降级 warn，**仍然报出来**）。

`CompileResult.guard_warnings` 就是为这个加的：**"写成功了"与"有没有话要说"
必须分开承载** —— 只读 `guard_issues` 的话，`--force` 那一刀就成了静默覆盖
（又是 P0 的形态）。

实测（真实项目）：`ball_moving_game.rpy` 改 1 行、顶层语句全保住；
`whackamole.rpy` 改 2 行、13 处顶层语句全保住；`pomodorro.rpy` 拒写。

## 边界③：顶层 `init python:` 随表走，回到文件级

昨天只做到"知道它会丢"。这一轮做的是**保真**（用户给的二选一里更彻底的那个）：

    解析器：顶层 `python:` 块 → `PythonNode`（带块头原文）→
            `ParseResult.file_blocks`（`FileBlock`）—— 不再当"未建模块"跳过
    表    ：挂到**第一张拍**上，走隐藏列 `FileBlocks`
            （表只有"拍"一个单位，信息只能搭在拍上）；
            纯定义文件会**造一张空拍**来携带它
    渲染  ：`render_beats_to_rpy` 在**所有 label 之前**原样写回

实测 `whackamole.rpy`：原文 2 个块 / 56 行块体 → 产物 **2 个块 / 56 行，真丢 0**。

## 续十二：交付前最后一扫 → 抓到「导出控制流」串位（真 bug）

### 怎么发现的

不是测出来的，是**看根目录**看出来的：一个叫 `False` 的 178 字节文件，
内容是控制流产物（`label a_control` / `b_control`）。
文件名是 `False` = 有个路径变量被 `str()` 了。顺藤摸到：

```
window_graph_ops.py:462   lambda: self.export_control_flow(wrapper=True)
window_graph_ops.py:464   lambda: self.export_control_flow(wrapper=False)
```

而签名是 `(self, target=None, wrapper=None)` —— `wrapper` 是**第二个位置
参数**，所以 `False` 落进了 `target` → `str(False)` 当路径写盘 →
紧接着 `Path(False).is_file()` 抛 TypeError（在 Qt 槽里直接炸）。
两个菜单项**全部**失效，其中一个还会先吐一个垃圾文件。

### 三层修法（每层理由不同）

1. **签名层**：`wrapper` 改 **只许关键字传**（`*`）。妙处是那两个 lambda
   **本来就是按关键字写的**，改完签名它们自动变对，一行都不用动；
   而且"串位"从此**写不出来**（位置传 → 解释器当场报错）。
2. **判据层**（`session_graph.export_control_flow`）：不是 `str`/`Path`
   直接 `ok=False`，**不碰磁盘**。这层与调用方怎么写无关。
   只做第 1 层的话，别的调用方照样能把 `None` 塞进来。
3. **测试层**：`tests/test_control_flow_target.py`（12 条）。
   `monkeypatch.chdir(tmp_path)` + 断言"目录里一个文件都不许多出来"——
   判据用"有没有副产物"，比"`ok` 是不是 False"更贴事故形态。

### 变异验证（两条都做了）

- 关掉判据层（`if False and ...`）→ **8 红**，且失败原因正是 `pathlib`
  的 TypeError = 原始事故形态；
- 把 `wrapper` 改回位置参数 → **1 红**（签名那条）。
  两层各自独立回归，没有"一条测试挡两层"的假象。

### 教训

- **垃圾文件是 bug 的指纹**：根目录多出莫名其妙的文件，先问"哪个路径变量
  被字符串化了"，比 anywhere 都快。这次从"看见文件"到"定位调用点"不到 5 分钟。
- **`wrapper` 这类"开关型参数"默认就该 keyword-only**：它和 `target`
  语义差太远，位置传错还**不报错**（bool 能 `str()`），是典型的静默通道。

   `SINGLE_LINE_BEAT_FIELDS`，用 `g` 读、**清洗过就丢掉**并留痕）。

1. **`_inline_note` 里加 `src_first == src_last`** —— 行号是运行期元数据、
   **不进表**，于是表那条路全丢。判据改成"列里有值 = 那一行是单行"（由词法器
   采集时定死）。
2. **选项行的注释不是独立 AST 节点**：`menu:` 里的选项行是 `MenuNode` 的一部分，
   `cur_inline` 拿到的是 `menu:` 那一行的。要在 `_parse_menu` 里把注释挂到
   `MenuOptionNode` 上、`add_stmt(...)` 多带一个 `inline=` 参数。
3. **`render_beat_to_rpy` 有两个 return**：条件拍那条（`if cond:` + 本体）

- 渲染出的产物再解析一遍**不翻倍**。

  **整份**摆错，连嵌套之后的拍都算进假选项）—— 假阳性比漏报更贵。

### 续：条件翻倍修掉（N2 不动点）

病根：解析器把外层条件 `_combine` 进里层每一拍，而外层 `if:` 往往**已经由结构
写出来了**（菜单块条件写在 `menu:` 外面）→ 里层再写 `(flag0) and (flag2)`，
产物再解析被**再累加** → 每轮更长。

修法：`strip_condition_context(cond, context)` 按**合取项**减（两边脱包裹括号
比字面量）；减不干净原样返回（不许漏合取项）；只剩一项时脱括号以**收敛**
（`_combine` 每轮再包一层，不脱就永远多一层括号）。

实测：`if flag0:` → `menu:` → 选项体 `if flag2:` 现在产出 `if flag0:` +
`if flag2:`，R1 == R2 逐字节；**真实项目产物不变**（212a48c5b565 / f8f75139b8e4）
→ 零附带影响；hell 失败 11 → 8；新增用例 3 条（含 `strip_condition_context`
的保守性：`a and c` 上下文下 `(a) and (b)` → `b`）。

### ① 加立绘 → "导出后没有 show"：摊开是**三个**独立缺陷

**(a) 界面 `NameError`（用户看到的"什么都没发生"）**

`window_export.py` 里 `_overwritable` 是个**未定义的名字**（`NameError`）——
P3-14 那次 mixin 拆分把 `export_script` 搬进本模块，而那个自由函数留在
`main_window.py`。触发条件恰好是"导出被拦下"那条路：

```python
if not res.get('ok') and _overwritable(res):     # ← 走到这里就 NameError
```

症状是最糟的那种：**点了导出什么都不发生**（没有对话框、没有文件、状态栏也不说话）。
为什么现有守卫都没抓住：`REQUIRES` 契约只静态扫 **`self.*`**（自由函数不在里面），
单测又只 `from main_window import _overwritable` 直接调那个函数，**从没走过这一行**。

→ 函数搬到唯一使用者 `window_export.py`（公共名 `overwritable`），
`main_window` 以旧名转出；并补一张**静态网** `tests/test_no_undefined_names.py`
（标准库 `symtable`：模块里引用了、本模块看不到的全局名）。它顺线又抓到
`main_window._build_graph_page` 里的 `left` —— 那个 `NameError` 被
`except Exception` 吞掉，"右栏最窄 300 / 最宽 420"两条约束**从来没生效过**
（左边那一栏叫 `mid`）。扫描器自己也有变异验证（否则"永远绿的网"比没网更危险）。

**(b) 结构补空拍被判成"新卡片" → 整份补丁作废**

```

```

```renpy

    return
```

解析器会给它补一张**什么都没有的拍**；它没有源行号 → `_insert_ids_of` 当成
"编辑器里新插的卡"；又渲染不出任何行 → `_insert_points_for` 记 `failed=1`
→ 整份补丁作废。于是**任何带空 label 的章节里，"改一句话 / 加一张立绘"都导不进去**，
而那个文件里根本没有新卡片。

→ ① 把"渲染不出行"的新拍从 `insert_ids` 摘掉；② 空拍不再计 `failed`；
③ **对位率的分母**（`PatchResult.total_beats`）也排除它们 —— 否则空 label 一多，
13 拍被压到 92%、三张就掉出门槛，"只改一句台词"莫名其妙退回全量。

**(c) 卡片往返把作者的图像名改掉（"立绘没出现"的另一半）**

```
show ling base_arms_akimbo sigh        ← 作者写的
→ 提交一次（翻页/保存/导出都会先提交）
show ling base_arms_akimbo_sigh base_arms_akimbo_sigh
```

`Symbols.attr_for` 的**子串兜底档**：项目里那张图登记成 `base_arms_akimbo_sigh`
（一条属性），于是 `base_arms_akimbo` → 兜底命中整条、`sigh` → 也命中同一条 ——
**两个词合并成一条，图像名被改写，游戏里就找不到这张立绘**。
原测试喂的是 `symbols=None`（那条路不做归一）→ 一直没暴露。

修法两版，第一版被 golden 快照当场打脸（值得记）：
- 第一版："一组里有一个词被吃 → **整组原样**" → 把**中文词**留进了 `show`
  （`ling base_arms_akimbo 无语@i11`）—— 那是"中文漏进脚本"，比原缺陷还糟；
- 第二版：撞车时退回**词表原话**（`无语 → sigh`）→ 正好是作者写的那一份
  （`ling base_arms_akimbo sigh@i11`）。判据落**在词上**，而且相信词表
  （`attr_for` 文档里就写着"词表是权威档"，但实现只在"映射恰好是完整属性"时才权威）。

### ⑤ 第三批（两张截图）：保存了、可「当前舞台」和演出预览没变

## 续二十五：第六批（"图片加载还是慢 / 加载不完全" + 底色开关）

**先量再修**（这次全靠探针，没有靠猜）：

```

%TEMP%\renpy_sge_thumbs 里 140886 个 PNG（平铺、从不过期）
冷解码 3856×2176 PNG = 384~434 ms；Qt 整图 696ms、setScaledSize 792ms（更慢！）

```

**四条真因**（全部实测确认）：

1. **74 条永远解析不到文件**：Path 写作 `sr_general/game/gui/…`（多一层项目
   目录名），而 `asset_preview_path` 只试 `project_root / Path` 一个基准 →
   `None` → 那 74 格永远只有文字、也不说为什么（看着就像"还在加载"）。
   改走 `resolve_thumb_source`（唯一真源）→ **74 → 0**。
2. **磁盘缓存是 14 万个文件的平目录**：键含目标尺寸 → 每个尺寸一份；
   从不过期、从不清理。每次 `is_file()` 都在巨大索引里翻。
   → 两级分片 + `prune_thumb_cache`（扫描预算 2s、每次最多删 3000、
   **一进程只排一次**）。实测平目录扫描 188ms → 分片查找 **1.46ms**。
3. **内存缓存按"张数"限 64**：候选 2816 张、卡片缩略图 140 KB/张 →
   滚两屏就把前面的挤掉，滚回去再解一次（434ms）。
   → **字节预算 64 MB**（小缩略图 31 KB/张，能装两千张）。
4. **只加载可见项 + 没有进度**：滚到哪儿都得等，而且"图还在解 / 这张根本
   没有 / 还要等多久"全靠猜。→ 后台补齐（低优先级 + 预算 600 条刹车）、
   提示条写"已加载 N / 共 M / 没有图片文件 K / 后台补齐中"、真的没图的写
   "（没有图片文件）"、没图的不入队解码。

**"更快的算法"联网/实测结论**：PNG **没有**解码级降采样（libpng 必须
inflate 全部 IDAT 行；Adam7 隔行可以只读第一趟，但 Qt/PIL 都不暴露）——
所以真正的赢面不是"更聪明的缩放"，而是：

  · **绝不重复解码**（缓存 + 字节预算）；
  · **并行**（QThreadPool，限流到核数）；
  · **只解看得见的**（视口优先 + 后台补齐）；
  · 33 MP 图上用 `reduce()`（BOX 均值）代替 BICUBIC 的一次卷积。

⚠ Qt 的 `setScaledSize` 实测**更慢**（792ms vs PIL 434ms）→ 主路继续用 PIL，
Qt 只当没装 Pillow 时的退路（这一点也写进了注释，免得下次又有人"优化"回去）。

**底色开关**：选择器右上角 ◐（浅/深），`QSettings` 记住；深底要同时翻
**文字色与选中色**（不然深底深字只是把问题换个方向）；卡片缩略图读同一个
开关。⚠ `QSettings.setPath(IniFormat)` 在 Windows 上**不一定生效**（实测仍
落注册表）→ 偏好存储做成可注入的 `settings_factory()`，测试换临时 ini。

4. `ensure_asset_tables` 读得动时**顺手把注册表带回来**（省一次 2890 行解析）。
