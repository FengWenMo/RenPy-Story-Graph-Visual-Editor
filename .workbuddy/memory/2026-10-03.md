## 6. 我上一轮说错了：.rpy 不能是投影（用户反驳，他是对的）

我说".rpy 不再是真源而是投影"——**错且危险**。用户三点：① .rpy 是源代码、真正跑
起来的东西；② 成了投影导出有误怎么办（还要链接小游戏作品）；③ 图只管自定义跳转，
不管本来就有的变量。

**实测比他说的还严重**（`tools/probe_opaque.py`）：全量从 Excel 重建会抹掉整层
"第三类东西"——`default score = 0` / `define e = Character("E")` / `init python:` /
`transform my_tf:` **全部丢失**（它们根本不进 Beats）。V3~V7 倒是保真。

**更糟：这条路径没有护栏。** `generation_guard.write_generation` **不检查目标已存在**，
实测把已有 .rpy 覆盖成 `label start: pass`。CLI 两条路径都中招
（`cli.py:115` xlsx2rpy、`cli.py:290` compile）→ **`compile` 输出到已有 .rpy = 静默毁文件**。

**修正后的模型（取代上一轮的三源 merge）**：

```
.rpy = 唯一真源（运行时输入）
Graph = 只读视图 + 只 patch 结构行；Excel = 只读视图 + 只 patch 演出行
第三类（default/define/init python/transform/screen/变量）= 谁都不碰，原样保留
patcher = 唯一写入通道
```
不是"多源→生成"，而是"**单源 → 多视图 → 受控 patch**"。
→ **patcher 不是优化，是正确性的基石**；全量生成只许用于新建文件。

## 10. 用户的根本矛盾 + 解法（本对话最重要产出）

> Excel 只负责**一章之中句子层级**编辑，不负责还原代码；逻辑判断靠 **Graph**；
> **可是 Excel 又要增量导出为 .rpy** —— 很矛盾。

**这不是设计错误，是 ownership 没有显式化**；物证：**两套 .rpy 生成器并存**
（`pipeline/renpy_exporter.export_to_renpy(graph)` + `story/beat_render.render_beats_to_rpy(beats)`），
各自偷偷承担一半职责，但导出路径只有"从 beats 渲染"一条，于是 Excel 被迫吃下整个
文件（含逻辑）。

**解法：所有权矩阵 + merge 导出**

| 层 | 真源 | .rpy 对应 |
|---|---|---|
| label 拓扑 / 跳转 | Graph | `label:` `jump` `call` |
| 分支条件 | Graph | `if` `elif` `else` `menu:` |
| 句子级演出 | Excel | `say` `show` `scene` `play` `with` |
| 原生代码 | CodeBlock 保真 | `python:` 手写行 |

导出改成 `merge(Graph 骨架, Excel 内容, CodeBlock)`，而非 `render(beats)`。
**连接键已有：LineId**。Excel 表不用还原 if 语法，只需 BranchId 列锚到 Graph 分支
节点；patcher 配对键从"内容相似"升级为 `line_id`。
分步：① 两生成器各司其职（**不改数据结构**）② line_id 接入 patcher
③ `Condition` 列降级为只读投影（改逻辑去 Graph，双向同步会引入冲突治理，先别做）。
代价：编剧改分支必须开 Graph——**有意的强制分工**，但 UI 要给入口
（Excel 里点一下跳到 Graph 对应节点）。
