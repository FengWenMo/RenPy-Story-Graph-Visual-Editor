## 二、金标定性：**是"该刷新"（陈旧金标），不是真回归** —— 证据链

用户点名要"定标准是刷新还是真回归"。方法：**分离"代码变了"与"真机项目数据变了"**。

### 做法（可复现）
把工具仓的历史提交抽成独立源码树，用它跑**当前**真机项目，与金标比：
`git archive <rev> storygraph tools | tar -x -C .pip-tmp/wt_<rev>`，再跑该树自带的
`tools/probe_*_fingerprint.py --check <golden>`。

### 关键实验（每一条都是"同输入 → 同结果"的对照）
| 实验 | 结果 |
|---|---|
| `HEAD`(10-13) vs **当前工作区** 逐项对账（describe + hydrate 全量快照） | **完全相同**（describe 0 差、hydrate 0 文件变）→ 10-14 未提交改动与此无关 |
| 用**创建金标那次提交**（describe=`52d3ec9`、hydrate=`19933aa`）跑当前项目 | **照样 mismatch，且差异一模一样**（`call 12→18` / 同 2 文件）→ 差异只来自**项目数据** |
| 真机项目 git：`git diff 141eab8(10-07) HEAD --stat` + `status --porcelain` | 项目 10-12 提交改过 `music.rpy`、加过 `gui/dutui/Frame 13/Play1.png`；工作区未提交改了 `settings_config.rpy`、新增 `game/asset_tables/`、新增未跟踪 `game/minigame/mini_game_flipcard.rpy` |
| 逐个"变了的文件"对号 | `mini_game_flipcard.rpy`=**新增文件**（金标 53 文件 → 现 54；它正好 **6 条 `call screen`** → 精确解释 `call 12→18`）；`music.rpy`=项目提交改过；`settings_config.rpy`=未提交改过；`scan` 多出的那张图 = `Play1` = 项目提交里新增的 png |
| `script.rpy`（源文件没改却变了）**决定性** | 把它 **21 个历史版本**逐个解析比哈希 → 金标哈希 `d0c11f66…` 精确对应 **`c430138`(10-02)** 那版内容，当前是 `141eab8`(10-07) → **金标捕的是一份更早/不一致的项目内容快照** |

### 结论与动作
**陈旧金标（金标本身在漂）→ 刷新。** 已刷新 6 条：
`golden_parse / render / hydrate / describe / patch / scan`（原值备份在 `.pip-tmp/golden_bak/`，
可 `git checkout tests/golden_*.txt` 回滚）。刷新后金标族 **18 passed / 0 failed**。
`validate` / `sync_pipeline` 两条本来就没变（**没变的就没变**，这本身是"不是工具回归"的旁证）。

⚠ **由此暴露的 P1 结构性问题**：这些金标把期望值钉在**一份活的、会随时被编辑的真机项目**上
（而且金标生成时的项目状态**不对应任何一个提交** —— script.rpy 是 10-02 的内容、

## 三、`assign_tokens`：把三套并行实现收成一份（对应路线图 D5）

### 改了什么
- `authoring/pattern.py` 新增 **`assign_tokens(tokens, slots, *, groups=None, policy)`**
  ——「一行词 → 每格占哪几个词」的**唯一实现**；
- `match_line` 改为它的**薄转发**（只多做三件事：切词、按格子下标对齐 cells、把失败说成人话）；
- `story/spec_args._claim` 改为薄转发（`policy='candidates'`）；`slot_value_map`
  删掉自己那份拷贝，改成"按格子取词 → 去引号 → 挂列名/原文键"。

### 分配规则（**甲 = 书写顺序**）
`keyword` 逐字相等（否则 `bad_kw`）／`optional` 出现吃两词／`multi` **长的先试、
取第一个"让后面每格也都还能吃到词"的长度**（`_can_allocate` 可行性判定；一个都不吃也合法）／
`choice` 勾了 `limit` 只认候选（否则 `rejected`）／其余吃一个。
**失败信号四类**：`bad_kw` / `rejected` / `unfilled`（该吃词却没词）/ 没人认领的词。

### 两个**明写**的分岔（不再是"两套代码各写一遍"）
1. 枚举格的**候选跳过**：试切 `order-first`、读值 `candidates`（写在 `pattern.POLICIES`）；
2. **引号**只在读值侧去掉（试切报的是切出来的原文）。
新增判据 `tests/test_assign_tokens_single_source.py` 把这两处钉住（5 条，全绿）。

### 顺带修好的老问题
多值格"该吃几个"以前两侧不一致（试切回溯让位、读值贪心吃满）→ 现在都用 `_can_allocate`
的可行性判定，读值侧也跟着变成甲：`show lan happy sad` 读成 服装=happy、神态=sad
（以前读值会把 `happy sad` 全给服装、神态空着）。

## 四、收掉第 2 条重复：`show`/`scene` 子句关键字 **5 份 → 1 份真源**

### 收在哪
`core/vocabulary.py` —— 它自己的模块 docstring 就写着"**加新词表请加在这里，
不要就地再写一份**"，而且已经立了"公共内核只写一份、各处差异用**内核 ± 显式增减**
表达"的模式（见该文件「语句头词表」那一节）。新增：

- `SHOW_CLAUSE_KEYWORDS = {'at','as','with','behind','onlayer','zorder'}`
  （依据官方语法 `show_statement -> "show" "expression" simple_expression
  ( "as" name )? ( "onlayer" name )? ( "at" … )? ( "behind" … )? ( "with" … )?`
  外加同族 `zorder`；docs 明说 scene 取同一批 properties）
- `SHOW_INTRO_KEYWORDS = {'expression','screen','layer'}`
  （**引入型**：替换图像名，后面跟的不是图名）

### 各站现状（改写后**生效集合逐字未变**，除了一处是**补漏**）
| 站点 | 从前 | 现在（写成什么） |
|---|---|---|
| `parsing/renpy_parser._SHOW_KEYWORDS` | 规范集 | `= SHOW_CLAUSE_KEYWORDS` |
| `parsing/renpy_parser._SCENE_KEYWORDS` | `{at,with,onlayer}` | `= SHOW_CLAUSE_KEYWORDS - {as,behind,zorder}`（**刻意保持原状**） |
| `story/beat_stage_parse._SHOW_ARG_KEYWORDS` | 规范集（纯重复） | `= SHOW_CLAUSE_KEYWORDS` |
| `story/excel_export._SHOW_KEYWORDS` | 有 `on`、**漏了 `onlayer`** | `= SHOW_CLAUSE_KEYWORDS \| {on}` ← **补回真词** |
| `assets/.../_SHOW_STOP_WORDS` | 规范集 + `expression` | `= SHOW_CLAUSE_KEYWORDS \| {expression}` |
| `story/generation_guard` 的 stopwords | `(with,behind,onlayer,zorder,as)` | `= SHOW_CLAUSE_KEYWORDS - {at}`（一致 ✓） |
| `authoring/learn_statement._NOT_A_VALUE` | 手抄一份（缺 `zorder`） | `= SHOW_CLAUSE_KEYWORDS \| SHOW_INTRO_KEYWORDS \| {True,False,None}` |

**唯一的行为变化**：`excel_export` 补回 `onlayer` —— 从前 `show cg onlayer overlay`
里的 `onlayer` 会被当成属性报"引擎没认"（假警报），现在不会。
真机实测：`onlayer`/`zorder`/`on` 在 show/scene/hide 行里**都是 0 次**（`behind` 3、` as ` 2），
所以这次统一在真机上**行为不可见**、金标不会动。

### 发现但**没动**的口径分歧（都写在各自站点的注释里）
1. **`_SCENE_KEYWORDS` 比 show 窄**：官方语法说 scene 取同一批 properties，
   于是 `scene bg behind x` 现在会把 `behind x` 当图像名的一部分。拓宽属于**改口径**
   （某个真叫 `behind` 的属性就不能再用），要单独定。
2. **`screen` / `layer` 没进 assets 的 `_SHOW_STOP_WORDS`**：于是
   `show screen foo` 会把 `screen` 当图像名（`expression` 却进去了）。同样属于改口径。
3. **`patcher._KEYWORD_SPEAKERS`** 是**另一类**重复（"不可能当说话人的语句关键字"，
   与 `vocabulary.RENPY_STATEMENT_VERBS` 也重叠），本轮不动。
