## 回答用户的"我没搞明白"（都核过源码）

  **不新建文件、不新建 label**。

## 排序键再修正：浅层优先（避免静默换图）

上一笔补的排序用**纯路径字典序**，真机金标立刻抓到「会静默换图」：

```
game/images/bg_1.jpg        ← 资源表里 bg_1 指的是这张
game/images/bg/bg_1.jpg
```
`bg/` 的 `/`(0x2f) < `_`(0x5f) → 深层的**先扫到**，抢走干净 ID `bg_1`，
浅层被改名 `bg_bg_1` → 重扫一次就换图，无提示。同类还有 `frame`
（`gui/frame.png` 被 `gui/dutui/other/frame.png` 抢走）。

改成 `(路径深度, 路径)`：浅的优先、同深度字典序。跨平台确定，且与排序前一致。
金标 `tests/golden_scan_fingerprint.txt` 更新，`probe_scan_fingerprint --check` MATCH。

⚠ 遗留：`_make_unique_id` 本质是"先到先得"，重扫已有项目时同名文件 ID 归属
仍可能变。彻底解决要按"最优候选"分配（浅层 > 深层、精确扩展名 > 模糊），
单列任务。

## sync 指纹的最后一条：行顺序不该进哈希（CI 全绿）

日志显示只剩 1 条红：`test_sync_pipeline_golden`，
**本地 `f57f7065…` / Linux `a86b522c…`** —— 同一个行为两个指纹。

根因：`probe_sync_fingerprint.table_fingerprint` 把**行号 r** 也喂进了哈希，
而 `sync_asset_tables` 写表的行顺序来自"扫描顺序"（先扫到的文件先占行）。
文件系统返回顺序 Windows ≠ Linux → 行顺序不同 → 指纹必然不同。

改法（`tools/probe_sync_fingerprint.py`）：
- `table_fingerprint`：整行取值后**排序**再哈希（列号 c 保留，列顺序仍算内容）
- `_norm`：**list 也排序**（`unregistered` / `missing` 是"扫到了哪些文件"）
→ 金标 `f57f7065…` → `94579ad7…`，本地连跑两次一致，CI 三版本 **success**。

⚠ **行顺序**这条金标不再验 —— 由 `test_asset_tables_autocreate` 单独守
（它断言了具体顺序）。两条判据分工，别指望一条全包。
