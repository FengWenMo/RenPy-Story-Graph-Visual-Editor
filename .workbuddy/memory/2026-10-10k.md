# 2026-10-10（续 10）：契约前提的复核 —— 实测推翻了上一轮的表述

> 用户批评："契约驱动"有致命前提 —— 你们的程序**不用 CDS 注册**，而是直接改解析逻辑 /
> 往已有语句参数序列插东西，所以"引擎公布的声明"不存在；并提出三条弱点
> （契约粒度不够细 / 数据流方向冲突·优先级没定义 / 扫描是滞后指标）。

## 一、⭐ 实测结果（推翻了前提，也修正了我上一轮的说法）

在真机 `D:\千连万理\RenPyTest\sr_general` 逐项核对：

| 核查 | 结果 |
|---|---|
| 被魔改的引擎 | **没有**（项目根无 `renpy/` 目录）→ 官方引擎 |
| `python early:` / `register_statement` | **0 处** |
| `swim_suit` | **不存在**；真实属性是 `clothes2` / `base_swimsuit` / `hanfu_base` |
| `show lan clothes2 happy at i21` | **100% 标准 Ren'Py**（`show <tag> <属性…> at <变换>`） |
| 属性从哪来 | `layeredimage` 的 `group outfit:` / `attribute clothes2:`（`definitions.rpy:417-419`） |
| 语句头词频（前 30） | 全标准（`attribute/add/xpos/text/if/imagebutton/vbox/linear/return/…`） |

**地基结论**：**项目里没有"被魔改的语法"**。看起来"工具不认识"的 `clothes2` 不是新增语句，
是**立绘属性词汇** —— 而属性的声明/枚举/校验**Ren'Py 自己全提供了**。**这类东西根本不需要契约。**

⚠ **我的表述错误（要认）**：前两份设计稿里的 `swim_suit lyj "泳装" intensity=3` 是**我编的示意图**，
不是对项目的观察。真实情况比它简单得多。

## 二、⭐ 关键发现：Ren'Py 自带可枚举、可校验的属性注册表（官方 API）

| API | 给什么 | 解决哪个抱怨 |
|---|---|---|
| `renpy.list_images()` | 全部已定义图像（tag+属性） | "有多少写法我不知道" |
| `renpy.get_available_image_tags()` | 全部 tag | 同上 |
| **`renpy.get_ordered_image_attributes(tag, attributes=(), sort=None)`** | **按"适合展示给用户"排序、且与给定属性*兼容*的属性列表** | **"候选值要我一个个手填"** ← **这就是答案** |
| `renpy.has_image(name, exact=False)` | 名字合不合法（成员测试=裁判） | 验漂移 |
| `renpy.get_registered_image(tag).attributes` | 每个属性带 `.group`/`.attribute` | 分组名也在引擎里 |
| `renpy.sh lint --error-code` | 官方静态检查，出错退出码 1（文档明说 useful for CI） | CI 门禁 |
| `layeredimage` 的 `group`/`attribute` | 属性分组结构（声明，不是猜） | 服装/表情怎么分 |

→ **候选值不该由人填，该问引擎要。** 我上一轮让人"声明候选值"是绕远了。
→ **分组名 `outfit`/`expressions` 也是引擎里声明的**，工具不用自己发明（`attr_groups` 应降级为覆盖层）。

## 三、修正后的**四级阶梯**（不是"契约 vs 不契约"）

```
① 引擎原生可枚举（图片/属性/tag/变换/角色/标签）→ 引擎自带 API
   ✅ 零配合 · 不漂移 · 本项目 99% 靠这级
② 程序用 CDS 注册（python early）            ✅ 不漂移 ｜ ❌ 要求程序愿意用
③ 程序真改了引擎源码                         · 3a 引擎补丁即契约（diff 引擎 vs 上游）
                                             · 3b 就近声明（写在补丁旁，抗漂移强于独立文件）
④ 归纳 + 裁判 + 人确认（扫脚本 + lint/has_image 当裁判）→ 只当"发现/报警"，永不当真源
```
**用户的"致命前提"只杀死第 ② 级**，不构成整条路的致命伤。**本项目站在第 ① 级（最好办的一级）。**

## 四、三条弱点的处置（都承认，都给出做法）

1. **粒度不够细** → 承认（对"新增语句"永远只是部分契约）。
   处置：定义表每个字段标**来源** —— **派生**（引擎读的，只读）/ **人工**（中文名/分组/例子，这才是"你的"）/ **内容**（`.rpy`）。
   ⚠ 不是新发明：复用既有 `capability.Provenance` 与资产表 `update_keys=` 的模式。
2. **优先级/三向漂移** → 写死三条：**形状→引擎；语义→人；内容→`.rpy`**。
   **对不上 = 报错，不是"谁赢"**（落在既有"要么全对要么完全不动"哲学上）。
   例：引擎说 `swim_suit` 不存在、可选修表里有 → **报"引擎不认识这个词"**，不许默默用。
3. **扫描滞后** → 承认；补**实时那一半 = 引擎 oracle**（`list_images`/`get_ordered_image_attributes` 枚举 + `lint --error-code` 判）。
   落地：**一次性 dump 脚本** → `storygraph.engine_facts.json`（可 diff、进版本库）→ 引擎改了就 diff 出漂移。
   ⚠ 代价诚实说：需引擎侧跑一次（一次性 + 可进 CI），不是"无限行为探测"。
